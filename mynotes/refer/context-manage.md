你问的是给自己写小说 agent 做上下文管理——这个我可以直接给方案，不用检索，属于设计经验。
核心矛盾

长篇小说远超单次上下文窗口。硬塞会：开头被截断、人物设定前后矛盾、伏笔丢失、文风漂移。所以要做的是分层 + 检索 + 压缩，而不是想办法塞更多。
推荐的分层结构

1. 常驻层（每次请求都带，控制在 800\~1500 字）

   世界观硬设定：地理、力量体系、时间基准
   人物卡：只放名字、身份、与主角关系、当前状态（在哪个地点、生死、立场）
   全局写作约定：视角、人称、时态、文风样本（一段 100 字范例）、禁用词与雷点
   当前剧情锚点：现在进行到哪一卷哪一章、这一卷的核心矛盾

这一层必须是结构化短卡片，不是正文。人设卡维护成 JSON/YAML 最稳，好做增量更新。

1. 近期层（滑动窗口，6000\~12000 字）

上一章正文 + 最近 2\~3 段关键对话/场景。用滚动摘要替代原文：每写完一章，压缩成 300 字梗概，保留"发生了什么 + 谁态度变了 + 留下了什么钩子"。

1. 检索层（按需召回）

把全书拆成场景单元（每单元 800\~1500 字），每个单元生成三元索引：摘要 + 出场人物 + 涉及线索/伏笔。写新章节时，根据"本章涉及的人物 + 需要回收的伏笔"做检索召回，取回原文片段作为参考资料。

这是解决"伏笔丢失"的关键——单独维护一个伏笔台账：伏笔内容、埋设章节、计划回收章节、状态（未回收/已回收/废弃）。每次生成前，把"本章应回收"和"超期未回收"的条目强制塞进上下文。

1. 冷存储层

全书正文全量存外部，靠检索访问，不进上下文。
工程上的几个关键点

摘要要分层级：段落级→场景级→章节级→卷级。需要细节时向上取细，需要宏观时取粗。避免每次都从最细的摘要开始拼。

一致性检查做成独立步骤：生成后不要直接出稿，先用一次调用拿"候选正文 + 人物卡 + 相关设定"，只让它检查矛盾（人物位置、能力边界、时间冲突、称呼变化），输出问题列表再修。这比指望一次生成就完美要可靠得多。

状态用工具写入，不要靠模型记忆：人物状态、伏笔状态、章节进度这类，让 agent 通过结构化的"更新状态"输出，由你的代码去改 JSON，而不是让它自己在文本里记住。文本里的记忆会漂。

章节结束做归档流水线：生成梗概 → 抽取人物状态变更 → 抽取新伏笔/回收伏笔 → 抽取新专有名词入词典 → 更新全书索引。这套流水线跑完，下一章才干净。

专有名词词典：所有出现的人名、地名、招式名、组织名都进表，生成时作为"只许用这些"的白名单，能显著减少同一个人三个名字的情况。
上下文拼装顺序

实际发请求时按这个顺序拼，重要的放两头（中间容易失焦）：

\[系统] 写作规范 + 文风样本
\[用户] 当前任务：写第 N 章，推进 X，回收伏笔 Y
\[资料] 检索召回的场景原文片段（标记为参考资料）
\[资料] 前情梗概 + 人物卡 + 伏笔台账相关项
\[资料] 上一章结尾正文（原文，保证衔接语气）
\[指令] 字数、视角、留悬念要求

召回的资料明确标成"资料"而不是"指令"，能减少模型被参考内容带跑。
一个容易踩的坑

滚动摘要会逐渐失真——摘要的摘要会丢掉情绪转变和动机。建议不要做无限递归压缩，固定为"章节梗概由原章节正文生成，不由上一版摘要生成"，保证每层摘要都能追溯到原文。
