## b) 与赛道的关联性

### 主赛道：创意造物

Hastings 是"AI 参与创意生产"的典型样本，且不止于"生成一段文字"：

1. **创意生产范式升级**：普通写作 AI 是"一次性生成"，Hastings 把创作变成**可管理的长周期工程**——角色是数据模型、伏笔是带状态的账本、章节是文件、文风是可检索的知识库。这是"用 Agent 工程方法重构创意工作流"的实践。
2. **从"能写"到"写对"**：创意造物赛道不缺生成 Demo，缺的是**质量可控的生成**。Hastings 用状态机约束 + 自动审计 + 五层评测体系，让 AI 创作物达到"设定不漂移、伏笔必回收、线索必公平"的专业标准。
3. **人机协作而非替代**：用户是"出品人"（提构想、定调性、审审计报告），AI 是"主编+执笔"，创意决策权始终在人。

## c) 作品简介（八要素）

### 1. 问题定义

AI 辅助长篇小说创作存在三大痛点，现有工具均未解决：

1. **设定漂移（Context Drift）**：写到第 10 章，AI 已忘记第 1 章的角色人设、凶手手法——LLM 上下文窗口装不下整部小说的全部设定；
2. **伏笔失控**：人类作者靠大纲表格和记忆管理伏笔，AI 写作则"埋了就忘"或"临时硬圆"，读者体验崩塌；
3. **公平性缺失**：推理小说的核心契约是 fair play——解谜所需线索必须在揭晓前全部呈现给读者。当前没有任何 AI 写作工具能**结构化验证**这条原则。

### 2. 目标人群

| 人群 | 特征 | 核心诉求 |
|---|---|---|
| 悬疑/推理小说创作者（网文作者、类型文学爱好者） | 有故事构想，但长篇结构管理吃力 | 有人帮我"记账"：谁说过什么、伏笔埋在哪、什么时候该回收 |
| 推理小说深度读者 | 熟悉 fair-play 守则，对"线索不公平"极度敏感 | 读/写出逻辑自洽、线索公平的本格推理 |
| AI 协作写作体验者 / 开发者 | 想理解 Agent 如何真正落地一个垂直场景 | 一个架构清晰、可学习、可复现的 Agent 应用样板 |

### 3. 应用场景

**典型流程（以"东方快车式封闭列车谋杀案"为例）：**

1. **立项**：用户用一句话描述故事构想，Agent 引导建立故事工作区——角色卡、受害人、凶手、作案手法、线索清单、伏笔计划、时间线，全部落为可检视的 YAML/ Markdown 文件；
2. **创作**：Agent 逐章写作。每章落盘前做 Bible 一致性预检（角色言行 vs 人设、时间线冲突检测）；落盘后自动触发审计；
3. **审计**：伏笔按计划埋设了吗？线索公平呈现了吗？手法描述与锁定稿矛盾吗？审计报告结构化输出，用户一目了然；
4. **文风模仿**：用户上传喜爱的作家作品集（如阿加莎全集），Agent 建立可检索的文风知识库 + 统计风格档案，写作时"学其节奏结构，不抄其内容"。

**应用环境**：本地 Web 应用（React SPA + FastAPI），数据全部文件制存储，可 git 版本管理，零云依赖。

### 4. 核心创意

> **一句话：把"编码 Agent 对代码仓库做的事"迁移到"写作 Agent 对小说工作区做的事"。**

| 创新点 | 说明 | 独特性 |
|---|---|---|
| **Story Bible 五账本 + 状态机** | 角色/线索/伏笔/手法/时间线均为带状态机的结构化数据（如伏笔 `planned→planted→echoed→resolved`），LLM 只能通过工具触碰，非法迁移被工程层拒绝 | 用工程约束补偿 LLM 可靠性，而非指望"更大的上下文" |
| **手法锁定机制（method_lock）** | 作案手法一经锁定，`write_chapter` 拒绝写入任何矛盾描述，防"烂尾"——灵感来自数据库事务与代码 review | 类型文学创作首次引入"不可变核心设定"概念 |
| **Fair-play 可验证化** | "线索公平性"从文学口号变成可计算指标：已呈现线索 / 解谜所需线索 = 100% | 业界首个将推理小说二十条守则结构化的 Agent |
| **双通道文风模仿** | RAG 场景级检索（few-shot 示范） + 离线文体统计档案（句长分布/对话占比/高频手法，宏观约束） | 克服纯 RAG"形似神不似"问题 |
| **写作/审计双 Agent 分离** | 写作者不当自己的法官：独立审计 Agent 上下文隔离、利益隔离、可独立评测 | 借鉴代码 review 与审计制度 |

### 5. 功能模块

```text
┌─────────────────────── React 前端（对话流 / Bible 面板 / 章节阅读器 / 语料管理） ───────────────────────┐
│                                        WebSocket 事件流                                                  │
├────────────────────────────── FastAPI 服务（会话 CRUD / 事件桥 / 上传） ─────────────────────────────────┤
│                                                                                                          │
│   ┌──────────── 写作 Agent（AgentHarness） ────────────┐    ┌────── 审计 Agent（独立 Harness） ──────┐   │
│   │  工具集：bible_query / bible_upsert / method_lock  │ →  │  foreshadow_audit / 对账指标计算        │   │
│   │  write_chapter / revise_chapter / timeline_check   │    │  输出 audits/chXX.json                 │   │
│   │  style_search / style_profile                      │    └───────────────────────────────────────┘   │
│   └────────────────────────────────────────────────────┘                                                 │
│                    │ 文件制工作区（YAML 账本 + Markdown 正文 + JSON 审计）                                │
├──────────────────── RAG 管线（Chroma + BGE-M3：语料切分 → embedding → 检索） ───────────────────────────┤
├──────────────────── tau_agent（Agent 内核）+ tau_ai（Provider 层，OpenAI 兼容协议） ───────────────────┤
└──────────────────────────────────────────────────────────────────────────────────────────────────────────┘
```

模块关系：**内核层**（tau 复用，零改动）→ **领域层**（Story Bible + 工具集，本项目核心）→ **增强层**（RAG 文风 + 审计 Agent）→ **服务层**（FastAPI）→ **展示层**（React）。

### 6. 实现思路

- **技术架构**：Python 3.12 + uv / FastAPI + WebSocket / React 18 + TypeScript + Zustand；Agent 内核复用开源框架 Tau（验证"内核不动、应用层重写"的架构假设）；数据格式 YAML（账本）+ Markdown（正文）+ JSON（审计），全部人类可读、可 git；
- **核心机制 ① —— 工具即守门人**：状态机校验、锁定机制、对账逻辑全部在工具层强制执行，LLM 无旁路通道；
- **核心机制 ② —— RAG 文风**：BGE-M3 本地 embedding + Chroma 向量库，场景级（300–600 token）与段落级（100–200 token）两级切分，元数据过滤 + 向量召回，不依赖 LangChain 等框架，手写 ~200 行管线；
- **核心机制 ③ —— 五层评测体系**：FakeProvider 确定性回放（Agent 行为像纯函数一样可测）→ 结构化对账指标（伏笔回收率/线索利用率/手法一致性）→ LLM-as-Judge（rubric + 多次采样控方差）→ 文体统计距离（KL 散度/TTR）→ 端到端冒烟报告。

## 精简版简介（用于报名表 200 字以内字段）

> 黑斯廷斯备忘录（Hastings' Memo）是一个悬疑小说写作 Agent。它把编码 Agent 管理代码仓库的方法迁移到文学创作：角色、线索、伏笔、作案手法、时间线是五本带状态机的"故事账本"，LLM 只能通过工具读写，非法操作被工程层拒绝；作案手法一经锁定不可篡改，伏笔终稿前必须 100% 回收；RAG + 文体统计双通道模仿名家文风；写作与审计双 Agent 分离，让"线索对读者公平"从文学口号变成可计算指标。基于开源 Agent 内核 Tau 构建，支持任意 OpenAI 兼容大模型端点。
