# 评测工作台重设计

日期：2026-11-15（W7：2026-11-16）。状态：**W1–W7 已落地**。上位设计：[评测体系重建设计](design.md)。参考：[Agent 评测白皮书 01：评测全览](https://tech.meituan.com/2026/09/10/Agent-Evaluation-White-Paper-01.html) 第四、五节；作者提供的 Agent Trace 示意图。原型：[eval-workbench-20261115](../../prototypes/eval-workbench-20261115/index.html)（仅供布局与视觉参考）。

## 1. 为什么重做

第一版工作台只是把 `report.json` 排成表格。它能回答「门禁过没过」，答不了「坏在哪一步」。白皮书把这件事说得很直接：归因靠把执行全链路铺开，逐一定位问题点，观测是地基；看不见的问题不可能稳定解决。

`smoke-2` 冒烟就是例子。报告写着：

```text
committed_via_candidate (must): fail — 未找到经候选核对的提交回执
chapter_in_model_input (quality): skipped — 无模型输入快照
```

只看这两行，无法区分两种完全不同的情况：

| 可能原因 | 归因 | 该改哪里 |
| --- | --- | --- |
| 模型绕过候选，直接写了文件 | 产品问题（工具或写前检查） | 产品 |
| 候选提交发生了，但判分没从事件里认出回执 | 评测判错 | 判分逻辑 |

两种情况的修法相反。判断依据就在那一轮的 Trace 里，而这份 Trace 跑完就丢了。

另一个事实只有对照运行前后的正文才看得出来：`smoke-2` 运行后的 `正文/0003 客栈夜询.md` 与运行前逐字相同，本轮没有改动任何正文。报告里 `only_region_changed` 与 `preserved_verbatim` 的「通过」，是因为什么都没改，不能说明改稿做对了。第一版工作台不展示差异，这个情况在界面上看不出来。

据此还需在改稿评测集补一条必须项：**目标区域确有改动**（锚点区域内文本与初态不同）。它和「仅区域内变化」「保留片段在」一起，才能把「没动」判成失败。

### 1.1 现状缺口

| 缺口 | 事实 | 影响 |
| --- | --- | --- |
| 证据不落盘 | 运行器在内存里收齐全部事件，只把结论写进 `report.json`；`attempts/<案例>--<次>/` 只留运行后的作品文件 | 工作台无 Trace 可画；改判分后无法离线重评（违反 design 第 10.4 节） |
| 模型输入未取回 | 开了 `capture_inputs`，但运行器不读输入附件 | 质量项永远 `skipped` |
| 证据只是字符串 | 检查项 `evidence` 形如 `"receipts=[]"`、`"正文/0003 客栈夜询.md"` | 无法跳到对应的步骤或段落 |
| 过程环节未算 | design 第 6.2 节的六个环节没有落地 | 端到端失败时报不出最早异常环节 |
| 界面 | 两栏表格 + 表单；检查项只是一行文字 | 可视性差，人工复核时看不到改动差异 |

## 2. 工作台要回答的三个问题

按白皮书「离线评测守住已知，Case 挖掘与归因负责定位和分派」的分工，工作台对一次运行依次回答：

1. **过没过**：门禁结论、阻断项、相对基线的变化。（O）
2. **哪条坏了**：哪个案例、哪次试验、哪个检查项。（O）
3. **坏在哪一步，该改谁**：过程环节最早失败点；Trace 上对应的步骤；它的输入、输出、错误；最后定归因。（I + A）

第三个问题是这次重做的重心。前两个问题现有数据就能答，只是要排得更清楚。

## 3. 前提：每次试验留一份完整证据包

界面改造之前，先改运行器的落盘。没有这一步，工作台只能继续画表格。

### 3.1 目录

```text
data/evaluation/runs/<运行>/
  report.json                       # 结论；检查项带结构化证据引用
  reviews.json                      # 人工复核与归因
  attempts/<案例>--<次>/
    meta.json                       # workspace_id、conversation_id、各步 turn_id、耗时、用量
    work/                           # 运行后的作品（现有内容移入）
    evidence/
      before.json                   # 运行前文件快照（路径 → 内容）
      diff.json                     # 运行前后差异，按文件、按段
      events.jsonl                  # 本次试验收到的全部原始事件
      traces/<turn_id>.json         # 每一步结束后读一次产品的单轮 Trace 接口，原样保存
      inputs/<operation_id>.json    # 模型输入附件（开启 capture_inputs 时）
```

约束：

- Trace 用产品已有的单轮 Trace 接口取回，保存原始返回，**评测不自己重算时间线**。产品和工作台读的是同一种数据。
- 取回发生在轮次结束、临时作品目录被清理之前；之后工作台完全离线，不依赖产品服务在线。
- 判分只读证据包。改了判分逻辑，`score` 用证据包重评，不再调用模型。

### 3.2 结构化证据引用

检查项的 `evidence` 从字符串改为引用列表，每条指向证据包里可定位的一处：

```json
{
  "id": "committed_via_candidate",
  "level": "must",
  "verdict": "fail",
  "reason": "未找到经候选核对的提交回执",
  "evidence": [
    { "type": "span", "turn_id": "t_01", "span_id": "tool:call_7" },
    { "type": "missing", "turn_id": "t_01", "expected": "候选提交回执" }
  ]
}
```

| 类型 | 指向 | 工作台怎么画 |
| --- | --- | --- |
| `span` | 某轮 Trace 的某一步 | 时间线该行打标记，点击选中 |
| `file` | 文件 + 原文锚点片段 | 差异视图滚到该段并高亮 |
| `input` | 某次模型请求的输入附件 + 片段 | 详情区「输入」块高亮片段 |
| `missing` | 预期出现却没出现的步骤 | 时间线末尾加一行虚线占位 |

`missing` 是这次 `smoke-2` 最需要的一类：「没有回执」本身也是证据，要画出来，而不是只写在原因里。

### 3.3 过程环节

运行器按 design 第 6.2 节对每次试验算六个环节，写进报告：

```json
"stages": [
  { "id": "scope", "verdict": "pass", "span_id": "tool:call_2" },
  { "id": "read", "verdict": "skipped", "reason": "无模型输入快照" },
  { "id": "candidate", "verdict": "fail", "span_id": null },
  { "id": "verify", "verdict": "not_reached" },
  { "id": "repair", "verdict": "not_reached" },
  { "id": "commit", "verdict": "fail", "span_id": "write:e_41" }
],
"first_failed_stage": "candidate"
```

## 4. 界面

### 4.1 整体布局

沿用作者示意图的三段式：顶栏身份条，中间 Trace 时间线，右侧详情。左侧加一条窄栏切换案例与试验，下方放检查项、差异和复核。

```text
┌ 顶栏：运行名 · 模式 · 代码提交 · 模型 · 预算 · [门禁不通过] ─────────────────────────┐
├───────────┬──────────────────────────────────────────────────────┬──────────────┤
│ 案例/试验  │ 过程环节条：范围 → 读原文 → 候选 → 核对 → 修补 → 提交       │ 详情           │
│ ● 雪夜 #1 │──────────────────────────────────────────────────────│ 输入           │
│           │ Trace 时间线（步骤 · 耗时 · 状态 · 甘特）                 │ 输出           │
│           │   ◆ 检查项标记钉在对应步骤上                              │ 属性           │
│           │   ┄ 预期未出现的步骤画成虚线行                            │ 事件           │
│           │──────────────────────────────────────────────────────│ 检查项          │
│           │ [检查项] [正文差异] [人工复核] [归因]                      │              │
└───────────┴──────────────────────────────────────────────────────┴──────────────┘
```

### 4.2 顶栏

一行定位本次运行：运行名、冒烟/门禁、代码提交、提示词与工具指纹、模型名、已用预算、门禁结论。门禁结论用颜色区分，不另加说明文字。有基线时显示「对比 <基线运行>」，点开看版本身份差异。

### 4.3 左栏：案例与试验

每条案例一行，下挂各次试验；状态点区分通过、失败、待复核、基础设施错误、未运行。可筛选「只看失败」「只看待复核」。门禁模式下每案 3 次，三个点并排，一眼看稳定性。

### 4.4 过程环节条

时间线上方一条六段的条，对应第 3.3 节的环节。通过、失败、跳过、未到达用颜色区分，**最早失败的环节加粗**。点击某段，时间线滚到并选中该环节对应的步骤。

它回答「坏在哪一步」的粗粒度版本；时间线回答细粒度版本。

### 4.5 Trace 时间线

数据就是证据包里的 `traces/<turn_id>.json`，与产品「运行追踪」同一种结构，画法也对齐：

- 行：作者轮次 → 模型回合（可展开）→ 模型请求、工具调用、规则检查、写作上下文装配、文件变更、回复。父子关系用缩进和连线表示。
- 列：步骤名、耗时、状态、甘特条。
- 失败步骤整行着色，错误事件画成菱形点。
- 多步案例（`steps` 多于一条）按轮次分段，段间显示作者消息。

评测独有的两层叠加：

| 叠加 | 画法 | 来源 |
| --- | --- | --- |
| 检查项标记 | 行尾小菱形，颜色表示结论；悬停显示检查项名 | 检查项 `evidence` 中的 `span` 引用 |
| 预期未出现 | 时间线末尾的虚线行，名称为预期步骤，状态「未出现」 | `missing` 引用 |

### 4.6 右栏：详情

选中一步时，固定五块，与示意图和产品运行追踪一致：

| 块 | 内容 |
| --- | --- |
| 输入 | 工具参数；模型请求的输入附件（未保存时写明「未保存模型输入」） |
| 输出 | 工具结果、模型结束原因与用量、写入路径与变更摘要 |
| 属性 | `span_id`、`parent_span_id`、类型、名称、重试来源、错误码 |
| 事件 | 失败或拦截说明，格式 `[错误码] 位置：现象。建议：…`；失败时置顶 |
| 检查项 | 引用了这一步的检查项及结论 |

选中一个检查项时，右栏换成检查项视图：级别、结论、判定原因、全部证据引用（可点击跳转）。

### 4.7 下方标签页

**检查项**：表格列出全部检查项，带 C/I/O 视角标签、级别、结论、原因。点击行即在时间线和右栏定位证据。

**正文差异**：运行前后并排。允许修改区域（锚点起止）用底色框出，`preserve` 片段加下划线，区域外的改动标红。`only_region_changed`、`preserved_verbatim` 的结论直接在这里看得到。

**人工复核**：每个人工项一张卡片，左边问题与结论选择，右边嵌入相关差异片段和模型最后回复。点差异里的段落即自动填入证据位置，不用手打 `after:正文/0003.md 雪夜段落`。

**归因**（失败试验才出现）：选择归因类别，填一句说明，写进 `reviews.json`：

| 归因 | 后续 |
| --- | --- |
| 上下文装配 / 模型理解 / 工具或写前检查 / 候选核对 / 提交 | 产品问题，修复后跑门禁 |
| 评测判错 | 改检查项并升版本，用证据包重评 |
| 不是问题 | 关闭 |

归因页默认选中最早失败环节对应的类别，作者确认或修改。这就是白皮书说的「定期检查是不是评测判错了」的落点，评测体系迭代和产品迭代从这里分流。

### 4.8 运行总览

运行里有多条案例时，进入工作台先看总览：顶部汇总与门禁，下面是案例 × 试验的矩阵，每格一个结论色块；有基线时每行标出变好、变差、不变。点格子进入第 4.1 节的单次试验视图。

## 5. 实现方式

时间线和详情区是这次的主体。三种做法：

| 方案 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| A | 在现有静态页里手写时间线 | 与前端完全无关 | 产品「运行追踪」已经有一套；两份实现会逐渐不一致 |
| **B（推荐）** | 把产品运行追踪的时间线与详情抽成只吃数据的展示组件；前端加一个独立的工作台入口，构建产物由评测服务提供 | 一套时间线两处用；产品改了 Trace 结构，工作台同步受益 | 要先把组件里的取数逻辑拆出去；评测运行依赖一次前端构建 |
| C | 工作台只放链接，跳到产品运行追踪页 | 改动最小 | 要求产品服务在线、临时作品不删；离线重评和换机查看都不行 |

推荐 B。边界：

- 工作台入口不进产品路由，产品界面看不到它。
- 共享的只是展示组件；评测后端仍不导入产品业务模块（design 第 8 节约束不变）。
- 展示组件的详情区读附件时，从「调产品接口」改为「由调用方传入取数函数」：产品传接口调用，工作台传读证据包。

## 6. 分步实施

| 步 | 内容 | 完成标志 |
| --- | --- | --- |
| W1 证据包 | 运行器落盘 `meta`、`before`、`diff`、`events`、`traces`、`inputs`；判分改读证据包；`score` 可离线重评；补「目标区域确有改动」必须项 | 重跑一次冒烟，`smoke-2` 那条失败能凭证据包判断是哪种原因 |
| W2 结构化证据与过程环节 | 检查项证据改引用列表；算六个环节与最早失败点 | 确定性测试覆盖四种引用和环节计算 |
| W3 组件拆分 | 产品运行追踪的时间线、详情抽成展示组件；产品页行为不变 | 现有运行追踪 e2e 仍通过 |
| W4 工作台单次试验视图 | 顶栏、左栏、环节条、时间线 + 检查项叠加、详情、检查项与差异标签页 | 用 W1 的真实证据包打开，能从失败检查项一路点到出错步骤 |
| W5 复核与归因 | 复核卡片嵌差异、点选证据；归因页写回 | 复核和归因写回后 `score` 合并正确 |
| W6 运行总览 | 多案例矩阵、基线对比 | 门禁模式（每案 3 次）可读 |
| W7 Case 库 + 跑测控制 | 只读 Case 库（可跳相关运行）；工作台选题触发冒烟/门禁（进度/取消）；CLI 与工作台共用 `run_batch` | 三入口可用；Job API 校验与单任务互斥有测试 |

W1 不依赖界面方案，可以先做；它也是修 `smoke-2` 那条失败的必要一步。

## 7. 不做

- 编辑/新建案例 YAML、确认基线与登记豁免的专用 UI（仍可后做）。
- 跨运行的趋势图、在线监控看板（冷启动阶段不做）。
- 模型评委打分（design 第 9.2 节暂不启用）。
- 多 Job 并行、跨机调度。

## 8. 已确认（2026-11-15）

1. 实现方式按方案 B：共享展示组件，工作台为独立入口，不进产品路由。
2. 归因页放进本次（W5），结论写回 `reviews.json`；阶段 4 的「加入案例池」沿用同一份归因数据。
3. W1 证据包先于界面单独实施；完成后重跑一次冒烟，凭证据包判明 `smoke-2` 失败的原因，再进入 W2。
