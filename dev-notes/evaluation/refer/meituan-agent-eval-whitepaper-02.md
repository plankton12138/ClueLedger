《Agent评测白皮书》系列关注如何将评测方法落到实际项目中。在系列第一篇《Agent评测全览》中，我们介绍了评测体系的整体构成，以及评测体系与 Agent 相互促进的两条迭代闭环。

作为系列的业务实践篇，本文以商家 AI 助手的巡检任务为贯穿案例，介绍如何构建业务 Benchmark，通过评测器校准和错误分析，同时推动评测体系完善与 Agent 能力提升，并借助图灵支撑持续回归与模型选型，为上述方法在具体业务中的落地提供参考。

## 一、背景

### 1.1 业务背景

商家广告助手是面向投放巡检、异常诊断、数据报告和计划编辑等场景的业务 Agent。执行任务时，它需要读取持续变化的真实账户数据、调用多个工具、遵守投放规则，并根据结果给出建议，必要时直接调整投放计划。

因此，判断它能否用于生产，不能只看最终回答是否「像对的」，还要验证整个任务是否正确完成：意图和时间范围是否理解准确，数据与工具调用是否正确，关键规则是否遵守，最终账户状态或交付物是否符合预期。

### 1.2 对标业界

为建立商家广告助手的评测体系，我们调研了代表性的 Agent Benchmark，重点关注三个问题：任务如何组织、执行环境如何构造、结果如何判定。

业界 Benchmark 的共同思路，是让 Agent 在可执行环境中完成完整任务，再通过测试、验证器或 Judge 检查结果。
![图2](https://p0.meituan.net/meituantechblog/1c1d9dd8cb5e604097bc6140e1cd8f95265956.png)

<!-- image 2: https://p0.meituan.net/meituantechblog/1c1d9dd8cb5e604097bc6140e1cd8f95265956.png -->


公开 Benchmark 可以帮助我们设计评测，但它们的成绩不能直接作为商家广告助手的上线依据。因为它们覆盖的任务、业务规则和数据，与广告投放不同。我们可以复用其任务设计、环境构造和判定方法，再围绕广告业务建立自己的 Task 集，配齐执行环境、判定机制和验证框架，验证 Agent 是否满足实际业务要求。

后文将介绍：如何把真实业务场景转化为 Task 集，明确成功标准与 Rubric，配置执行环境、判定机制和评测协议，再通过错误分析推动 Agent 迭代。

### 1.3 建设目标：可测、可信、可优化

我们希望这套评测体系做到三件事：

1. **可测**：把真实业务流程转化为可执行、可判定的场景和成功标准。
2. **可信**：稳定、规模化地执行评测，并让过程可观测、结论可复核。
3. **可优化**：从评测结果定位根因、验证改动，并逐步连接线上业务效果。

## 二、商家广告助手的 Benchmark 设计

商家广告助手需要完成巡检、诊断等任务。设计 Benchmark，首先要明确测哪些业务场景，以及每个场景下怎样算成功。再将这些要求落实为 Task 集、执行环境、判定机制和评测协议，让不同 Agent 版本可以在相同条件下比较。

### 2.1 评测场景设计

开始建设评测集时，首先遇到的困难往往是：该用哪些任务来测试它？

从线上 Bad Case 入手，能够抓住真实问题，但样本容易集中在已经暴露的错误上，难以形成系统覆盖；对于尚未上线或使用量较少的 Agent，可积累的案例也十分有限。如果由团队主动构造评测样本，又需要回答：应该设计哪些场景，怎样判断关键流程和风险已经覆盖，避免选题只依赖个人经验？

经过思考与实践，我们总结出两条互补路径：一条从业务 SOP 自顶向下拆解，确保核心流程和关键分支不遗漏；另一条从线上使用和离线测试中的 Bad Case 自底向上补齐，覆盖设计阶段难以预见的边界与风险。两类场景共同组成可持续维护的评测集。

#### 从业务 SOP 拆解评测场景

所谓评测场景，就是准备拿什么样的题来考 Agent。历史对话只能说明用户过去「怎么问」，核心流程和关键分支不一定能得到完整覆盖。我们先从业务 SOP 出发，把每个 Skill 还原为业务状态图，明确六类要素：业务状态、数据依赖、条件分支、提前停止点、能力边界，以及跨 Skill 的转交点。由此得到的不只是测试用例列表，更是一张「在什么条件下应该做什么、何时应该停止或转交」的行为规范。

以到店 KA 业务的每日巡检为例，其主流程如下：

这张图需要按「状态驱动的分支流程」理解，而不是从头执行到尾的固定链路：

- 未发现异常门店时，跳过投放层下钻，但仍要生成巡检报告。
- 账户余额不足时，只产生账户级预警，不单独触发门店下钻。
- 只有发现问题投放后，才进入分层归因。
- 命中预算、余额、状态或时段等直接根因后，停止后续弱证据检查。
- 如果用户实际要做投放日报复盘、计划诊断或计划编辑，则转交相应 Skill，并结束当前巡检流程。

业务状态图的价值，是将「应该怎么做」从隐含在专家经验中的知识，转化为设计评测场景的明确依据。

#### 用真实 Bad Case 补齐边界与回归

业务 SOP 描述的是预期行为，却无法穷举 Agent 在实际执行中的非预期失效。我们从线上使用和离线测试中收集 Bad Case，先把具体错误抽象为可复用的失效模式，再扩展为边界、异常和回归场景。

例如，在一次线上任务抽检中，我们发现商家要求巡检昨日投放，Agent 输出了一份结构完整的报告，但 Trace 显示其实际查询的是当天数据。

在评测中，这不会只作为一道错题保留，而会被抽象为「日期理解与计算失效」，并进一步覆盖今日、昨日、历史日期和周末等不同情况。

#### 丰富维度

通过业务 SOP 的自顶向下拆解，以及真实 Bad Case 的自底向上补充，我们为 KA 每日巡检设计了六类共 41 个评测场景。核心流程场景保证每日巡检主链路及关键分支得到覆盖，其他分组则补充触发词变体、业务变量和能力边界等变化。其中，路由转交与核心主流程同样重要：生产可用的 Agent 不仅要知道「应该做什么」，还要知道什么时候不应启动完整巡检，而应追问、转交或拒绝：

### 2.2 定义成功标准与判定方法

#### 定义成功

以到店 KA 巡检任务为例，商家让 Agent「巡检昨日投放」，收到一份报告就算完成了吗？我们从三个方面拆解：

1. **执行流程遵循业务 SOP 了吗？**
   - 观测工具调用顺序是否符合 SOP 设计，例如是否先调用取数工具，再进行门店筛查，接下来再下钻分析，最后输出巡检报告
   - 必要步骤是否都覆盖到，例如数据查询、门店筛查
   - 是否存在低效工具调用
   - 是否存在重复工具调用
   - 是否存在非必要步骤或低效步骤，例如多门店下钻分析时，是否并行分析
   - 条件分支逻辑是否正确执行，例如未发现异常门店时，是否跳过投放层下钻，直接生成巡检报告

2. **执行过程和结论有据可依吗？**
   - 工具的参数值是否与任务上下文语义一致，例如查询日期是否对应商家要求的「昨日」
   - 是否选择了正确的工具
   - 调用工具时是否违反静态参数约束
   - Agent 输出是否忠实于工具实际返回的数据

3. **确定输出的巡检报告是可交付的吗？**
   - 输出结果是否缺失内容，例如是否真的输出了一份巡检报告
   - 输出格式是否遵循必要模板，例如巡检报告必要的表格是否输出了
   - 输出结论是否存在模糊表述
![图6](https://p0.meituan.net/meituantechblog/db1ddba1f0a8b493ac0e0c91f7c678c3415555.png)

<!-- image 6: https://p0.meituan.net/meituantechblog/db1ddba1f0a8b493ac0e0c91f7c678c3415555.png -->


这些检查项构成任务的评分细则（Rubric）。其中，必要步骤、顺序调用、正确工具、参数一致性、参数合规性、输出忠实性、输出完整性、输出遵守必要模板作为**成功必需项**；低效与重复工具调用、规划效率、结论表达等指标主要用于**质量分层和问题诊断**，不影响任务是否成功。

判定成功时，可以从 Trace 中精确取证的检查项由**确定性 Grader** 判定，需要理解业务语义和证据关系的部分交给 **LLM Grader**。

#### 评测指标

一次巡检通过了检查，还不能说明 Agent 已经可靠：换一种业务场景还能完成吗？同一任务多跑几次，会不会时好时坏？完成任务又要花多少时间和成本？为回答这些问题，我们汇总各场景、多次执行的检查结果，并结合运行中的资源消耗，形成以下五个维度的评测指标：
![图7](https://p0.meituan.net/meituantechblog/7217564645d0c19ffd452f3e26217caf2546248.png)

<!-- image 7: https://p0.meituan.net/meituantechblog/7217564645d0c19ffd452f3e26217caf2546248.png -->


- **任务完成率**：整体成功情况
- **Pass@k / Pass^k**：分别衡量能力上限与执行稳定性
- **工具调用顺序命中率、必要步骤覆盖率等**：定位任务成功/失败的主要原因
- **规划效率、结论确定性等**：观测输出质量
- **Token、LLM 调用轮次、端到端时延、TTFT**：衡量资源消耗与生产运行效率

### 2.3 评测 Task Schema

评测场景明确「测什么」，成功标准明确「怎样算做对」。将二者组织成可执行的 Task，还需要明确测试账号、运行日期、业务数据状态和必要权限等前置条件。对 2.1 节的 41 个场景实例，为每个实例补充 Grader 和执行环境前置条件后，最终形成 41 个可执行评测 Task。下面以 KA 每日巡检中的一条真实 Task 为例，说明完整 Task 结构：
![图8](https://p0.meituan.net/meituantechblog/0d6bd2144925d3bfd2cfe37397e4b622545455.png)

<!-- image 8: https://p0.meituan.net/meituantechblog/0d6bd2144925d3bfd2cfe37397e4b622545455.png -->


实现中，`tool_calls_dag` 主要对应路径规划，`no_hallucination` / `hallucination.*` 对应工具与事实一致性，`output_fields` / `output.*` 对应输出质量，`execution.conditional` 用于检查条件分支。任务完成率、Pass@k、Pass^k 及成本时延由 Harness 基于多次 Trial 聚合，不属于单个 Task 的 Grader。

一条 Task 通过一组确定性规则和语义 Rubric，分别约束 Agent 的工具调用、参数边界、事实依据和最终交付。

### 3.1 校准评测器

评测器本身也会出错。OpenAI 审计 138 道难以攻克的 SWE-bench Verified 任务时，发现其中 59.4% 存在任务描述或测试设计缺陷。这说明，即使广泛使用的 Benchmark，也需要持续校准。

商家 Agent 同样如此：Trace 解析、确定性 Grader 或 LLM Rubric 一旦存在偏差，就可能导致错误归因。因此，在依据评测优化 Agent 前，需要先确保「尺子」可信。

#### 可信

评测器投入规模化使用前，需要先证明它能够稳定复现业务专家的判断。我们建立由业务专家确认的校准集，同时覆盖明确的 Good Case、Bad Case 和边界 Case，并分别验证 Trace 解析、确定性 Grader 和 LLM Rubric，避免用一个总体一致率掩盖不同环节的问题。

确定性 Grader 的校准重点，是检查规则是否准确表达了必要的业务约束。早期评测 Task 使用线性顺序描述工具调用，适合表达简单的前后依赖，却容易将合理的并行与汇聚路径判为失败。人工复核发现这类假阴性后，我们将复杂路径升级为 **DAG**：节点表示必要工具调用，边只保留真实的数据依赖，互不依赖的步骤允许采用不同顺序。规则修正后，再回放历史样本，确认误判得到消除且没有引入新的问题。
![图10](https://p0.meituan.net/meituantechblog/cf4cd8717ee190f3658f88387137b680224979.png)

<!-- image 10: https://p0.meituan.net/meituantechblog/cf4cd8717ee190f3658f88387137b680224979.png -->


LLM Grader 则需要重点验证它与业务专家在语义判断上的一致性。我们对 LLM Rubric 进行人工抽检，分析和判断问题来自 Rubric 表述、证据缺失，还是业务标准本身存在歧义。对于证据不足的高风险问题，评测器也应允许返回「无法判断」，而不是强制给出缺少依据的二元结论。

需要特别区分：评测误判减少说明尺子变得更准确，不代表 Agent 能力得到提升。只有使用校准后的同一套标准重新执行 Benchmark，才能判断 Agent 是否真正变强。

#### 长期可信

通过初始校准并不意味着评测器会永久正确。模型、Agent 和 Skill 持续迭代，业务 SOP 和能力边界会发生变化，账号状态、工具接口和 Trace 格式也可能漂移。因此，评测器需要像被评对象一样持续维护。

持续校准不等于永久进行全量人工复核。我们的实践是将三种机制结合起来：

- **自动回归**：每次修改 Trace 解析、确定性 Grader 或 LLM Rubric 后，在固定校准集和历史样本上重新执行，检查是否引入新的误判。
- **稳定抽检**：评测运行稳定后，定期随机抽取少量样本进行人工复核，监测人机一致性和数据分布是否发生变化。
- **触发复核**：当模型、Skill 或执行环境发生较大变化，指标分布突然异常，或者线上反馈与离线判断明显不一致时，提高人工复核比例。

在这套机制下，人的职责是校准标准、处理争议、复核高风险结果和识别新的失效模式。新的问题经过确认后，再回流到校准集、Grader 和历史回归样本中，形成评测器自身的持续迭代闭环。

### 3.2 根因分析

任务失败只是一个结果，并不是根因。任务完成指标告诉我们「是否失败」，分层指标则将问题进一步定位到路由、必要步骤、工具参数、条件分支、事实依据或最终输出等具体检查项。

原子指标能够指出问题发生在哪里，但根因仍需要从执行证据中确认。同一个「必要步骤缺失」，既可能是 Skill 没有明确约束，也可能是模型在长上下文中遗漏了要求，还可能来自数据、环境或 Grader 异常。定位到具体检查项后，我们直接查看与该指标关联的局部 Trace、工具参数和返回结果，通常即可确认问题原因和对应的优化点。

只有当指标与 Trace 结论冲突、局部证据不足、同一问题随机出现，或者仍无法区分 Skill 与模型问题时，才进一步查看完整 Trace、重复执行或补充控制变量验证。这样既利用指标缩小分析范围，也保留 Trace 作为最终判断依据，避免每个 Bad Case 都从头排查完整执行链路，降低问题定位成本。

### 3.3 具体例子——巡检任务优化

评测器校准后，我们以 KA 每日巡检为例，展示如何根据分层指标定位问题、实施优化，并使用同一套 Benchmark 验证效果。

#### 定位问题

分层指标显示，每日巡检的问题主要集中在四个方面：配置职责混杂、命令路由不唯一、条件分支和停止条件不明确，以及稳定逻辑过度依赖模型。结合相关局部 Trace 确认根因后，我们将问题转化为对应的系统优化动作。

## 四、评测体系的工程化落地

前文介绍了业务 Benchmark 的设计，以及如何通过错误分析推动 Agent 迭代。随着模型、Skill 和工具持续更新，团队需要复用任务与判定标准、批量执行评测，并保留问题复核和版本比较所需的证据。为此，我们借助图灵评测平台，将评测准备、执行判定和分析回归组织为可重复运行的流程，减少每轮评测的重复配置与人工操作。

<!-- image 14: https://p0.meituan.net/meituantechblog/ac55f68681cdb51e218fc7039cbfc02f422638.png -->


### 4.1 构建可信的评测流程

沿用「每日巡检」的案例，即使 Agent 生成了一份完整报告，团队仍需确认：它是否查询了正确日期、执行了必要的筛查与下钻、依据真实数据得出了结论。前文定义的成功标准与校准方法，需要落实到每一轮评测中。图灵通过任务与环境管理、逐项判定、证据下钻和人工质检，为条件可核对、结论可追溯、偏差可修正提供支撑。
![图15](https://p1.meituan.net/meituantechblog/49b41468a4a039aa4f085bc6b28dff7e338712.png)

<!-- image 15: https://p1.meituan.net/meituantechblog/49b41468a4a039aa4f085bc6b28dff7e338712.png -->


#### 统一任务与配置，让版本比较有可核对的基线

比较两个版本的巡检完成率，首先要确认它们面对的是同一批任务和同一套要求。我们通过 Task 集管理维护任务输入、前置条件和预期行为，并通过环境配置复制线上 Agent 配置作为评测基线，明确模型、Prompt、Skill、工具和权限。验证某项改动时，团队需要明确变更项，并核对其余配置是否一致。

例如，验证新版 Skill 能否正确处理「昨日」，应复用相同任务与判定标准，对照查询日期和任务上下文。真实账户数据会随时间变化，团队还需核对运行日期、账号和数据状态；复制配置并不等于固定了业务数据。只有运行条件可比，完成率变化才具有解释意义。

#### 将业务标准落为检查项，让判定能够追溯到执行证据

在图灵的 Evaluator 中，我们将 Rubric 配置为可执行检查项：可精确取证的内容由脚本判定，涉及语义理解的内容由 LLM 判定。成功必需项决定任务是否完成，质量诊断项用于分析优化，并在多轮评测中复用统一口径。

在进行根因分析时，团队可从评测报告下钻到具体 Task、失败检查项和执行片段，复核日期是否正确、结论是否忠实于数据。检查项帮助定位偏差，根因确认仍需结合上游证据，必要时通过复现或对照验证。

#### 把人工复核接入评测流程，让误判能够被发现和修正

我们通过图灵的人工质检抽检 LLM Judge 的判定结果，以人机一致率衡量其与业务专家判断的一致程度，并重点复核争议样本和高风险结果。对不一致的样本，结合执行证据排查 Rubric 表述、证据理解或业务标准歧义，调整后通过历史样本回归验证，持续发现并修正评测偏差。

例如：工具返回「投放消耗下降」，Agent 却在报告中写成「投放效果变差」。LLM Judge 判为忠实于数据，业务专家则认为消耗下降不足以证明效果变差，判为不通过。针对这类分歧，团队明确 Rubric 中「结论必须有数据支撑」的要求，再用历史样本验证人机一致率是否改善。

### 4.2 评测效率：从单次评测到持续回归

商家广告助手需要随着模型、Skill 和工具的变化反复评测。首次评测完成后，后续每次迭代都要回答：改动是否解决了目标问题，其他场景是否退化，成本与耗时是否发生变化。图灵将 Task 集、Evaluator 和 Pipeline 保留为可复用的评测资产，让团队沿用已有流程验证新版本，减少重复配置、逐条执行和结果整理。

#### 复用已有评测资产，减少每轮准备工作

首次建立巡检 Benchmark，需要配置任务、执行环境和检查项，并校准评测器。后续更换模型或调整 Skill 时，若任务与成功标准不变，可复用 Task 集、Evaluator 和 Pipeline，重点更新被测配置、补充必要场景。

#### 批量串联执行与判定，减少人工操作和数据搬运

准备完成后，图灵通过 Pipeline 串联任务批量执行、结果采集和机器评测，并关联 Task、执行环境及 Agent 版本。巡检报告、查询参数、工具返回和 Trace 随执行过程采集，再由已配置的 Evaluator 完成逐项判定，减少逐条发起任务、复制执行结果和单独组织判定的操作。

以调整巡检停止条件为例，团队可以复用已有巡检任务批量验证，查看哪些任务仍出现无异常下钻、命中直接原因后继续检查等问题。机器先按统一规则完成检查，人工再结合随机抽检和重点复核处理争议结果，使新增一轮评测能够沿用前一轮的执行与判定配置。

#### 从修复单个问题走向持续回归，减少重复整理与验证

修复一个失败任务后，还需要检查改动对其他场景的影响。图灵的评测报告汇总任务完成情况、各维度指标、耗时与 Token 用量，并支持下钻到具体 Task、检查项和相关 Trace。团队可以从场景与检查项层面缩小排查范围，再查看对应证据，减少在分散日志和结果文件之间反复查找。

例如，显式化停止条件后，既要验证「无异常时不继续下钻」，也要检查「存在异常时仍能完成必要诊断」。团队在可比条件下复用 Task 集、Evaluator 和 Pipeline 执行回归，对照优化前后的目标检查项、整体完成率与成本耗时，确认改动是否带来预期收益，以及是否引入新的退化。

由此，每次迭代都可以在已有任务、标准和证据基础上继续验证。业务人员将精力集中到新增场景、异常结果和优化判断，平台承担可重复执行的任务组织、机器判定与结果汇总，使评测能够持续跟上 Agent 的迭代节奏。

## 五、Takeaway

回顾整个实践，业务 Agent 评测体系不是一次性建设完成的测试平台，而是一套从业务任务出发，逐步形成场景、指标、证据、诊断和迭代闭环的业务基础设施。其他业务不必复制我们的 Task 和指标，但可以复用这套建设路径。

- 从业务任务出发，而不是从公开数据集出发。公开 Benchmark 提供通用参照，业务 Benchmark 负责定义真实生产要求。
- 从业务风险推导指标，而不是先有指标再寻找解释。每个指标都应对应具体风险和执行阶段。
- 指标既要能够衡量，也要能够诊断。任务失败后，应能够下钻到原子检查项和局部证据。
- 评测器和 Agent 分别迭代。尺子变准和能力变强是两个不同的闭环，不能混为同一类收益。
- 离线 Benchmark、线上过程指标和业务结果共同构成证据链。离线提升是必要条件，但不能自动推导出业务收益。

## 六、结语

当 Agent 从「生成内容」走向「完成业务任务」，评测也需要从判断答案好不好，转向判断它是否沿着正确路径、基于真实证据、以可接受的成本稳定完成交付。

一套真正有价值的业务 Agent 评测体系，不以 Task 数量、指标数量或自动化程度为终点。它的价值在于：业务问题能够被稳定复现，失败能够被快速定位，优化能够被可信验证，线上变化又能持续反哺下一轮评测和业务迭代。
