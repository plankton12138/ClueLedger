# 最小可归因补齐 · 开发计划

日期：2026-11-14。状态：**确定性与浏览器 e2e 已通过；在线单例待作者开启 `capture_inputs` 后手测一轮**。目标：把现有「运行追踪」补到白皮书冷启动底线——凭一条 Turn 的 Trace 复现 Bad Case。本阶段是[评测体系重建设计](design.md)的前置阶段，不删除旧 `eval/`，不新建评测框架。

> **For agentic workers:** 按本计划分阶段实施；每阶段先确定性测试，再用 `.env` 在线模型做单例验收。失败先修，再复跑同一单例。

**Goal:** 打开任意一轮运行追踪，能看见完整父子时间线，并在详情区读到该步的输入、输出、属性和失败事件；任意一轮（含未写入）都能还原受理时的作品版本。

**Architecture:** 复用现有活动记录、单轮 Trace 投影与 `RuntimeTrace` 页面。只补记录缺口与详情呈现，不引入独立 Trace SDK，不新建观测服务。

**Spec:** [评测体系重建设计](design.md) 第 10 节中与归因相关的两项；白皮书「最小可归因」示意。

## 1. 范围

### 1.1 本阶段做

| 编号 | 交付 | 对应缺口 |
| --- | --- | --- |
| O0 | 受理轮次时记录作品版本 | 未写入的失败轮次无法还原初态 |
| O1 | 归因场景下模型输入可稳定取得 | 图右侧 INPUT 不全 |
| O2 | 详情区按「输入 / 输出 / 属性 / 事件」组织 | 原始 JSON 难用于复现 |
| O3 | 失败步在时间线与详情顶部一眼可见 | ERROR 不够突出 |
| O4 | 专项验收 | 确定性 + 在线单例 |

### 1.2 本阶段不做

- 独立 `trace_id` 体系、生产环境标签、跨任务看板
- 单独运行候选核对的接口、「加入案例池」、跨会话按错误码筛轮次（属后续评测阶段）
- 删除或重写旧 `eval/`
- 改甘特时间线的基本交互（展开 Loop、选中、订阅仍沿用现实现）

## 2. O0：受理时记录作品版本

### 2.1 行为

在 `TurnService.accept`（或等价受理入口）成功写入 `turn_started` **之后、执行开始之前**，记录一条点事件，例如：

```python
{
    "type": "work_revision_recorded",  # 具体 type 名实施时与活动契约对齐
    "turn_id": ...,
    "conversation_id": ...,
    "baseline_commit": <当前作品 git head 或等价>,
    "story_revision": <冻结上下文中的 story.revision，无则空字符串>,
    "at": ...,
}
```

约束：

- 所有模式都记录（local / server）。
- 本轮从未写入时，该记录仍存在，且足够导出「轮次开始时的作品快照」。
- 与现有 `version_baseline`（首次写前建立的 Git 基线）并存：前者是**受理时刻**的作品身份，后者是**写前会话**的 Git 基线。二者可能相同，语义不同，不可互相替代。
- 幂等：同一 `request_key` 复用已受理轮次时，不重复写入第二条。

### 2.2 Trace 呈现

- 单轮 Trace 顶栏或 Turn 摘要增加只读字段：`work_revision`（提交短哈希或 story revision，以实际可回放字段为准）。
- 时间线上可作为点事件「受理时作品版本」，或仅出现在顶栏；优先顶栏，避免干扰 Loop 甘特。

### 2.3 验收

| 情形 | 结果 |
| --- | --- |
| 只读轮次（无文件写入）结束 | Trace / 活动中能读到受理时版本字段 |
| 有写入的轮次 | 受理时版本与写前 `version_baseline` 均可查，含义不混淆 |
| 同键重放 accept | 不产生重复版本事件 |

确定性测试覆盖记录与幂等；不要求在线模型。

## 3. O1：模型输入可稳定取得

### 3.1 行为

- 保持 `capture_inputs` 默认 `false`（避免日常占用与隐私扩大）。
- 运行追踪详情中：若当前未开启保存输入，模型步详情明确显示「未保存模型输入」，并提供跳转到活动记录设置或一键开启的入口（local 模式）。
- 评测与归因约定：在跑评测或准备导出案例前，通过已有 `PUT .../activity/settings` 将 `capture_inputs` 设为 `true`。本阶段不强制每次对话都开。
- 开启后，模型步的「输入」区必须能读到与当次请求对应的附件（沿用 `input_detail`）；工具步的参数来自事件 `args`，结果来自 `result_detail` 或工具结束事件。

### 3.2 验收

| 情形 | 结果 |
| --- | --- |
| `capture_inputs=false` | 模型步详情提示未保存，不假装有完整输入 |
| 开启后跑一轮含工具的对话 | 模型步可打开输入详情；工具步可见参数与结果 |
| 详情过期 | 摘要仍在，附件缺失时标明过期，不报成成功加载 |

确定性样例可注入带/不带 `input_detail` 的事件；在线单例确认真实附件可打开。

## 4. O2：详情区结构化

### 4.1 布局

选中任一 Span 后，详情区固定四块（无内容的块显示「无」或隐藏，不要留空标题堆叠）：

| 块 | 内容来源 |
| --- | --- |
| 输入 | 工具：`args`；模型：输入附件或「未保存」提示；Gate / 装配：相关判定输入 |
| 输出 | 工具：结果附件或结束载荷；模型：结束原因与输出用量；Write：路径与变更摘要 |
| 属性 | `span_id`、`parent_span_id`、`kind`、名称、重试来源、`error_code`、阶段（stage）等 |
| 事件 | 本步相关的失败/拦截说明；Gate 判定原因；格式 `[错误码] 位置：现象。建议：…` |

不把整段原始活动 JSON 作为默认主视图；需要时可保留「原始事件」折叠项供调试。

### 4.2 验收

| 情形 | 结果 |
| --- | --- |
| 选中成功的工具调用 | 输入、输出、属性三块可读 |
| 选中失败的工具或 Gate | 「事件」块在详情顶部可见错误说明 |
| 选中模型请求 | 属性含用途与用量；输入块符合 O1 |

浏览器确定性用例扩展现有 `runtime-trace.spec.ts`。

## 5. O3：失败可见性

### 5.1 行为

- 时间线行：`failed` / `blocked` / `completed_with_errors` 等失败态与成功态在样式上可区分（沿用或加强现有 `data-status`）。
- 选中失败步时，详情**先**展示「事件」块中的错误，再展示输入输出。
- Turn 顶栏状态已有文案；若整轮失败，顶栏状态保持失败语义，不因后续仍有 Reply 而显示成成功。

### 5.2 验收

| 情形 | 结果 |
| --- | --- |
| Gate 拦截 | 时间线可见拦截，详情顶部有原因 |
| 工具失败后重试成功 | 失败步与成功步均可选；失败原因保留；Loop 可显示已恢复 |

## 6. O4：验收清单

### 6.1 确定性

- 后端：受理版本记录与幂等；Trace 摘要字段；无输入时的详情契约。
- 前端 e2e：详情四块、失败置顶、未保存输入提示、Loop 展开与选中仍可用。

### 6.2 在线单例（`.env`）

1. 开启 `capture_inputs`。
2. 发起一轮会调用 `read_file`（或等价）的只读请求。
3. 在运行追踪中确认：顶栏有受理时作品版本；模型步可打开输入；工具步有参数与结果；时间线父子关系正确。
4. 再发起一轮预期会被 Gate 拦截或工具报错的请求（若不易构造，可用确定性样例代替本条在线步骤），确认失败展示符合 O3。

模型失败时先修产品或记录，再复跑同一单例，不短时间大量重复。

## 7. 阶段顺序与完成定义

```text
O0 作品版本记录
 → O1 输入可取得（含未开启时的明确提示）
 → O2 详情分区
 → O3 失败可见
 → O4 确定性 + 在线单例
```

本阶段完成的标志：作者任选一轮真实对话，仅凭运行追踪页面即可回答「哪一步出错、该步输入输出是什么、受理时作品是哪一版」，无需读服务端日志。完成后进入[评测体系重建](design.md)的下一开发阶段（删除旧评测、重建改稿评测集等），届时另写实施计划。
