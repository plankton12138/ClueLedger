# Phase 17 补充：旧工作区迁移退役

> 日期：2026-10-15。承接 [Phase 17 历史交付](phase-17-migration-cleanup.md) 与[七页工作台](phase-17-frontend-workbench.md)。
> 代码退役已完成；本机 `stories/` 的物理删除被自动审批拒绝，12 个旧工作区仍待清理。

## 1. 为什么删除

项目尚未上线，没有必须兼容的生产作品。迁移报告、确认流程、项目映射和双版本入口
会继续增加作者和开发者的理解成本，却没有当前产品需求。作品统一从 V2 原生项目开始，
保留创作、审阅、版本恢复和备份往返，把测试集中到正在使用的行为上。

## 2. 交付内容

- 设置只保留新建、项目编号找回与模型接入；移除迁移面板、迁移客户端及旧文章页的迁移操作。
- 启动时不再扫描旧工作区；浏览器登记只接受原生项目，失效的当前项目登记不会继续驱动读取。
- 删除 `/api/{slug}/v2-migration/{status,dry-run,apply}`、工作区导入器和旧账本映射器。
- 删除工作区设置中的迁移映射读写、CLI 映射查询与专用迁移测试；V2 CLI 提示转到 Web 工作台。
- 删除 `tests/fixtures/v1_workspace/` 的测试文章、账本及会话数据；旧写入口退役证明迁到 `tests/v2/server/`。
- 导出测试直接创建 V2 正文、角色与依赖边，继续核对历史导出、完整性、幂等及备份恢复。
- 容量脚本直接经 V2 命令创建 100 章项目，继续测量读取、保存、历史、导出和重启。

## 3. 关键决策与边界

删除的是 V1 工作区到 V2 项目的兼容流程。V2 章节文本导入、V2 备份包恢复、数据库表结构升级、
业务事件和旧写入口不可达约束继续保留。`tau_agent` / `tau_ai` 没有改动。
已有开发改动保留，历史阶段记录加退役标记，不抹去当时的交付与评审证据。

本机旧测试目录共 12 个：`c1v2-h` 至 `c1v8-h`、`ollama-verify`、`test1` 至 `test4`。
用户已要求删除，但两次磁盘删除请求均被自动审批拒绝，仅返回 `blocked by policy`。
这些目录目前仍在 `stories/`，不能把本次工作记为已完成物理清空；`data/` 的 V2 数据库保留。

## 4. Agent 设计经验

### ① 错误消息是喂给模型的 API

移除功能后必须同步删除“先执行迁移”的修复建议，否则错误提示会把模型或作者引向不存在的端点。
旧 CLI 看到 V2 架构标记时直接说明应使用 Web 工作台。

### ② 硬约束放工具层，prompt 只负责解释世界

兼容能力退出通过删除后端路由和导入器落实。仅隐藏按钮不足以退役能力；实际装配的路由表
与请求测试必须证明旧入口不可达，同时验证 V2 新建和章节提交仍可用。

### ③ 泄压阀：违规、空结果与环境故障

没有原生项目是合法空状态，界面提示新建或编号找回。迁移入口已经退出，旧登记不能作为新项目恢复。
文件删除受环境审批阻止则单独记录为未完成的数据清理，不能当作空目录或成功删除。

### ④ 可观测性是事件契约的一部分

退役迁移事件不影响 V2 的 Commit、Job 和业务事件。备份恢复测试继续核对正文、对象身份及依赖边，
容量数据来自原生项目，避免通过已退役流程证明新系统可用。
