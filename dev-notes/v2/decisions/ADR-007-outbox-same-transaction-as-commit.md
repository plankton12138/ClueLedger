# ADR-007：Outbox 事件与业务提交同事务，统一提交序列

- 状态：已接受（2026-10-14）
- 关联：[DESIGN.md §10.2](../DESIGN.md#102-提交与事件)、[DESIGN.md §10.3](../DESIGN.md#103-恢复)

## 上下文

V1 中 events_store 为每个 session 实例独立计数，事件与数据写入不在一个事务里：可能出现"数据已写入但事件丢失"或"事件宣称完成而数据未生效"。前端快照依赖事件重放，事件序号分叉导致对账（reconcile）负担。

## 决定

业务变更与 Outbox 事件在**同一数据库事务**中写入；独立发布器把 Outbox 转换为 WebSocket、活动流和后台任务输入。全局只有单一提交序列（Commit Sequence），事件顺序由它决定，任何消费者不得自行计算顺序。恢复规则：进程中止时已提交事务完整、未提交回滚；发布失败时 Outbox 保留待恢复后继续；无 Commit 的任务进度事件不得伪装成业务完成事件。

## 后果

- "一次成功提交必同时产生可查询的 Commit、变更摘要和事件"成为不变量（P7）；
- 断线重连可以按提交序列可靠重放，reconcile 不再承担"猜漂移"的职责；
- 事件消费有天然延迟（经发布器），需要前端区分"已提交"与"已推送"；
- 事件表需要清理策略（发布完成后归档）。

## 替代方案

- 继续每会话独立事件流 + 事后对账：一致性永远靠猜，无法支撑可恢复性验收（总体验收场景 9）；
- 直接推送 + 落库双写：双写不同事务，必然出现一侧丢失。

## 触发重新评审的条件

- 发布器成为吞吐瓶颈且 Outbox 积压影响交互（应优化发布器批量/并行策略，事务绑定不变）；
- 引入多存储引擎（如事件独立库）时必须重新证明原子性等价机制。
