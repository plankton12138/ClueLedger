# ADR-002：不可变 Revision + Commit + Branch 的版本模型

- 状态：已接受（2026-10-14）
- 关联：[DESIGN.md §6](../DESIGN.md#6-版本与生命周期)、[repository-kernel.md](../modules/repository-kernel.md)

## 上下文

V1 的数据文件只有"当前值"，没有历史。撤销靠重新写回旧值，Agent 覆盖人工编辑无法检测，Bible 修改后也无法回答"哪些下游对象是基于旧事实生成的"。

## 决定

所有可版本化对象统一为 Artifact --拥有--> Revision 模型：

- **Revision** 不可变：一经写入永不修改，修正以新 Revision 表达；
- **Commit** 原子：一组 Revision 与关系变化在同一提交中生效或全部不生效，构成单一提交序列；
- **Branch** 可移动：指向一条 Commit 历史的引用，用于修订分支、试写和"以历史 Commit 为基础生成反向 Commit"式的撤销；
- 对象级生命周期（Proposed/Accepted/Superseded 等）独立于全局阶段存在；Bible 更新不回退项目，只沿依赖图把下游对象标记为 stale。

## 后果

- 撤销、分支试写、影响分析（"这个对象依赖哪个版本的 Canon"）都变成可查询的历史问题；
- 存储放大：正文按版本累积，需要内容寻址或去重控制体积；
- API 与 UI 必须暴露版本概念（base_revision_id），V1 式"直接改当前值"的心智模型需要迁移。

## 替代方案

- 只做快照式 undo 栈：实现简单，但无法回答跨对象依赖问题，也无法支持分支；
- Git 直接作为存储：版本能力现成，但领域对象粒度与文件粒度不匹配，且把领域不变量外包给 VCS 使守卫难以插入。

## 触发重新评审的条件

- Revision 粒度被证明过细（例如逐段落版本导致 Commit 体积失控）且合并策略无法补救；
- 出现需要实时协同编辑的需求（乐观版本 + Lease 模型需重新设计）。
