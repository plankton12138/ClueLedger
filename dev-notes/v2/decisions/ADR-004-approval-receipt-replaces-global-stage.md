# ADR-004：退出全局阶段授权，改用审批凭证绑定变更集

- 状态：已接受（2026-10-14）
- 关联：[DESIGN.md §9](../DESIGN.md#9-守卫与授权模型)、[DESIGN.md §11](../DESIGN.md#11-旧系统迁移边界)

## 上下文

V1 用六阶段全局状态机（intake → … → writing）决定"当前允许编辑什么"。长期创作中作者随时要回头改 Bible：全局阶段要么卡住流程，要么靠作者"推进阶段"解锁，与真实意图脱节；"同一会话确认过"这类模糊授权也无法防止后续越界写入。

## 决定

全局阶段不再承担授权与写入控制，只保留为导航用途。写权限由 **Approval Receipt（审批凭证）** 控制，凭证至少绑定：change_set_id、base_commit_id、允许修改的 Artifact/范围表达式、允许的命令类型、有效期与使用次数、授权来源与作者可见摘要。并发用乐观版本检查；耗时任务用仓库级 Lease（带到期时间，不属于任何 WebSocket 或 Agent 会话）。"对象数量达标""项目已进入某阶段"均不构成授权。

## 后果

- 作者获得"随时改 Bible，只让依赖对象 stale"的工作流；
- 每次授权可审计、可过期、可计数，Agent 无法凭旧会话记忆越权；
- UI 需要展示"这次批准允许改什么"，授权交互比"解锁阶段"更细，需要作者教育成本；
- V1 状态机在迁移期继续服务 V1 路径，Phase 17 退出。

## 替代方案

- 保留全局阶段但允许任意阶段回退：仍然无法表达"允许改 A 不允许改 B"的范围授权；
- 纯 RBAC/角色权限：面向多用户系统，对单机单作者项目过度设计，且不绑定变更集。

## 触发重新评审的条件

- 审批粒度被证明过细，作者被高频授权请求打断（应调整默认授权范围模板，而非回到全局阶段）；
- 出现多作者协作场景时重新评审凭证的签发者模型。
