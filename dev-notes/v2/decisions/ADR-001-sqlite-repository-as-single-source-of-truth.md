# ADR-001：SQLite/Repository 是唯一可写事实源，文件仅用于导入导出

- 状态：已接受（2026-10-14）
- 关联：[DESIGN.md §10.1](../DESIGN.md#101-存储决策)、[repository-kernel.md](../modules/repository-kernel.md)

## 上下文

V1 把工作区数据保存为散落的 JSON/YAML/Markdown 文件（bible、manuscript、events、session 各自持有文件写路径）。多写入口导致人工编辑与 Agent 写入可能分叉，事件与数据无法原子一致，也没有跨对象的版本与回滚。

## 决定

V2 使用本地事务数据库（SQLite）保存全部项目状态：Artifact、Revision、Commit、Branch、依赖边、Change Set、审批、任务、作者模型和 Outbox 事件。所有写入经 Repository 端口与统一 Commit Service 提交。Markdown/YAML 只承担三种职责：导入旧工作区、人类可读导出、调试快照/备份。导出文件不是第二事实源，修改导出文件必须通过显式导入操作形成新 Commit。

## 后果

- 数据一致性由数据库事务保证，提交与事件可以同事务落盘；
- 任意 Commit 可本地重放出相同状态，为迁移报告和撤销提供基础；
- 引入 schema 管理与迁移成本；直接手改文件不再生效，调试需经导出或查询接口；
- V1 的文件写入代码在 Phase 17 前保留为只读/导入路径。

## 替代方案

- 继续 JSON/YAML 文件 + 全局写锁：实现简单，但无法原子提交多对象变更，事件顺序无法与数据绑定；
- 双写（文件 + 数据库）：同一数据两个可写入口，必然分叉，违反跨模块红线。

## 触发重新评审的条件

- 单机 SQLite 在 100 章 × 5,000 字规模出现不可接受的读写竞争；
- 出现真实的多人协作或云端同步需求（需要换事务存储实现，端口不变则仅补实现，不推翻本决定）；
- 用户强依赖手改文件作为日常工作流且拒绝导入步骤。
