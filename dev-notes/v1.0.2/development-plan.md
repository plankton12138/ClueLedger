# 1.0.2 开发计划：上下文容量与输入预算

日期：2026-10-30。状态：**待实施**。目标版本 `1.0.2`，运行基线 `1.0.1`。本计划只覆盖本次容量与预算讨论，不把此前列出的全部压缩缺点合并进补丁版本。

## 1. 问题与已核实基线

当前 `model_limits.py` 依次读取服务商元数据和精确模型目录；缺少窗口与输入上限时，`input_limit()` 返回 `None`。`context_boundary.py` 与 `model_activity.py` 因而不能执行依赖上限的自动压缩和发送前拒绝。装配分区的字符限制不覆盖完整消息、工具定义和轮内结果，不能代替完整请求预算。

当前内置 DeepSeek 目录缺少 `deepseek-flash`、`deepseek-v4-pro`。但 `_reported_capacity()` 已认识 `context_window` 和 `max_output_tokens`，本版应复用并验证这条解析路径，不能重复实现第二套解析器，也不能仅凭已保存元数据为空推断解析器有缺陷。

2026-10-30 核对的官方资料：

| 精确模型 ID | 窗口 tokens | 最大输出 tokens | 依据 |
|---|---:|---:|---|
| `deepseek-flash` | 1,048,576 | 393,216 | [官方模型列表示例](https://api-docs.deepseek.com/zh-cn/api/list-models/) |
| `deepseek-v4-pro` | 1,048,576 | 393,216 | 同上 |

[模型价格页](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)用 1M / 384K 表达相同规模；目录用接口示例的精确整数，并记录来源、核对日期。实施时复核官方文档及有权限获取的实际响应；示例不当作当前账号响应的实测证据。输出上限是模型能力，不表示本项目要请求如此长的回复。

## 2. 范围与设计决定

### 2.1 统一计算规则

记 `P` 为项目最大输入，`W` 为已知模型窗口，`I` 为已知模型最大输入，`O` 为已知最大输出，`R` 为实际请求回复额度，`S` 为窗口安全余量，`B` 为有效输入预算。

```text
P = context_policy.max_input_tokens，默认 128,000
R = min(阶段请求的输出额度, O)，O 未知时用阶段请求额度
S = min(4,096, floor(W × 5%))，仅 W 已知时参与换算
B = min(P, I（若已知）, W - R - S（若 W 已知）)
自动压缩起点 = ceil(B × 90%)
主进度占比 = 完整输入估算 / B
```

P 为净输入上限，系统说明、工具定义、消息及协议估算都计入；不要再从 P 重复扣除 R 和 S。两种模型容量都未知时，B=P，模型窗口仍为 null；未知输出上限也不得伪造。常规写作 R 默认保持 4096，实际请求参数与冻结预算必须相同。

任何已知限制算出零或负数均报配置错误，不能像当前 `usable` 过滤那样跳过非正限制后退到较大的上限。正整数校验拒绝 bool、字符串、零与负数；P 必须有限，配置为 null 不表示关闭保护。

### 2.2 默认值与配置

- 新增服务端 `context_policy.max_input_tokens`，默认 128000；沿用现有配置文件读取和保存入口，不新增单独文件或环境变量优先级。
- 本值是计划采用的产品默认值，不是已确认最优值。在线验证记录受它影响的摘要次数、延迟、输入输出量；实现时可通过明确的服务端配置调整，不隐式扩大。
- 暂不增加前端预算编辑器，也不恢复手填模型容量。配置序列化、连接编辑保存都必须保留项目策略。
- 元数据仍优先于目录；目录按官方预设与精确模型 ID 查询。自定义中转不套用原厂目录，使用它自己的元数据；没有则按项目预算控制。
- 本版只补有官方依据的两个新模型，不根据名称前缀自动扩展别名。原目录条目不因新增模型被随意改成新容量。

### 2.3 受理与恢复

P、W、I、O、R、S、B、来源和策略版本进入同一次模型快照。运行中的请求、自动摘要、继续推理、用量事件使用该快照；作者切换模型或修改配置只影响后续受理。

沿用 1.0.1 统一操作及暂停、继续、重启规则，实施时核对 `operations.py` 和 `service.py` 的真实路径，不回接 0.9 的旧独立操作接口。不同阶段 R 不同时，从冻结策略派生阶段预算并记录，不在前端计算。

空闲用量按有效公开历史和冻结写作约定重建；当前选择与历史估算不同则明确归属，不能把旧估算直接除以新模型预算。尚未有请求时，可返回当前选择的容量和策略，但估算为 null；读取接口不写事件、不读取凭据、不调用模型。

已知容量异常时报告 `[CONTEXT_POLICY_INVALID] 模型设置：回复预留与安全余量超过已知窗口。建议：核对模型容量与输出额度后重试。`。必要输入仍超限时沿用 `[CONTEXT_REQUIRED_INPUT_TOO_LARGE]` 及项目现有错误格式。

## 3. 接口与页面契约

沿用 `GET /api/file-workspaces/{workspace_id}/conversations/{conversation_id}/usage`，不增加第二个容量查询接口。以下字段贯穿冻结预算、请求估算事件、会话投影、响应模型和前端类型。

| 字段 | 本版语义 |
|---|---|
| `context_window_tokens` | 模型总窗口，可为 null，绝不写入项目预算 |
| `model_input_limit_tokens`（新增） | 根据已知 I 与 W-R-S 算出的模型可用输入，可为 null |
| `project_input_limit_tokens`（新增） | P，已绑定有效模型时为正整数 |
| `input_limit_tokens` | B，主进度与请求执行共同使用的有效输入上限 |
| `input_limit_source`（新增） | `project` / `model` / `both`；未知模型时为 project，相同上限为 both |
| `capacity_source` | 原有模型容量来源，与项目策略来源分别表达 |
| `model_identity`（新增） | 连接与精确模型 ID，用于归属；不含密钥或账号凭据 |
| `policy_revision`（新增） | P、阈值与预算规则版本；纳入原有估算指纹和 limits revision |
| `output_reserve_tokens` / `safety_tokens` | 本次实际回复额度与模型窗口换算余量；未知 W 时不虚构窗口余量 |

保留原字段名并调整本版语义注释、服务端序列化和前端类型；不保留两套计算。未选模型或连接不可用时预算视图可为空，页面提示先选择模型，不承诺可以发送。

`budget` 使用 B 判断 ok/near/over。主进度由服务端提供的 B 作分母，百分比明确表示输入预算占用；模型窗口放容量明细。暂无估算不显示 0% 或占满。超过预算时文字可超过 100%，进度条宽度限制在容器内。

页面保留现有分项、回复预留、压缩和停止入口，容量明细补项目上限、模型窗口、模型可用输入、来源和自动压缩起点。不增加重复的顶部标签。完整示意见[产品方案](../../product-design/v1.0.2/README.md)。

| 阶段 | 任务与主要文件 | 完成条件 |
|---|---|---|
| P0 基线与口径 | 复核官方资料，穷举模型调用与用量读取入口；检查 `model_probe.py`、`model_connections.py`、`provider_config.py`、`operations.py` 的当前路径 | 保存模型列表字段样本、调用清单与冻结规则；确认没有重复预算实现 |
| P1 容量与策略 | 更新 `model_catalog.py`；验证发现→保存→重启→精确模型的元数据链路；新增配置策略与统一预算计算，更新 `model_limits.py` | 官方模型无元数据也有目录容量；未知模型有项目预算；较小供应商容量不被扩大；配置往返不丢策略 |
| P2 请求与生命周期 | 接通 `provider_runtime.py`、`model_activity.py`、`context_boundary.py`、`context_summary.py`、`service.py` 及统一操作恢复 | 每个实际生成阶段都检查完整输入；预算未知不再成为跳过理由；暂停继续、手动压缩与自动压缩不换策略 |
| P3 用量与页面 | 更新 `conversation_usage.py`、`api.py`、`frontend/src/api/contextUsage.ts`、`ConversationUsageBar.tsx` 与现有格式化函数 | 响应、事件、空闲重建和页面口径相同；模型未知仍可展示项目输入占比；切换会话不串数字 |
| P4 验证与交付 | 执行[验收计划](acceptance.md)，同步版本、锁文件及开发/产品入口 | 定义的回归与在线链路均有证据；发布说明清楚区分已执行与待执行 |

依赖顺序：P0 → P1 → P2 → P3 → P4；编写接口测试可随 P1/P2 前置，不能先上线新分母而后台仍不执行限制。

### P2 特别约束

- 预算检查覆盖写作、讨论、检查、结构相关生成、手动/自动摘要和连接生成测试；模型发现本身不属于生成。阶段小额度可沿用，但不能绕过统一检查。
- 所有请求在真正发送前重新计算完整估算，包含工具参数、结果和协议开销；不得仅比较资料字符预算。
- 已有跨轮压缩成功/失败后都再次检查 B，轮内裁剪仍保护必要输入；错误前已经保存的改动不重做。
- 近期保留量继续按 B 的四分之一、2000—24000 边界计算；四次摘要调用预算、完整轮次切分和单次溢出恢复不扩展。
- 供应商拒绝的单次恢复也记录相同 B 和前后估算；不通过自动提升 P 处理拒绝。
- 模型窗口未知但 B 已知时，摘要分段也必须按 B 检查，避免未知容量导致一次发送全部历史。
- 继承的摘要引文校验不足、反复压缩信息损失、旧公开消息裁剪风险不因本版预算修复而宣称解决；本版若使这些风险更频繁暴露，保留失败证据并作为发布判断的一部分。

## 5. 版本与文档

本次计划不修改包版本。完成实现与验收后，将主包、前端包及对应锁文件统一为 `1.0.2`；构建与显示版本一并核对，桌面端保持既定交付边界。数据格式独立，不做旧数据迁移。

实施记录维护在本版目录，完成后更新本版入口、开发导航和产品导航；历史版本说明只保留必要链接，不批量改写。根目录 README 与 `mynotes/` 不修改。

## 6. 完成判定

不是以“页面不再出现未知”作为完成标准。必须证明：已知模型容量有依据；未知模型有执行中的项目预算；主进度、自动压缩与真实请求使用同一 B；小窗口不被扩大；配置与模型切换不改变已受理请求；首次进入、刷新、暂停继续、重启及在线验证均有对应证据。
