# 空闲会话容量刷新修复

日期：2026-10-30。

## 原因

截图对应会话的用量接口返回约 20,331 tokens，其中约定与资料 3,298、工具定义 10,580、对话与结果 6,453；模型身份为官方连接的 `deepseek-flash`。该请求保存时容量未知，项目预算字段也为空。

当前目录已经收录该模型，但原读取逻辑仅在首次请求前使用当前容量。有请求后始终沿用历史快照，导致已有会话继续显示“输入预算未知”和“模型窗口未获取”。前端也只随会话事件刷新，打开面板和修改模型设置没有触发重新读取。

## 读取规则

- 运行中保留请求的冻结容量与预算；两次模型请求之间仍按整轮运行状态处理。
- 空闲后读取当前模型容量与项目预算。同一连接和精确模型 ID 复用原输入估算，按当前预算重新判断余量并更新估算指纹。
- 切换连接或模型后显示当前容量与“待估算”，不把旧模型的输入规模套到新窗口。最近一次实测输入仍作为历史事实保留。
- 打开用量面板和模型配置版本变化都会重新读取。未知预算的说明只陈述预算未获取，不再据此判断没有可用模型。

这些操作不发起生成请求、不改写会话历史，也不要求先发新消息或清空会话。

## 验证

- 用截图对应的真实会话事件验证新投影：占用保持 20,331 tokens，模型窗口为 1,048,576，输入预算为 128,000，来源为内置目录。
- 后端相关回归：`test_conversation_usage.py`、`test_usage_api.py`、`test_context_usage.py`、`test_model_limits.py`，98 passed。首次运行被系统临时目录权限阻止，改用仓库内独立 `--basetemp` 后全部通过。
- 前端用量单元测试：24 passed；前端构建通过。
- 修改文件的静态检查通过，`conversation_usage.py` 类型检查通过。
- `frontend/e2e/context-usage.spec.ts`：5 passed，使用独立配置和状态目录，覆盖打开面板刷新容量、换模型后待估算、会话隔离、压缩控制与窄屏显示。Windows 测试服务退出时发生清理等待，结束本次隔离服务后测试正常退出，退出码为 0。
- 确认本机各作品均无运行轮次、当前连接使用系统凭据存储后，按原参数重启开发后端。原会话真实 `/usage` 接口已返回窗口 1,048,576、输入预算 128,000、占用 20,331，当前模型仍可用。[脱敏接口记录](../artifacts/context-window-fix-20261030/live-usage-after.json)。
- 浏览器直接连接重启后的本机后端，未拦截接口，打开原会话面板核对预算、16% 占比、窗口与来源；[页面截图](../artifacts/context-window-fix-20261030/live-context-window.png)。

此项修复不替代 1.0.2 的在线生成链路验收。
