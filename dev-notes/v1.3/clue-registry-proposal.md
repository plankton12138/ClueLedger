## 1. 背景与动机

### 1.1 现状

v1.2 已有的结构化事实层：

| 机制 | 管什么 | 形态 |
|---|---|---|
| 章节台账（prose ledger） | 哪些章「真的写了」 | 全局数据文件，随章事务维护 |
| 结构唯一来源（`STRUCTURE.md`） | 铁律 / 路线 / 章节骨架 / 模块索引 | 全局结构文件 |
| 模块（人物 / 旧案 / 物件 / 日常锚 / 伏笔账…） | 领域事实 | 每模块一份 markdown，人类可读 |
| 起草注入 | 起草时注入铁律、台账、对账结论 | `_drafting_injection` |
| 写后自查 | 必发生核对 / 铁律自查 / 读者认知 | 三层模板 |
| 感知区分 | 台账类静默 / 计划性变化必须带说明 | `updates` 分类标注 |

其中伏笔/线索目前落在「伏笔账」模块里，是一份**手工维护的自由格式 markdown 表**（实测样例见 v1.2 测试工作区：`| 项 | 埋 | 收 | 状态 |`，如「箱扣缺漆 | 1 | 5（老魏说出箱子来历） | 已埋」）。它有三类问题：

1. **无锚定**：只记「埋在第 1 章」，不指向具体段落。改稿后无法验证这条线索的承载文本还在不在、是否被改写走了样。
2. **双写漂移**：章节正文与伏笔账是两个手工维护的事实来源。模型改了正文、忘了更新账，或账上记的与正文实际写的对不上——这正是既有机制（台账、对账、自查）在其它层面已经消灭过的问题，唯独在线索层面还开着口子。
3. **不可核对**：「已埋」「部分收」是模型自报的状态，没有任何确定性检测兜底。契诃夫之枪哑火（埋了不收）、空响（收了没埋过）都只能靠模型自觉。

### 1.2 目标

- 线索成为**随章事务自动维护的结构化事实**，与正文同生共死，不再依赖事后手工补账。
- 每条线索**锚定到段落**，改稿后能确定性检测「线索失联」。
- 全局聚合视图支持：
  - 起草时注入「当前全部未回收线索」；
  - 对账产出确定性报告（未回收 / 回收无埋设 / 锚失联 / 计划未落实）；
  - 修订触及锚定段落时给出提醒。

### 1.3 非目标

- 不做语义级的线索识别（不从正文自动「发现」线索——那是模型的事，不是数据结构的事）。
- 不改变「伏笔账」作为人类可读投影的地位，只是让它从**权威**降级为**派生视图**。
- 不引入全局权威注册表（见决策 2）。
- 不重写 v1.0.4 已验证的「视图 + 诊断 + brief」悬疑投影，本提案为其提供更硬的事实底座。

## 2. 三条核心设计决策

### 决策 1：哈希锚定，不用段落下标

任何一次修订（插段、删段）都会让段落下标整体漂移。锚采用：

```
anchor = {
  para_hash,    # 段落正文的内容哈希（去除首尾空白后计算）
  para_prefix,  # 段落前 N 字（N=16），用于失联时的重新定位提示
  chapter_revision  # 锚定时的章节修订号
}
```

读取时按哈希解析；解析失败标 `orphaned`（失联），携带 prefix 供模型重新锚定，**绝不静默失效**。这和台账的幂等重放、建章确认门的引文校验是同一哲学：对不上就显式失败并归因。

### 决策 2：章级权威，全局视图派生

类似 coding agent 中「根目录 AGENTS.md 指向各包目录的 AGENTS.md」：**每章的线索数据是权威，全局注册表只是聚合产物**，随时可从各章文件重建，不持久化为第二权威。

- 写第 N 章时，线索登记随第 N 章的提交事务落盘 → 天然同步，无需全书重扫。
- 聚合视图坏了就重建，不存在双写同步问题。
- 跨章回收（第 1 章埋、第 5 章收）怎么记录？**回收方章文件里写一条 `resolves: <clue_id>`，聚合时归并**。clue_id 全局唯一（格式见 §3.2），所以跨章引用不依赖全局表。

### 决策 3：计划先行，事后核对

纯事后让模型标记线索，会把每段都标成线索，噪声淹没信号。采用本项目一贯的「计划在先」：

- **计划线索**：在结构层以单独的「计划线索」节声明（骨架行不嵌入，见 §9 定案 2），带 id 的条目如「CL-03 箱扣缺漆：第1章埋、第5章收」＋一句意图说明。
- **落实核对**：章提交时，本章提交的线索登记必须能对应到计划线索（落实），或显式声明为意外线索（`origin: emergent`，带说明）。
- 章写完了、计划线索没落实也不拦提交，但对账报告列为「计划未落实」，留给下一回合或作者裁决。

## 3. 数据结构

### 3.1 存放位置与形态

- 章级：随章事务写入的机器可读 JSON（与台账同目录族，建议 `clues/ch{N}.json`）。
- 全局：不落盘的聚合产物；对「伏笔账」这类人类可读模块，提供 **导出/刷新命令** 把聚合视图投影成 markdown 表。

选择 JSON 而非带 schema 的 markdown 表的理由：这是机器事实层，不是给人改的；人类入口走「伏笔账」投影，与 v1.2「结构唯一来源、模块是视图」的分工一致。

### 3.2 章级 schema（`clues/ch{N}.json`）

```json
{
  "chapter": 3,
  "revision": 2,
  "entries": [
    {
      "id": "CL-03",
      "kind": "伏笔",
      "status": "planted",
      "origin": "planned",
      "note": "老魏说出箱子来历",
      "anchor": {
        "para_hash": "…",
        "para_prefix": "箱扣上的漆掉了一块",
        "chapter_revision": 1
      },
      "resolves": null
    },
    {
      "id": "CL-01",
      "kind": "悬念",
      "status": "resolved",
      "origin": "planned",
      "note": "老周追问，他当场承认",
      "anchor": null,
      "resolves": {
        "clue_id": "CL-01",
        "planted_in": 1,
        "anchor": { "para_hash": "…", "para_prefix": "你能不看？", "chapter_revision": 1 }
      }
    }
  ]
}
```

字段说明：

| 字段 | 约束 |
|---|---|
| `id` | 全局唯一。计划线索用结构层分配的 `CL-NN`；意外线索 `EM-<章号>-<序号>` |
| `kind` | 枚举：`伏笔` / `悬念` / `象征` / `物件` / `信息` |
| `status` | 枚举：`planted`（已埋）/ `advanced`（推进）/ `resolved`（已收）/ `retired`（明确不收，须带 note 说明为什么，如「纯细节不收」） |
| `origin` | `planned`（对应计划线索 id）/ `emergent`（须带 note） |
| `anchor` | status ∈ {planted, advanced} 必填；resolved 时挪进 `resolves.anchor` |
| `resolves` | 本章是回收方时填写；`planted_in` 指向埋设章号；被引用的 clue_id 必须在聚合视图里存在匹配章号的 planted 记录（提交门校验，见 §4） |

### 3.3 生命周期状态机

```
declared(计划) ──章提交确认锚点──▶ planted ──后续章推进──▶ advanced ──▶ resolved
                                      │                                 ▲
                                      └──── 同一 id 跨章 resolves ─────┘
任意状态 ──作者/模型显式声明──▶ retired（不收）
锚哈希解析失败 ──▶ orphaned（失联，非终态，可重锚恢复）
```

校验规则（写入时即拒绝，早失败）：
- `status=planted/advanced` 必须有 `anchor`；
- `resolves` 引用的 clue_id 必须存在匹配章号的埋设记录（提交门校验，见 §4），且 `planted_in ≤ 本章号`；
- `retired` 必须带 note；
- `origin=emergent` 必须带 note；
- id 在同一章文件内不得重复。

**回收登记的语义（2026-11-05 可行性切片澄清，发现 1）**：跨章回收的推荐形态是**同 id 状态更新**——第 5 章的回收条目 id 就是 `CL-01` 本身，状态改 `resolved`，`resolves` 指回自己的早期埋设（§3.2 样例即此形态）。因此 `resolves.clue_id == 本条目 id` 且 `planted_in < 本章号` 是**合法路径**，不是自引用矛盾。仅两种形态拒绝：
- `planted_in == 本章号` 且指向自己（同章自埋自收，同一条目内闭环）；
- `planted_in == 本章号` 且指向的 id 不在本章条目内（埋收同章必须两个条目同在本章文件：一条 planted、一条用独立 id `resolves` 引用它）。

## 4. 对账规则（确定性检测）

在既有对账结论之外新增「线索报告」，全部可从章级文件 + 结构层确定性推导：

| 检测 | 条件 | 归因 |
|---|---|---|
| 空响 | 某章 `resolves` 指向的 id 在聚合视图无匹配章号的 planted 记录 | `CLUE_ORPHAN_RESOLUTION`（确定性矛盾，**提交门在写入前拦截，矛盾数据不落盘**，见 §10 发现 2；聚合侧检测保留为兜底；其余四项只报告不拦） |
| 哑火 | 计划线索（结构层声明埋设章 ≤ 当前已写最大章）无任何 planted 记录 | `CLUE_NOT_PLANTED`（报告项，不拦截） |
| 悬枪 | 已写到结构层声明「收」的章，仍 planted/advanced 未收未 retired | `CLUE_UNRESOLVED`（报告项，不拦截） |
| 失联 | 锚哈希解析失败 | `CLUE_ORPHANED_ANCHOR`（列出 prefix 供重锚） |
| 计划未落实 | 计划线索声明本章埋/收，本章提交事务未含对应登记 | `CLUE_PLAN_MISSED`（与 §2 决策 3 的「不拦提交、进报告」一致） |

与既有机制的关系：缺章检测继续管「写了没」，线索报告管「埋了没、收了没、还连着吗」。两者共用对账结论的注入通道，`_drafting_injection` 一次性注入全部。

## 5. 注入点与交互

### 5.1 起草注入（killer feature）

`_drafting_injection(plan)` 在既有铁律/台账/对账之外追加：

```
【未回收线索】
- CL-03 箱扣缺漆（伏笔，第1章埋，未收）："箱扣上的漆掉了一块…"
- CL-05 老花镜来历（物件，第2章埋，计划第5章收）："…"
【本章计划】
- CL-06（计划本章埋）：A-08空物证袋再次出现
【失联待重锚】
- CL-04 照片背面字迹（第2章锚失联，前缀"背面一行小字…"）
```

只注入**未回收 + 本章计划 + 失联**三类，已收/已退役的不占上下文——长篇越写注入越膨胀的问题在这里就被掐住了。

### 5.2 写后自查

自查模板（第三层「读者认知」处）增加一条线索核对项：「本章计划线索是否全部落锚？是否有回收动作与登记一致？」解析沿用 `split_self_check` 的分层关键词切分，缺段按既有失败归因同款处理（新增 `SELF_CHECK_CLUE_MISSING`）。

### 5.3 修订交互

修订回合收尾时，对**改动涉及哈希失联**的线索给出感知区提示（走既有 `updates` 分类标注通道，标 `bookkeeping` 静默或 `planned` 附说明）：

> 「本次修改使第 2 章的 CL-04（照片背面字迹）锚定失联，前缀"背面一行小字…"。请重新锚定或声明 retired。」

不静默重建锚——重锚是认知动作（线索改写走了样和挪了个位置是两回事），必须过模型或作者。

## 6. 事务与原子性

- **随章提交事务**：线索登记作为章提交事务的一部分落盘（`_persist_locked` 时序与台账登记一致），恢复路径幂等重放同样重放线索登记。
- **骨架不算**：与台账同规则——骨架提交不产生线索条目。
- **原子性兜底扩展**：写作回合（write/revise 用途 + 章节目标 + 有写入收据 + 无正文候选 → `EXPECTED_PROSE_MISSING`）不变；新增**一致性兜底**：本章有正文提交但 `clues/ch{N}.json` 缺失/损坏 → 对账报告 `CLUE_FILE_MISSING`，提示补登，不拦截（线索是增强层，坏掉不能堵死写作主路径）。
- **请求键幂等**：线索登记复用章提交事务的 request key，不单开幂等键。

## 7. 迁移

现有手写伏笔账（v1.2 测试工作区样例的 `| 项 | 埋 | 收 | 状态 |` 表）：

1. 提供**一次性半自动迁移命令**：解析表格 → 生成草稿条目（id 自动分配、status 映射「已埋→planted / 部分收→advanced / 已收→resolved / 待埋→仅计划」）→ 锚定字段留空标 `orphaned`。
2. 每章首次修订时，由模型在对话中逐条重锚（有 note 与 para_prefix 辅助定位）。
3. 迁移完成后，`伏笔账.md` 转为由聚合视图刷新的投影，不再手工编辑；文件头加「本文件由线索聚合自动生成」标记。

解析不了的手写表（自由格式）不做强迁：标记「未结构化线索」，注入时降级为原样展示，作者可随时手动补结构。

## 9. 评审定案（2026-11-05）

以下五项已评审定案，规格冻结：

1. **retired 与 resolved 的边界 → 显式 retired**：作者或模型声明过的「不收」才进登记，状态记 `retired`；未登记的纯细节不进登记，但一旦登记为 retired，对账不再追它。理由：不登记会让三章后模型忘记「这个沉默是故意的」而误收。
2. **计划线索声明位置 → 结构层单独一节「计划线索」**：每条一行 `CL-03 箱扣缺漆：第1章埋、第5章收`，可承载整条线索的意图说明；骨架行保持干净，不动格式 5 唯一来源的骨架节。
3. **章节重编号/插章 → 现在不管**：格式 5 目前不支持插章，不为不存在的能力预付复杂度；clue_id 已全局唯一，将来支持插章时迁移 `planted_in` 为机械活。
4. **意外线索配额 → 无硬限**：用提示词约束（「意外线索应罕见，须带说明」），注入侧每章截断上限兜底噪声（上限值在 P2 实施时定），不新增「线索太多」这类创作端怪错误。
5. **对账强制力 → 仅「空响」硬失败**：`CLUE_ORPHAN_RESOLUTION` 拦截提交（确定性矛盾）；哑火/悬枪/失联/计划未落实只进报告与注入提醒，不堵写作主路径，由模型在下一回合自行处理。

## 10. 实施记录：最小可行性切片（2026-11-05，提交 6c5a47b0）

P0 动手前先做了不接事务层的纯模块验证（`workspace/chapter_clues.py` + 28 例单测 + `scripts/clue_minimal_demo.py` 端到端演示），埋设→推进→回收全生命周期与空响/失联/哑火三个反例均跑通；全量回归 1793 passed。验证撞出两个规格盲点，已回写本文：

1. **回收登记的语义**（已补入 §3.3）：跨章回收是同 id 状态更新（第 5 章条目 id 就是 `CL-01`，`resolves` 指回自己的早期埋设），自引用在跨章场景是合法路径；仅同章自埋自收（同条目闭环）与同章缺 paired planted 条目两种形态拒绝。首版实现一刀切禁自引用会导致所有跨章回收无法登记。
2. **空响拦截的时机**（已补入 §4）：拦截点必须在提交事务写入**之前**（提交门 `validate_commit` 对照此前各章聚合视图），事后聚合检测只能兜底——矛盾数据先落盘再报告，权威文件已被污染，不构成「拦截提交」。

切片刻意不接入 `story_store` 事务层；接入（`_persist_locked`/`_recover_locked` 随章落盘与幂等重放、提交工具 `updates` 通道）属 P0 正式范围。
