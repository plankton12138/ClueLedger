# 1.0.3 开发计划

日期：2026-10-30。状态：**P0—P5 已实施，P6 技术项通过，作者体验待确认，P7 待执行**。运行版本仍为 `1.0.1`；未达发布门槛前不修改包版本。本计划正式承接[原构思总览与线索联动讨论](../v1.0.1/notes/2026-10-30-story-overview-linkage-plan.md)，不把讨论示意当作完成记录。

## 1. 产品目标

作者通过全书总览理解各条故事线的关键变化、相互影响和收束，再进入线索详情或正文处理细节。构思节点表示关键行动和变化；章节仍在正文目录，通过多对多正文关联查看。

必须完成：

1. 按阶段纵向推进、按故事线横向排列，阶段可折叠，汇合节点唯一。
2. 故事线具有独立目标、主要阻力和计划收束；跨线关系保存具体影响说明。
3. 构思与正文线索使用同一身份，作者计划和实际正文依据分开。
4. 节点 → 线索 → 其他节点／正文的双向定位及返回位置恢复。
5. 模型先建立整体关键推进，再细化线索；保存的结构持续参与后续讨论与写作。
6. 相关状态联合提交、重启恢复、暂停隔离、并发检查、幂等与有范围的撤销。
7. 真实在线生成和联动修改验收，明确结构、叙事判断和作者体验各自结论。

## 4. 模块职责

### A. 结构与身份

新增阶段及操作，节点由 `stage_id` 明确归属；阶段顺序表示揭示推进，不重写实际事件时间。故事线目标与结局允许未定。章节不进入节点必填项，先有片段也能保存到未分阶段区域。

线索身份只保存在账本，构思计划通过同一 `clue_id` 引用。新身份由服务端分配，模型可在同一请求中使用临时引用；回执返回映射，重试复用同一结果。同名不等于同一线索。

明确区分节点呈现、计划回收和正文中实际回收；使用过程由引用导出，不在多个位置各保存一份可编辑清单。详细字段见[数据契约](data-and-runtime.md)。

### B. 提交、恢复与影响

扩展现有提交日志覆盖构思、线索身份／贡献和必要正文补丁。相关改动在工作副本校验后记录同一提交决定，确定性恢复补完。独立线索写入口也必须遵守同一锁顺序和恢复边界。

读视图先恢复已决定提交，再验证联合快照，防止看到半更新关系。引用的删除、撤销和更名覆盖正文贡献与计划依赖；被后来修改或新增引用的对象不能被旧撤销静默删除。

修改计划后标明相关位置待核对；语义差异通过实际原文核对。作者要求正文一起改时才在授权范围内改写，不能用保存计划代替正文修改。

### C. 读取与引用

扩展现有图、节点、线索及变更接口，不新增重复资料系统。构思读取全书作者计划和相关正文观察，章界读取只展示截止位置内的正文观察，缓存键包含范围和相关修订。

引用同时校验结构、线索计划与账本版本。任务受理后固定对象和范围；浏览其他位置不重定向运行中的修改。具体请求和字段见[接口与页面](api-and-frontend.md)。

### D. 总览与联动

复用当前画布组件，布局计算独立为纯函数。固定列顺序、计算阶段高度、在阶段内遵守推进顺序；共同节点只保留一张卡。阶段折叠产生展示摘要，不伪造真实节点或因果关系。

下方详情显示关键变化、行动及关联入口；完整线索安排与依据在右侧展开。节点选择不强制关闭对话。反向定位展开阶段并恢复可读位置，不发起模型调用；正文返回恢复选中对象、展开状态和视口。

### E. 生成、输入与核对

在同一任务中形成各线目标、关键推进和汇合，再细化线索使用。先做总体安排不表示必须新增一轮确认；只有缺少影响核心故事的决定时才提问。

全局输入保留阶段、各线目标、重要变化和关系，局部输入包含当前任务及必要前文。采用 1.0.2 的完整请求预算，容量不足时明确拆分和覆盖情况，不静默裁掉后半部结构。

结构校验负责引用和顺序。在线叙事核对负责独立目标、跨线影响、支线收束、转折前提和信息边界；一次有边界的修正后仍有缺口则保留问题和未完成状态。不给作品增加笼统的“精彩度”分数。

| P4 总览与联动 | `StoryCanvas.tsx`、新增 `storyLayout.ts`、`StoryClues.tsx`、共用详情、布局与状态 | 固定样例完成节点→线索→另一节点→正文→返回；折叠保留关系、无重复节点、无串作品迟到更新 |
| P5 真实创作 | `prompts/authoring.py`、`prompts/story.py`、`story_context.py`、`story_review.py`、创建表单与 Agent 接口 | 真正提交多线结构；后续修改和写作收到当前关系及必要前提；流式、暂停、插话与预算继续生效 |
| P6 验收 | 按[验收计划](acceptance.md)执行受影响回归、浏览器、在线样例与实际请求检查 | 必需项有真实证据；未通过与未执行分别记录；严重一致性或信息边界问题为零 |
| P7 交付 | 更新现行文档、主包与前端版本及锁文件，验证构建显示 | 验收完成才同步 `1.0.3`；证据、限制、继承项和作者体验状态一致 |

主要依赖：P0 → P1 → P2 → P3 → P4 → P5 → P6 → P7。P1 后可前置纯布局和接口样例开发；任何提前开展的页面工作都不能替代 P2/P3 完成条件。测试随相关模块同步编写和运行。

原四批讨论对应：数据与提交为 P0—P3，页面闭环为 P4，真实创作为 P5，验证交付为 P6—P7。

## 6. 可检查的开发结果

- P3 后：通过真实接口保存多线结构和计划线索，重读得到同一身份、阶段和关系；失败重试和撤销可检查。
- P4 后：固定样例验证布局和联动，明确属于交互验证，不能据此宣称模型能生成精彩多线。
- P5 后：在线模型根据要求生成并保存结构，后续对话能引用、修改并进入真实写作。
- P6 后：分别呈现确定性结果、在线语义发现和作者体验；不以成功的一次覆盖之前失败尝试。

## 7. 验证与证据

确定性验证覆盖新字段、引用、图顺序、身份解析、事务恢复、撤销、接口和缓存。浏览器覆盖折叠、跨线关系、双向定位、返回、滚动缩放、字号、窄屏和快速切换作品。

在线评测只使用 `.env` 配置的模型，覆盖空白多线、已有正文、局部修改、真实写作、换会话恢复和输入预算。保存全部尝试、模型身份、操作与修订、实际请求分区、结果收据、失败和耗时／用量；不输出密钥。

按改动运行必要回归，最后执行仓库规定的类型、静态检查、构建与受影响完整测试。历史测试数量只属于原批次，本版在实际执行后填写。完整场景与通过条件见[验收计划](acceptance.md)。
