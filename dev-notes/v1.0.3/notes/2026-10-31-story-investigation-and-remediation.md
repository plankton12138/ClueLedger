## 1. 结论与产品目标

这次问题横跨生成、图形布局和提交协议。保存了故事线名称，并不代表节点已经形成多线推进；布局也没有使用故事线列。阶段摘要另行覆盖在节点上，长文本没有预留高度。模型提交失败后的修正缺乏语义保护，出现了改变知情时点、降低约定强度的结果。

改造目标是：作者能看清各条线分别改变了什么、怎样影响其他线、在哪里共同收束；保存过程能指出具体对象的问题，并在修正格式时保留故事含义。单线故事仍然合法，不为获得分支图形而添加故事事件或因果关系。

建议沿用已有的“阶段纵向、故事线横向”产品方向，补全数据语义、布局、生成检查与提交诊断。仅增加卡片间距或提示词，不能覆盖本次已确认的问题。

### 2.1 单链：数据与显示均有原因

真实结构的 17 条推进边覆盖全部 18 个节点，构成完整路径，推进图中没有分叉或汇合。六条故事线作为成员关系存在，但其中 16 个节点同时属于多条线。

- **生成层**：主要按事件发生／揭示先后把节点串在一起。例如“讲话之后散席”“第二天清晨发现遗体”也被用作推进理由。阶段和线目标虽已填写，却没有产生独立推进及交汇的结构。
- **布局层**：`StoryCanvas.tsx:74–96` 只把故事节点尺寸和 `next` 边交给布局器，未使用 `threads.order`、故事线归属或阶段高度。以真实结构和当前默认尺寸 `280 × 112` 重放，18 个节点的横坐标全部为 `200`。
- **可读性**：卡片当前显示行动摘要，没有显示 `change`；故事线名称也没有形成列标题。已有“关键变化”数据必须点开详情才能看到。
- **折叠行为**：`StorySurface.tsx:61–70` 实际做的是阶段筛选：隐藏其他节点及跨阶段边。它没有生成保留前后连接的阶段摘要对象。`stages` 仍完整传给画布，没有成员的阶段标题会保留默认位置。

因此，仅按现有 `thread_ids` 把所有多归属节点放入公共行，同样不能解决问题：本样本中将有 16/18 个节点进入公共行。需要区分“主要推进哪条线”“涉及哪些线”和“确实汇合多条线”。

### 2.2 遮挡：阶段摘要没有参与排布

`StoryCanvas.tsx:74–84` 测量和布局的对象只有故事卡片；阶段摘要在布局完成后放到首节点 `x - 12, y - 52`。`index.css:1184–1186` 允许阶段摘要根据文字自然增高，没有为它在图中保留空间。

本次四个摘要分别为 84、88、61、74 个字符。只要摘要实际高度超过 52 像素，就会侵入首节点区域；截图中的“雪”摘要正覆盖首节点。字号放大和换行会扩大重叠。将摘要放到卡片后面或调低层级只会改变被遮住的内容，不能建立正确间距。

本次布局复现使用默认尺寸，未将计算结果冒充浏览器实测。遮挡结论来自截图与定位／尺寸代码的直接对应。

### 2.4 修正过程中发生了语义变化

1. **知情时点改变。** 为通过自引用校验，`node-blackbox` 的一项知情生效节点由自身改成了后面的 `node-pills`，原始来源仍为 `node-blackbox`。这改变了字段表达的知情时点。另有消费侧缺口：`story_context.py:457–483` 按承载节点判断可见性，没有使用 `effective_event_node_id`；离线检查在 blackbox 处仍能读到这条知识。存储和模型输入的时点解释不一致。
2. **约定强度改变。** 首次尝试含 8 条 required、2 条 preference；最终 10 条全部为 preference，来源全部为 model_suggestion。最终回复虽说明了降低强度，但没有完成从已确认模块继承约定的流程。
3. **重复提交范围过大。** 知情错误和开放线索冲突期间，模型连续重发整批 71 项操作来修正局部问题，放大了生成成本与内容漂移机会。

模块内的文字在这次调查中只作为作品内容和来源证据，不作为对调查工作的指令。“根据现有模块开始构思”也不应在未来实现中被解释成允许任意模块命令扩大权限。

### 2.5 接口与验收遗漏

- `read_story` 节点返回 `threads` 的**标题**，HTTP 图接口的同名字段返回 **ID**，写操作使用 `thread_ids`。模型读取又省略 `clue_uses`、`knowledge_changes` 和边 `reason`，无法仅凭这份读取完整重建局部修改。
- 当前 `update_story` 已从数据模型生成操作 schema；问题不应归因于“没有结构化 schema”。跨对象校验、知情规则和来源授权仍主要在执行时才暴露。
- `service.py:1213–1221` 根据保存收据汇总完成结果，没有核验作者要求的结构形态是否形成。
- P6 中 O01 被记录为“空白多线创建”，对应在线用例却明确要求“只有发现和对质两个节点”，并断言两个节点（`story-workflow-online.spec.ts:72–84`）。它证明的是最小创建链路。
- “三线总览可读”页面用例使用手工构造的 5 个节点、短阶段摘要，检查节点存在、按钮数量、页面不溢出并截图，没有几何不重叠断言，也没有检验真实模型生成的多线关系。

历史测试结果保留，但不能继续据其推导“真实模块生成多线、长摘要无重叠已经通过”。

## 3. 改造后的作者体验

默认仍是一份构思。阶段从上到下，每条故事线有稳定的横向位置；列头说明故事线名称，目标与阻力按需查看。节点优先展示标题和关键变化，行动细节进入详情，避免用长段梗概占满总览。

| 对象 | 表达方式 |
|---|---|
| 主要推进一条线的节点 | 放在该线列内；涉及其他线不因此复制节点 |
| 真实汇合节点 | 独立公共行，只显示一次；关联参与线及真实输入／输出 |
| 尚无归属的片段 | 放在未归属区域，允许合法空值 |
| 阶段 | 标题和摘要拥有独立高度，正文区域从摘要之后开始 |
| 折叠阶段 | 摘要替代内部节点，保留与前后阶段的已有连接；展开恢复原图 |
| 重新解释／回收关系 | 默认按需显示，选择节点或线索时突出相关关系 |

六条线会占用较大横向空间；保留画布横向滚动、专注构思和定位，不缩小正文来强行塞进窄屏。真实结构只有单线时如实显示，结构检查说明缺少哪些独立推进安排，由作者决定是否需要改故事。

## 4. 模块改造与实现要点

### A. 数据语义及读写契约

复用阶段、故事线、节点、现有三类边和事务机制。建议增补最小的节点职责信息：

```python
class StoryNode(StrictRecord):
    # 原有 id/title/action/change/stage_id 等字段保留。
    thread_ids: list[StoryId] = Field(default_factory=list)  # 涉及的线
    primary_thread_id: StoryId | None = None               # 主要推进的线
    is_convergence: bool = False                          # 多线成果在此共同作用
    reveal_order: int | None = None                       # 可选的阶段内展示顺序
```

以上是拟议字段，不是当前接口。主线必须属于 `thread_ids`；汇合不能只由“成员数大于一”推断。`reveal_order` 允许相同值，未定允许 null；它不产生因果边。`next` 表达推进依赖或跨线影响，单纯“先发生后发生”使用展示顺序或现有实际时间关系。

前后端及模型工具统一 `thread_ids`、`clue_ids`；标题从身份对象读取。模型的节点详情必须包含完整线索使用、知情变化及边理由；摘要读取明确 coverage，指定节点读取可取得可编辑对象，不能把截断内容标为完整读取。前端轻量图继续按需读详情，不强行携带所有正文内容。

接口沿用现有 graph／node／changes 路由。后端响应模型、前端类型、工具 schema、固定样例同时更新，不加另一套平行的图数据源。

### B. 统一布局及真实折叠

新增独立的 `storyLayout.ts`，输入包括阶段、线顺序、主归属、汇合关系，以及卡片／阶段标题的实际尺寸。先按推进依赖计算阶段内层次，再按列和公共行放置矩形，最后走线。

核心约束示例（不是完整布局实现）：

```typescript
const stageTop = previousStageBottom + stageGap;
const contentTop = stageTop + measuredStageHeader.height + headerGap;
const nodeTop = Math.max(contentTop, predecessorBottom + edgeGap, laneBottom + nodeGap);
const nodeLeft = laneLeftById.get(node.primary_thread_id!);
// 汇合行占用其参与列，推进这些列的已用高度；共同节点只登记一次。
// 阶段结束高度取所有卡片与公共行的最大底边，而非固定节点数公式。
```

必须同时处理：

- 实际测量全部可见卡片和阶段摘要；字号、列宽或摘要变化后重排。
- 阶段先后是硬约束，同阶段的线顺序稳定；无成员阶段和未归属片段不落在 `(0,0)`。
- 布局以作品、修订、尺寸、展开集合为输入；迟到结果不得覆盖新作品或新修订。
- 反向定位等待目标展开和对应布局结束，随后定位，避免先居中再被排布移走。
- 折叠边保存原始 edge ID 映射，去重但不补造连接。空阶段正常显示或隐藏的规则统一。
- 阶段摘要、卡片、公共行均纳入不相交检查；小地图和滚动范围避开主要阅读区域。

### C. 分步生成、候选校验与一次提交

创建任务内部按“骨架 → 线索及知情细节 → 完整核对 → 提交”推进。分步不意味着每一步都要求作者确认；只有核心故事决定缺失或权限不足时提问。

建议在现有任务记录下保留一份可恢复的构思草稿。扩展 `update_story` 的准备／提交模式及 `read_story` 的草稿读取，任务 ID、generation、base revision 均由应用冻结。准备阶段支持带覆盖信息的增量草稿；正式提交仍复用现有故事／线索联合提交与撤销。

```python
issues = validate_fields(candidate)
issues += validate_references(candidate)
issues += validate_clue_lifecycle(candidate)
issues += validate_authority(candidate, frozen_sources)
if issues:
    return repair_report(draft_id, issues, preserved_fields)
# 作者要求多线时，再检查独立推进、跨线影响和收束；结论必须指向对象。
return commit_checked_candidate(candidate, expected_revision, request_key)
```

准备阶段的缺项与非法引用分开：尚未补回收位置可以标为待补，正式提交 explain 计划时必须有相应使用。`leave_open + resolve` 继续报告冲突，不能为了过校验自行改结局。模型只修报告指出的对象，不必重发整份结构。

`next` 图是单链、多归属节点过多等只能触发结构诊断，不能用分支数代替文学评价。对明确的多线任务，诊断和一次有边界的语义核对要指出每条线的独立目标、转折、影响和收束。没有达到要求时保留草稿及未完成原因；普通单线任务不得因此被拒绝。

### D. 错误反馈及语义保护

在应用工具边界识别 `_raw_arguments`，保留既有提供层解析信息，返回独立的参数语法错误；不把不合法 JSON 解释成空 operations。错误返回受长度上限限制的问题列表，而非只取第一条。

每个问题至少包含 `code`、`operation_index`、`object_id`、`field`、`related_ids`、`message`、`suggestion`；全图错误须给出具体线索与节点。普通界面展示事实与处理建议，字段路径和原始参数放在可展开详情。

拟议文案示例：

```text
[STORY_ARGUMENTS_INVALID] 构思提交参数第 7356 列：JSON 语法不完整。建议：补齐对象括号后重新提交当前批次。
[STORY_GRAPH_INVALID] 线索「手记」／节点「别馆廊下」：开放结局计划同时设置了回收作用。建议：核对该处的线索作用，并保留已确定的结局安排。
```

知识来源应区分现场观察和基于已有证据的推断。建议增加来源类型：现场观察可以来自当前事件；推断来源必须存在、可达且不能从未来获知。不再用“一律禁止生效节点等于来源节点”替代知情语义。

同时修正 `story_context` 的消费规则，明确事件内的生效边界，并依据 `effective_event_node_id` 而非承载节点注入知识。角色获知先后结合实际事件时间判断；倒叙的揭示顺序不能直接代替角色经历顺序，读者已知范围另行判断。该规则与正文写作核对共用。格式修正不得移动生效时点；无法确定时点时保留问题，不自动迁移到下一个节点。

### E. 模块来源与约定继承

保留既有必需约定和真相的修改保护。新增的是可核验的来源继承路径：应用冻结本轮采用的模块版本，并将“已有作者确认的结构化约定”“普通参考文字”“本轮模型建议”分开。

```python
if constraint.source_ref:
    source = frozen_sources.require_exact(constraint.source_ref)
    require_author_confirmed_constraint(source)
    require_same_scope_and_content(source, constraint)
    strength, origin = source.strength, "author_module"
else:
    strength, origin = classify_direct_author_request_or_proposal(author_text, constraint)
```

这是规则示意；`source_ref` 和 `author_module` 均为拟议契约增补，模块来源不伪装成本轮作者原话。来源引用需绑定模块 ID、版本、条目和内容摘要，由应用验证；不能仅凭模型填 `origin`、引用含“必须”的文字或模块标题包含“真相”授予权限。普通参考中的限制尚未确认为正式约定时，集中列出待确认项，可一次确认。原 required 项不能在修正报错时被自动保存为 preference。

### F. 结果与状态展示

保存收据继续证明“哪些内容已保存”，结构核对独立说明“哪些作者要求已满足或待定”。存在未解决的约定继承或结构缺口时，不单靠操作数量返回完整成功。

已修正的中间错误可在过程记录中折叠，最终只突出仍需处理的问题；原始失败和修正过程保留。先改进错误内容和处理流程，再调整展示，不能仅隐藏红字。
