## 1. 结论

作者指出的是位置与内容归属不一致：顶部列标题表达故事线，事件卡片却可以被单独拖到其他列或阶段，拖动没有对应的结构修改。本次确认这是交互约束遗漏，自动布局检查通过不能覆盖这个问题。

截图中的 `Tool draft_revision not found` 是另一个问题。应用收到的工具调用名称为 `draft_revision`、参数为空；实际只有 `read_story` 与 `update_story`，`draft_revision` 是读写工具中的版本参数。工具调用被正确拒绝，但缺少针对性的恢复说明；预算控制信息随后直接拼入错误摘要，形成截图中的混杂文案。

本次任务最终成功提交，不是草稿版本丢失、预算耗尽或整个生成失败。

## 2. 卡片为什么会脱离对应列

`StoryCanvas.tsx` 创建阶段标记和故事线列头时显式设置 `draggable: false`（77、83 行），事件卡片没有这个设置（70—72 行）；画布也未设置 `nodesDraggable={false}`（130—139 行）。本地安装的画布组件默认允许节点拖动。`elementsSelectable={false}` 不会关闭拖动。

拖动经 `onNodesChange` 改变页面内节点坐标，连线端点也随卡片移动；它不更新 `primary_thread_id`、`thread_ids`、`stage_id` 或 `reveal_order`，不发起结构变更请求。正式节点格式不保存页面 x/y 坐标；刷新重新按故事线与阶段排布。视口缓存也只保存整张图的平移和缩放。

因此，这里同时存在三种影响：

- 卡片可以出现在另一列或另一阶段，位置不再代表真实归属。
- 自动排布保证的不遮挡会被手动拖动破坏。
- 页面看起来已调整，正式结构却没有修改；刷新或重排后位置恢复。

### 隔离复现

使用当前前端构建和独立服务，准备三列、每列一个节点。将第一列节点向右和向下拖动后：

| 观测 | 拖动前 | 拖动后 | 刷新重新打开 |
|---|---:|---:|---:|
| 卡片相对原列头的横向偏移 | 0 | 304 px | 0 |
| 页面布局坐标 x/y | 112 / 87 | 416 / 144 | 112 / 87 |
| 正式故事线归属 | a | a | a |
| 正式结构修订 | 同一修订 | 未改变 | 未改变 |

拖动后卡片与第二列节点发生可见遮挡。真实作品截图中的“八个人在同一座馆”正式主要归属为“十三年前的十四个人”，涉及另一条故事线不等于改变主要归属；不能只根据截图里卡片所在位置反推数据已改变。

### 建议的产品选择

**建议当前采用自动排布，禁止单张卡片拖动，保留整张画布平移、滚动、缩放、点击和定位。** 该总览的横轴表示故事线，纵向表示阶段与推进关系，单张卡片坐标不是独立内容。此方案直接保留标题与内容的对应关系，改动范围也清楚。

若以后需要手动调整，应明确作为“调整归属／顺序”能力设计：显示可放置区域、释放后吸附、预览将改变的故事线和阶段；确认后通过结构接口保存并重新排布，支持冲突拒绝与撤销。拖动汇合节点还要核对多线参与范围。只让某个列头跟着一张卡片移动，会影响同列其他节点，不能解决归属问题。

### 错误来源与确定范围

通用工具执行器 `tau_agent/loop.py:308—310` 根据调用名称查找工具，找不到时返回英文 `Tool {name} not found`。该轮提供的工具列表没有名为 `draft_revision` 的工具，`story_tools.py:991` 将它定义在 `update_story` 参数中。

可以确定应用执行边界收到的名称是 `draft_revision`，而不是正确的 `update_story`。从调用结果看，版本参数名称被当成了工具名。该轮 `input_captured=false`，未保留原始供应商流式响应，不能进一步断言是模型原始输出还是上游兼容响应在解析前后的具体环节产生了错误。

应用应拒绝未知工具并提供有效工具和参数结构指引，不应把 `draft_revision` 自动别名映射成写入工具，也不应猜测缺少的操作内容。

## 4. 预算信息为什么直接显示在错误旁边

这是上一轮预算反馈接入遗漏的显示边界：

1. `agent.py:3406—3413` 的工具后处理把 `execution_budget` 追加为文本块，对失败工具也执行。
2. `AgentToolResult.text`（`tau_agent/tools.py:41—42`）将所有文本块无分隔连接。
3. `service.py:3500` 直接截取该文本作为工具活动摘要，未区分模型控制信息和作者文案。
4. 前端 `ToolActivity.tsx:66` 原样显示失败摘要。

实际链路的确定性注入复现得到与截图相同的文本：

```text
Tool draft_revision not found{"execution_budget": {"remaining_model_rounds": 18, "reserved_for_commit_and_reply": 3}}
```

预算追加不是未知工具调用发生的证据原因，但它确定造成了错误显示混杂。成功准备的原 JSON 后面也会拼上第二个 JSON 对象，完整文本不再是单一可解析 JSON；这会增加工具结果解读成本。本次没有证据证明它导致了那次名称错误，二者不能直接建立因果结论。

建议分别表达模型需要的执行预算、机器诊断与作者可见摘要。模型侧保留预算，界面默认只显示简短错误；详情保留有用参数与诊断。未知工具应采用项目错误格式，明确“调用名称不存在，草稿已保留”，并指导使用 `read_story` 读取版本、在 `update_story` 中传入该版本；错误码在实施时统一确定。
