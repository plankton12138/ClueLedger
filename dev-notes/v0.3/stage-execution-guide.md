## 1. 使用方式与文档分工

三份文档各管一层，执行时按「产品方案 → 计划 → 本文」的顺序读：

| 层 | 文档 | 回答的问题 | 使用时机 |
|---|---|---|---|
| 为什么 | `product-design/` 四份方案 | 用户旅程、验收动机、排除项 | 开工一个阶段前重读相关章节 |
| 做什么 | [development-plan.md](development-plan.md) §4–§7、§9 | 数据身份、错误码、接口契约、任务清单、退出条件 | 每个子任务动手前核对 |
| 怎么做 | 本文 | 执行顺序、代码手法、测试先行、取证方式 | 执行中随手对照 |

使用规则：

1. **开工前**：读本文该阶段整节 + 计划对应模块节（M01–M14）+ 产品方案相关段落；运行 `git status --short` 确认无回退他人改动的风险；核对上一阶段退出证据确实存在（不凭「上一阶段做完了」的记忆）。
2. **执行中**：按子任务小节推进；每个子任务先写失败测试再写实现；实现顺序一律「后端用例与真实回读 → 前端接线」，前端不先于契约动工。
3. **收工时**：逐条勾选该子任务的「验证与退出条件」；写构建笔记 `dev-notes/v0.3/notes/v03-<任务号>-<主题>.md`；原子提交；更新导航。
4. **偏差处理**：实现证明需要偏离计划时，在构建笔记「与计划偏差」记录问题、选择、原因、替代方案与验证证据；若影响可观察行为，先同步计划契约再改代码，不能只改常量。

## 2. 全局执行纪律

### 2.1 子任务执行循环

每个子任务（如 V03-2.3）按同一个循环执行，不因任务大小跳步：

```mermaid
flowchart LR
    A[读上下文<br>模块+产品段落+前置证据] --> B[写失败测试<br>记录失败原因]
    B --> C[后端用例与状态<br>领域命令→统一提交]
    C --> D[真实回读契约<br>查询接口/事件]
    D --> E[前端接线<br>消费同一契约]
    E --> F[质量门<br>局部测试→全量→静态检查]
    F --> G[文档收口<br>构建笔记+导航+as-built]
    G --> H[原子提交]
    H -->|下一子任务| A
```

**开工五问**（每子任务开工时自答，答不上来就先补齐）：

1. 本任务的退出条件是什么（从计划 §7 表格原文引用）？
2. 前置阶段的退出证据在哪（测试名、构建笔记路径）？
3. 要改哪些模块，对应 0.2 as-built 契约是什么？
4. 本任务是否触碰禁改区：Phase 11 现状清单 §7 的 28 条函数级写入口、tauagent 内核、`LEGAL_EMPTY` 永不设异常子类？
5. 失败测试写在哪，它现在为什么失败？

**提交纪律**：

- 一次提交只完成一个可解释目标；退出条件未满足时保持工作树未完成状态，不为「看起来整齐」强行提交半成品。
- 提交信息建议格式：`v03-<阶段>.<序号>: <一句话目标>`，正文写关键决定与验证证据位置。
- 涉及持久数据的提交必须同时包含内存后端与 SQLite 后端的契约测试；只测内存后端不算过。

## 3. 横切工程手法

本节手法在多个阶段反复使用，先在此统一，各阶段只引用不重复。

### 3.1 错误契约落地

沿用现有 `HastingsError(code, category, where, why, fix)`；三要素是喂给模型与用户的 API，不做「人话翻译」。计划 §4.4 的每个目标错误码在对应任务中登记，统一放一个常量注册表便于盘点：

```python
# application/errors.py 旁的目标示例：0.3 新增错误码集中登记，注册表驱动前后端对齐。
V03_ERROR_CODES: tuple[str, ...] = (
    "EDIT_SAVE_CONFLICT",
    "MANUSCRIPT_BASE_CONFLICT",
    "EDIT_SESSION_BLOCKS_PUBLISH",
    "SOURCE_NEEDS_RECHECK",
    "IMPORT_PREVIEW_STALE",
    "IMPORT_DUPLICATE_CONTENT",
    "EXECUTION_NOT_AUTHORIZED",
    "TASK_BUDGET_EXHAUSTED",
    "UNDO_DEPENDENCY_CONFLICT",
    "OPERATION_KEY_REUSED",
)
```

手法要点：

- `where` 用机器可定位的坐标（字段路径/资源 ID），`fix` 说清「怎样算对」的可执行动作；前端按 `code` 分支，绝不解析中文消息。
- 合法空结果（`no_change`、零建议、图谱未记录、已读且无需修改）**返回正常值而非异常**，与违规、环境故障分流——这是防模型陷入道歉-重试循环的关键。
- 每新增一个错误码，同次补三类测试：领域抛出、API 映射到 HTTP 状态（409/422/条件错误/环境故障）、前端按 code 分支的纯函数用例。

### 3.2 幂等入口统一手法

所有外部写命令带稳定 `operation_id` / `request_id`。对齐现有 `CommitService` 的指纹设计（指纹只含「写什么」，排除 expected_head 等并发凭据，避免合法重放被误判冲突）：

```python
# 目标骨架：业务层幂等包装，同键同指纹返回原结果，同键不同内容 409。
async def execute_once(
    store: OperationReceiptStore,
    operation_id: str,
    request_fingerprint: str,
    run: Callable[[], Awaitable[OperationResult]],
) -> OperationResult:
    existing = await store.find(operation_id)
    if existing is not None:
        if existing.fingerprint != request_fingerprint:
            raise violation(
                "OPERATION_KEY_REUSED",
                where=f"operation/{operation_id}",
                why="同一操作键携带了不同内容",
                fix="新意图使用新的 operation_id；原操作回执见 details.original",
                original_operation_id=existing.operation_id,
            )
        return existing.result  # 重放：返回原回执，不重复执行
    result = await run()
    await store.save(operation_id, request_fingerprint, result)  # 与业务提交同事务
    return result
```

回执保存必须与业务提交共用同一个事务端口（见 §3.3）；先存回执再提交、或提交成功后再补回执，都会在崩溃窗口产生「有结果无提交」或反之。

### 3.3 仓库事务扩展与双后端合同

关键业务状态（回执、操作记录、副本表）进入仓库提交，不在 `CommitService.commit()` 之后调用其他存储假装原子——「同一个 SQLite 文件」不等于「同一个事务」（计划 §4.2）。

实施步骤建议：

1. 在 `RepositoryStorage` 的事务端口上扩展辅助表读写（如 `txn.aux_read(bucket, key)` / `txn.aux_write(bucket, key, payload)`），内存后端实现同端口。
2. `CommitRequest` 增加辅助写入承载字段，或提供「同事务附加写入」入口——选择在 V03-0.5 冻结，双后端契约测试先于实现。
3. 契约测试矩阵（双后端参数化 × 每类写点）：

| 注入点 | 断言 |
|---|---|
| 正文 revision 写失败 | head 不动、回执不存在、副本保存序号不变 |
| 回执写失败 | head 不动、操作记录不存在 |
| 证据状态写失败 | 正文与摘要失效均不生效 |
| Outbox 写失败 | 全部回滚，事件不外泄 |
| 重复提交同键 | 返回原回执，不产生第二个 commit |

### 3.4 显式启动凭据 ExecutionGrant

每项模型功能必须有可追溯的作者启动依据（不变量 I05）。凭据是**应用持久数据**，界面不能伪造为后端已授权：

```python
# 目标骨架：启动凭据。字段即审计记录，缺一不可派发。
@dataclass(frozen=True, slots=True)
class ExecutionGrant:
    grant_id: str
    source: Literal["author_message", "author_button"]
    source_message_id: str | None      # source=author_button 时可空，但按钮事件必须可回查
    function: Literal["draft", "revision", "summary", "suggestion", "holistic_revision"]
    analysis_scope: tuple[str, ...]    # 只读分析范围
    write_scope: tuple[str, ...] | None  # None 表示本功能无写权限
    call_budget: int
    grant_version: int
    connection: ConnectionSnapshot     # 只含 connection_id/revision/provider/model，绝不含 Key
```

派发前统一检查：凭据存在、功能匹配、范围匹配、预算未耗尽、连接快照仍可解析。任何一条不满足返回 `EXECUTION_NOT_AUTHORIZED` / `TASK_BUDGET_EXHAUSTED`，**不运行、不部分运行**。

### 3.5 执行日志端口

三条内容分流：模型公开过程、应用执行事件、正式回复。日志投影为「作品游标 + 全局唯一事件 ID + 源事件 ID 唯一约束」：

```python
class ExecutionLog(Protocol):
    async def append_once(self, source_event_id: str, event: ExecutionEvent) -> bool:
        """按源事件 ID 幂等追加；重复投递返回 False，不产生第二条。"""
    async def page(self, project_id: str, after_sequence: int, limit: int) -> LogPage: ...
    async def subscribe(self, project_id: str, after_sequence: int) -> AsyncIterator[ExecutionEvent]: ...
```

手法要点：同一源内保持因果序；跨源排序只用持久入日志序号，不比较两个流的 sequence；历史分页、实时 SSE、断线补齐共用同一事件 ID 空间；序列化走白名单字段并脱敏（排除 Key、认证头、配置原文、私有凭据路径）。

### 3.6 前端 API 模块组织

- 在 `frontend/src/api/` 下按职责拆 desk 模块（如 `desk/editSessions.ts`、`desk/operations.ts`、`desk/graphs.ts`），每个模块只导出该用例的请求/响应 DTO 与调用函数；不再向全局状态塞任意 payload。
- 共同 DTO（`OperationResult`、错误信封、分页）收敛在既有 V2 接口层（计划 §6.4），两端从同一来源导入。
- 状态单一事实源：正式稿/副本/候选/任务快照四类身份（I01）在 `state/` 中用可辨识联合区分；图谱、建议不另建事实源，只缓存投影查询结果并标注 at_commit_id。

### 3.7 迁移脚本模板

迁移必须可重入、可中断、可回退（计划 §8.1）：

```python
# 目标骨架：检查点式迁移。每步幂等，失败可从中断处重跑。
MIGRATIONS: dict[int, Callable[[MigrationCtx], None]] = {
    4: create_edit_session_tables,      # 版本号独立于产品版本，当前 schema v3 之后递增
    5: create_operation_receipts,
    6: create_execution_log_table,
}

def run_migrations(db: Database, to_version: int) -> MigrationReport:
    current = db.schema_version()
    for version in sorted(MIGRATIONS):
        if version <= current or version > to_version:
            continue
        with db.transaction() as txn:          # 每步一个事务，失败回滚到上一步检查点
            MIGRATIONS[version](MigrationCtx(txn))
            txn.set_schema_version(version)
    return verify_schema(db, to_version)       # 向前兼容读：旧程序写新库必须被拒绝
```

### 4.3 V03-0.3 启动凭据与恢复策略

**目的**：建立 I05/I06 的执行点：未授权 Job 拒绝派发；打开作品、手改保存、重启都不产生模型调用。

**测试先行**（失败测试样板）：

```python
async def test_no_implicit_model_call_on_reopen_and_save(model_recorder, app):
    await app.open_project("winter-manor")       # 打开作品
    await app.save_edit_draft("chapter_1", "新文本")  # 手改自动保存
    await app.restart_server()                    # 重启恢复
    assert model_recorder.calls == []            # 零模型调用；当前实现会因旧自动队列失败
```

**实现要点**：

1. 在 Job 派发入口统一加 `ExecutionGrant` 校验（§3.4）；旧 payload 无凭据的 Job 标为 `historical_paused`，不派发。
2. 恢复策略：重启回读完成结果、继续无模型投影；执行中的模型调用无法确认完成时标 `interrupted`（先用 waiting+reason 表达），等作者继续，不自动重发。
3. 模型运行记录器做成测试夹具：可注入到任何 provider 构造点，记录每次调用的功能、凭据来源、时间。

### 4.4 V03-0.4 切断旧自动链路

多标签序号 CAS、断网请求重排、**完成成功但副本关闭失败**的重启幂等收口（可补偿：已提交操作识别已完成副本，不发布第二个版本）。

## 10. V03-6 人物关系与线索关联图

**开始条件检查单**：账本、正文来源和证据状态查询共用稳定契约。

**阶段退出演练**（第二批统一退出）：跨章修改/重启/无模型/冲突/关联撤销全部保护内容；两张图谱有真实来源与可操作的文字路径。

### 10.1 V03-6.1 只读投影

图谱与目录查询固定同一 commit；节点/边带对象 ID、版本、语义层（truth/knowledge/disclosure/plan）、来源与证据状态；候选单独类型不混入正式集合。**不建立第二份可写事实**（I08/I09 落点）。

### 10.2 V03-6.2/6.3 人物图与线索图

人物图区分真关系/误信/猜测，未记录不变成「不知道」；线索图支持/反驳/误读/解释 + 计划/实现分离；来源正文变化立即显示需核对（复用 M05 证据机制，不另建失效逻辑）。测试：「截至某章」用叙述位置筛选、角色知情按获知事件过滤，两种条件不混用一个 chapter_index。

### 10.3 V03-6.4/6.5 交互与文字等价

右侧局部图、主区展开、加入讨论、来源定位、布局持久化（拖动只写布局偏好，零领域写入）；不用画布也能完成查看/定位/继续写作——键盘与目录具备相同操作能力，这是可访问性验收（A22）的硬要求。

## 11. V03-7 对话整体调整、手法结构与时间线

**开始条件检查单**：跨章发布、后续冲突处理、叙述位置/故事时间与图谱基础均已通过。

**阶段退出演练**：三章以上更换凶手/手法/背景，无逐章审批，约定保留要求落实，四类图谱和真实执行日志可回看。

### 11.1 V03-7.1 意图区分与授权

结构化意图三分：讨论（无写权限）/候选/执行（范围明确授权）。模型说「已获授权」不构成授权（M10 第 2 条）；显式自然语言可直启，歧义只问影响执行的关键选择（最多 1–2 个）。

### 11.2 V03-7.2/7.3 覆盖台账与有限执行

覆盖台账逐章 `unread/read/checked_unchanged/changed/blocked` + 读取区间；只读摘要不能记 checked_unchanged。预算初值 12 次调用/任务（V03-0.7 测定），修正最多两轮，子工作者计入总预算；到上限等待作者，保留内部进度，不新建隐含子 Job 绕预算。

### 11.3 V03-7.4 统一发布与副本门禁

发布只允许一次正式正文/账本统一提交；任务期间新建副本同样阻止冲突发布（发布时查持久副本与来源依赖）。

### 11.4 V03-7.5/7.6 手法图与时间线

手法图只投影已有正式文字与关系，缺项显示「尚未记录」——**不新增结构化步骤对象、不模型补图**；时间线真实事件/证词分轨、未知保留区间、获知事件与叙述位置分开。测试夹具必须包含倒叙/插叙/不可靠叙述。

### 11.5 V03-7.7 影响高亮与关联撤销

高亮有版本差异依据（不代表修订/分数/嫌疑概率）；整体操作纳入关联撤销体系，保护后续独立修改。

## 12. V03-8 数据恢复、默认切换与交付验收

**开始条件检查单**：所有范围内用例均有真实接口与局部验收；**不得带未替代的旧入口直接切默认壳**。

本阶段是统一压测、恢复、生产构建与旧入口最终退役，**不是功能欠账容器**。

### 12.1 V03-8.1/8.2 升级与备份演练

按计划 §8.1 八步执行：只读盘点 → 一致备份（SQLite 快照 API，不裸复制 WAL）→ 增量建表 → 内容转换 → 旧任务隔离 → 影子查询核对 → 默认切换 → 回退预案。备份/恢复对齐计划 §6.5 补充合同：一致快照边界、清单哈希、ID 冲突策略、模型任务恢复为中断、凭据排除。

### 12.2 V03-8.3/8.4 生产闭环与压力

不传特殊测试开关的生产构建 + 默认后端启动完整闭环（创建→生成采用→跨章修改/撤销）；日志断线/游标补齐、任务迟到、多窗口/作品/讨论压力（对照 §9.6 性能目标取证）。

### 12.3 V03-8.5/8.6 视觉走查与旧入口退役

四种窗口（1440×900 / 1280×800 / 1024×768 / 390×844）+ 200% 缩放 + 键盘 + 中文输入法；截图必须来自真实内容与状态。旧写入只能适配统一管线（API 调用矩阵 + 不可绕过证明），被排除功能不能从旧 UI/API 被意外启动。

### 12.4 V03-8.7/8.8 真模型实测与文档收口

真模型与本地接入实测（模拟与真模型证据分开；失败留记录）；更新所有模块 as-built、导航、运行说明与发布记录。**完整验收未过不标 0.3 交付**；无真实凭据/本地环境缺失等保留为显式未验项。
