# V03-6.2 人物图：真关系/认知分层、视角与叙述位置筛选

> 阶段开发记录；实现范围、待办与测试结果均对应记录时点。当前行为见[模块说明](../modules/README.md)，剩余缺口见[运行与验收状态](../release.md)。

关键词：人物图、真关系 vs 角色认知、作者全知/角色视角、叙述位置、获知事件过滤、未记录不变成不知道、局部聚焦、`GET /graphs/characters`

## 目标与结果

V03-6.1 建立了统一只读投影（节点/边/语义层/来源/证据状态）；人物图不在其上另存一份
数据，只在同一投影上做**筛选**，回答「这些人怎样关联，各自想要什么、隐瞒什么、知道
什么」。两条硬验收：**真关系与角色理解分开**，**未记录不变成「不知道」**。

最终交付：

- 领域纯函数 `domain/story/graph.py::character_projection`：在 `graph_projection` 的
  结果上按视角与叙述位置筛选；只保留关系边（truth 层）与认知边（knowledge 层）。
- 位置解析 `domain/story/narrative/order.py::last_beat_of_node`：「截至某章」先解析为
  该章内最后一个节拍，再交给已有的 `story_state_at_beat` 折叠，不新造失效/位置逻辑。
- 应用查询 `application/queries/graphs.py::GraphQueries.characters`：按 Commit 回读，
  附中文标签、视角/位置声明与局部邻居；**只读端口**。
- HTTP `GET /api/v2/projects/{project_id}/graphs/characters`：查询参数
  `at_commit_id / perspective / at_beat_id / at_chapter_id / focus`。

## 关键决定

1. **统一投影上做筛选，不重建边。** 6.2 消费 6.1 的 `GraphProjection`，边 ID、标签、
   语义层、来源、证据状态都沿用同一份口径——图谱仍不是第二份可写事实（I08/I09）。
2. **两类边分开显示。** 关系边 `relation_type=="relationship"` 属 truth 层（客观真关系，
   如「姐妹」「雇佣」）；认知边 `relation_type=="knowledge"` 属 knowledge 层（角色理解，
   如「怀疑」「误信」）。**认知边永远不升级为客观事实**（M12 头部图）。
3. **视角两种模式。** `author`（默认）露全部关系边与认知边，关系贴 `public_state` 与
   `true_state`；`perspective=<角色>` 只露该角色参与的关系边与本人认知边，关系只贴
   `public_state`，`true_state` 置空并标 `true_state_hidden`——「作者知道真相」与
   「某个角色以为如此」在数据上就分开，前端不必自行判断该不该显示。
4. **叙述位置复用状态折叠。** `at_beat_id` 直接走 `story_state_at_beat(catalog, beat, after=True)`：
   认知按 `at_beat_id`（获知事件）在结构顺序中生效、后序覆盖前序、未绑定按起点；
   关系是**基础事实**（`_fold` 先把快照里的关系全部铺开），任何位置都在，只是状态随位置变化。
   `at_chapter_id` 先经 `last_beat_of_node` 解析为章内末节拍，再走同一条路径——两种条件
   绝不混用一个章节下标，叙述位置、故事时间、章节序号是三样东西。
5. **未记录不合成不知道。** 认知边只在存在 `story.knowledge` 记录时生成；没有记录就是
   缺口（边缺失、角色视角下对应事实节点也不出现），**绝不**补一条 `unaware` 边冒充已记录。
6. **节点集按模式收缩。** 作者全知看到投影内全部节点（人物/关系/事实/认知，聚焦邻居才
   有落脚点）；角色视角只保留视角角色与视图内边的端点，无关人物/关系条目不入图。
7. **局部聚焦在模式内取邻居。** `focus` 返回 `{node_id, neighbor_ids}`：作者全知按统一投影
   取邻居（可含线索/地点/场景）；角色视角只在本视图过滤后的边集内取，避免借局部关联
   提前泄露后续信息。聚焦对象必须存在于投影节点集，否则按未知对象拒绝。

## 实现问题与未完成项

- **踩坑（领域设计）**：关系在 `_fold` 里是**基础事实**（先铺开全部关系，再叠加
  节拍状态变化），所以「位置筛选」对关系只影响状态值、不影响是否存在；认知才是
  真正按获知事件增删的。若把关系也当位置增删对象，会误删所有还没写进节拍的关系。
  这一层判断放在领域函数注释里写清，避免后续把两种筛选混为一谈。
- **踩坑（环境）**：`pyproject` 里 `ruff>=0.5` 未锁版本，本机 `uv run ruff` 解析到 0.16.10，
  `ruff format --check` 会命中 17 个与本任务无关的历史文件（`queries/ledger.py`、
  `canon/entries.py` 等）。这是既有版本漂移，**未在本任务内改动无关文件**，已在
  v0.3/README 质量门一行标注，建议单独一次「锁定 ruff 并统一格式化」处理。
- 留白 1：人物图暂不含「未解疑问 / 读者对某角色的认识 / 作者计划的变化」等人物详情
  聚合（产品设计 §5.5 末段），属前端详情面板与后续查询，不在本任务。
- 留白 2：`at_beat_id` 与角色视角的组合语义（「该角色在该节拍已知什么」）已由
  `story_state_at_beat` 覆盖，但**跨视角的知情早晚违规判定**属 V03-7.5/7.6 时间线与
  提前知情规则，本任务只忠实投影，不做判定。
- 留白 3：真实工作区尚无「按节拍归位的认知」写路径（`story.knowledge` 的 `at_beat_id`
  不在直存字段里），位置筛选用直接提交预置测试覆盖；前端图谱接线随 V03-6.4/6.5。
