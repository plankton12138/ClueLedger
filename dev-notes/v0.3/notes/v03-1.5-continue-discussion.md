# V03-1.5 接着讨论

关键词：source_message_ids、不复制作者消息、零自动重放、接着讨论、CHAT_INVALID_COMMAND

## 目标与结果

演示切片的后半段（保存想法 → 连接 → 从某条消息继续讨论）的后端闭环。交付：

1. `ConversationService.send_turn_from_messages`：引用已保存作者消息启动轮次——主消息（第一条）归入新轮次（`open_turn` 的 upsert 语义天然不复制），其余消息保留原位、经历史自然进入模型上下文；只有作者显式调用才启动模型（连接成功零自动重放，I06）。
2. `ChatTurn.source_message_ids`：引用范围随轮次落库并可回读（M02「不复制作者消息」的可审计载体）；普通发送为 None。
3. REST 演进：`POST /conversations/{id}/turns` 接受 `source_message_ids`（与 `text` 互斥，混给/都不给 → `CHAT_INVALID_COMMAND`，新错误码登记）。
4. 校验：消息必须存在于本讨论内且为 author 消息（跨讨论/不存在/助手消息 → `CHAT_MESSAGE_NOT_FOUND`，按既有状态映射落 404）。
5. 测试 `tests/v2/server/test_continue_discussion.py`（3 项）：保存想法零调用 → 显式接着讨论恰好一次调用 → 幂等重放不再调用 → 消息列表不重复；保存→重启→读历史零自动发送；跨讨论/助手消息/互斥拒绝。

## 关键决定

1. **复用 `open_turn` 的 upsert 而非新存储方法**：主消息以相同 message_id 传入 user_message，`_put_message` 幂等覆盖（reparent turn_id）；幂等重放路径 `_find_user_message` 自然找回。不加存储端口方法。
2. **多消息引用只 reparent 第一条**：其余消息留在讨论历史（模型上下文经 `_build_context` 自然包含）；轮次记录完整 `source_message_ids` 供审计。
3. **源消息状态保持 `not_requested`**：它表达「保存时未请求模型」这一历史事实；轮次执行状态在 turn 上，不在作者消息上——不把消息状态复用为轮次状态。
4. **`CHAT_MESSAGE_NOT_FOUND` 落 404**：既有 `_status_for` 的 `_NOT_FOUND` 后缀映射；跨讨论/不存在/非作者消息统一 404 + code 分支（前端按 code 不按状态码）。
5. 与计划无偏差。切片剩余部分（前端壳层把「接着讨论」接到入口/对话 UI）随 V03-1.1 组件接线完成。

## Agent 设计经验（四透镜）

1. 错误消息：`CHAT_INVALID_COMMAND` 处理「混给/都不给」两种意图不明；`CHAT_MESSAGE_NOT_FOUND` 的 fix 明确「跨讨论/跨项目引用拒绝」。
2. 硬约束：非 author 消息不能作引用源——「模型回复不能作为引用源」防止把模型输出伪装成作者发起；互斥校验在端点层，归属校验在服务层。
3. 泄压阀：幂等重放返回原轮次且不再调用模型——重试不双发。
4. 可观测性：`source_message_ids` 随轮次持久化，回看时可回答「这轮是从哪条想法继续的」。

- `uv run pytest -q`（全量）：1433 passed；`ruff check` 全过；`mypy` 237 files 无问题。

## 踩坑与留白

- 坑 1：`ChatTurn` 无 payload 字段——初版把 source_message_ids 塞进不存在的字段；给模型加 `source_message_ids` 可空字段（to_dict/from_dict 同步）。
- 坑 2：测试期望跨讨论拒绝为 400——实际 `CHAT_MESSAGE_NOT_FOUND` 按既有映射是 404；按 API 语义修正测试而非状态映射。
- 留白 1：多消息引用时「实际引用范围」目前等于请求列表；范围裁剪（预算）在 V03-4 上下文装配时细化。
- 留白 2：前端「接着讨论」按钮接线（desk 壳层 + chat state）待 V03-1.1 组件部分。
- 留白 3：grant 化发送（讨论轮次也带 ExecutionGrant 快照）在 V03-1.3 连接同源后统一接线；当前 model_binding_resolver 仍是快照来源。
