# V03-7.4 内部工作版本暂存与统一发布

> 交付日期：2026-10-19。计划 M10 第 9/10 条；执行指导 §11.3。

## 为什么做这个

V03-7.3 解决了「花多少次、什么时候停」，但停下之后要能把这一轮的改动**一次性**
放进正式版。最容易出问题的地方是「半套更新」：正文已经换成新版本，账本还是旧的；
或者发布到一半发现作者开着手工修改副本、正式版刚被别人改过。

这一层把「准备」和「提交」分开：

- 执行期间所有改动先落在**内部工作版本的暂存区**（章全文 + 账本新建/修订），
  不产生 Commit；
- 发布时把正文命令与账本变化放进**同一个 Commit**，任一对象的基础已变则整体不发布；
- 发布前依次检查：任务运行中 → 无活动副本 → 正式基础未前进 → 未覆盖章节都已暂存 →
  预算未耗尽、关键选择已定。

## 做了什么

### 领域：`domain/revision/staging.py`

- `StagedChapter`：章 ID + 章基础版本 + 完整新文本。空文本、缺基础直接拒绝
  （本版不支持用空文本删章）。
- `StagedLedgerChange`：`entry_id=None` 为新建（必须有 `kind`），否则为修订
  （必须有 `expected_revision`，发布时做 revision CAS）。
- `RevisionStaging`：章节按 `chapter_id`、账本按 `stage_id` 覆盖式 upsert；
  `is_empty` 是「有没有可发布内容」的唯一口径。

### 应用：`application/services/revision_publish_service.py`

暂存（`revision_stage` 辅助表，key 为 task_id）：

- `stage_chapter`：章必须在本轮工作版本声明的章节集合内；`base_revision_id` 与任务
  基础版本的章基础不一致即 `REVISION_STAGE_CHAPTER_CONFLICT`（409）。
- `stage_ledger`：暂存时就按基础目录跑一次领域命令，字段/引用错误立即报；
  `stage_id` 缺省时修订用 `entry_id`、新建用 `kind + 内容指纹`（同内容重复暂存是覆盖）。
- `unstage_*`：取消暂存，不碰正式内容。
- 首次暂存会把 `queued` 任务推进到 `running`；等待/停止/已完成的任务不能暂存。

发布（`POST .../publish`）：

1. 已完成的同一 `operation_id` → 直接回放首次结果；不同 ID → `REVISION_TASK_COMPLETED`。
2. 空暂存 → `REVISION_PUBLISH_EMPTY`（400，不创建版本）。
3. 活动副本 → `REVISION_EDIT_SESSION_ACTIVE_CONFLICT`（409）。
4. 基础前进 / 预算耗尽 / 关键选择未定 → 409，`details.blockers` 给出全部阻断项。
5. 覆盖：未覆盖章节**全部已暂存**才算覆盖（暂存内容就是本次任务的覆盖证据），
   否则 `REVISION_COVERAGE_INCOMPLETE_CONFLICT`。
6. 逐章按 `base_revision_id`、逐条账本按 `expected_revision` 组命令，交给
   `PublishManuscriptChange.publish_commands(extra_changes=...)`——正文与账本同一 Commit。
7. 成功后：暂存章记 `changed`、任务标完成并记录 `published_operation_id` /
   `published_commit_id`、清空暂存区。

### 接口

| 方法 | 路径 | 作用 |
|---|---|---|
| POST | `/projects/{id}/revision-tasks/{task_id}/staged-chapters` | 暂存一章全文 |
| DELETE | `.../staged-chapters/{chapter_id}` | 取消该章暂存 |
| POST | `.../staged-ledger` | 暂存一条账本新建/修订 |
| DELETE | `.../staged-ledger/{stage_id}` | 取消该条暂存 |
| GET | `.../staged` | 回读暂存区与计数 |
| POST | `.../publish` | 一次发布正文与账本 |

## 验证

- 暂存领域 5 项：按章/按 stage_id 覆盖、空文本与缺基础拒绝、修订缺 revision 拒绝、
  空暂存与序列化往返。
- 接口 11 项：空发布 400、两章一次提交（新 head 唯一父提交 = 发布前 head）、
  未覆盖阻断且暂存后放行、活动副本 409、任务开始后正式版前进 409、章基础过期 409、
  正文+账本同 Commit、账本修订 revision CAS、同 operation_id 回放 / 不同 ID 拒绝、
  预算耗尽 409、取消暂存。
- 质量门：`uv run pytest -q` 全量通过（数字见 `dev-notes/v0.3/README.md`）；
  `ruff check src/hastings tests/v2` 全过；`mypy src/hastings` 256 files 无问题。

## 已知留白（明确归属）

1. **执行循环仍未接**：谁读章、调模型、调 `stage_*` 与 `consume_calls`，属执行器；
   本任务只提供暂存与发布面。
2. **账本关系**：只暂存条目本身（`artifact_changes`），不暂存 `relation_changes`；
   同一批新建条目不能互相引用（按基础目录校验，看不到同批未提交条目）。
3. **基础前进一律阻断**：尚未实现 M10 §10 的「无关变化可重核重建提交计划」；
   目前统一要求作者重新核对范围。重叠与无关变化的区分留给后续。
4. **删除**：不支持用空文本删除整章；账本删除本来就不是本版操作。
5. **前端**：暂存与发布没有界面入口；作者侧预览/发布确认随整体执行界面补齐。
6. 发布成功后覆盖台账仍绑定旧基础（工作版本不随发布关闭）；任务已完成，不再发布。

## Agent 设计经验

- **准备与提交分开，才能谈「一次提交」**：如果边执行边写正式版，再想保证原子性就只能
  事后补偿；先把改动放在暂存区，提交时只有一条路径，回滚就是「什么都没发生」。
- **覆盖证据跟着暂存走**：未覆盖章节要求「已暂存」而不是「已标 changed」，避免为了
  过检查先把章标成已改、实际却没准备内容。发布成功才写 `changed`，语义不漂移。
- **门禁按「作者下一步做什么」排序**：先报活动副本（去完成/放弃），再报基础前进
  （重新核对），最后报预算（继续）。一次只让作者处理最靠前的那件事，错误信息才有用。
- **回放键要落在任务上**：发布完成后任务里记着 `operation_id`，重试不用再跑一遍
  领域命令，也不会因为新生成的条目 ID 不同而误判成新请求。
