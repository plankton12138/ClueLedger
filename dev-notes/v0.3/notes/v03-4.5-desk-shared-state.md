## 动手前对齐的产品设计

开工前重读了三份方案，本次决定都对应其中明确条款：

| 方案原文 | 落地 |
|---|---|
| §5.2「每次导入、采用或修改完成创建唯一的持久结果记录：绑定发起会话或本作品当前会话，无会话时复用『创作记录』默认讨论」 | `OperationService.submit(origin_conversation_id=…)`，四个入口（试写采用 / 导入确认 / 修改完成 / 历史恢复）都带 `conversation_id` |
| §5.2「归属固定后，作者明确启动的任务始终更新该记录；切换讨论或作品不改变归属，不自动跳转视图」 | 归属在**提交那一刻**写进操作记录；投影只认记录，不认「现在打开的会话」 |
| §5.1「待确认入口…展开为独立候选区」+ §5.2「右侧只提供数量和定位入口」 | `/desk-state` 只回计数与权威 ID；前端侧栏不另存条目列表 |
| §6「桌面收纳规则：已明确启动的任务即使离开视图后完成，也只更新固定归属的记录」 | 撤销继承原操作的归属，作者在哪儿看到修改就在哪儿看到撤销 |
| §6「未完成人工修改保留副本及继续入口」「当前未处理的问题保留简短入口」 | `desk-state` 报 `open_edit_chapters` / 副本 ID，空状态整块不渲染 |
| 桌面交互原则「失败直接写明失败对象、原因和下一步」 | 来源讨论不存在或属于别的作品时入口 404 报错，而不是静默归错 |

## 六个关键取舍

**1. 归属由「提交时记录的会话」决定，不由「投影时的当前会话」决定。**
V03-2.1 的投影刻意不取事件携带的会话，怕的是把结果投进作者当时正打开的讨论。
本刀把同一个 `conversation_id` 字段的语义改窄成「提交时固化的来源」：切换讨论
不再影响已有结果，而投影也不会投错——两个顾虑同时解决。

**2. 来源写错在入口报错，不静默回落。**
投影层仍然保留回落（防止非 REST 调用方），但 REST 入口先校验：会话不存在或
属于别的作品一律 404。归属错了比归属空更糟——作者会两处都找不到它。

**3. 撤销继承原操作的归属。**
撤销产生新操作记录，归属跟着被撤销的那次走。作者在哪条讨论里看到「改了什么」，
就在同一条里看到「已撤销」，历史不断链。

**4. 投影状态是「查」出来的，不是「推」出来的。**
`GET /operations/{id}` 直接问固定归属会话里有没有那条引用消息：有即
`projected`，无即 `pending`。Outbox 重放仍由 worker 循环负责，这里只读，
不因为查不到就判失败——操作结果本身从来不以投影完成为前提。

**5. `/desk-state` 只回计数与 ID，不回正文。**
这是「不重复建议列表事实源」的字面执行：侧栏拿 `candidate_group_id` 去候选组
接口取条目。`content_hash` 让前端判断要不要重取，不必逐字段比对或定时轮询。

**6. 最近结果按操作记录投影，不按内存事件。**
侧栏原来的「操作结果」是内存 map，重开页面就空了。现在用记录里按修订时间
倒序取 8 条灌回同一个 map（按 operationId 合并），两种来源共用一份缓存。

## 留白与风险

1. **前端只接了「后续状态」与「最近结果」两块**：完整账本侧栏、图谱入口、执行日志
   入口仍在 V03-8.6 默认壳统一处理，本刀不改 `components/desk/` 的既有结构。
2. **`recent_operations` 上限 8 条**：够回答「刚才改了什么」，不变成历史列表；
   完整历史走 `GET /chapters/{id}/history`。
3. **投影状态只覆盖固定归属会话**：来源会话若被作者手动删除，消息随之消失，
   此时 `pending` 会一直显示——这是「记录还在、展示丢了」的诚实状态，比假装已投影好。
4. **`desk-state` 不读对话内容**：因此无法回答「哪条讨论里有这条结果」之外的信息；
   需要时由前端拿 `refs.candidate_group_id` / `operation_id` 再查。
