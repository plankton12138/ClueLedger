# V03-5.4 构建笔记：撤销的三方逆向、冲突选择与正文/账本一次恢复

状态：**已交付（同一操作内的正文与账本）**（2026-10-18）。范围：撤销一次操作
时，后来独立写下的正文/账本内容默认保留；重叠处逐项选择；正文与关联账本
一次提交恢复；未完成选择前零写入。后续建议采用产生的账本变化与正文操作的
**因果关联**仍随 V03-7.7。

## 场景与退出条件

计划要求：撤销预览、后续独立文本/账本/新增引用冲突选择；保留新内容；
解决前无半套恢复，选择只说明保留差异。典型例子：正文从九点改八点、账本
随之八点，撤销默认恢复两者；账本后来独立改成八点半，必须保护八点半，不能
直接写回九点。

## 四个决定

**1. 用三方逆向，不用整章旧文本覆盖。**
撤销不是「把当前章替换成 before」：操作之后作者可能又写了新段落。这里把
``after`` 当 base、``before`` 当 ours（要恢复的内容）、``current`` 当 theirs
（后来写的内容）做段落级合并：

- 当前仍等于 after ⇒ 直接恢复 before；
- 非重叠的后续修改 ⇒ 干净合并，自动保留后来内容；
- 重叠 ⇒ 逐处报告 `restore`（before）/`current`（后来内容）两段事实，作者选择。

这与 V03-5.2 的保存合并是同一套“段落级、文本相等才相等”的判断，不做语义推断。

**2. 账本恢复进同一个 Commit，不另开一次提交。**
`PublishManuscriptChange.publish_commands` 新增 `extra_changes`：正文命令与
关联账本 ArtifactChange 一起准备、一起 CAS、一起提交。任一对象在预览后被
改过，整个撤销显式冲突，不留下“正文恢复了、账本没恢复”的半套状态。

账本条目按内容 Artifact 恢复（before content + 当前 revision 作 CAS）；新建的
章节/账本条目仍然阻断——本版没有删除原语，撤销不能靠“删掉”实现。

**3. 每个冲突都必须显式选择，选择绑定预览。**
预览返回 `preview_token`（head、冲突集合、当前 revision 的哈希）与
`decisions`；apply 带旧 token 会被拒绝并要求重新预览。选择按
`text:<章>:<冲突序号>` 与 `ledger:<条目>` 两个 ID 空间给出，值为
`restore` 或 `keep`：

- 全部覆盖才写入；漏选或给出已不存在的 ID ⇒ 409，正文与账本都不动；
- `keep` 不发布半套合并，结果里列出保留项，说明差异仍在；
- 撤销 ID 由“原操作 + 选择”派生：同一组选择重试复用原提交，换一组选择是新意图。

**4. 新增引用只报告，不删除。**
操作之后新增的正文证据链会由统一发布器按新正文重新核对（`will_recheck`）；
新增的账本条目如果引用了被恢复的条目，列为 `kept` 引用，撤销后仍然存在。
“保留某项账本更新”不等于它的旧正文依据继续有效——这一点仍由证据状态回答。

## 接口与行为

| 动作 | 路径 | 关键点 |
|---|---|---|
| 撤销预览 | `GET /operations/{id}/undo` | 章节/账本/冲突/引用/decisions/preview_token；`can_undo` 在需要选择时为 false，但 `hard_blocked` 为 false |
| 执行撤销 | `POST /operations/{id}/undo` | body `{choices, preview_token}`；缺选择或 token 过期零写入 |

预览的章节状态：

| 状态 | 含义 | 处理 |
|---|---|---|
| `ok` | 当前仍等于操作后 | 恢复 before |
| `mergeable` | 之后有非重叠修改 | 三方合并，保留后来内容 |
| `conflict` | 重叠修改 | 逐处 restore/keep |
| `created` / `missing` | 操作新建/之后消失 | 阻断，不删除不重建 |

账本状态同理：`ok` 默认恢复，`conflict` 逐条选择，`created`/`missing` 阻断。

- `tests/v2/undo/` **20 项**（原 12 项 + 新增 8 项）：
  - 干净合并：撤销第一段、保留后改的第二段；
  - 重叠冲突：缺选择 409 零写入，`keep` 保留当前，`restore` 恢复 before；

  `mypy src/hastings` 242 files 无问题。

## 留白与边界

1. **因果关联仍不完整**：撤销只按原 `OperationRecord` 的 before/after 找范围。
   正文操作之后通过“账本建议采用”产生的账本变化，目前没有指回原正文操作的
   因果字段；这部分随 V03-7.7 的统一发布（建议采用也留下操作记录/来源）补。
   因此本刀的“关联账本”是**同一操作内**的账本变化，以及这些条目的后续独立修改。
2. **前端未接线**：写作台没有撤销预览/选择界面；冲突选择目前只有 API 与测试。
3. **无 redo**：撤销的撤销需要新的正向恢复入口，当前只保证重复撤销幂等。
4. **无删除**：新建章节/账本仍阻断；删除语义留给后续版本。
5. **选择粒度是段落与整条账本**：不做字段级合并、不做字符级选区；与正文编辑
   的段落粒度一致。
