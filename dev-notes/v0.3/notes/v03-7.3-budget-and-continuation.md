# V03-7.3 有限执行：预算、修正轮次与等待/继续

> 交付日期：2026-10-19。计划 M10 第 7/8/11 条；执行指导 §11.2。

## 为什么做这个

「一次整体修改」最容易失控的地方不是模型写得好不好，而是**边界**：跑到一半预算用完了、
章节没读完、关键选择还没定，系统如果继续跑，就会在作者不知情的情况下烧掉调用、或者
把「没读过」当成「不用改」。V03-7.2 已经能逐章记录「读没读、读的是摘要还是全文」，
但那份台账还不知道**这次任务允许花多少次调用、修正几轮、什么时候必须停下来问作者**。

这一层补的就是这个「有限」：

- 一次整体任务有一个总预算（默认 12 次调用，启动时可缩小），子工作者与修正都从**同一份**
  预算里扣；
- 修正最多两轮，超过就等作者，不自动再修；
- 到上限、覆盖没做完、关键选择未定 → 任务进 `waiting`，**保留内部进度**（已用次数、
  修正轮次、覆盖台账都不丢），不标完成；
- 停止/失败同样保留正式稳定版与进度；作者显式「继续」才追加预算、推进 attempt；
- 同一作品同时只允许一个进行中任务——这是「不能新建子任务绕预算」的存储层落点。

## 做了什么

### 领域：`domain/revision/task.py`

- `RevisionBudget`：`call_limit` / `calls_used` / `repair_rounds` 的累积账本。
  - `consume(calls=n)` **要么整笔记上、要么一笔不记**；超出剩余次数直接拒绝，不静默截断。
    子工作者把自身调用数合并进来，不能自己开一份预算。
  - `with_repair_round()` 到两轮即拒绝；`with_additional_calls(extra)` 只追加上限，
    不清零已用次数。
- `RevisionTask`：`queued → running → waiting / cancelled / retryable_failed /
  terminal_failed / completed` 的状态机，`attempt` 与 `grant_version` 随继续推进，
  `requires_revalidation` 在继续后置真。
- `publication_blockers(task, coverage_complete, head_commit_id, pending_choices)`：
  纯函数报告「为什么还不能发布」——状态不对、基础前进、覆盖未完成、预算耗尽、选择未定。
  它**只报告不发布**，发布归 V03-7.4。

### 应用：`application/services/revision_task_service.py`

- `start`：绑定 V03-7.2 的工作版本（幂等打开，不重置基础），开任务；同 `request_id`
  重放返回原任务；已有进行中任务时，不同 request_id 一律 `REVISION_TASK_ACTIVE_CONFLICT`。
  上一轮任务已停止/失败后再开新任务，会**强制开新的工作版本**（全部章回到未读）——
  新任务是一份新授权，不能继承上一轮用旧预算读出的覆盖进度。
- `begin` / `consume_calls` / `start_repair`：执行记账。预算或修正轮次不足时，
  **先把任务落成 `waiting` 再抛错**——调用方拿到错误时，进度已经写进任务记录。
- `mark_waiting`：执行循环发现未覆盖/待选/中断时落等待（预算等待不能手工指定）。
- `stop` / `continue_task`：停止保留进度；继续追加预算、`attempt + 1`、
  `grant_version + 1`，不清零旧消耗。
- 存储：`revision_task` 辅助表的 `current` 一条记录原子读-改-写；被替换的任务归档到
  `revision_task_archive/{task_id}`，按 id 仍可回读。

### 接口：`interfaces/api/revision.py`

| 方法 | 路径 | 作用 |
|---|---|---|
| POST | `/api/v2/projects/{id}/revision-tasks` | 开任务（`request_id`、可选 `call_budget`） |
| GET | `/api/v2/projects/{id}/revision-tasks/current` | 当前任务；没有时 `{task_id: null, opened: false}` |
| GET | `/api/v2/projects/{id}/revision-tasks/{task_id}` | 预算、等待原因、覆盖摘要、发布前阻断项 |
| POST | `/api/v2/projects/{id}/revision-tasks/{task_id}/stop` | 停止 |
| POST | `/api/v2/projects/{id}/revision-tasks/{task_id}/continue` | 继续（`additional_calls`） |

`GET` 视图把 `publication` 一并算好：`ready` + `blockers[]`（每条含 code/why/fix），
前端不需要自己重算「能不能发布」。

## 验证

- 领域 11 项：预算整笔记账、耗尽不越界、修正两轮上限、启动只能缩小预算、继续保留消耗、
  停止后可继续、已完成不可继续、等待幂等、发布阻断项逐条报告。
- 接口/服务 10 项：无正文时给下一步、启动默认 12 次、同 request 重放、进行中再开 409、
  超默认预算 400、停止后继续、预算耗尽落等待且保留已用次数、修正两轮后落等待、
  覆盖完成后 `publication.ready=true`、停止后重开新任务会开新工作版本。
- 质量门：`uv run pytest -q` 全量通过（数字见 `dev-notes/v0.3/README.md`）；
  `ruff check src/hastings tests/v2` 全过；`mypy src/hastings` 254 files 无问题。

## 已知留白（明确归属）

1. **执行循环本身**（谁在什么时候读章、调模型、调 `consume_calls`）属 V03-7.4；
   本任务只保证记账口径与状态机。
2. **发布**：`/publish` 与统一正文/账本提交属 V03-7.4；本任务只提供
   `publication.blockers` 作为发布前检查的输入。
3. **关键选择的内容**：目前只区分「有没有待定选择」（`waiting_reason=author_choice`
   计 1 个），选择项本身仍由 V03-7.1 的 `choices` 承载，尚未写进任务记录。
4. **前端**：无任务面板；作者侧「预算/覆盖/等待」界面随整体执行界面阶段补齐。
5. 预算默认值 12 仍是工程初值（V03-0.7 口径），未按真模型样本重新测量。
