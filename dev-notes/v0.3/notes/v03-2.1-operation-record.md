# V03-2.1 OperationRecord 与固定讨论投影

关键词：OperationRecord、operation_receipts、固定讨论（创作记录）、幂等重放、投影失败可找回

## 目标与结果

V03-2 的公共依赖：把一次正文提交包装成**可定位的操作**（计划 §3.3 第 1/6 步、§4.1/§4.2）。交付：

1. **`OperationRecord` 领域模型**（`domain/manuscript/operation_record.py`）：按计划 §4.1 建模为版本化
   Artifact（kind = `operation_record`，ID `art_op_<后缀>`，沿用 art 前缀身份）；内容含
   operation_id / 请求指纹 / 类型 / 作品 / **固定会话 ID** / 来源 / before 版本 / 变更章清单。
   `after_commit_id` 不冗余存储——携带记录的那个 Commit 就是 after 版本，由查询侧解析。
2. **`OperationReceipt` + `operation_receipts` 辅助表**：与提交**同事务**（V03-0.5 的
   `CommitRequest.aux_writes` 端口）；只存提交前已知的信息（指纹/归属/固定讨论），避免把
   提交后才能确定的状态写进指纹。committed vs no_change 由查询侧裁决：记录 Artifact 存在
   ⇒ committed；回执在、记录不在 ⇒ no_change。
3. **`OperationService`**（`application/services/operation_service.py`）：
   - `submit`：读基础快照补全 old_revision_id → no_change 预检（与引擎同一口径）→
     正文变化 + 记录 Artifact + Outbox 事件（`manuscript.operation.committed`，携带固定会话 ID）
     + 回执，同一 `CommitRequest` 原子生效；同键同指纹返回原结果，同键不同指纹
     `OPERATION_KEY_CONFLICT`（409）。
   - no_change：只提交回执——引擎 no-op 分支同事务落库，不创建正文空版本、不创建记录
     Artifact、事件不发出（§3.3 第 6 步）。
   - `get_operation`：**只依赖仓库**（回执 + 记录 Artifact + 引入 Commit 回溯），不依赖对话
     投影——投影失败或未完成时结果仍可找回（§4.2）。
4. **固定讨论投影**（`application/workflows/operation_projection.py`）：
   - 会话 ID 由作品确定性派生（`creation_log_conversation_id = conv_hash(creation-log|prj)`），
     默认讨论唯一；重试/重启/多入口幂等回到同一讨论。
   - `OperationDiscussionProjector` 消费操作事件：会话不存在则**以显式 ID 幂等创建**
     （`ConversationStore.create_conversation` 新增可选 `conversation_id`，双后端实现），
     引用消息 ID 由 operation_id 派生、`append_message` 同 ID 覆盖——Outbox 崩溃窗口重投
     不产生重复消息。
   - **不能投递到当时正在打开的会话**：消费者只写固定会话（ID 由作品派生，不取事件携带值），
     作者会话零接触。
   - `FanOutSink` 扇出：计数端（V03-0.4）与投影端并联；投影失败事件保持待发布，**不回滚
     已原子生效的正文**，恢复后只补展示。
5. **REST**：`GET /api/v2/projects/{project_id}/operations/{operation_id}` 返回
   `OperationEnvelope`（V03-0.2 冻结的信封）；未命中 `OPERATION_NOT_FOUND` → 404 信封。

## 关键决定

1. **回执不含提交后状态**：committed/no_change 由「记录 Artifact 是否存在」在查询侧裁决——
   回执内容全部提交前可知，指纹稳定；避免两阶段写回执或预测-纠正的复杂度。
2. **no_change 预检 + 引擎兜底**：新 Artifact（记录）无法参与引擎 no-op 检测，因此服务先
   预检内容差异，无差异时只提交回执（changes=()）。并发窗口（预检后 head 被他人移动）由
   引擎 old_revision 检查兜底报冲突，不静默错分状态。
3. **引入 Commit 用回溯查询**：`_find_introducing_commit` 从 head 沿链找首次引入记录
   Artifact 的 Commit（O(n)，V03-2.2 统一发布可加索引优化）；不在记录内容里冗余 after，
   保持「记录即提交的一部分」的单一事实。
4. **事件 payload 带固定会话 ID 但消费者不信任它**：事件里的 conversation_id 仅作审计展示，
   投影消费者一律重新派生——防止未来某调用方把作者会话 ID 塞进事件导致串台。
5. **与计划无偏差**；`create_conversation` 的显式 ID 参数为向后兼容新增（缺省行为不变）。

## Agent 设计经验（四透镜）

1. 错误消息：`OPERATION_KEY_CONFLICT` 带原指纹前 12 位，作者/调用方能对上「是不是同一个操作」；
   `OPERATION_NOT_FOUND` 的 fix 指回提交方返回的 operation_id。
2. 硬约束：回执与提交同事务（任一写失败整体回滚，head 不动）；投影消费者只写固定会话
   （物理上无法投递到作者会话）。
3. 泄压阀：no_change 是合法结果（回执照写、不造空版本）；投影失败是可恢复状态（事件待发布 +
   查询可找回 + 展示「同步中」），不阻塞作者继续写作。
4. 可观测性：Outbox 事件 + 记录 Artifact + 回执三处可交叉核对；FanOutSink 保留计数端，
   旧链路分类报告语义不变。

## 踩坑与留白

- 坑 1：v2 路由前缀是 `/api/v2`（项目段在各路由路径里），新路由写成
  `/operations/{id}` 落成 FastAPI 默认 404——先核对前缀再插路由。
- 坑 2：`CommitRequest(**dict)` 让 mypy 全参数丢失推断——改用显式参数的闭包构造。
- 坑 3：领域 `violation` 抛 `ManuscriptViolation`（纯领域类型），application 边界才转
  `ViolationError`——测试断言要按层选类型。
- 留白 1：`_find_introducing_commit` 为 O(n) 回溯；V03-2.2 统一发布落地时如需 O(1)，
  在 aux 或事件索引中记 commit_id（届时指纹一并演进）。
- 留白 2：`submit` 的 changes 由调用方构造；V03-2.2 的 `PublishManuscriptChange` 准备器
  接管变化集合产出（摘要失效/证据核对同事务合成），本服务接口已按其输入形状预留。
- 留白 3：固定讨论的前端展示（创作记录会话在侧栏/写作台的呈现）随 V03-2.2+ 的操作
  结果区接线，本任务只保证数据面。
- 留白 4：`FanOutSink` 中一端失败会暂停另一端该轮消费（发布器单事件推进语义）；
  计数端无副作用可安全重放，如未来接入有副作用的第二消费者需改独立队列。
