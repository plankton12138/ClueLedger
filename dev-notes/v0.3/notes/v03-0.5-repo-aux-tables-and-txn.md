# V03-0.5 仓库辅助表迁移与事务扩展

关键词：aux_records、同事务辅助写入、schema v4、双后端契约、故障注入矩阵、拒绝旧程序写新格式

## 目标与结果

落实计划 §4.2 的原子性方案：关键业务状态（回执、操作记录、副本表）进入仓库提交，不再「同一个 SQLite 文件、各自事务」假装原子。交付：

1. **端口扩展**（`application/ports/repository.py`）：`RepositoryTxn` 增加 `aux_read/aux_write/aux_list/aux_delete`——辅助表与正文 Revision 同一事务边界。
2. **请求模型**（`domain/repository/requests.py`）：`AuxWrite(bucket, key, payload)` / `AuxKey(bucket, key)`；`CommitRequest` 增加 `aux_writes/aux_deletes`，随提交同事务生效；纯辅助提交（无内容差异）返回 `no_change` 且不创建正文空版本。
3. **CommitService**：`_apply_aux` 在幂等记录写入后同一事务内应用（写点顺序：artifact→revision→commit→relation→branch→outbox→idempotency→**aux**）；请求指纹纳入 aux_writes/aux_deletes（「写什么」的一部分，同键同内容才重放）；新增 `aux_read/aux_list` 读助手。
4. **schema v4**：`aux_records(project_id, bucket, key, payload)` 主键 (project_id, bucket, key)；迁移步 3 登记（`CREATE TABLE IF NOT EXISTS` 幂等）；`SCHEMA_VERSION=4`；内存后端 `_MemoryData.aux` + 克隆快照同端口实现。
5. **测试** `tests/v2/repository/test_aux_txn.py`（18 项）：双后端（内存/SQLite）辅助表契约 5 组（round trip、项目/bucket 隔离、搭载内容提交、同键重放与冲突、纯辅助重放稳定）；故障注入矩阵 4 写点 × 双后端（insert_revision / put_idempotent_result / aux_write / append_outbox_events → head 不动、辅助记录不存在、重试单次发布不重复版本）；Outbox 失败事件不外泄；v3→v4 升级保数据、可重入、旧程序（SCHEMA_VERSION=3）拒绝打开 v4 库（REPO_SCHEMA_TOO_NEW）。

## 关键决定

1. **辅助写在事务末位**：幂等记录之后应用 aux——任一回执/副本写失败连带整个提交回滚（矩阵第一、二行）；纯辅助提交走 no_change 早退路径但仍在同一事务应用。
2. **指纹纳入辅助写入**：同键同内容才返回原回执；同键不同 aux 内容显式 `REPO_IDEMPOTENCY_CONFLICT`（既有指纹机制的自然延伸，排除集仍是并发凭据）。
3. **纯辅助提交的幂等记录不落库**（沿用 0.2「no_change 不记幂等键」）：重放以 upsert 自然幂等（同 payload 覆盖同值）；`operation_receipts` 的「无变化回执 + 同键不同内容冲突」由 V03-2.1 的 `execute_once` + 回执存储（bucket `operation_receipt`）在业务层收口——与执行指导 §3.2 的骨架一致，不在仓库层提前造第二套幂等。
4. **`append_event` 式栅栏未触及**：辅助表是数据端口不是事件端口，无代际概念；`job.paused` 事件继续由 JobStore 管理。
5. **兼容读证明的边界**：旧程序保护 = `migrate()` 版本门（v4 库对只认 v3 的程序拒绝打开）；绕过 migrate() 直接写裸 SQL 不在 schema 版本机制射程内（计划 §8.1 已声明「不能通过降级版本号绕过」由门禁保证）。测试断言拒绝发生，不断言「表不可见」。

## Agent 设计经验（四透镜）

1. 错误消息：`AuxWrite.__post_init__` 对空 bucket/key 给三要素 ValueError；迁移拒绝沿用 REPO_SCHEMA_TOO_NEW 三要素（含 db_version/supported 详情）。
2. 硬约束：双后端同端口（内存后端同样实现四个方法）——契约测试参数化保证「只测内存不算过」（执行指导 §2.1）；aux 表主键物理防同键重复行。
3. 泄压阀：`aux_read` 不存在返回 None（合法空结果）；纯辅助提交 no_change 是正常返回不是异常。
4. 可观测性：故障矩阵逐写点断言「head/版本/辅助记录」三元组不变——半提交在任何注入点都不可能被误判为成功。

## 踩坑与留白

- 坑 1：测试里把 actor 传成 tuple（`("system","sys_test")`）触发 `'tuple' object has no attribute 'kind'`——复用 conftest 的 `SYSTEM_ACTOR`（Actor 实例）修正。
- 坑 2：曾预期「旧程序连 aux_records 表都看不见」——表物理存在（新程序建的），裸 SQL 可写；保护点是 migrate() 版本门。测试按真实保护面断言。
- 留白 1：`calls_used` 记账、connection revision 精确跟踪未做（V03-0.3 已记）。
- 留白 2：EditSession/DraftChapter/OperationRecord/OperationReceipt 的记录模型（字段、状态机）在 V03-2.1/2.4 落地；本任务只提供存储与事务基座。
- 留白 3：备份/恢复对 aux_records 的覆盖（计划 §6.5 完整备份）在 V03-8.2 验收；迁移步骤已保证表随库走。
