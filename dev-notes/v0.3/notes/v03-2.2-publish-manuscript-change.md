# V03-2.2 统一发布 PublishManuscriptChange（第一部分）

> 阶段开发记录；实现范围、待办与测试结果均对应记录时点。当前行为见[模块说明](../modules/README.md)，剩余缺口见[运行与验收状态](../release.md)。

关键词：统一发布管线、确定性证据核对、摘要失效、意图指纹、no_change、原子发布（I03）

## 目标与结果

0.3 最核心的写路径（计划 §3.3 六步、M05）：导入/候选采用/修改完成/历史恢复/整体调整/
关联撤销全部复用的统一发布用例。本部分交付**管线主体 + 保存入口接入**：

1. **`domain/manuscript/evidence.py`**（纯函数，无 I/O）：
   - `EvidenceLink`（正文证据）：锚定类型（设定/披露/认知，I09 分存）、目标账本对象、
     来源章 + 引用片段（quote）+ 来源指纹、关系依赖、状态 valid/needs_check、
     previous（前次依据，needs_check 时保留供人工重新关联恢复）。
   - `evidence_after_change`（计划 M05 示例的实现）：无关变化不失效；来源片段仍可在
     新章全文中原样定位 → **重锚有效**（source_hash 更新为新指纹）；无法定位 →
     **needs_check**，不调用模型猜测。
   - `ChapterSummaryState` + `summary_after_change`：来源章变化 ⇒ fresh → stale
     （保留内容与来源清单），已过期不重复记因；无关章保持。
2. **`application/services/publish_manuscript_change.py`**（六步实现）：
   - (1) 回执重放：operation_id 定位已有结果，同键不同指纹显式冲突；
   - (2)(3) 同一基础快照 + 领域命令**纯函数**产出变化集合（不提交、不调模型）；
   - (4) 按实际差异判定受影响章节（章对象与段落对象都按 `chapter_id` 归章），
     确定性核对证据、失效章摘要与全书概览——全部作为新 Artifact 修订汇入变化集合；
   - (5) 经 `OperationService.submit` 把正文 + 证据 + 摘要 + 概览 + 操作记录 + 回执 +
     事件放进**一个 CommitRequest** 原子生效（I03；任一写失败整体回滚）；
   - (6) 返回操作信封；投影未完成仍可按 operation_id 找回。
3. **OperationService 扩展**：`submit` 接受 `events`（领域业务事件同事务入 Outbox）、
   `changed_chapter_ids`（显式章节清单，替换 2.1 的 ch_ 前缀启发——真实章对象是
   `manuscript.chapter` kind，不是 ch_ 前缀）与 `request_fingerprint`（见关键决定 1）。
4. **保存入口接入**：`POST /projects/{id}/chapters/{id}/save` 改走发布器；
   `operation_id` 由保存意图确定性派生（`op_hash(chapter.save|project|chapter|key)`）——
   同一意图重试落回同一操作；响应新增 `operation_id` 字段（其余字段不变）。
5. 新 kind 命名空间：`evidence.link` / `summary.chapter` / `summary.overview`——刻意
   **不**用 `manuscript.` 前缀，避免 `ManuscriptCatalog`（按前缀收集章/段落）把派生
   资料混进领域命令的遍历范围。新 ID 前缀 `evd_`/`sum_` 已登记进 V03_ID_PREFIXES。

## 关键决定

1. **意图指纹取代内容指纹**：重放指纹 = `hash(command.name + 规范化意图 + refs)`
   （repr 稳定，与 handler 同一手）。领域命令每次执行会为新对象生成新 Artifact ID，
   内容指纹在重试间不稳定；意图指纹跨运行恒定，回执重放据此判等。
2. **no_change 乐观预检**：提交前先与基础快照逐对象比对（与引擎同口径）——全部一致
   ⇒ 只提交回执（引擎 no-op 分支同事务落库），不造正文空版本、不造记录 Artifact；
   引擎的 old_revision 检查兜底并发窗口。
3. **证据核对的「变化集合」= 变化对象 ∪ 受影响章节**：证据按章引用来源，段落级
   变化必须归到章（否则引用章的证据永远判「无关」——首轮实现踩过）。
4. **`after_commit_id` 不写进记录内容**：携带记录的 Commit 即 after 版本（2.1 决定
   的延续）；证据重锚用**内容指纹**而非 commit 定位，同样规避自引用。
5. **保存路由兼容**：响应保留全部既有字段（status/commit_id/new_head/summary/
   warnings/chapter_base），新增 operation_id——旧前端不破坏，幂等语义从进程内
   （handler 内存表）升级为持久回执（重启后仍可重放），严格增强。

## 实现问题与未完成项

- 坑 1：证据核对首版用「变化对象集合」判断来源章是否变化——段落级变化的集合里只有
  段落 ID，按章引用的证据永远判无关。修正：变化集合并入受影响章节。
- 坑 2：`no_change = bool(changes)` 语义写反（空变化=要求回执却被当有变化）；改为乐观
  预检（从 True 起，遇实际差异置 False）。
- 坑 3：领域命令每次运行为新对象生成新 Artifact ID → 内容指纹在重试间不稳定 → 同键
  重放误判 409。改用意图指纹（决定 1）。
- 留白 1：**导入与恢复入口尚未接入发布器**（仍走 handler 直提）——管线与保存入口已验证，
  接入是机械工作，随 V03-2.3/2.5 各自任务收口（import 走 2.3 预览确认管线更完整）。
- 留白 2：计划 §9 的逐写点故障注入矩阵（正文/摘要/证据/记录/回执/Outbox）由引擎层
  （V03-0.5 双后端故障注入）+ 发布层并发冲突测试共同覆盖；发布器自身的注入用例随
  导入/恢复接入一起补齐。
- 留白 3：证据的创建流（候选采用/账本写入时生成 evidence.link）在 V03-3/4 落地——
  本任务只交付核对与失效，创建入口为空是合法状态。
- 留白 4：`_chapter_text_after` 以「\n」拼接单元文本作重锚语料；quote 含跨段落换行的
  匹配精度随 TextUnit 选区哈希（§4.1 完整形态）在 V03-4 细化。
