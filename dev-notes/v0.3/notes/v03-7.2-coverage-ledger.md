# V03-7.2 全局上下文与原文覆盖台账、内部工作版本连续修订

关键词：覆盖台账、五状态、读取区间、摘要不得记 checked_unchanged、内部工作版本、全局上下文只读投影、未覆盖可查

## 目标与结果

作者表达一次整体意图后，系统要连续把授权范围内的章读一遍、改需要改的章，而不是让作者
逐章盯着后台流程。这里有个先决问题：**系统凭什么说「这一遍读完了」**？如果只拿「目录里
扫过标题」「读了一段摘要」就宣布某章无需修改，作者事后无从回查，整体调整就变成了黑箱。

V03-7.2 补的就是这份可回查的**原文覆盖台账**与**内部工作版本**（计划 M10 第 5–6 条 /
阶段指南 §11.2）。核心是一句话：**只读摘要/目录不能记 `checked_unchanged`**——「看过一眼」
与「全文检查过」是两件事，台账必须区分得出来。验收口径「逐章实际读取与未覆盖可查，
不将摘要读取当全文检查」正落在此。预算（12 次调用/任务）、两轮修正、到上限等待作者属
V03-7.3，本次不实现。

## 关键决定

1. **硬约束落在领域层，服务层只喂事实。** 「摘要不得记 `checked_unchanged`」不是端点或服务的
   判断，而是 `CoverageLedger.with_confirmed_unchanged`：确认无需修改**要求** `read_kind == full`
   且区间覆盖整章，否则抛 `COVERAGE_NOT_FULLY_READ` 并给三要素。服务层只把该章真实的来源版本与
   整章字数喂进来——判定权单点，不被上层绕过。
2. **「读取区间」是一等公民，且随来源变化重置。** 每章记字符区间而非布尔「读过」：分段读取
   可拼接覆盖整章；正文一变（来源哈希变），既往区间作废、退回 `read`，逼调用方重读——避免拿
   旧版的「已检查」结论套到新正文上。
3. **`changed` 即覆盖，且与「无需修改」互斥。** 改过的章记 `changed`（改动本身就是覆盖），
   它不能再被标 `checked_unchanged`（抛 `COVERAGE_INVALID_TRANSITION`），防止把「改过」与
   「判定无需改」两种不同结论混成一个。
4. **持久化不新造事实源，沿用仓库辅助表。** 内部工作版本作为辅助表 `revision_work`/`current`
   的一条记录，单事务读-改-写；`context` 是「正式基础 + 逐章目录/来源 + 覆盖台账」的**只读投影**，
   按版本从仓库推导，不另存第二份（I08/I09）。
5. **`holistic_revision` 的覆盖台账落地在此，但不提前造执行入口。** V03-7.1 留白里「整体执行的
   覆盖台账随 V03-7.2」在这补上；预算、两轮修正、等待作者与统一发布仍留 V03-7.3/7.4，本次只做
   「读得到、查得到、改得准」。

## Agent 设计经验（四透镜）

1. **错误消息是喂给模型的 API（三要素）**：`COVERAGE_NOT_FULLY_READ` 的 `fix` 直说
   「先读该章完整正文（区间覆盖整章）再做无需修改判断；目录/章节摘要读取不算全文检查」——
   模型拿到的不是「非法」，而是「回去读完整章」这一步可执行动作。未知章、受阻无原因、非法
   动作同样带 `where/why/fix`，HTTP 信封原样透出。
2. **硬约束放工具层/边界，prompt 只解释世界**：摘要与全文的区别不是靠提示词自律，而是
   `read_kind` + 区间覆盖的机械判定；「未覆盖不能当完成」由 `complete` 属性给出，发布检查
   以后只认它。上层想「通融」也通不过领域这关。
3. **降级处理（区分三情形）**：**违规**（未知章、摘要/局部读取却要标无需修改、受阻无原因）
   → 明确拒绝 + 修正指引；**合法但空结果**（`GET` 时尚未打开、某章仍未覆盖）→ 正常返回
   `opened: false` / `uncovered` 清单，指明下一步，不报错；**无法自动判定**（读取受阻的具体
   条件）→ 记为 `blocked` 并**强制记录原因**，归为可回查的未覆盖项而非猜。
4. **可观测性是事件契约的一部分**：`GET /revision-work` 把逐章状态、读取区间、未覆盖原因与
   全局上下文一并回给作者——「哪些章真读过、哪些还没覆盖、为什么没覆盖」都是同一事实源的投影；
   `context` 与 `coverage` 不各拼一套，前端/模型/审计读到的是同一份。

## 踩坑与留白

- **踩坑（私有方法越界）**：领域台账最初用私有 `_require` 做章节定位，服务层调用触发 ruff
  `SLF001`。改为公开 `require_entry`——服务层复用领域定位是**有意**的跨层契约，不该藏在私有名
  后（内部迁移方法同步改回 `self.require_entry`）。
- **踩坑（mypy no-any-return）**：`_now()` 里 `clock.now().isoformat()` 因 clock 参数类型是
  `Any` 命中 `no-any-return`；按既有 `EditSessionService._now` 口径 `str(...)` 收口。
- **踩坑（格式门）**：`ruff format --check` 命中新代码两处（字典字面量引号归一 + 元组换行），
  直接 `ruff format` 收口（仅空白/引号）。
- **留白 1：预算与两轮修正属 V03-7.3。** 本次不实现 12 次调用/任务初值、修正上限、到上限
  等待作者与新增预算记录；台账已备 `with_change` 等迁移供其接入。
- **留白 2：统一发布与副本门禁属 V03-7.4。** 「发布只允许一次正式正文/账本统一提交」「未完成
  副本阻止发布」未接；本次只产出可查的覆盖台账与内部进度记录，`changed` 只是**记录**本次已改，
  真正的分支暂存/合并（把提案变化并入工作版本）随 V03-7.3/7.4。
- **留白 3：`context` 尚未并入模型 `ContextSnapshot`。** 全局上下文当前是 REST 可回读投影；
  把它堆进执行循环供模型使用属 V03-7.3，本任务先把「读得到、查得到」落稳。
- **留白 4：前端未接。** 本任务为后端契约 + 领域台账；作者侧界面（覆盖清单展示、未覆盖提示）
  随整体执行的界面阶段补齐。
