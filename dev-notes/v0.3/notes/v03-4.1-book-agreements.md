# V03-4.1 构建笔记：本书约定

> 阶段开发记录；实现范围、待办与测试结果均对应记录时点。当前行为见[模块说明](../modules/README.md)，剩余缺口见[运行与验收状态](../release.md)。

状态：**后端与契约已交付**（2026-10-18），前端入口待定（见「留白」第 1 条）。
范围：作者显式维护的作品级要求——查看、新增、修改、移除、冲突选择，以及按版本冻结的快照。

## 为什么先做这一刀

V03-4 的四个能力（常驻上下文、摘要、建议、撤销）都建立在一个前提上：模型每一轮拿到的
「本书要求」是**可追溯、可版本化**的东西，而不是散落在历史对话里的几句话。没有这个前提，
4.2 的上下文装配器只能把整段对话塞进提示词，既说不清来源，也无法回答「这次用了哪版要求」。

它也是唯一能纯本地交付、不烧模型调用的一块：作者在作品设置里写一句「全书第一人称」，
下一次试写就该照着写。所以它先落地，给后面的装配器一个稳定的输入。

继承既有的历史、并发与导出能力，没有为它新开一张可写表。

## 三个关键取舍

**1. 冲突按「主题维度」判定，不做语义推断。**
「全书第一人称」和「全书第三人称」显然冲突，但让代码判断两句话是否矛盾需要模型——
那就违背了「无模型可维护」。做法是给每条约定一个登记过的 `topic`（人称、时态、
语气、节奏、篇幅、用语、禁忌、结构、其他），同一主题在任一时刻最多一条 `active`。
判断变成集合比较，结果是确定的、可测的；语义理解仍留给作者，或留给以后真正需要时的
模型建议（那时它也只是给建议，不改变这条不变量）。

**2. 「待选择」是一种状态，不是一句提示。**
产品要求「未明确替换时不把两项同时作为已生效约束」。如果只在 UI 弹一个确认框，
后端就会出现两条生效约定并存。现在新要求可以存成 `status=pending_choice`：
它可以进入列表、可以等作者决定，但不进快照、不参与背景装配。作者选定后
`PATCH {status: active, supersedes: [旧ID]}`，在同一 Commit 里把旧项改成
`retired/superseded` 并写一条 `supersedes` 关系——历史读得出来「谁替换了谁」。

**3. 快照按 Commit 冻结，但指纹不算 commit_id。**
已启动的任务要用自己的约定版本（M07 第 3 条），所以 `GET /agreements/snapshot?commit_id=`
按版本取。但 `content_hash` 只对「约定内容 + 各条 Revision」做哈希：无关的正文提交
不该让「约定版本」看起来变了，否则 4.2 的背景缓存会被每次保存击穿。
两件事分开后，测试可以同时断言「无关保存不改指纹」和「改约定后旧 Commit 的快照原样」。

## 数据影响

- 新增 Artifact kind `story.agreement`，内容含 `statement/topic/scope/status/source_kind/
  source_message_id/retired_reason/superseded_by`。未登记的旧字段进 `legacy_metadata`，
  与 Canon 模型同一套 schema 约定。
- 不进 `CANON_KINDS`：`canon()` 与账本列表都不返回它，避免「作品要求」混进可引用的设定；
  但 `is_story_kind()` 为真，导出、历史、备份自动带上。
- 不物理删除。移除 = `retired/removed`，默认列表不显示，`include_retired=true` 可查。
- 来源可追：`source_kind=author_message` 时 `source_message_id` 必填，凭空来的要求不入库。
- **导出目录显式登记**：`interfaces/exporters/v2_package_exporter.py` 的 `_BIBLE_DIRS`
  对未登记 kind 直接报错（不静默归类），所以新增了 `agreements` 目录；测试断言带约定
  的作品能导出成功且包内出现 `bible/agreements/*.yaml`。这是新 kind 最容易漏的一处：
  不加这一步，带约定的作品导出会整包失败。

## 错误码

| 码 | HTTP | 场景 |
|---|---|---|
| `AGREEMENT_TOPIC_CONFLICT` | 409 | 同主题已有生效约定，且未声明替换 |
| `AGREEMENT_REVISION_CONFLICT` | 409 | 基于过期 Revision 修改（别人先改了） |
| `AGREEMENT_NOT_FOUND` | 404 | 约定的 ID 不存在或不是约定 |
| `STORY_INVALID_COMMAND` | 400 | 未登记的主题/范围/状态、替换跨主题、待选择却声明替换 |

两个 `_CONFLICT` 都是「先由作者做选择」，自动重试没有意义；其余是输入错误。

## 留白与风险

1. **没有前端入口**：计划把约定放在「作品设置」，但 0.2 的七页工作台里没有这个页面，
   0.3 的默认壳要到 V03-8.6 才切。现在的候选落点是写作台右栏或 4.2 的背景面板——
   这属于交互决定，等 4.2 装配器成型时一起定，不在本任务里先造一个临时页。
2. **快照尚未绑定 Job**：`AgreementSnapshot` 可以按版本取，但 `ContextSnapshot`（`tks_`）
   与任务启动的接线在 4.2，本任务只保证取得到、算得稳。
3. **冲突只覆盖同一主题**：跨主题的矛盾（「不写暴力」与「要有血腥现场」）需要作者自己
   发现。这是有意的边界——宁可漏判，也不做没有依据的语义裁决。
4. **多人协作**：`expected_revision` 提供了并发保护，但两个标签页同时改同一条约定时，
   界面还不提示「别人刚改过」，只有 409。提示归 4.5 的侧栏共享状态。
