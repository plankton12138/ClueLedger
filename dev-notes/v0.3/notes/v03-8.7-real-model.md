## 关键判断与坑

1. **「失败证据」是独立结果类型**：驱动用 `ok=None` 表示按设计记录的真实失败（S4），报告单列，不计入通过——避免把"环境缺失被正确记录"说成"功能通过"，也避免把失败藏起来。
2. **三处字段口径以实测为准**（初版驱动按猜测断言，全部修正）：
   - 预算：任务视图是 `budget.call_limit/calls_used/remaining`（不是 `call_budget`）；
   - 覆盖：`revision-work.coverage[].status`（不是 `state`），`complete` 需全书下过结论；
   - 停止：任务终态是 `cancelled`（不是 `stopped`）。
3. **覆盖断言必须对全书**：S2 采用第二章后，任务的基础版本包含两章；只对第一章下结论时 `complete=false`——这不是产品缺陷，而是覆盖口径正确工作的证据。修正测试口径后通过。
4. **开任务零调用**：`POST /revision-tasks` 不触发模型（Job 数不变、`calls_used=0`），与 V03-7.3「开任务不调用模型、执行由作者继续」一致；预算门禁在任务视图可读。

模型输出（仅证据，不作质量结论）：*「钟停在九点。林昭将伞靠在门边，雪水沿伞骨滴落石板。柜台后无人，登记簿半开，末行是林雪的名字……」*

### 两处如实记录的产品缺口（不计通过）

1. **试写候选对「现有章」不带原文**（**同日已修，见下节**）：`drafting.create` 的 `previous_text` 固定为空，`background.render` 也未把目标章作为 `target` 展开；提示词只有「现有章节 {id}」这个标签。所以首轮 `--deep` 把原文作为**作者附加要求**显式写进 instruction 才让模型真的改原文。
2. **任务预算无消费方**：`RevisionTaskService.consume_calls` 在生产代码里**没有调用方**（仅领域 `task.start_repair` 有实现）。S5 的真实模型调用发生在 V03-3 试写服务，`calls_used` 始终为 0——有限执行的预算账本目前是记账面，不是执行门禁。报告把这条单列为失败证据（`ok=None`），不写成通过。

### 结论口径

- 「真模型修订全循环」从未验项里移出：链路（读→改→覆盖→暂存→发布）有真实模型证据。
- 但**改动来源**是试写候选而非预算受限的执行器；预算归因与「自动读原文」两项缺口转入 release §5，等产品裁决/接线，不冒充已验。

## 修复：改写现有章时由服务端装入原文（2026-10-19 同日）

`drafting.create` 在 `target` 指向现有章时，用 `domain/manuscript/summary.chapter_text`
取该章**当前版本**的活动正文，作为 `previous_text` 交给提示词渲染（段落标题
`现有正文`，原为 `上一稿正文`——现在同时服务「改写正式章」与「候选二轮修订」两种基础）。

```python
base_text = manuscript_chapter_text(catalog, target) if target != TARGET_NEW_CHAPTER else ""
written = await self._generate(brief, previous_text=base_text, adjustment="")
```

取舍：

- **不做长度截断**。截断会让模型「改完」却丢掉后半章，比报错更危险；章过大时由
  Provider 的上下文限制如实失败，作者可拆章或缩小范围（与「不静默省略背景」同一原则）。
- **不在服务里登记覆盖读取**：试写是独立候选路径，没有绑定 `revision-work` 的任务与
  work_id；读取登记仍由发起方（修订任务/驱动）做，避免伪造一次「任务已读」。
- 新章试写不带该段：没有原文就不伪造一段（单测锁定）。

验证：

- 单测 2 项（`tests/v2/drafts/test_drafting.py`）：改写现有章时提示词含原文两段且
  `现有正文` 只出现一次；新章试写不含 `现有正文`。drafts 套件 30 passed。
- `--deep` 复跑（报告 `eval/runs/2026-10-19-v03-8.7-deep-revision-v2/`，10 通过 + 2 失败证据）：
  instruction **不再含原文**（`instruction 未含原文=True`），模型输出仍保留「九点 / 林雪 / 杯」，
  并写出 instruction 未提的「雪水顺着伞骨滴落」「壁炉里的火只剩一层灰」——证明它读的是原文而不是要求。
- 如实说明输出质量：本轮输出 120 字（原文 123 字），属**轻度改写**（标点与个别措辞），
  不是大幅重写；这是模型行为，链路口径只断言「非原样返回」，不据此宣称改写质量。

## 远程端点实测：DeepSeek（2026-10-19）

本机 `.env` 里已有 DeepSeek key（沿用 `OPENAI_API_KEY` / `OPENAI_BASE_URL` / `HASTINGS_MODEL=deepseek-flash`），
但两处让"有 key 也用不了"：

1. **`config.yaml` 会盖住 `.env` 的端点**：`base_url` 没有 env 字段，只有「config.yaml 缺失/为空」时才走
   `env_fallback_config()` 读 `OPENAI_BASE_URL`。本机配置里 `default` 档案写的是 `https://api.openai.com/v1`、
   `default_model` 为空——于是 DeepSeek 的 key 被发到 OpenAI，且模型名为空被判定未配置。
   修法（本机配置，已改）：`default.base_url → https://api.deepseek.com/v1`、`default_model → deepseek-flash`，
   key 继续引用 `OPENAI_API_KEY`。
2. **驱动写死 ollama 且不加载 `.env`**：`desk_driver.py` 原来只找 `name == "ollama"` 的档案，也不 `load_dotenv`。
   已加 `--provider`（默认 ollama）并在启动时加载仓库根 `.env`；S4 改用所选档案构造失败证据。

实测（`--provider default --deep`，报告 `eval/runs/2026-10-19-v03-8.7-deepseek/`）：

- **13 通过 + 2 证据，失败 0**，耗时 34s（本地 qwen3:8b 同场景约 5–6 分钟）；
- S1 讨论 65 增量 / 96 字、S2 候选 277 字、S5 改写 104 字（保留三要素）、S6 预算 1 停在第 2 章后继续跑完；
- 端点连通性另测：DeepSeek `/models` 200（模型列表含 `deepseek-flash`，context 1,048,576）；OpenAI 官方端点经本机代理 502，无法验证。

口径：DeepSeek 是 **OpenAI 兼容的远程端点**，不是 OpenAI 官方；「远程 Provider 可调用」有证据，
「OpenAI 官方」仍无可用 Key，不混为一谈。
