## 3.1 为什么是「部分」

计划写的是「实施 Beat 有效信息转换及活动 Schema/工具/上下文清理」。真正的活动路径有两条：

1. **写作台的任务建议 → 起草**：V03-3 之前，`chapter_draft` 的缺失项要求「已接受节拍」与「选择节拍」，
   writer 上下文还会装配 `beat_states`。这条路径是产品要保留的那条，所以先把节拍从这里彻底摘掉：
   - `missing_items`：`chapter_draft` 不再产生 `TASK_NO_BEAT_TARGET` / `TASK_NO_PLAN`，空项目也不再报
     `TASK_NO_BASE`（空 head 是合法首章来源）；只保留「写哪一章」这一条真实缺失。
   - writer 角色文案：依据从「已接受 Beat」改为「本书账本 + 作者要求」。
   - 上下文装配：只有目标本身是 `narrative.beat` 时才计算 `beat_states`，账本驱动的起草不再触发
     `ordered_beats` 与节拍状态投影。
2. **旧「创作台」的规划/起草工作流**（`story_proposals`、`agent_workflows` 的 `planning_forms`）：
   仍然可以创建 `narrative.beat`，也仍然能跑通既有测试。计划要求「先证明新路径无 Beat 引用，再删活动类型」，
   而 3.2 的账本写入与 3.3 的起草都要先确认没有历史任务依赖，所以这一刀留到后续收尾做，
   当时只登记、不删。

**V03-3.2 之后的收尾状态**：起草路径与七页侧栏对节拍的依赖已经解除——
`AgentWorkflows.draft` 接受空节拍目标（只校验传入的目标确实是节拍），任务卡的章节草稿改为
选择目标章节，不再自动绑定已接受节拍。`narrative.beat` 类型、planner 创建入口和 AgentTasks 的
节拍起草仍在：类型退出需要先完成有效信息转换（状态变化/披露 → 事件与正文位置），并随默认入口
切换一起做，归 V03-8。3.1 因此保持「部分交付」。

**已知后果**：从旧创作台发起「规划故事与节拍」仍会写入节拍对象。写作台不会读它们，也不要求它们。

## 3.3 起草输入与空项目

`DraftBrief` 的字段就是计划 M05 的六项：账本引用、作者要求、视角、目标（新章/现有章）、篇幅、叙事边界。
`base_head` 可以为 `None`：空作品没有 main head，起草照常进行，采用时按 `import_chapter` 建首章。

提示词是确定性拼接（`render_user_prompt`），同样的 brief 得到同样的文本，便于测试与事后追溯：

- 只列被引用到的账本条目，按作者选择顺序，不做语义检索、不补全未引用设定；
- 「作者未决定的关键真相保持未定」写进系统提示——这是「不确定凶手仍可试写」的产品要求，
  不能靠模型自觉，所以同时由提示词与测试夹具双向固定；
- 生成结果先做结构性清理（去代码围栏、去标题行、去尾部说明），**清理后的文本就是预览与提交的那一份**。

`GET /projects/{id}/ledger` 是这一任务新增的只读投影：人物、地点、前提、规则、线索、真相、关系、时间线、事实，
**不含节拍**。前端引用清单与提示词共用同一个 `entry_view`，避免两处口径漂移。

## 3.4 预览与采用

候选存在辅助表（`draft_candidates`），不是仓库对象：采用前不产生任何提交，也不改正式正文。

- `preview_hash = hash(candidate_id, revision, title, text, base_head)`。采用只带哈希，不带正文；
  服务端按存储的修订重算一次，不一致 → `DRAFT_PREVIEW_CONFLICT`（409）。
- 「继续调整」生成新修订，`current_revision + 1`。旧修订随即不可采用：带旧哈希或旧修订号 → `DRAFT_REVISION_CONFLICT`（409）。
  这同时挡住「先点开旧预览、再在另一处调整、回来点采用」的迟到路径。
- 改写现有章时，`brief.base_chapter` 固定为生成时的章基础；采用前再比对一次，正文已被别处推进 →
  `DRAFT_TARGET_CONFLICT`（409），候选与草稿都保留，不静默覆盖。
- 目标章在未结束的手工修改副本里 → `EDIT_SESSION_CONFLICT`（409），要求先完成或放弃副本。

## 3.5 采用后的定位与唯一结果

采用 = 一次 `PublishManuscriptChange`：

- 新章走 `import_chapter`，章 ID 由候选 ID 派生（`ch_<hash>`），重试不产生第二份正文；
- 现有章走 `save_full_text`，带 `expected_chapter_base`；
- `operation_id` 由候选 + 修订 + 哈希派生，重试命中回执重放，返回同一操作；
- 响应给出 `chapter_id` 与 `operation_id`；前端刷新目录、选中该章、写入「后续状态」
  （摘要待更新 / 建议尚未整理由 V03-2.6 的查询给出）。

候选被采用后再调采用 → `status=no_change` 并返回原 `operation_id`（幂等，不造第二个版本）。
