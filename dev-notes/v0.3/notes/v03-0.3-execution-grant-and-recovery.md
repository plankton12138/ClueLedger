# V03-0.3 显式启动凭据、派发门禁与恢复策略

关键词：ExecutionGrant、派发门禁、零隐式模型调用、historical_paused、interrupted、恢复策略、模型运行记录器

## 目标与结果

建立 I05/I06 的执行点：未授权 Job 拒绝派发；打开作品、手改保存、重启都不产生模型调用。交付：

1. `src/hastings/application/execution.py`：`ExecutionGrant`（grant_id/source/source_message_id/function/analysis_scope/write_scope/call_budget/calls_used/grant_version/connection）+ `ConnectionSnapshot`（只含 connection_id/revision/provider/model，绝不含 Key）+ `authorize_dispatch` 门禁检查（凭据存在、功能匹配、预算未耗尽、连接可解析 → 否则 `EXECUTION_NOT_AUTHORIZED` / `TASK_BUDGET_EXHAUSTED`，不运行不部分运行）+ `JOB_TYPE_FUNCTIONS`（Job 类型=WorkerRole：planner/writer→draft，reviser→revision，auditor/coordinator→suggestion；style_observer 未登记 fail closed）+ `TASK_KIND_FUNCTIONS`（草稿类型命名空间）+ `DEFAULT_CALL_BUDGET=12`（M10 工程初值）。
2. 派发门禁落在 `V2Runtime._authorize_job`，两条入口共用：`worker_loop` 选择阶段（暂停一次后状态离开 queued，不会反复重试）与 `execute_agent_job`（`/agent-jobs/{id}/run` 手动运行的纵深防御）。无凭据 → `historical_paused`；凭据无效 → `not_authorized` + 事件负载带 error_code 与三要素。
3. `JobStore` 端口扩展 `pause` / `mark_interrupted`，SQLite 与内存双后端同端口实现；output 保持 `NoResult` schema 合法（kind/reason），结构化详情随 `job.paused` / `job.interrupted` 事件落库。
4. 启动恢复：v2 lifespan 在 worker_loop 前 `jobs.mark_interrupted()`（与 `chat.mark_interrupted()` 并列）——执行中任务标 interrupted 等作者继续，不自动重发。
5. 凭据附着：`POST /agent-jobs` 按角色签发（planner/writer→draft、auditor/coordinator→suggestion；style_observer 拒绝启动）；`start_task_job` 按草稿签发（source=author_message 时有 source_message_id，否则 author_button）；`grant_id` 只由操作键派生——同 `idempotency_key` 的任意次启动（含卡片绑定丢失后的重放）携带同一凭据，JobStore 指纹匹配可找回既有 Job。
6. 测试 `tests/v2/server/test_execution_grants.py`（14 项）：模型运行记录器（可注入 agent runner 与 chat runner 工厂）+ 执行指导 §4.3 失败测试样板（打开/保存/重启零调用）+ 四类门禁拒绝 + 授权放行 + interrupted 不重派 + pause/mark_interrupted 双后端契约 + 凭据单元（预算消耗、来源约束、wire 往返）。

## 关键决定

1. **新 Job 状态用 waiting+reason 表达，不新增枚举**：计划 §4.3「`interrupted` 可先用 waiting+reason 表达，确需新枚举时同步 Job 存储、API 和前端，不只改显示文案」；`historical_paused`/`not_authorized`/`interrupted` 都走 output.reason，事件负载带结构化详情。避免 V03-4 设计 continue 端点前散改枚举。
2. **门禁在 dispatch 层而非 WorkerJobRunner.execute**：修订流（repair）经 `owner.jobs.submit` + 直接 `worker.execute` 在已授权父任务内同步执行，不过 `execute_agent_job`；子工作者计入父任务预算的账在 V03-7 落实。门禁拦的是自动派发（事件派生、重启重派、手动 run）。
3. **grant_id 只由操作键派生**：否则「任务已建但卡片未关联」的重放场景指纹不匹配（既有恢复测试即该场景），同键必须同授权。
4. **style_observer 在 API 层拒绝而非派发层暂停**：计划 §8.3「API 不能绕过 UI 创建此类 Job」——排除功能在入口就明确失败（EXECUTION_NOT_AUTHORIZED），不留「建了再暂停」的中间态。
5. **HTTP 状态**：ViolationError 经既有映射落 400（未新增 403 分支）；前端按 code 分支，不依赖状态码（计划 §4.4）。
6. **与计划偏差**：`GrantFunction` 增加 `"discussion"`（普通对话：作者发送即授权，不经 JobStore 派发，记录备查）；执行指导 §3.4 骨架的 function 枚举未含它。recover() 的租约过期重排队语义保持 0.2 as-built（检查点续跑不重放 worker），进程重启的「不自动重发」由 mark_interrupted 落实——两场景分离，既有 `test_expired_job_resumes_checkpoint_without_replaying_worker` 不破坏。

## Agent 设计经验（四透镜）

1. 错误消息：门禁两类暂停都带 error_code + 三要素进事件负载；`operation_key_reused` 式的 details.original 回传模式沿用——暂停记录可回答「为什么没跑、怎样继续」。
2. 硬约束：授权检查在应用层派发入口（领域/工具层不感知凭据）；连接快照类型层就排除 Key 字段（dataclass 只有四个非敏感字段，物理上带不进去）。
3. 泄压阀：合法空结果（no_result）与门禁暂停分流——前者 completed 正常终态，后者 waiting+reason 等作者；记录器证明「没调用」而不是「调用了但没显示」。
4. 可观测性：模型运行记录器作为测试夹具可注入两个构造点；暂停/中断都落持久事件（`job.paused`/`job.interrupted`），重启后分类报告可回看。

## 踩坑与留白

- 坑 1：Job 类型是 WorkerRole（planner/writer/...）不是草稿 task_kind（plan/chapter_draft/...）——初版映射表用错命名空间，被既有闭环测试当场抓住（no_result.details extra_forbidden）。
- 坑 2：pause 的 output 初版带 details 字段，违反 `NoResult` StrictModel——accept 路径 `validate_worker_output` 炸出 extra_forbidden；详情改走事件负载。
- 坑 3：`_authorize_job` 在 worker_loop 每轮对 analysis_pending 任务重复读库——pause 前置状态检查（非 queued/retryable_failed 直接返回）消除无效写。
- 留白 1：`calls_used` 递增的持久化（每次模型调用后回写凭据）未实现——当前只在放行时校验；调用计数记账随 V03-7 覆盖台账落实，`consume()` 已就位。
- 留白 2：connection revision 精确跟踪（V03-1.3 连接同源）未做，当前记 0。
- 留白 3：V03-0.4 切断 AnalysisDispatcher 装配后，自动链连 Job 都不再创建；本任务的门禁是双保险，旧数据（0.2 积累的自动队列）的分类报告随 V03-0.4 产出。
- 留白 4：三个旧语义测试按 0.3 需求改写（closed_loop 的 style_observer 改断言拒绝；两个自动观察恢复测试改断言暂停与零调用），已在测试 docstring 记录 0.2→0.3 语义变化。
