## 为什么做这个

「不传特殊测试开关也能跑」听起来像运维检查，实质是一个**装配耦合**问题：以前
`main()` 把 config 解析、ProviderBook、registry、SQLite 工作台全部内联，测试只能
各起一个 `V2Runtime.memory()`——两条装配链分开演进，「生产能起」永远是假设。

这一次先重构再验收：把装配抽成 `assemble_server()`，冒烟测试因此走**与
`python -m hastings.server` 完全相同的一段代码**。

## 做了什么

### 装配抽取 `hastings/server/__main__.py`

- `assemble_server(...)`：config 路径解析（`--config` > `--config-dir/config.yaml` >
  默认）、静态目录探测、`.env` 加载、`load_server_config`、引导档案与未配置判定、
  凭据存储、`ProviderBook`、`WorkspaceRegistry`、`V2Runtime.sqlite`、`create_app`；
  返回 `AssembledServer`（app + 运行时 + 实际生效路径 + 未配置标记 + 凭据迁移失败）。
- `main()` 只做参数解析、打印与 `uvicorn.run`——**没有第二份装配逻辑**。
- `load_env=False` 是给测试的唯一旋钮，且只跳过「读真实 .env / normalize_base_url」；
  其余链路与生产一致。没有 `HASTINGS_TEST` 之类的功能开关。

### 冒烟测试 `tests/test_server_production_loop.py`

按真实 HTTP 路径走完整回路（临时目录 + `load_env=False`，不碰 `data/` 与真实 `.env`）：

1. `/capabilities` 能力公布；
2. 创建作品；
3. 导入正文（预览 → 按哈希确认）；
4. 账本直接保存（人物/线索，无模型路径）；
5. 跨章修改：开副本声声明两章 → 逐章自动保存（`save_seq` CAS）→ 完成发布；
6. 撤销那次修改 → 正文回到导入版本，原历史保留为新提交；
7. 设定候选：暂存 → 采用（`source_operation_id` 指回那次修改，影响查询回报关联采用）；
8. 备份闭环：预览 → 导出 → 改一版 → 恢复（未确认 409，确认后按备份还原）；
9. 恢复后再开一轮副本并发布，证明工作台恢复后仍可写。

另有装配测试：工作台库确实建在指定路径、静态目录按生产规则探测、`/capabilities`
在未配置模式仍可访问。

## 验证

| 检查 | 结果 |
|---|---|
| 后端全量 | 见 `dev-notes/v0.3/README.md`（本次 +3 用例） |
| `ruff` / `mypy` | 全过 |
| 前端 | 本任务未改前端；生产构建产物沿用既有 `npm run build` |

未配置模式被显式断言：`assembled.unconfigured is True` 时服务照起、可建可写，
模型调用在 prompt 时才 fail fast——这与产品「空启动」设计一致，不是降级。

## 已知留白（明确归属）

1. **模型相关步骤未纳入本闭环**：建议生成/试写/摘要任务需要真实凭据，属 V03-8.7
   真模型实测；本任务覆盖的是不依赖模型的完整产品回路。
2. **真实 uvicorn 进程启动未纳入自动化**：测试用 `TestClient` 驱动同一 app 对象；
   「手工 `python -m hastings.server` 能起并托管前端」需要运维记录，落地时补一条
   启动日志证据。
3. **凭据迁移/OS 凭据存储**只在装配层接线，未在冒烟里制造失败档案；故障提示路径
   属 V03-8.7。
4. `assemble_server` 的 `load_env=False` 不恢复已设置的真实环境变量——测试另行
   monkeypatch 隔离（见测试夹具）。
