# V03-2.3 正文导入：解析、预览与整批确认

关键词：导入预览、内容去重、显式替换、确定性章身份、回执重放先于命令、辅助表预览

## 目标与结果

已有稿件进入同一版本体系，且「作者看到的预览」就是「确认后写入的正文」。交付：

1. **`interfaces/importers/manuscript_text.py`**（纯函数）：字节解码（UTF-8 / BOM，
   其他编码显式失败）、Markdown 标题与「第X章 / Chapter N」分章、无标题按文件名
   作单章、书名/卷名不误判为「前言」、按段落序列计算章指纹与批次指纹。
2. **`domain/manuscript/commands.py::import_batch`**：新增若干章 + 显式替换若干章
   合成一个 `ManuscriptChange`，复用 `import_chapter` 与 `save_full_text` 两个既有
   纯函数；批次内重复目标在命令层拒绝。
3. **`application/services/import_service.py`**：预览持久化（辅助表 `import_preview`，
   24 小时）、内容去重、目标调整（PATCH，revision CAS + 章基础校验）、整批确认
   （经 `PublishManuscriptChange` 一次提交）。
4. **REST**：`POST/GET/PATCH /projects/{id}/imports/previews[/{id}]` 与
   `POST .../confirm`；`GET /capabilities` 的 `import.status` 由 `draft` 改为
   `implemented`。
5. **前端**：`api/imports.ts`（原始字节 base64 上传）+ 写作台「导入正文」对话框
   （预览清单、重复提示、新增副本/替换二选一、确认后刷新目录并定位首章）。

## 关键决定

1. **预览不造正文版本**：预览落仓库辅助表，写入走「只有 `aux_writes` 的
   CommitRequest」——引擎 no-op 分支落库，不产生空 Commit、不移动 head。
   预览与正文同一存储，重启后仍可确认，不需要第二套持久化。
2. **章身份由 `preview_id + 序号` 确定性派生**：同一预览的重试落回同一批
   `art_` ID；不同预览得到不同身份——同内容再次导入天然是副本，不会被误判成
   「更新同一章」。
3. **回执重放必须先于领域命令执行**（修 2.2 的隐含缺陷）：2.2 的
   `publish_command` 声称第 1 步是回执重放，实际是先跑命令再交给 `submit`。
   保存类命令恰好幂等，所以没暴露；导入用确定性章 ID，重试会先撞
   `MANUSCRIPT_DUPLICATE_ID`，永远走不到回执。新增
   `OperationService.find_replay` 并在 `publish_command` 开头调用。
4. **指纹按段落序列，文件名不参与**：`content_hash({"paragraphs": [...]})`。
   用整段文本会把「空行数量不同」判成不同内容；文件名作去重依据会把改名后的
   同一稿判成新稿（计划 M06 第 6 条）。
5. **重复处理三种，替换逐章显式**：`cancel` / `append` / `replace`。选 `replace`
   时必须为**每个**内容重复的章给出目标与当前 `chapter_base`——这是 M06
   「替换需要明确目标」的直接落地；不给默认值，避免「以为在新增、实际覆盖」。
6. **编码判定在服务端**：前端上传原始字节的 base64，由服务端按 UTF-8/BOM 解码。
   浏览器先 `file.text()` 会把 GBK 稿静默变成替换字符，作者看到乱码却不知道
   是编码问题。
7. **替换与新增在同一命令里**：`import_batch` 组合两个既有纯函数，整批一次
   `CommitRequest`；任一目标的基础冲突在命令阶段抛错，提交前就失败——「无半份
   正文」由构造保证，不靠事后回滚。

## Agent 设计经验（四透镜）

1. **错误消息**：编码错误带字节偏移与「另存为 UTF-8」的修复动作；重复内容
   错误列出章数与三种选择；替换缺目标指出「哪一章、缺什么」。
2. **硬约束**：解析与命令都是纯函数，无写端口；预览阶段没有任何正文写入口；
   确认只经统一发布器，不新增第二条写路径。
3. **降级处理**：`cancel` 与 `no_change` 都是合法结果；重复内容不阻塞新增副本；
   预览过期只作废预览，不影响已导入正文。
4. **可观测性**：确认返回 `operation_id` / `changed_chapter_ids`，可按操作
   找回；预览返回每章指纹与重复匹配，作者能核对「哪一章会变成什么」。

- 专项：`uv run pytest tests/v2/imports -q` → **18 passed**（2026-10-18）。
  覆盖三种解析、预览不写正文、确认文本等于预览、重试幂等、同内容三种决定、
  替换需目标与基础、同批重复目标、同名不同内容新增、整批失败无半份、格式/
  编码/章数上限、预览过期、空文件。

## 踩坑与留白

- 坑 1：`publish_command` 先执行命令、后查回执——导入重试直接撞已存在章。
  修正见关键决定 3；这是 2.2 就该有的顺序，属于被导入任务逼出来的缺陷。
- 坑 2：章指纹用整段文本 → 空行数量不同判不等，重复导入识别不出来。改按
  `split_paragraphs` 的序列取指纹，与库里「活动段落」同口径。
- 坑 3：最初让 `replace` 默认替换「内容相同的那一章」，与计划「替换需要目标」
  冲突，也容易让作者误以为只是新增。改为逐章显式目标，缺一个就整批拒绝。
- 留白 1：**与活动修改副本重叠的拦截**（`edit_session_blocks_import`）随
  V03-2.4 接入——当前还没有副本事实源，硬造一个检查只会是伪证据。
- 留白 2：单批总量 20 MiB 未校验（当前只校验单文件 10 MiB 与 1000 章）；
  预览清理没有定时任务，过期在读取时判定（不占版本、不阻塞写作）。
- 留白 3：预览里的顺序调整（PATCH 改 order_key）未实现，默认追加到现有末尾。
- 留白 4：旧 `POST /chapters/import` 保留兼容（旧创作台仍在用），V03-8.6
  统一入口时退役；新前端只走预览/确认。
- 留白 5：预览正文完整存辅助表，10 MiB 文件会形成较大 JSON；后续可改为临时
  文件引用，接口形状不变。
