# 执行循环接线：预算终于成为门禁（V03-8.7 补记）

> 阶段开发记录；实现范围、待办与测试结果均对应记录时点。当前行为见[模块说明](../modules/README.md)，剩余缺口见[运行与验收状态](../release.md)。

> 日期：2026-10-19。范围：`application/services/revision_execution_service.py`、`interfaces/api/revision.py`、`domain/revision/task.py`（发布门禁口径）、测试与文档。
> 证据：单测 6 项（`tests/v2/server/test_revision_execution_api.py`）+ 领域/发布用例修订；真模型报告 `eval/runs/2026-10-19-v03-8.7-execution-loop/`。

## 1. 为什么要接

`revision_task_service.py` 里有一行注释：「执行记账（执行循环在 V03-7.4 调用）」。
但 `consume_calls` 在生产代码里**没有调用方**：预算、等待、继续全部建好了，模型调用却不经过它们。
后果不是"少一条测试"：

- `call_limit=12` 是数字不是门禁，`calls_used` 永远 0；
- 覆盖台账靠人手动登记，不是执行器读一章记一章；
- 前端若显示「已用 0/12」是假账。

`--deep` 首轮把这条缺口作为失败证据记了下来（`release.md` §5 第 7 条）。本轮把它接上。

## 2. 形状

`POST /api/v2/projects/{id}/revision-tasks/{task_id}/run`

```json
{"instruction": "把这一章改得更克制，保留全部事实。", "chapter_ids": [], "request_id": "round-1"}
```

逐章按序、每章五步：

1. `consume_calls(1)` —— **先记账再调用**，不足时账本自动落 `waiting/budget_exhausted`；
2. `record_read(kind=full)` —— 真实读取登记；
3. `drafts.create(target=章)` —— 复用试写候选（提示词自带该章「现有正文」，见同日修复）；
4. `stage-chapters` —— 按任务基础版本的章基础 CAS 暂存；
5. `mark_changed` —— 下覆盖结论。

返回 `{status, chapters[], stopped, task}`：`status` 为 `executed` / `stopped` / `noop`。

## 3. 边界（都有测试）

| 边界 | 行为 | 用例 |
|---|---|---|
| 预算不足 | 停在下一章之前，**不再调用模型**；任务 `waiting/budget_exhausted`，已完成的暂存与覆盖保留 | `test_budget_stops_before_the_next_model_call` |
| 重放 | 同 `request_id` 返回原摘要（`status=replayed`），不重复记账、不重复调用 | `test_replay_does_not_charge_twice` |
| 继续 | 追加预算后只跑未下结论的章；发布仍是一次提交 | `test_continue_then_finish_and_publish_once` |
| 基础前进 | `head != task.base` → `REVISION_BASE_MOVED_CONFLICT`，不拿旧基础暂存 | `test_base_moved_blocks_run_instead_of_staging_old_text` |
| 未知章 | `REVISION_STAGE_UNKNOWN_CHAPTER`，不调用模型 | `test_unknown_chapter_is_rejected_without_model_call` |
| 停止后 | `cancelled` 任务要求先「继续」，不直接执行 | `test_stopped_task_requires_continue_before_running_again` |

默认范围是**还没下结论的章**（`changed`/`confirmed_unchanged` 跳过）：继续一轮不会把预算再花在改过的章上；要重改就显式给 `chapter_ids`。

## 4. 顺带修掉的旧规则：预算用满不等于不能发布

`publication_blockers` 原来无条件检查 `task.budget.exhausted`。接通记账后这条会立刻咬人：
两章、预算 2，全部改完并覆盖完整，却因为「2/2 用满」拒绝发布——等于要求作者**追加一次用不到的预算**才能发布，把 `calls_used < call_limit` 变成了发布前置条件。

改为：只有**因预算停下**（`state=waiting` 且 `waiting_reason=budget_exhausted`）才阻止发布。
「跑完了、覆盖齐了、预算刚好用满」是合法完成态。API 层观察到的仍是：因预算停下的任务发布被拒（此时先被「不是运行中」拦下，任务视图给出 `waiting_reason`）。

## 6. 口径说明（避免误读）

- **手动路径不计预算**：直接 `POST /drafts` 再手工暂存（S5 走的就是这条）不经过执行循环，不消耗任务预算——这是设计边界，不是漏洞。预算门禁的证据在 S6。
- **模型失败不退款**：调用已发生（真实 token），记账保留；任务保持 `running`，错误原样上报。
- **顺序执行**：没有多章并行，也没有子工作者合并记账（`calls=n`）的用例；`start_repair` 仍未接。
- **改写质量不作结论**：同日三次真模型跑里，有一次输出漂成「玻璃幕墙 / 监控屏幕」且事实保留不足；链路口径只断言「非原样返回 + 记账 + 发布」，不据此评价改写好坏。
- 前端任务卡还没有「执行一轮」按钮；本轮只接 API 与驱动。

## 7. 去向

- 前端接 `/run`（任务卡按钮 + 逐章进度 + `calls_used/limit`），并把「因预算停下」显示成可继续的等待态。
- `start_repair` 接上「再修一轮」的触发点，让两轮上限真正可执行。
- 真 uvicorn 进程取证仍缺（A28）。
