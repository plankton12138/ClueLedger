# V03-4.6 构建笔记：基础关联撤销

状态：**已交付**（2026-10-18）。预览、冲突判定与**写入**（一次提交恢复多章正文）已完成；
账本与正文的「一次同时恢复」随 V03-7 的统一发布扩展，见留白。
范围：按 `operation_id` 回答「这次操作能不能撤、撤了会动什么」，可撤时把它落成一次新版本。

> 本笔记先写于「只做预览」阶段，后半部分记录写入实现；标题保留，内容按最终状态整理。

## 为什么先做预览

计划里 M11 的要求是「无冲突时正文与账本一次恢复；遇冲突只展示事实与阻断」。
第一句是写入，第二句是判断——而判断依赖的信息比写入更基础：撤销范围从哪来、
什么算「后续冲突」、哪些变化本版根本不该碰。先把这三件事定清楚，写入才不会变成
「点一下就覆盖了新内容」。

这一刀交付的是一份可核对的事实清单，也是后面 apply 的输入契约。

## 交付内容

| 层 | 产物 |
|---|---|
| 应用 | `application/services/undo_service.py`：`preview()` 对比三个版本给出事实与阻断；`apply()` 走统一发布器、多章一次提交 |

## 五个关键取舍

**1. 撤销只能沿着操作记录走。**
`OperationRecord` 里有 `before_commit_id`，after 版本就是携带记录的那个提交。
没有操作记录的写入（账本单存、候选采用）没有「一次操作」的因果边界，不纳入撤销——
否则只能靠时间戳猜「这次改动包括哪些」，那比不提供撤销更危险。

**2. 冲突的定义是「当前 revision 不等于操作后的 revision」。**
比较的是章的基础版本（`chapter_base`），不是 commit：一次无关章的提交不该把撤销判成冲突。
同一章后来又改了哪怕一个字，都算冲突——只展示事实，不覆盖。

**3. 同时改了账本的操作，本版直接阻断。**
只恢复正文、留下账本，等于制造一处作者看不见的不一致；而「一次提交同时恢复两者」
需要统一发布器支持多章合并，那是后半的工作。现在明确告知「不做半边恢复」。

**4. 新建的内容不撤销。**
操作新建了章节时，撤销等于删除——本版没有删除原语。这类操作直接阻断并说明，
不尝试「标记删除」这种半成品。

**5. 未结束的修改副本优先阻断。**
有活动副本时，即使没有后续修改也不撤：撤销会改变副本的基础，让作者正在改的东西失去依据。
判断放在冲突之前，因为它的处置方式不同（先结束副本，而不是先决定冲突）。

## 判定顺序

```
操作有提交？
  └ 否 → 阻断：没有产生版本变化
记录了 before_commit？
  └ 否 → 阻断：这是首次提交
有未结束的手工修改副本？
  └ 是 → 阻断：先完成或放弃副本
章节/账本有后续修改？
  └ 是 → 阻断：只展示冲突事实
操作新建了章节？
  └ 是 → 阻断：删除不是本版能力
操作改了账本？
  └ 是 → 阻断：不做半边恢复
通过 → can_undo = true
```

顺序即优先级：先排除「根本没有可撤的东西」，再排除「撤了会更糟」，最后才是范围限制。

## 写入：为什么先扩发布器

「多章一次恢复」不能靠循环调用 `publish_command`：那会产生 N 个提交，第一章成功、
第二章失败时留下半套状态。所以先给 `PublishManuscriptChange` 加了 `publish_commands`：

- 多条命令**对同一个基础快照**求值，合并成一个 `CommitRequest`；
- 证据核对与摘要失效照常跑一次，撤销恢复的文字同样会被重新裁决；
- 单命令仍走旧的指纹形状，升级后重放既有操作不会因为指纹变了而报冲突。

撤销侧的三条实现决定：

1. **恢复内容取自 before 提交**，用 `catalog.manuscript().text_of(chapter_id)` 拿整章文本，
   经 `save_full_text` 走与保存相同的段落 diff 规范化——不手写「删除新段落」。
2. **CAS 用操作后的章基础**（`expected_chapter_base = after_base`）：预览到执行之间
   又有人改了同一章，命令层直接拒绝，不会覆盖。
3. **撤销 ID 确定性派生**（`op_` + hash("manuscript.undo", 作品, 原操作)），
   并先查回执：连点两次返回同一提交，而不是被自己的结果判成「之后又被修改」。

## 留白与风险

1. **账本与正文的一次同时恢复**：本版撤销只处理稿件命令；操作若同时改了账本，
   预览会阻断（不做半边恢复）。「正文 + 关联账本一个提交」要等 V03-7 的统一发布
   扩展（账本命令与稿件命令合并准备）。
2. **撤销的撤销（redo）**：现在连续两次撤销返回同一提交；要支持 redo 需要记录
   「哪次撤销了哪次操作」并给出正向恢复入口。
3. **派生状态**：撤销走统一发布器，摘要失效与证据核对照常执行；但预览不展示
   「哪些摘要会因此过期」，留给前端。
4. **同章重复命令**：`publish_commands` 要求同一章只出现一次（两条命令都基于同一
   基础，后者会覆盖前者）。撤销每章只恢复一次，天然满足；跨章修改（V03-5）需要
   在调用侧保证同一章只出现一次。
5. **跨作品防护**：依赖 `operation_id` 与回执同作品；传入别的作品的 ID 读不到回执，
   由既有 `get_operation` 保证，未单独覆盖。
6. **发现一个既有问题**：旧导入路由 `/chapters/import` 的 `order_key` 默认为空，
   连续导入两章会得到相同章序，章节目录的顺序因此不稳定（测试里已改为按标题取身份）。
   新版导入预览（V03-2.3）会计算章序，不受影响；旧入口在 V03-8.6 退役时一并收敛。

## Agent 设计经验

- **先做判断，后做动作**：把「能不能」和「怎么做」分开实现，判断部分立刻可用
  （作者能看到为什么不能撤），动作部分可以慢慢补而不留半成品。
- **冲突要按「对象是否被改过」判定，不要按 commit 判**：否则一次无关提交就把撤销
  判成冲突，用户会觉得系统不可信。
- **阻断原因要能指导下一步**：每条 `blocked_reason` 都写「先做什么」，
  不是单纯说「不允许」。
- **幂等的敌人是自己的结果**：撤销完再看预览，会看到「之后又被修改」——其实是
  撤销本身造成的。先查回执再判冲突，才不会自己挡自己。
