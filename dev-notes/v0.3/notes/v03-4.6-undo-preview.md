# V03-4.6 构建笔记：基础关联撤销（预览与冲突判定）

状态：**前半交付**（2026-10-18）。只读预览、冲突判定、阻断原因已完成并测试；
**写入（一次提交同时恢复正文与关联账本）待后半**。
范围：按 `operation_id` 回答「这次操作能不能撤、撤了会动什么、为什么不能撤」。

## 为什么先做预览

计划里 M11 的要求是「无冲突时正文与账本一次恢复；遇冲突只展示事实与阻断」。
第一句是写入，第二句是判断——而判断依赖的信息比写入更基础：撤销范围从哪来、
什么算「后续冲突」、哪些变化本版根本不该碰。先把这三件事定清楚，写入才不会变成
「点一下就覆盖了新内容」。

这一刀交付的是一份可核对的事实清单，也是后面 apply 的输入契约。

## 五个关键取舍

**1. 撤销只能沿着操作记录走。**
`OperationRecord` 里有 `before_commit_id`，after 版本就是携带记录的那个提交。
没有操作记录的写入（账本单存、候选采用）没有「一次操作」的因果边界，不纳入撤销——
否则只能靠时间戳猜「这次改动包括哪些」，那比不提供撤销更危险。

**2. 冲突的定义是「当前 revision 不等于操作后的 revision」。**
比较的是章的基础版本（`chapter_base`），不是 commit：一次无关章的提交不该把撤销判成冲突。
同一章后来又改了哪怕一个字，都算冲突——只展示事实，不覆盖。

**3. 同时改了账本的操作，本版直接阻断。**
只恢复正文、留下账本，等于制造一处作者看不见的不一致；而「一次提交同时恢复两者」
需要统一发布器支持多章合并，那是后半的工作。现在明确告知「不做半边恢复」。

**4. 新建的内容不撤销。**
操作新建了章节时，撤销等于删除——本版没有删除原语。这类操作直接阻断并说明，
不尝试「标记删除」这种半成品。

**5. 未结束的修改副本优先阻断。**
有活动副本时，即使没有后续修改也不撤：撤销会改变副本的基础，让作者正在改的东西失去依据。
判断放在冲突之前，因为它的处置方式不同（先结束副本，而不是先决定冲突）。

## 判定顺序

```
操作有提交？
  └ 否 → 阻断：没有产生版本变化
记录了 before_commit？
  └ 否 → 阻断：这是首次提交
有未结束的手工修改副本？
  └ 是 → 阻断：先完成或放弃副本
章节/账本有后续修改？
  └ 是 → 阻断：只展示冲突事实
操作新建了章节？
  └ 是 → 阻断：删除不是本版能力
操作改了账本？
  └ 是 → 阻断：不做半边恢复
通过 → can_undo = true
```

顺序即优先级：先排除「根本没有可撤的东西」，再排除「撤了会更糟」，最后才是范围限制。

## 留白与风险

1. **没有写入**：apply 需要「一个 CommitRequest 同时恢复多章正文 + 关联账本」，
   现有统一发布器按单条稿件命令准备，需要扩展成「多章合并准备 + 一次提交」。
2. **账本只报告不恢复**：即使撤销的是账本修订（有旧 revision），本版也不写；
   等 apply 一起做。
3. **不做「撤销的撤销」**：apply 之后要不要允许 redo，属于交互决定，未定。
4. **派生状态**：撤销正文后摘要/证据应由现有发布管线重新裁决；预览只列章节，
   不提前改动摘要状态。
5. **跨作品防护**：现在依赖 `operation_id` 与回执同作品；即使传了别的作品的 ID，
   也读不到对应回执——这一点由既有 `get_operation` 保证，测试里没有单独覆盖。

## Agent 设计经验

- **先做判断，后做动作**：把「能不能」和「怎么做」分开实现，判断部分立刻可用
  （作者能看到为什么不能撤），动作部分可以慢慢补而不留半成品。
- **冲突要按「对象是否被改过」判定，不要按 commit 判**：否则一次无关提交就把撤销
  判成冲突，用户会觉得系统不可信。
- **阻断原因要能指导下一步**：每条 `blocked_reason` 都写「先做什么」，
  不是单纯说「不允许」。
