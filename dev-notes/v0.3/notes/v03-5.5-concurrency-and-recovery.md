# V03-5.5 构建笔记：多标签页、断网重排与完成后的收口恢复

> 阶段开发记录；实现范围、待办与测试结果均对应记录时点。当前行为见[模块说明](../modules/README.md)，剩余缺口见[运行与验收状态](../release.md)。

状态：**已交付**（2026-10-18）。范围：同一副本被多个标签页/重试同时操作时，
保存与完成都只有一个赢家；完成已经提交但副本关闭失败时，重启后回放原结果，
不发布第二个正式版本。

## 三个场景

1. **多标签页保存**：两个标签页都从 `save_seq=0` 开始写。CAS 只允许一个成功，
   另一个收到 409；重新读取最新序号后仍可继续，不是永久失效。
2. **断网/请求重排**：迟到的旧请求携带旧序号，会在 CAS 处被拒绝；同一
   `request_id` 的重试原样返回，不重复自增。
3. **完成成功但副本关闭失败**：提交已经生效、head 已前进，但写「当前副本」
   或归档时失败。重启后如果直接重跑完成，会按新 head 重新准备命令，产生
   不同的指纹，甚至第二个版本。收口必须**先认回已提交的操作**。

## 四个决定

**1. 完成的幂等键在准备之前就确定。**
完成操作 ID 由「会话 + 每章 save_seq」确定性派生。这一轮在合并/准备之前先按
这个 ID 查回执：已经提交就直接补完关闭并返回。不能等到发布器里再判重——
那时重试已经按新 head 重新准备了命令，`paragraph_sources`、`expected_base`
都会变，指纹对不上，`OPERATION_KEY_CONFLICT` 反而会挡住真正的恢复。

**2. 关闭失败是「已提交 + 未关闭」，不是失败。**
提交成功后依次写当前副本、归档；任一写失败，正式版本已经存在。重试完成时
先走第 1 条的回放路径，只补关闭，不再产生版本。已完成但未归档的副本（当前
指针已是 `closed`、归档缺失）由下一次「开始修改」补归档，旧会话仍可读。

**3. 两个标签页同时完成，认回同一个提交。**
两个请求可能都通过准备、都调用发布器；先到的提交成功，后到的
`expected_head` 过期。这里捕获 `REPO_HEAD_CONFLICT`，若该操作其实已经提交，
就返回它的结果并补关闭，而不是把并发点按报成冲突。没提交成功的
`REPO_HEAD_CONFLICT` 仍原样抛出。

**4. 操作 refs 必须与 head 无关。**
`paragraph_sources` 原来只记录「与当前正文不同」的章，重试时 head 已变，
refs 随之变化，指纹不稳。现在记录全部计划章；`merged_chapters` 也写进 refs，
回放时能如实报告合并范围。

## 验证证据

`tests/v2/edit_sessions/test_concurrency_recovery.py` **5 项**：

- 两标签页同一序号：恰好一个 200，另一个 409；重读序号后可继续；
- SQLite 下两个线程同时保存：恰好一个赢家，序号只前进一格；
- 两个线程同时完成：两个 200 返回同一 operation/commit，副本关闭；
- 关闭失败 + 重启：提交已生效、当前副本仍 open；重启后完成回放同一 commit，
  head 不再前进，正文只发布一次；
- 归档失败：当前指针已 closed、归档缺失；重试返回同一提交，下一次开始修改
  补归档，旧会话的章节清单仍可读。

全量 `uv run pytest -q` → **1769 passed**；`ruff check src tests` 全过；
`mypy src/hastings` 242 files 无问题。

## 留白

1. **前端未接线**：写作台没有并发/恢复提示；两个标签页仍由后端 409 兜底，
   前端需要刷新序号与「完成后重新打开」的交互随 V03-8.6。
2. **断网是请求级重排，不是网络代理级故障注入**：覆盖的是旧序号迟到、
   同 request_id 重试与并发提交；真实断网/超时重发的端到端走查留给 V03-8。
3. **无 redo**：撤销的撤销仍需新入口；完成回放只保证不重复发布。
4. **客户端复用 operation_id 的防护**：回放前核对 refs 里的 session_id，
   不属于本副本就拒绝；这只防误用，不构成授权。
5. **阶段退出仍未完整演练**：V03-5 的五个任务已交付，但「完成 → 采用账本建议
   → 独立再改 → 撤销」中的建议采用与正文操作的因果关联随 V03-7.7。
