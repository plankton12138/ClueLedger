# V03-2.5 历史恢复接入统一发布与证据人工核对

> 阶段开发记录；实现范围、待办与测试结果均对应记录时点。当前行为见[模块说明](../modules/README.md)，剩余缺口见[运行与验收状态](../release.md)。

关键词：恢复即新发布、章版本历史、chapter_base 判重、副本保护、证据重锚、旧依据

## 目标与结果

历史恢复从「旁路 handler 直提」改为走统一发布；作者能看到一章的正式版本并
恢复，证据在原文变化后可以人工重新关联。交付：

1. **`workflows/restore_version.py`**：`RestoreChapterVersion` 改为
   `(reader, publisher, edit_sessions)`，恢复经 `PublishManuscriptChange`
   （kind `chapter.restore`），`operation_id` 由 `idempotency_key` 确定性派生；
   返回 `PublishResult`。
2. **副本保护**：该章在未结束修改副本里时抛 `EDIT_SESSION_CONFLICT`，要求先
   完成或放弃本轮，不自动放弃副本。
3. **`queries/chapter_history.py`**：`GET /projects/{id}/chapters/{cid}/history`
   按 `chapter_base` 判重（改别的章不算本章新版本），当前版本在首位，
   `limit ≤ 50`。
4. **`services/evidence_service.py`**：`GET /evidence-links?chapter_id=`（需核对
   排前）与 `POST /evidence-links/{evidence_id}/reanchor`（引用片段必须在当前
   正文中可定位；旧依据进 `previous`；经 `OperationService` 产生操作记录）。
5. **前端**：`api/history.ts`；写作台「版本历史」从占位变为真实列表与恢复；
   右栏「正文证据」列出需核对项并提供重新关联输入。

## 关键决定

1. **恢复 = head 上的新提交**：不移动分支、不重写历史；旧版本永远可追溯，
   恢复本身也进历史。幂等靠 `operation_id` 派生 + 回执重放，重试不产生第二个版本。
2. **历史判重用章基础而不是提交数**：`chapter_base` 是活动段落顺序与文本的哈希，
   别的章提交不会让它变化——否则「改第 2 章」会在第 1 章历史里凭空多一版。
3. **重锚只改关联，不改真相**：人工给出仍存在的引用片段，服务端再核对一次；
   找不到就拒绝。旧关联写进 `previous`，可回看「原来依据是什么」。
4. **副本保护放在用例层**：不在路由里检查，任何调用方（HTTP、脚本、未来整体
   调整）都绕不过去。
5. **证据重锚复用操作记录**：证据是版本化 Artifact，修改走 `OperationService`，
   与正文操作同一套幂等与可回看语义，不新增写路径。

## 实现问题与未完成项

- 坑 1：历史若按「提交是否出现」判重，改别的章也会在本章历史里多一版；改为
  `chapter_base` 判重后版本数正确。
- 坑 2：发布器的章全文用 `"\n"` 拼接，`catalog.text_of` 用 `"\n\n"`；证据重锚
  必须按发布器口径取哈希，否则下一次保存会把刚重锚的证据再判一次待核对。
- 留白 1：历史每版读一次快照，复杂度随提交数线性增长；增量索引与压测留 V03-8，
  不在本任务提前优化。
- 留白 2：历史只给 200 字预览，没有逐段差异；「差异对比」视图仍是占位，等
  V03-5 的三方比较一起做。
- 留白 3：证据重锚入口只在写作台右栏；账本详情与图谱里的完整入口随 V03-6。
- 留白 4：恢复后不自动重跑摘要或整理建议（I06：模型功能必须显式启动）；
  V03-2.6 提供「待更新摘要 / 尚未整理建议」的独立启动入口。
