# V03-7.1 讨论/候选/执行意图区分与授权

关键词：意图三分、讨论无写权限、候选只读、执行写范围、同范围不重复审批、只读分类、原消息授权

## 目标与结果

作者一次自然语言表达对正式内容的写权限并不相同：「假如姐姐是凶手会怎样」只是假设，
「先看看方案，不改正式内容」只是要一份可比较的方案，「按这个整体修改」才是范围明确的授权。
产品要求这三者被**确定性地区分**，而不是让模型自称「已获授权」就放行（M10 第 2 条）。
V03-7.1 补的就是这道区分与「同范围不重复审批」，且严守既有边界：讨论运行器仍无正式写端口。

最终交付：

- 领域 `domain/conversation/intent.py`（新增）：纯函数三分分类 `classify_intent(text)` 与
  完整分类 `classify_author_intent(text, target_ids=…)`，给出 `function` / `analysis_scope` /
  `write_scope` / 关键选择 / 分类依据 `reason`。讨论与候选恒 `write_scope=None`；执行按是否
  含整体线索映射 `revision` 或 `holistic_revision`；写范围未知时给最多 2 个关键选择。
- 应用 `application/services/intent_service.py`（新增）：`IntentService.classify`——**只读**，
  不创建任务、不调用模型、不写正式内容。只接受作者消息（非作者消息拒 `CHAT_MESSAGE_NOT_FOUND`，
  模型回复不能作为授权源）；`guard_intent_write_scope` 在凭据构建边界加一道硬断言；执行意图
  与本次会话已启动、范围相同的任务一致时置 `reuses_authorization=True`。
- 接口 `interfaces/api/conversations.py` + `server/v2.py`：`POST /conversations/{id}/intents`
  （body 二选一：`text` 预览、`message_id` 已保存作者消息）；`application/errors.py` 增错误码
  `INTENT_WRITE_SCOPE_INVALID`。
- 前端 `api/intent.ts`（新增）：只读分类客户端 + 展示口径纯函数（讨论/候选恒「不改正式内容」，
  执行才给功能与写范围）；`components/chat/IntentNote.tsx`（新增）只读提示条；`ChatComposer`
  输入预览（停止打字 400ms 后按 text 分类，讨论不显示）；`ChatMessages` 作者消息「意图区分」
  按 `message_id` 分类——这就是「原消息授权」的口径。
- 测试：后端专项 27 项（纯函数 13 + API 14，含同范围复用、非作者消息拒绝、缺输入拒绝）；
  前端专项 8 项（客户端形状 + 展示口径纯函数）。

## 关键决定

1. **分类是确定性纯函数，规则只看作者文本，不看模型输出。** 模型说「已获授权」不构成授权；
   凭据来源只能是作者消息或按钮。落地方式是把「讨论无写权限」做成两道锁：领域分类恒
   `write_scope=None`，应用层 `guard_intent_write_scope` 再拒一次伪造的非空写范围。
2. **分类放 domain 层并按依赖方向对齐。** 它只依赖文本、是纯规则，不涉及端口与存储，因此
   domain 层即可；`function` 字面量与 `application/execution.GrantFunction` 一致，但由应用层
   收编校验，domain 不 import application。
3. **无法判断一律降级为 discussion（最安全），并让假设线索优先级最高。** 「假如改成……会怎样」
   这类假想必须落在讨论，不能被「改成」误判成执行写入——先看假设/讨论线索，再看只读方案与候选，
   最后才看执行。
4. **范围已知就不给澄清问题。** 执行意图若已带写范围（作者消息引用目标），关键选择为空元组；
   只有范围未知才问最多 2 个「影响执行的关键选择」。于是「明确同范围执行不重复审批」同时体现
   在两处：分类不再追加问题 + `reuses_authorization` 标记。
5. **同范围复用的功能等价类单列，不直接复用 `TASK_KIND_FUNCTIONS`。** 后者是「任务种类→模型
   凭据功能」的映射，**不含 `targeted_revision`**（定向修订走变更流程、不经模型凭据）。复用判定
   看的是「作者视角的功能等价类」，故在服务内单列 `_DRAFT_KIND_FUNCTIONS`（含
   `targeted_revision→revision`）并写明原因——否则最常见的修订任务永远判不出同范围已授权。
6. **前端不新增任何写端口。** 意图条与消息提示条都只是只读展示；是否继续执行仍由既有显式入口
   （创作操作 → 定向修订）承接，整体执行的覆盖台账与预算随 V03-7.2/7.3，V03-7.1 不提前造执行入口。

## Agent 设计经验（四透镜）

1. **错误消息是喂给模型的 API（三要素）**：`guard_intent_write_scope` 与 `_from_message` 的拒绝
   都给出 `where/why/fix`（哪里错、为什么错、怎样算对）；前端 `V2Error` 原样透出 `why`+`fix`，
   不做「人话翻译」，也不吞码。
2. **硬约束放工具层/边界，prompt 只解释世界**：讨论/候选不带写范围不是靠提示词自律，而是
   domain 恒 None + 应用层断言；「模型不能授权」不是写在提示词里，而是 `_from_message` 检查
   `role == author` 这道入口检查。
3. **降级处理（区分三情形）**：**违规**（非作者消息、伪造写范围、缺输入）→ 明确拒绝三要素；
   **合法但空结果**（写范围未知）→ 正常返回关键选择，指明下一步，不调模型猜；**无法判定**的
   模糊文本 → 降级为 discussion（最安全），不冒进执行。
4. **可观测性是事件契约的一部分**：分类结果把 `intent/function/analysis_scope/write_scope/
   requires_choice/reason/reuses_authorization` 一并回给前端——作者一眼看出这次会不会改正文；
   `reason` 保留命中的线索词，便于回看「为什么这么判」。

## 踩坑与留白

- **踩坑（错误信封形状）**：新 API 测试一开始断言 `response.json()["code"]`，实际信封是
  `{"error": {code, …}}`，两处 `KeyError`；对齐既有测试后改为 `["error"]["code"]`。
- **踩坑（mypy no-any-return）**：`IntentService` 构造器参数类型写成 `Any` 触发
  `Returning Any from function declared to return "Conversation"`；改用 `ConversationStore` /
  `TaskDraftStore` 端口 Protocol 作为参数类型。
- **踩坑（复用映射缺口）**：直接复用 `TASK_KIND_FUNCTIONS` 会让 `targeted_revision` 永远判不出
  「同范围已授权」；单列 `_DRAFT_KIND_FUNCTIONS` 并注释原因，避免把「定向修订走变更流程」的
  既有语义改坏。
- **踩坑（格式门）**：`ruff format --check` 在本机 0.16.10 下要求顶层定义间保留空行，两处新端点
  被命中；直接 `ruff format` 收口（仅空白）。
- **留白 1：意图条是只读展示。** 输入预览在停止打字 400ms 后按 `text` 分类；「显式自然语言直启
  执行」与「到预算等待作者」随 V03-7.3（覆盖台账、调用预算）。
- **留白 2：预览携带不了已附引用**，故输入预览的 `reuses_authorization` 恒为 false；同范围复用的
  界面呈现由作者消息的「意图区分」（`message_id` 分类，含引用目标）承担。
- **留白 3：`holistic_revision` 仍走既有「定向修订」任务草稿**；整体执行的覆盖台账/预算随
  V03-7.2/7.3。
- **留白 4：分类线索是确定性词表**（非模型/NLP）；同义扩展与误判样本待真模型走查补充。
