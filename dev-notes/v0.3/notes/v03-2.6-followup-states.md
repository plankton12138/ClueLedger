# V03-2.6 操作结果与后续状态（部分交付）

> 阶段开发记录；实现范围、待办与测试结果均对应记录时点。当前行为见[模块说明](../modules/README.md)，剩余缺口见[运行与验收状态](../release.md)。

关键词：summary_state、ledger_suggestions_state、I06、不自动运行、显式入口的边界

## 目标与结果

操作之后，作者能看到「哪些后续工作是待处理的」，且系统不会自作主张去执行：

1. **`queries/followups.py`**：按受影响章节计算两个确定性状态——
   `summary_state`（`missing` / `stale` / `fresh`）与
   `ledger_suggestions_state`（`not_started`，V03-4 产生建议组后为 `available`）。
2. **`GET /operations/{id}`** 附带这两个状态与 `result_url`；只读查询，不创建
   Job、不调用模型。
3. **前端**：`api/followups.ts` + 写作台右栏「后续状态」——导入或修改完成后
   显示「摘要 · 待更新」「账本建议 · 尚未整理」，并注明两项都是独立模型功能。

## 与计划的偏差（显式）

计划 V03-2.6 要求交付「两个独立的启动入口」。本次只交付**状态可见**部分，
**没有**提供可点击的启动按钮：

- **问题**：摘要与账本建议任务的真实执行属于 V03-4.3/4.4。此刻做按钮，要么
  创建一条没有消费者、永远不会执行的请求，要么伪造一个任务状态。
- **选择**：只做状态与查询契约，入口随任务一起交付。
- **理由**：M14 明确「未实现工具不显示可点击占位」；一条永远 pending 的请求
  比没有按钮更糟——作者会以为任务已经排队。I06 当前可验证的部分是「未点击
  不产生 Job 与模型调用」，由构造保证（服务类不持有模型端口）。
- **替代方案**：持久化「已请求」队列，等 V03-4 消费。放弃原因：产品面上它是
  死状态，且需要额外的状态机与过期处理，收益为零。
- **验证**：3 项状态测试 + 全量 1561 passed；没有任何任务/模型端口接入本查询。

## 关键决定

1. **状态在查询时计算，不落存储**：摘要与建议都是派生资料，再存一份「状态」
   会形成第二事实源；直接从版本化 Artifact 读，永远与正文一致。
2. **三态语义**：受影响章节任一没有摘要 → `missing`；任一过期 → `stale`；
   全部最新 → `fresh`。无受影响章节时，有摘要即 `fresh`（no_change 不伪造
   「待更新」）。
3. **建议状态不猜测**：在 V03-4 产生建议组之前恒为 `not_started`；不根据
   「有没有正文变化」推断「该整理了」。
4. **面板只显示文字**：没有按钮就没有可误解的入口；文案直接说明启动入口随
   各自任务提供。
