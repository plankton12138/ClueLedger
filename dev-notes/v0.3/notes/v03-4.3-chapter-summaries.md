## 为什么要先修一个隐患

V03-2.2 的失效裁决把摘要 Artifact 当成「只有五个字段的状态对象」：
`ChapterSummaryState.to_wire()` 只输出 `summary_id/chapter_id/source_hash/status/reason`。
一旦摘要里开始存正文（这次就要存），**任何一次保存正文都会把摘要正文擦掉**——
状态从 fresh 变 stale 是对的，内容跟着消失是错的。

所以这一刀的第一件事不是写生成，而是把状态模型扩成「状态 + 内容」：
`text / sources / model / generated_at / task_id` 加一个 `extra` 兜底未知字段。
失效时原样带过去，并补了一条测试（`test_saving_body_marks_stale_but_keeps_the_text`）
直接盯住这个回归。

## 五个关键取舍

**1. 来源清单就是「章基础 + 段落 revision」。**
没有引入新的哈希口径：`source_hash` 直接等于 `chapter_base`，因为既有失效裁决只比较它。
这样「来源变了没有」在全系统只有一个答案，不会出现「摘要说新鲜、发布器说过期」。

**2. 落地前再核对一次，不一致就不写。**
生成前冻结清单，模型返回后重取当前 head 再算一次。不一致返回 `superseded` 并**不产生版本**，
已存在的旧摘要（此时通常已被标 stale）保持原样。计划原文是「迟到结果标 superseded、
不覆盖更新章」，实现上采取更强的一档：连 superseded 内容也不落盘——旧摘要的价值
（作者上次看到的文字）高于一份已知过期的结果。

**3. 显式启动是硬约束，不是文案。**
保存、导入、试写采用都不调用 `SummaryService`；`summary.start` 是唯一入口。
测试 `test_saving_never_starts_a_summary_by_itself` 直接断言保存后模型调用次数为 0
（I06：保存只做失效，不做生成）。

**4. 先同步跑通，再任务化——业务语义一次没改。**
第一版用「POST 内等待生成」，把领域逻辑与状态核对跑通；随后补任务化时没有改业务：
`SummaryService.start` 多了 `before_commit` 钩子，任务执行器在提交前查一次「是否被停止」。
于是「停止」不是靠取消 asyncio 任务（可能停在任意位置、留下半套状态），而是
**在唯一的写入点前拒绝**。同步入口与异步入口共用同一个执行器，只是前者 await 它。

**5. 摘要任务不走写作任务的授权与租约。**
写作任务有「可写范围」，所以需要 `ExecutionGrant` 与仓库 lease；摘要只写派生资料，
没有正文可写。共用任务表与状态机，但派发时不走 `_authorize_job`——否则每个摘要都得
伪造一份「写作授权」，把授权模型稀释成形式。代价是摘要任务在 `worker_loop` 里有一条
独立分支，需要在同一项目内串行（避免同章两个任务同时读写摘要版本）。

**6. 提示词要求「未交代」。**
摘要最大的风险不是漏，而是补：模型顺手把「旅馆老板去哪了」编圆，下一章的背景就带着
一条不存在的事实。提示词明确要求不确定处写「未交代」，并把输出限制为要点、
不超过 1200 字——概览要装多章，单章摘要不能长篇复述。

## 数据影响

- `summary.chapter` 的内容从 5 个字段扩到 10 个：`text`、`sources`（章基础 + 段落
  revision 列表）、`model`、`generated_at`、`task_id`，另有 `extra` 兜底未来字段。
- 旧摘要（只有 5 个字段）照常可读；`to_wire` 只在有值时才写新字段，因此既有测试与
  旧数据都不受影响。
- 摘要仍是派生资料：不进 `CANON_KINDS`、不进账本清单、不参与正文引用；导出会随
  snapshot 一起打包（既有行为）。

## 错误码

| 码 | HTTP | 场景 |
|---|---|---|
| `SUMMARY_CHAPTER_NOT_FOUND` | 404 | 作品无正文或章节不存在 |
| `SUMMARY_NOT_AVAILABLE` | 400 | 没有接通模型（不是「摘要失败」，是没能力） |
| `SUMMARY_EMPTY_RESULT` | 400 | 模型返回空内容；不写任何版本 |
| `SUMMARY_JOB_NOT_FOUND` | 404 | 任务不存在 |
| `SUMMARY_JOB_CANCELLED` | 400 | 已停止的任务不能重试 |

任务失败时同步入口把 `terminal_failed` 翻译回原错误码（如 `SUMMARY_EMPTY_RESULT`），
环境类故障抛 `EnvironmentFailure`（503）；**不会把失败包装成「已完成但结果为空」**。

## 留白与风险

1. **执行日志未接**：任务有自己的事件序列（`job.queued/running/completed`），但还没
   投影到 `ExecutionLog`，前端看不到进度流。与 4.5 的侧栏状态一起接更合适。
2. **全书概览还是空的**：`BookOverview` 的失效逻辑在 V03-2.2 就有，但没有生成入口。
   计划把它算作摘要功能的子步骤（M08 第 4 条）。
3. **一次只做一章**：批量「更新所有过期章」需要任务编排与预算控制，属于概览那一步。
4. **未测量输出长度**：1200 字上限是初始值，真实模型可能超；超了不会截断，
   留着让作者看到并调整，等有样本再决定是否强制。
5. **纠正机制未做**：计划提到「用户纠正保留来源与版本」。当前只能重新生成，
   手工改摘要（不动正文）还没有命令。
6. **停止只在提交前生效**：模型调用本身不会被打断（没有向 provider 传播取消），
   停止的语义是「结果不落地」。真要省调用，需要在 provider 层支持中断，成本高、收益小。
