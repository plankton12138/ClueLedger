# V03-4.2 构建笔记：背景装配（前后两刀）

> 阶段开发记录；实现范围、待办与测试结果均对应记录时点。当前行为见[模块说明](../modules/README.md)，剩余缺口见[运行与验收状态](../release.md)。

状态：**已交付**（2026-10-18）。前半：装配器与只读接口；后半：试写与对话的提示词接线。
剩余两项明确顺延：「工具按版本读回原文与覆盖区间」随读取端口，「预算数值」待真实样本测量。

范围：把「约定 → 故事核心 → 章节概览 → 目录 → 目标展开」装成一份带版本、
带裁剪记录、带覆盖说明的背景包，让讨论与试写从同一个地方取，并且可以按项目读出来。

## 为什么先做装配器

4.1 交付后，约定能存能改，但没人读它——试写仍自己拼账本，对话仍自己拼历史。
两条路径各写一套，同一部作品在两处看到的背景不一致，而且谁也说不清「这次模型
到底看了什么」。这一刀要解决的不是提示词措辞，而是**先定义一份可检查的背景**：
有哪些块、来自哪个版本、哪些被裁掉、哪些章读了原文。

有了它，后面的摘要（4.3）、建议（4.4）、撤销（4.6）才有共同的输入契约。

## 五个关键取舍

**1. 「读」和「选」分开。**
收集器只负责把仓库读成输入，装配器只负责选择与裁剪。混在一起最典型的毛病是：
一边读快照一边按预算决定要不要再读一章，最后包里的材料来自不同版本。现在
一次装配只有一个 `commit_id`，所有 revision 都属于它。

附带好处是可测：装配器不碰仓库、不碰模型，12 项纯函数测试跑完不到 1 秒。

**2. 裁剪顺序固定，且必留层级装不下就报错。**
顺序是 约定 → 故事核心 → 章节概览 → 目录 → 目标展开，预算不够从后往前丢。
「目标展开」排最后是有意的：整章正文最贵，先保住约定、核心、概览和目录，
模型至少知道这本书有什么、写到哪，而不是抱着半章原文丢掉全局。

约定和核心设定装不下时**不静默丢**，直接报 `BACKGROUND_BUDGET_TOO_SMALL`：
一份缺了「全书第一人称」的背景，比没有背景更危险——模型会以为自己知道规则。

**3. 临时原文不是摘要。**
过期或缺失摘要时，可以按当前版本读原文顶替，但它在数据里是
`temporary=True` + `coverage.mode="temporary_text"`，渲染时也带标注。
这样「读过原文」和「有可用摘要」不会混为一谈，也不会写回正式摘要——
4.3 的摘要任务仍然只能由作者显式启动。

**4. 真相标注留给 4.7 的缝。**
`story.mystery_truth` 属于「作者知道、读者未必知道」，进核心层时标签带
「作者资料，勿提前披露」。现在只是标注，4.7 要在此基础上做披露边界判断
（前章润色不得让侦探提前断言）。先留标识，比事后从文本里猜安全。

**5. 目录一次成型，不逐条。**
账本目录与章节目录各是一块内容（多行文本），不是每章一个 item。目录的价值是
「让模型知道有这些东西」，逐条会让预算被几十个小条目吃掉，也让裁剪变得琐碎。

## 后半：接线（讨论与试写）

两条路径接同一个装配器，但接入方式不同，原因不是风格而是**权限与版本**：

- **试写**（`DraftingService._background_text`）：按 `brief.base_head` 取，
  也就是「这次试写所基于的版本」。作者在生成途中改约定，这篇候选看到的仍是旧版本——
  与 `previous_text`、`refs` 的来源版本保持一致，不会出现「正文是旧版、要求是新版」。
  接进 `render_user_prompt(background=...)`，位置在「作者要求」之后、「本书设定」之前：
  本次明确要求优先，长线约束只作底色。
- **对话**（`ConversationService.background_provider`）：只接收 `project_id`，
  **刻意不传 conversation_id**——同一部作品的不同讨论因此拿到逐字相同的背景，
  这就是「不同讨论同作品背景一致」的实现方式，不是靠约定，是靠没有输入可变。

预算不足时两条路径都**失败并说明原因**（试写 `DRAFT_BACKGROUND_TOO_SMALL`，
对话由装配器抛错使该轮次失败），而不是退化成「无背景继续写」。理由和必留层一致：
悄悄少给比明确失败更容易产出「看起来对、其实违反作者要求」的内容。

## 数据流

```
repository snapshot(commit)
   ├── StoryCatalog          → 约定快照（生效项 + revision）、可引用账本
   ├── ManuscriptCatalog     → 章目录（标题/序号）、按需读目标章原文
   └── summary.chapter 状态   → fresh / stale / missing
        ↓
BackgroundService.collect        （按版本取，不判断）
        ↓
assemble_background(纯函数)      （排序 → 分层 → 预算裁剪 → 版本/覆盖）
        ↓
BackgroundPackage.to_wire()      （items / omissions / coverage / versions / hash）
```

## 错误码

| 码 | HTTP | 场景 |
|---|---|---|
| `BACKGROUND_SCOPE_INVALID` | 400 | scope 不是 manuscript / discussion |
| `BACKGROUND_BUDGET_INVALID` | 400 | 预算不在 200—64000 |
| `BACKGROUND_BUDGET_TOO_SMALL` | 400 | 约定或核心设定放不进预算 |

## 留白与风险

1. **摘要是空的**：`summary.chapter` 由 4.3 产出，现在目标章基本走
   `temporary_text` 或 `omitted`。这不是缺陷，是顺序：先有容器，再有内容。
2. **预算数值未测量**：12000 / 64000 是初始值，等真实作品（计划 §9.6 的 100 章样本）
   跑过再定；现在只保证「超预算会被如实裁掉并能看到」。
3. **概览只收 fresh**：过期摘要不进概览，避免把旧事实当背景；代价是过一段时间
   概览会变薄，直到 4.3 的摘要任务补上。
4. **工具读回未做**：计划要求「工具返回固定版本原文与覆盖区间」，那是 Agent 读取端口
   的事，本任务只保证背景包里有覆盖区间；随 4.7/工具装配一起做。
5. **试写的显式引用与目录有重叠**：`refs` 仍按完整摘要列出，同时账本目录里也有它的
   一行摘要。信息重复但语义不同（精确引用 vs 索引），先保留；等 4.3 观察真实提示词
   长度再决定是否合并。
6. **对话背景不带当前章节**：讨论不传 `target_chapter_ids`，所以只有概览与目录，
   没有目标章的完整摘要。这与「讨论先聊清楚再动笔」的顺序一致；需要精确讨论某章时，
   走任务卡的显式引用。
