# V03-4.4 构建笔记：账本更新建议

状态：**已交付**（2026-10-18）。显式启动、带来源暂存、部分采用、来源变化拦截、零建议合法；
**任务化（排队/停止/重试）与「调整建议」交互**仍是留白。
范围：从正文整理出的账本变更建议，进入候选组、被部分采用为正式账本。

## 为什么复用候选组

V03-3.2 已经解决了一批难问题：类型化字段、引用闭合、假设拦截、一次提交、部分确认。
建议与手工候选的差别只有一个——**它是模型给的，因此必须能说明依据**。于是这一刀做的是：

- 给候选条目加 `source`（章、生成时的章基础版本、正文原句）；
- 给候选组加 `origin`（哪一章、什么模型、哪次请求）；
- 在采用前核对：正文变过就拒绝，而不是悄悄放行。

如果另写一套「建议表」，上面那些规则会立刻出现第二份实现，越走越远。

## 五个关键取舍

**1. 没有来源原句的提案直接拒绝整批。**
提示词要求每条带 `quote`，解析时逐条校验。缺一条就整批 400，不做「这条先跳过、其他照收」。
理由：候选组的价值是「作者能快速判断要不要」，一条没有依据的建议会消耗同样的注意力，
却无法核对。

**2. 来源核对放在「采用」而不是「生成后立刻」。**
建议可以在候选里躺很久，期间作者可能改正文。所以核对必须在采用前做，用生成时的
`chapter_base` 与当前比较，不一致返回 409 `SOURCE_NEEDS_RECHECK`，并保留旧建议供回看。

**3. 核对只作用于带 `source` 的条目。**
手工暂存的候选没有来源，不该被「正文变了」拦住——作者可能是根据讨论直接建的人物。
按条目类型区分，而不是给整个组加一个全局状态。

**4. 零建议是合法空结果，不建空卡片。**
模型回 `{"suggestions":[]}` 时返回 `status: empty`，不写候选组、不动已有条目。
计划里「零建议不创建空卡片」是产品要求，这一条在服务层直接短返回实现。

**5. 建议不改正文，也不自动触发其他功能。**
采用只写账本（既有 accept 的一次提交）；不会顺带重跑摘要，也不会因为保存正文就自动整理。
`test_saving_never_starts_suggestions_by_itself` 盯住「保存零调用」。

## 数据影响

- 候选组多两个字段：组级 `origin`、条目级 `source`。都在辅助表 `ledger_staged` 里，
  不进入仓库版本；正式账本仍然只由 `accept` 的一次 Commit 产生。
- `GET /ledger/candidates` 与 `GET /suggestions` 是同一份数据的两种读法（后者语义更明确）；
  现有接口保持不变，视图多了 `origin`/`source` 字段。
- 建议条目的正式身份仍由 `(group_id, item_id)` 确定性派生，重复点击不会重复入账。

## 错误码

| 码 | HTTP | 场景 |
|---|---|---|
| `STORY_INVALID_COMMAND` | 400 | 输出不是 JSON、缺 `quote`、kind 不在可写种类、超过 12 条 |
| `SOURCE_NEEDS_RECHECK` | 409 | 生成后正文已变，建议不能原样采用 |
| `LEDGER_HYPOTHESIS_NOT_ACCEPTABLE` | 400 | 假设条目不能进正式账本（沿用候选规则） |
| `SUGGESTION_CHAPTER_NOT_FOUND` | 404 | 作品无正文或章节不存在 |
| `SUGGESTION_NOT_AVAILABLE` | 400 | 没接通模型 |

`SOURCE_NEEDS_RECHECK` 原本会被通用映射判成 400，这次在 `_status_for` 里显式归为 409：
它不是输入写错，而是「先重新整理再采用」的选择。

## 留白与风险

1. **未任务化**：现在同步等待模型返回。摘要已经有一套任务骨架，建议接上去是下一步
   （长章 + 慢模型时体验差别明显）。
2. **「调整建议」未做**：计划里的三选一是「更新选中/调整建议/暂不更新」，
   目前只有前两项；调整需要把建议改写成候选编辑，属于交互设计。
3. **组内互相引用未支持**：同一批建议里 A 引用 B（B 尚未入账）会因引用不存在被拒。
   计划要求「依赖闭合」——现有 accept 只支持「引用已存在条目」，跨建议依赖要更复杂的
   占位解析（候选组已有 `@item_id` 机制，建议暂未接入）。
4. **建议不会自动过期**：正文改了只会在采用时被拦，列表里仍显示 pending。
   给条目加 `needs_recheck` 状态会更清楚，留给交互那一步。
5. **一次只整理一章**：跨章整理（整段剧情的新设定）不在本任务范围。

## Agent 设计经验

- **找到「已经解决的 80%」再动手**：建议与候选的差别只有一个字段（来源），
  但如果没有先看清候选组的实现，很容易写出第二套确认逻辑。
- **核对时机比核对规则更重要**：同一个 `chapter_base` 比较，放在生成后没用（作者还没改），
  放在采用前才拦得住。
- **空结果是产品语义，不是错误**：零建议要能返回、能显示、不能建空卡片；
  把它当异常处理会让作者以为「整理失败了」。
