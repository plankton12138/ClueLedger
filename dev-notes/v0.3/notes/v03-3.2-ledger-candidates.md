# V03-3.2 构建笔记：账本直接保存与设定候选成组

> 阶段开发记录；实现范围、待办与测试结果均对应记录时点。当前行为见[模块说明](../modules/README.md)，剩余缺口见[运行与验收状态](../release.md)。

状态：**已交付**（2026-10-18）。3.1 的「旧规划管线删除」仍是收尾项，不阻塞本任务。
范围：账本直接保存、设定候选成组/部分确认、真实版本回读；假设不入账，证词/认知保留原类型。

## 为什么先做这一刀

V03-3.3 的试写已经能「账本 + 作者要求 → 候选 → 采用首章」，但写作台没有账本写入入口：
空作品无法先建人物、地点，再引用它们试写。这是 3.3 留白里最挡路的一条，也是「模糊构想 →
确认姐妹/旅馆 → 不确定凶手仍试写」阶段演练缺的那一步。

第二个原因是写路径同源。账本条目与正文一样属于作品事实，必须经同一个仓库事务：
一次保存一个 Commit，失败不产生半套条目，成功后回读真实 `commit_id` 与 `revision_id`。
如果账本另开一条「直接写 JSON」的捷径，V03-4.6 的关联撤销就找不到可追溯的版本。

## 交付内容

| 层 | 产物 |
|---|---|
| 领域 | `domain/story/canon/entries.py`：十种账本条目的创建/修订命令；字段白名单、引用类型、枚举、revision CAS；`validate_fields` 与候选暂存共用同一套规则 |
| 应用 | `application/services/ledger_service.py`：直接保存与回读；`ledger_candidate_service.py`：候选组暂存/确认/跳过 |
| 接口 | `GET /ledger/schema`、`GET /ledger/entries/{id}`、`POST /ledger/entries`、`PATCH /ledger/entries/{id}`；`GET /ledger/candidates`、`POST /ledger/candidates/items`、`/accept`、`/skip` |
| 前端 | `components/desk/LedgerPanel.tsx`、`LedgerEditor.tsx`：服务端表单描述驱动的编辑表单、待确认区、假设标记、版本回读 |

可保存的种类（与前端下拉一致）：人物、地点、关系、线索、案件真相、事实、
认知/证词、时间线事件、世界规则、故事前提。节拍不在其中。

## 三个关键取舍

**1. 表单描述由服务端生成。**
十种条目如果各写一份前端表单，字段口径迟早与后端白名单漂移。现在
`GET /ledger/schema` 返回种类、字段、控件与引用目标，前端只按描述渲染；
测试同时断言「表单字段集合 == 领域白名单」，加字段时两边一起失败。

**2. 候选是独立事实，不是「未保存的正式条目」。**
候选落在辅助表（`ledger_staged`），没有条目 ID、不参与账本查询、不产生版本。
确认时才按选中的条目一次提交；未选中的继续留着，可以稍后单独确认。
引用同组条目用 `@item_id` 占位：确认时按依赖顺序解析，被依赖项未选中且尚未
确认则拒绝（`LEDGER_DEPENDENCY_UNCLOSED`），不造悬空关系。

**3. 假设与证词分开处理。**
「假设」没有对应 kind，暂存时必须显式标记 `hypothesis`；它可以在候选组里
存在、讨论，但确认时被 `LEDGER_HYPOTHESIS_NOT_ACCEPTABLE` 拒绝。
角色声称或猜测用「认知 / 证词」保存为 `story.knowledge`，`mode` 原样保留，
不会在采用时变成 `story.truth_fact`（I09）。这一条由服务端与测试共同固定。

## 幂等与迟到结果

- 直接保存：`request_id` 作为 Commit 幂等键；重试先查已提交结果，回读同一条目。
- 候选确认：条目 ID 由 `(group_id, item_id)` 确定性派生。提交成功但组状态未落盘时，
  重试按 `changed_artifact_ids` 认回条目并补齐组状态，不会重复入账。
- 候选组用 `revision` 做 CAS：基于旧列表确认会被拒绝（`LEDGER_CANDIDATE_CONFLICT`），
  前端重新读取后再确认。未选中项不受影响。

## 已知留白

1. **模型整理候选未接**：当前候选由作者在写作台「存为待确认」产生；对话/正文
   产生的设定建议复用同一确认规则，生产入口归 V03-4.4。
2. **候选不能原位编辑**：调整一条候选只能「暂不处理」后重新暂存；编辑入口随
   V03-4.4 的「调整建议」一起做。
3. **旧规划管线**：七页侧栏绑定与起草前置已解除；`narrative.beat` 类型、planner 创建入口与
   AgentTasks 的节拍起草仍在，类型退出归 V03-8（见 v03-3 笔记第 2 条）。
4. **账本保存不产生 OperationRecord**：保存返回真实 Commit 与 revision，但尚未进入
   操作结果/撤销追踪；关联撤销归 V03-4.6。
5. **候选组不自动清理**：与导入预览一样，长期堆积的清理归 V03-8。

## 七页侧栏与旧管线的收尾边界

3.2 顺带解除了七页对话对节拍的绑定：

- 后端 `AgentWorkflows.draft` 不再要求「必须从节拍开始」：只在目标被显式传入时校验其确实是节拍，
  空目标按账本 + 作者要求 + 章节起草；未知目标报 `DRAFT_TARGET_INVALID`（取代 `DRAFT_BEAT_REQUIRED`）。
- 前端任务卡：章节草稿的目标改为选择章节（新章/改写现有章），不再列出已接受节拍；
  模拟器同步去掉节拍与基础版本前置。
- 没有删除 `narrative.beat` 类型、planner 创建入口或 AgentTasks 的节拍起草：类型退出需要先完成
  有效信息转换（状态变化/披露 → 事件与正文位置）与默认入口切换，按计划归 V03-8。
  3.1 因此仍是「部分交付」，但活动起草路径已经无节拍前置。
