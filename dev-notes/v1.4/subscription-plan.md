# v1.4 在线账号、作品隔离与订阅方案

2026-11-06 · 分支 `feat/v1.4-subscription`

更新日期：2026-11-06。目标是将线簿 / ClueLedger 部署到服务器、绑定域名，支持用户在网站登录、购买订阅和写作。实施顺序、接口、代码示例和验收要求见[开发计划](development-plan.md)。

本文描述目标方案，不代表已交付。账号、作品隔离、订单权益、订阅模型代理与生产配置/部署脚本已接入并通过本地验证，见 [P3](notes/P3-billing.md)、[P4](notes/P4-metering.md) 与 [P5](notes/P5-deployment.md)；真实支付宝/模型联调、域名证书、邮件送达与恢复演练尚未形成已验收的完整链路。文中金额、额度和模型成本均保留为测算假设，正式售卖前须按供应商当前价格及实际用量重新核验。

## 一、结论摘要

1. 保留自带模型连接（BYOK）这一产品能力，另加一条**订阅通道**：作者买天数，用线簿提供的模型密钥写作，按实际用量扣点。网站版的两条通道均由服务端执行，并按账号隔离凭据。
2. 计量单位是「点」。以 `deepseek-v4-pro` 为 1.0 倍率基准，`deepseek-flash` 为 0.30 倍率。
3. 月卡设**每日点数上限**，额度按 24 小时窗口滚动重置；体验卡以全期总点数封顶。
4. 本版选择支付宝 **AI 网页应用收款**（`alipay.trade.page.pay` / `FAST_INSTANT_TRADE_PAY`），采用「一次购买 N 天」，到期不自动续费。沙箱的电脑网站支付收银台返回 SYSTEM_ERROR，故沙箱改走手机网站支付（`alipay.trade.wap.pay` / `QUICK_WAP_WAY`）；生产应用只授权了 `page.pay`，调用 `wap.pay` 会返回 `insufficient-isv-permissions`。
5. 订阅通道的模型请求必须经过中转服务，密钥不下发客户端。
6. 邮箱注册并验证，邮箱＋密码登录；内部稳定的 `user_id` 关联作品、模型连接、订单、权益和用量。第一版一部作品只属于一个账号。
7. 必须先登录再购买；支付与写作使用同一账号身份。生产不开放匿名购买、先付款后认领或任意服务器目录访问。
8. 先用单台服务器、单个对外域名和 HTTPS，写作与支付按进程分开；完成账号与作品隔离后再开放公网写作。

## 二、约束条件

设计被三条硬约束决定，先说清楚，后面每个选择都能追溯到这里。

### 2.1 支付侧：只有一次性收款

本方案使用 AI 网页应用收款的下单、查询、退款与关单能力，商品码固定为 `FAST_INSTANT_TRADE_PAY`；本版不接入周期扣款、协议支付或自动续期。

这意味着「订阅」只能表达为：作者支付一笔钱，购买从今天起 N 天的使用权。N 天到期后关系自然结束，是否继续由作者再次支付决定。

这个约束看起来是限制，实际影响是正面的：续费变成作者的主动决策，续费率是真实的，不存在「忘了取消」带来的虚高。对比赛的商业化表现评分反而更有利。

代价是必须用产品手段补上「自动续费」原本承担的召回职责，见 §6.3。

### 2.2 密钥侧：不能下发客户端

订阅通道用的是线簿持有的模型密钥，密钥只保存在服务端，不下发浏览器。每次请求都由服务端检查当前账号、作品归属、订阅和额度，再转发到模型供应商。

这条约束直接决定了系统必须有一个服务端组件，也就决定了接下来所有的鉴权、限流、计量都发生在服务端。

### 2.3 产品侧：自带模型通道必须保留

现有本地版通过 `provider_config.py` 和系统凭据存储管理作者自己的模型账号。服务器版保留这项能力，但需要把连接配置、当前选择和凭据存储全部改为账号范围；作者的密钥在受控服务端加密保存，前端只获得脱敏视图，费用仍归作者的模型账户。

两条通道并存，作者在设置里选择。不能把现有进程级配置和系统凭据存储直接作为网站所有用户的共享配置。原本地运行方式保留独立边界，不承担公网多用户身份。

## 三、两条通道的分工

| | 自带通道（现有） | 订阅通道（新增） |
|---|---|---|
| 密钥归属 | 作者自己 | 线簿 |
| 请求路径 | 浏览器 → 线簿服务端 → 作者配置的供应商 | 浏览器 → 线簿服务端 → 订阅中转 → 模型供应商 |
| 费用 | 作者的 API 账户 | 订阅已包含，按点计量 |
| 额度限制 | 无 | 每日点数上限 |
| 可用性要求 | 网站与作者供应商均可访问 | 网站与订阅中转均可访问 |
| 适用 | 已有 API 账号、用量大的作者 | 不想配密钥、想先跑起来的作者 |

这个分工解决了一个具体矛盾：如果只有订阅一条路，额度限制会惹恼已经在为 API 付费的作者；如果只有自带一条路，产品的上手门槛就卡在「先去申请一个 API key」。

两条并存之后，额度只作用于线簿付费的那部分成本，逻辑是自洽的。

## 四、计量单位：点

### 4.1 定义

以下模型规格、价格与时段均为原方案测算输入，尚未在本次计划更新中重新验证；正式配置与售卖前按当前官方信息核定。

**1 点 = `deepseek-v4-pro` 输出 1,000 tokens 的成本，按高峰时段价格计算。**

DeepSeek 高峰价（北京时间工作日 9:00–12:00、14:00–18:00）下，`deepseek-v4-pro` 输出价为 27 元/百万 tokens，因此：

```
1 点 = 27 元 / 1,000,000 × 1,000 = 0.027 元
```

按高峰价而不是空闲价定义，是因为额度必须是成本上限而不是平均值。作者如果在空闲时段写作，实际成本只有一半，差额留在平台侧，这也是引导作者在非高峰写作的经济动机。

### 4.2 扣点公式

```
points = (input_miss × 0.333 + input_hit × 0.011 + output × 1.000) × mult / 1000
```

| 系数 | 取值 | 来源 |
|---|---|---|
| `0.333` | 输入未命中缓存 | pro 输入 9 元 / 输出 27 元 |
| `0.011` | 输入命中缓存 | pro 命中 0.30 元 / 输出 27 元 |
| `1.000` | 输出 | 基准 |
| `mult` | 模型倍率 | 见 §4.3 |

公式里输入按 pro 的价格比例折算，而不是按各模型自己的输入输出比。原因是让倍率保持单一数字，作者容易理解；代价是 `deepseek-flash` 的输入略贵于其真实成本（0.100 对 0.074），误差出现在输入侧、方向对平台有利，可以接受。

### 4.3 倍率表

| 模型 | 倍率 | 上下文 | 输出上限 | 定位 |
|---|---|---|---|---|
| `deepseek-v4-pro` | 1.00 | 1M | 384K | 正文续写、结构整理、长上下文推理 |
| `deepseek-flash` | 0.30 | 1M | 384K | 校对、摘要、检索、短问答 |

换算成作者能感知的说法：同样 60 点，用 pro 大约写 4–9 章，用 flash 大约写 13–30 章。

### 4.4 典型消耗

按 pro、上下文长度取常见值估算，未计缓存：

| 场景 | 输入 tokens | 输出 tokens | 点数 |
|---|---|---|---|
| 短问答、格式调整 | 3,000 | 800 | 1.8 |
| 续写一章（上下文 5 章内） | 12,000 | 2,500 | 6.5 |
| 续写一章（上下文 20 章） | 42,000 | 2,500 | 16.5 |
| 全书结构整理 | 90,000 | 6,000 | 36.0 |

同一场景命中缓存后：

| 场景 | 缓存命中率 | 点数 |
|---|---|---|
| 续写一章（上下文 20 章） | 80% | 5.7 |
| 全书结构整理 | 60% | 18.6 |

这张表说明一件事：**长上下文写作的成本几乎全在输入，而输入的绝大部分是可缓存的稳定前缀。** 缓存命中率是这个商业模式能不能成立的关键变量，比定价更关键。相关工程要求见 §9.2。

## 五、定价与额度

### 5.1 档位建议

| 档位 | 价格 | 时长 | 额度 | 最坏成本 | 毛利 |
|---|---|---|---|---|---|
| 体验卡 | ¥9 | 3 天 | 180 点（日均 60） | ¥4.86 | 46% |
| 标准月卡 | ¥69 | 30 天 | 60 点/天 | ¥48.60 | 30% |
| 长篇月卡 | ¥129 | 30 天 | 120 点/天 | ¥97.20 | 25% |

「最坏成本」按额度用满、全部在高峰时段、零缓存命中计算。实际成本通常只有这个数的一半左右，因为空闲时段半价且缓存命中率在连续写作时很高。

### 5.2 体验卡与价格阶梯

体验卡的作用是降低第一笔付费的门槛，不是赚钱。但降低门槛的正确手段是**压低绝对金额**——¥9、三天、不用承诺一个月——而不是提高单位额度。这两件事经常被混为一谈，混了就会把阶梯装反。

判断一档定价是否合理，看单位点数价格，不看毛利率：

| 档位 | 点数 | 价格 | 元/点 |
|---|---|---|---|
| 体验卡（日均 60） | 180 | ¥9 | 0.0500 |
| 标准月卡（60 点 × 30 天） | 1800 | ¥69 | 0.0383 |
| 长篇月卡（120 点 × 30 天） | 3600 | ¥129 | 0.0358 |

三档单调递减，承诺越长单位越便宜。体验卡的毛利率 46% 看起来偏高，但那是短期承诺应得的价格：不要求作者承诺一个月，平台承担的风险更小，折扣理应更少。单看这个数字会以为在赚新人的钱，而实际每用户只有 4 块多的毛利，对一个获客动作来说，赚 4 块还是 1 块对生意没有影响。

反过来，把体验卡额度抬到日均高于月卡，毛利率确实降下来了，但价格阶梯会翻过来：承诺最短的档待遇最好。作者付完第一笔钱就会发现「试用比付费划算」，流失正好发生在刚转化的时点，损失远大于每用户多赚的三四块钱。

如果确实想在首次购买上显得大方，正确做法是不动档位表，另设一次性的新作者补贴：体验卡 180 点，首购再赠 60 点，实付 ¥9 拿到 240 点，折算成本 ¥6.48、毛利 28%。这样「多给」发生了，但档位表里的日均额度关系没被破坏，作者看到的是「新人多送 60 点」，而不是「试用档比月卡待遇好」。作者对前者是理解的，对后者是不理解的。

**体验卡每账号限购一次，且不设每日上限。** 整期暴露只有 ¥4.86，用总额度封顶就够了，按天切反而挡住体验期该有的集中写作。但如果不限购，作者会反复购买把它当作廉价月卡，所以限购是这条定价成立的前提。180 点用完，只能选月卡或自带模型，转化路径是封闭的。


### 5.3 为什么每日额度是硬上限

如果只给总额度（比如月卡 1800 点不分天），会出现两个问题：

一是成本无法预测。单人单日可能把整月额度一次跑完，当月的收入在第一天就花光。

二是体验不公平。额度被一天耗尽之后，作者剩下的 29 天都无法使用，投诉成本远高于限流的成本。

按天切分把风险控制在单日。代价是作者某天写得多会被挡住，所以超额时的处理必须给出路，见 §6.2。

体验卡不受这条约束，因为它的整期暴露只有 ¥4.86，用总额度已经足够封顶。日上限是为了管住月卡这种长周期、大额度的情况。

### 5.4 额度窗口的语义

**1 天 = 从购买时刻起 24 小时**，额度在每个 24 小时窗口开始时重置。

不采用「自然日 0 点重置」，原因是晚上 10 点买日卡的人会只剩 2 小时，这类边界会产生大量客诉。滚动窗口对每个作者都公平，实现上只是在购买时记一个 `starts_at` 锚点，之后按 `starts_at + k×24h` 切窗口。

界面上要明确显示「额度下次恢复：明天 14:30」，而不是「明天」。

### 5.5 不做的两件事

**额度不结转。** 未用完的点数不累加到次日。结转会让单日成本上限失效，且作者会倾向于攒额度到某天集中使用，反而更容易触发限流争议。

**不做免费档。** 免费额度在写作产品里会被脚本刷，且免费用户体验不到长上下文的差异，转化意义有限。替代方案是体验卡：¥9 三天，愿意付第一笔钱的人才是有效样本。

## 六、作者旅程

### 6.1 购买

```
作者邮箱注册并验证 → 登录 → 选择档位 → 服务端创建绑定 user_id 的订单
→ 支付宝付款 → 通知验签或主动查单确认 → 幂等写入权益 → 网站刷新权益
```

支付结果以异步通知或主动查询为准，不依赖同步跳转。订单号做幂等键，重复通知只记一次账。付款人可以代付，权益始终归创建订单的登录账号；`buyer_id` 只用于交易核对，不作为登录身份或订单认领依据。

### 6.2 使用与超额

订阅有效期内，作者在模型连接里看到「线簿订阅」这一项，选中即可写作。每次请求中转服务先检查剩余点数。

超额时的处理分三层，缺一层体验就会断：

1. **80% 时提示**：界面显示「今日额度剩余 12 点，约 1 章」，给作者预留决策时间。
2. **耗尽时降级不锁死**：写作功能仍然可用，只是不能发起新的模型请求；已写正文、大纲、线索全部可读可改。
3. **耗尽时提供可执行的下一步**：切到自带模型连接（如果配过），或查看准确的额度恢复时间。补充包尚未确定售卖，不在第一版展示购买入口。

第 3 层是这个设计里最容易被忽略但最影响留存的地方。额度用完是产品主动造成的阻断，必须由产品自己给出下一步。

### 6.3 到期与续期

没有自动续费，所以召回要靠产品：

| 时点 | 动作 |
|---|---|
| 到期前 5 天 | 界面顶部一条提示，不弹窗 |
| 到期前 2 天 | 提示升级为醒目样式，附「续 30 天」按钮 |
| 到期当天 | 记录一次「即将到期」事件到活动日志 |
| 到期后 | 保留阅读、编辑、导出及自带模型能力，停止订阅模型调用 |
| 到期后 7 天 | 一封提醒，说明数据仍在，随时可恢复 |

续期走的是同一套下单流程，只是把天数累加到 `expires_at`。如果作者在到期前续费，新天数从原 `expires_at` 起算，不吞掉剩余时间——这一点必须做对，否则会被认为在扣用户时间。

## 七、数据模型

以固定的 `user_id` 关联账号数据，邮箱用于登录，支付宝标识用于交易核对。生产第一版沿用单机 SQLite；每个连接开启外键约束，事务内完成权益发放和额度预留。暂不做多副本写入；新环境直接建库，不迁移旧数据。

| 数据 | 归属与约束 |
|---|---|
| `accounts` | 固定用户 ID、唯一邮箱比较值、密码哈希、验证时间、账号状态；不存明文密码 |
| `auth_challenges / sessions` | 验证与重置凭证仅存哈希，限定用途、有效期和单次消费；会话可撤销，登录与订阅有效期分开 |
| `workspaces` | `id + owner_user_id + storage_key`；服务器确定真实目录，客户端不指定根路径 |
| 作品附属数据 | 正文、会话、报告、附件、索引、任务、事件、导出都检查作品归属 |
| 模型连接与私有模块库 | 按账号存取；跨用户共用的仅为明确发布的只读内置资源 |
| `orders` | 下单即绑定非空用户 ID；金额使用整数分；支付宝 `buyer_id` 与用户 ID 分开 |
| `entitlements / refunds / notify_events` | 权益关联订单与用户；订单号、退款请求号、通知 ID 分别幂等 |
| `usage_windows / usage_reservations / usage_ledger` | 额度按账号累计，按请求预留、结算与恢复；整数微点避免小额请求被舍为零 |

续期按 `max(现有有效期末尾, 付款确认时间) + 购买天数` 生成权益；退款保留购买记录，通过退款记录与权益状态表达，不删除历史。表结构与事务要求见开发计划。

## 八、接口

### 8.1 支付宝侧

| 用途 | 接口 | 备注 |
|---|---|---|
| 下单 | `alipay.trade.page.pay` | `product_code=FAST_INSTANT_TRADE_PAY`；仅沙箱改用 `wap.pay` / `QUICK_WAP_WAY` |
| 查询 | `alipay.trade.query` | 通知未到或订单未决时主动确认 |
| 退款与查询 | `alipay.trade.refund` / `alipay.trade.fastpay.refund.query` | 确认真实结果并同步调整权益 |
| 关单 | `alipay.trade.close` | 确认未支付订单的关闭结果 |

通知先验签，再核对应用、订单、金额、收款方与交易状态；持久化成功后返回 `success`。同步回跳只展示结果，不发放权益。生产建议配置公网 HTTPS 通知地址，并实现未决订单后台查单；即使用户关闭页面仍须处理。省略通知地址时，后台主动查单须独立完成确认。

支付流程：下单接口返回 `payment_url`，内容是本站短链 `/pay/{order_no}?token=…`；前端下单成功后自动开新窗口打开它，被浏览器拦截时退回手动按钮。`/pay` 校验订单号与签名令牌后现签收银台地址并 302 过去，短链不改变订单状态；收银台地址带时间戳，每次打开才生成，不会过期。

### 8.2 网站与内部服务

所有账号、作品和支付接口共用经过验证的登录身份。浏览器使用服务器会话 Cookie，不把套餐、到期时间或用户 ID 当作可信请求参数；写操作校验请求来源与 CSRF。支付进程复用同一会话校验模块，不能信任客户端传入的 `X-User-ID`。

| 接口组 | 约定 |
|---|---|
| `/api/auth/*` | 注册、验证、登录、当前账号、退出、找回与重置密码 |
| `/api/file-workspaces/*` | 保留作品能力，列表、创建与导入限定账号范围；网络模式禁用任意目录选择 |
| `/api/model-*`、模块库、任务与事件 | 配置、凭据、资源与事件均限定当前用户 |
| `/api/billing/*` | 网站统一的套餐、订单、权益与用量入口，内部映射现有 `/v1/*` 支付路由 |
| `/notify/alipay`、`/return/alipay` | 受控公网通知与回跳；通知免用户登录但须验签，回跳不授予账号访问权 |
| `/pay/{order_no}` | 扫码短链；凭订单号与签名令牌跳转支付宝收银台，不改订单状态 |
| 内部 `/v1/chat/completions` | 订阅模型代理；仅接受可信用户上下文，不向浏览器发平台模型密钥 |

移除原计划的 `/v1/entitlement/claim`。现有匿名 `POST /v1/session` 仅是开发基础，生产不用于创建可购买账号。请求、响应与页面消费关系见[开发计划](development-plan.md#三前后端接口对齐)。

### 8.3 判额流程

校验登录、账号状态、作品归属和有效权益，再以原子事务预留额度，随后调用上游。同一账号的并发请求共享额度与并发限制；同一请求 ID 不重复扣费。

成功按真实 usage 结算并释放差额。流式中断缺失 usage 时记录待核对状态并保留有上限的预留，不以字符估算作为最终扣费；后台恢复在明确期限内完成结算或释放。每日窗口、体验卡总额和单次请求上限均须检查。


## 九、与现有代码的衔接

### 9.1 账号范围装配

现有 `server/__main__.py`、`server/file_app.py` 按本地作品目录、应用状态与模型连接装配；`relay/app.py` 有独立会话与订单。服务器版新增统一账号上下文，由同一用户 ID 装配作品服务、模型连接、私有模块库与订阅查询；后台任务显式携带可信账号和作品身份。

订阅通道复用现有模型调用协议，但增加平台订阅来源；现有第三方供应商订阅登录不等于线簿账号。不能仅靠新增 `kind` 字段或缓存到期时间完成计费控制，服务端每次执行均须确认实时权益。

### 9.2 提示前缀与成本验证

保留稳定系统提示与上下文顺序，避免把时间戳、随机 ID 放在可缓存前缀。稳定性不能削弱作品隔离：共享缓存只能包含公开静态内容，私有缓存必须包含用户与作品范围。

当前价格、缓存折扣、上下文上限和章节消耗须在正式定价前重新核验。按项目约定使用 `.env` 在线模型做受影响场景的单例验证，失败修复后定向复验，不短时间批量重复调用。

### 9.3 到期后的体验

登录会话和订阅到期分别处理。订阅到期不退出账号，不限制作者读取、编辑、导出已有作品；有自带连接时允许主动切换。错误格式统一为 `[错误码] 位置：现象。建议：…`，前端保留未提交内容。

## 十、风控与边界

| 风险 | 处理 |
|---|---|
| 登录与邮件接口被滥用 | 邮箱、来源和账号多维限速；验证/重置凭证限时单次使用；不泄露邮箱是否注册 |
| 读取他人作品 | 每次请求校验所有权；文件、导出、事件流与模型工具共同检查 |
| 并发超额 | 用户级原子预留与幂等结算，初始建议每账号最多 2 个模型请求 |
| 单次模型成本过大 | 请求前限定最大输出与预留上限；不足时返回建议，不默默截断正文 |
| 流式中断缺少 usage | 有限预留、待核对状态与超时恢复，不凭空产生最终费用 |
| 会话泄露或密码重置 | 可撤销会话、安全 Cookie、CSRF 校验；重置密码后撤销旧会话 |
| 退款后继续使用 | 退款确认后重算有效权益，后续请求读取实时状态 |
| 换设备或邮箱 | 固定用户 ID 保留作品与权益；换邮箱验证新地址并通知旧地址 |
| 生产配置混入沙箱 | 分离运行目录与密钥；生产缺项直接失败，不自动读取沙箱资料 |

退款政策、手续费与适用交易限制须在售卖前按商户当前规则确认并展示，不把体验卡使用状态直接写成一概不退款的承诺。邮箱账号用于产品身份，不代替可能另需满足的实名或经营要求。

## 十一、参赛材料口径

如果按 AI 网页应用收款提交，作品介绍里应该强调的三件事：

1. **支付不是贴上去的**。额度、窗口、超额降级、续期是一条完整链路，作者在界面上能看到剩余点数和恢复时间。
2. **两种付费方式并存**。自带密钥的作者不为软件付费也能用，愿意付费的作者不用配密钥。这是对「AI 写作工具该不该收订阅费」这个问题的回答，不是功能罗列。
3. **定价可解释**。1 点等于什么、一章大概几点、缓存命中为什么更省，这些能说清楚，说明作者真的算过成本，而不是拍了个价。

第 3 点尤其重要。评委看商业化表现时，最想确认的是「这个价格是不是拍脑袋定的」。

## 十二、已确定方向与待决事项

已确定：服务器网站与域名、邮箱账号、作品隔离、付款前登录、固定身份关联权益，以及 AI 网页应用收款的一次性订阅购买流程。实现默认采用邮箱＋密码、单人作品和单域名部署，按开发计划执行。

以下事项在对应阶段开始前确定，不阻挡账号与隔离模块先行开发：

1. 商业参数：套餐价格、日额度、体验卡限购、是否提供补充包；文中金额暂不作为正式承诺。
2. 部署资源：云服务商、地域、域名、邮件发送服务、备份目标、可用性与预算；大陆服务器备案准备提前进行。
3. 模型成本：当前官方价格、模型可用性、前缀稳定性及真实 usage/缓存命中结果。
4. 上线材料：商户主体、产品开通、应用与密钥配置、服务及隐私条款、退款规则。

本版不增加 AI 按量付费接入、自动续费、团队协作或多服务器集群；后续如需另立范围，不由本计划推定授权。
