## 1. 交付目标

1. 新作品直接进入对话：引导提问或自由发挥产出设定卡，确认过门槛；确认后模型起草第一版结构（`STRUCTURE.md`）并自主创建首批模块（走 v0.8 既有创建挂载机制），随事务直接入档（Git 可回退），作者在只读页与对话中核阅，不满意一句话改。
2. 每部作品有一份模型自维护的 `STRUCTURE.md`（作品根目录真实文件、Git 版本化、自由格式 Markdown）：开头铁律段 + 路线 + 章节骨架 + 模块索引。作者只读。
3. **正文台账由事实层维护**：事务层在每次入档时自动记录每章已入档修订号与状态，模型只读不可写、不进入 `STRUCTURE.md`；这是系统的「git status」，为确定性对账提供不依赖自由格式解析的事实基础。
4. 装配契约（冻结顺序）：铁律 → 结构全文 → `STYLE.md` 空占位 → 当次涉及挂载模块按需注入 → 正文台账（只读事实）→ 必发生清单（模型同回合自列，不落盘）。
5. **装配层确定性对账（第一道防线，纯函数）**：目标章号来自任务元数据（系统发起，非解析自由格式），与台账比对；目标章之前存在缺章即拦截改派或报警。
6. 章节入档事务扩展为三元原子提交：正文 + 结构文件更新 + 涉及模块更新，**直接落盘（不设暂存确认门）**，复用既有联合提交事务，可整体撤销；写作回合预期正文未产出按任务失败归因，任何部分不入档。
7. 建章、标题、方向建议由模型提出，作者确认或一句话调整。
8. 感知区分：记账类更新静默；计划性变化（改点位、新增线、改铁律）在对话中单独一行说明，附「不同意，改回来」。
9. 写后自查三层（必发生核对 / 铁律自查 / 读者认知提示）随起草同回合产出，概率性、如实标注「自查」；起草前强制对账流程为第二道保险。
10. 模块机制零改动：`library/modules.py` 及其前端流程维持 v0.8 形态。

完成标准不是「文件存在」，而是验收用例（UC-D01—D04、D06—D08、UC-S01—S05，见 [acceptance.md](acceptance.md)）可从空作品连续走完，且对抗用例（风格指令挤压剧情、伪造「已写」标记）下护栏实测有效。

## 3. 模块计划

### M1 对话起步与结构生成

**为什么**

意图手写输入是「作者先理解结构概念才能动笔」的负担；而逐章对话推进缺乏全书工作记忆。两者一并解决：对话起步换意图来源，设定卡确认后立即由模型生成结构文档与首批模块。

**设计**

- 新作品打开即进入会话，新增起步任务意图（模式：引导 / 自由发挥），复用现有会话受理、材料装配与流式链路。
- 引导提问的约束放在任务意图与提示装配层，不硬编码业务代码：一次只问一个问题、问题数量有上限、每问可跳过、作者随时可以说「就这样开始」、未知保持未知。`ask_author` 工具沿用。
- 起步以设定卡候选结束：模型把对话内容整理为一段作品意图（`book_intent` 候选），在对话中呈现。新增设定卡确认端点：服务端核对候选依据与当前状态后，联合提交写入作品意图；重复确认拒绝；可整体撤销。
- 确认后同链路起草第一版结构（含铁律、路线、骨架、模块索引）+ 自主创建首批模块（伏笔账、人物等，按书自选），随事务直接入档（Git 可回退），作者在只读页与对话中核阅，不满意一句话改。
- 无可用模型时新作品会话如实返回 `MODEL_UNAVAILABLE`，前端展示设置引导。

**主要落点**

- 修改：`task_intent.py`、`materials.py`、`service.py`、`api.py`、`story_candidate.py`、`agent.py`（结构读写工具，直接写入策略）、`structure_document.py`（复用）。
- 前端：新作品起步视图（对话承载）、设定卡确认卡。

**退出条件**

从新作品到第一版结构与首批模块入档全程对话完成；引导上限、跳过、「就这样开始」、未知保持未知有测试；设定卡确认幂等与撤销通过；无模型状态可见且不产生半提交。

### M2 结构文件层

**设计**

- 位置与形态：作品根目录真实 `STRUCTURE.md`，自由格式 Markdown；随作品复制、导出并由作品 Git 记录（复用 `files.py` / `git.py` 路径）。
- 唯一结构约定：文件开头为**铁律段**（以固定标记起始，装配器据此切分常驻注入）。铁律是写作规则不是数据字段，条数不设死，首版约三行由起步对话生成；标记丢失时降级为全文注入并提示。
- 作者只读：侧栏新增结构只读页（复用阅读组件渲染与页边风格），附「在对话里继续调整」；不提供编辑框。
- 外部编辑不设对照界面：装配前按磁盘现状如实注入；模型入档时自行整理外部改动并入本次事务。
- 字数预算：结构全文设冻结上限；超限时入档事务要求模型先提交压缩版结构（压缩随同一事务入档，Git 可回退），不静默截断。

**主要落点**

- 修改：`story_candidate.py`（结构事务载体）、前端结构只读页与侧栏入口。

**退出条件**

结构文件全程由模型产出与更新，链路内无编辑框；外部改动如实注入且入档可整理；预算超限触发压缩路径。

### M3 注入装配与护栏

**为什么**

实验证明：无注入时模型逐章只能靠上下文，一致性漂移；有注入但无护栏时，风格指令会把规定事件挤出章节（2026-11-03 实验中对话驱动版核心物件零出现）。装配解决「记得住」，护栏解决「不挤掉」。

**设计**

- 装配顺序（冻结为契约）：铁律 → 结构全文 → `STYLE.md`（本版空占位）→ 当次涉及模块 → 正文台账（只读事实）→ 必发生清单。
- **正文台账**：事实层数据，非模型可写文件；装配时只读注入并写进装配回执。台账与结构文件中任何「已写」标记冲突时以台账为准（此优先级写入装配契约与提示词）。
- **确定性对账（第一道防线，纯函数）**：目标章号来自任务元数据，与台账比对：目标章之前存在缺章 → 拦截本次装配，默认改派最早缺章，作者明确跳过才放行并记录。逻辑可离线单测（被动注入台账模型不对账 0/3，确定性检查不可下放给模型）。
- 模块按需选择：按写作目标（目标章、涉及人物/伏笔）选择注入模块，复用 `module_assembly` 既有「读相关原文」行为；目标未知时注入模块索引，由模型在会话内按需读取。全量重注入实测随章节数平方增长（第 4 章即 16.4k prompt tokens），**按需选择为必需项而非优化项**。
- 必发生清单：自由格式下纯函数派生不可行（试验证实），改为模型在起草同回合自列本章必发生项，进装配回执显式展示给作者一眼可否决；写后脚本做宽松关键词机检（匹配不判失败、报相对偏差），清单不落盘。自列为空时如实说明并建议补骨架或模块，不猜。
- 装配快照进请求回执：实际注入了哪些层、哪些模块、清单条目，可核对。

**主要落点**

- 修改：`assembly.py`、`materials.py`（结构层注入位）、`module_assembly.py`（选择调用位）。
- 新：`workspace/structure_assembly.py`（确定性对账、台账注入与装配快照、宽松机检）。

**退出条件**

装配契约冻结且每次请求可核对回执；确定性对账与宽松机检可离线单测；未涉及的模块不注入；预算内装配产物稳定。

### M4 事务同步与感知区分

**为什么**

结构文件如果靠模型「记得更新」必然脱节；必须把同步绑定进落盘事务。作者不能被模型的每次记账打扰，也不能对计划变化被蒙在鼓里。

**设计**

- 三元事务直接落盘（不设暂存确认门）：正文 + `STRUCTURE.md` + 涉及模块一次联合提交（复用既有 `StoryChangeService` 事务），可整体撤销。裁决依据：作者对结构文件只读，确认门是假控制；Git 逐次入档已提供回退，编码 agent 改自己的工作记忆不先请示。
- **正文台账维护（事实层）**：台账记录于事务层（每章 → 已入档修订号），三元提交成功时自动追加、整体撤销时自动回退；模型无写入口，不占对话回合。起步前为空。
- **原子性兜底**：写作回合预期正文未产出（试验复现过「只交文件更新不交正文」且自查对幻觉正文自洽）→ 整个任务按失败归因，正文、结构、模块任何部分不入档；「预期产出缺失」与「自查缺失」同列为确定性失败归因。
- 章节入档（起草采用、修改确认、建章确认）均走三元原子提交；基础修订过期规则不变（过期事务不可提交覆盖，只能比较后重新发起）。
- 感知区分在对话回显层实现：更新项分类为**记账**（伏笔标记已埋、章节状态更新——静默，仅入档回执可见）与**计划性变化**（改回收点位、新增叙事线、改铁律、删模块——单独一行说明，附「不同意，改回来」，改回由模型改写或走事务整体撤销）。分类由模型在入档时标注，装配层校验标注完整性。
- 结构更新的差异回显沿用既有差异三要素：改了什么、影响哪里（哪些章的骨架/点位随之移动）、基于哪个修订。

**主要落点**

- 修改：`story_changes.py`（三元事务扩展）、`story_candidate.py`（结构事务载体与分类标注）、对话回显事件（`tool_feedback.py` / `chat_stream.py`）。
- 前端：回显卡支持结构/模块差异段与计划性变化行。

**退出条件**

任何入档路径（起草采用、修改确认、建章）均产生结构同步，无「只入正文」路径；撤销整体回退三层；记账静默、计划性变化必有说明；结构文件写入直接落盘但每次入档均有 Git 记录可回退。

### M5 结构提案与写后自查

**为什么**

建章、标题是结构性决定，要求作者理解章节与信息线概念，改为模型提议、作者确认。放弃字段级机检换自由格式后，确定性校验降级为概率性自查。

**设计**

- **结构提案**：建章提案——模型在对话中提议建章（含可选标题），确认后走既有建章事务（同事务登记章节、分配正文路径、写入标题）；重复请求键幂等。标题起草作为设定类候选：确认写入或留空。章末收束与下一章方向在对话中给出，不设独立按钮。
- **写后自查三层**：起草任务同回合产出，随候选进入对话：①必发生清单逐条定位核对；②铁律逐条检查；③读者认知提示（当前误读是否立住、有无提前起疑），必须给可执行的修改建议。
- **强制对账流程（第二道保险）**：起草提示词规定，收到写作目标第一步必须核对目标章与台账，发现更早章节缺正文不得写目标章、改为补缺（被动注入无效 0/3，强制流程 3/3）。系统侧确定性对账仍是主防线。自查必须先引用对账结果，防止对幻觉正文自洽。
- 界面如实标注「自查」（模型自检，非系统校验），不承诺无漏报；自查失败（模型未产出自查段）按任务失败归因，不静默跳过。
- 作者采纳建议 → 模型修改随事务直接入档（Git 可回退），复检（仅对改动项）随入档产出；不采纳可直接入档，⚠ 不阻断。
- 自查提示词约束放任务意图与装配层，不硬编码业务规则；铁律内容本身来自结构文件，本层只定义「逐条自查」的流程。

**主要落点**

- 修改：`chapter_writing.py`（起草任务产出自查段）、建章提案确认端点、前端自查结果卡（✓/⚠ 样式）。
- 新：`prompts/` 下自查提示词模板（版本化）。

**退出条件**

起草候选必带三层自查；⚠ 建议可执行且采纳后随事务直接入档并复检；不阻断入档；自查缺失如实报错；建章全程无字段填写、失败回滚不留半登记。

## 4. 阶段顺序与退出条件

## 5. 关键实现顺序

1. 起步任务意图与设定卡候选（复用候选链路），确认端点与门槛衔接。
2. 结构读写工具（直接写入策略，走 `files.py` / `git.py` 同一路径，随事务入档）。
3. 起步起草第一版结构与首批模块（复用 v0.8 模块创建）。
4. 装配层结构注入位与 STYLE 空占位。
5. 正文台账（事实层）与确定性对账、宽松机检；必发生清单模型自列与回执展示。
6. 三元联合提交扩展（复用既有事务与整体撤销）。
7. 感知分类标注与对话回显。
8. 起草强制对账流程、自查三层与复检交互。
9. 建章提案与标题候选。
10. 结构只读页与入口收敛。
11. 验收与版本统一。

前端不得用本地假数据长期顶替真实交互；每阶段结束切回真实接口。

## 6. 风险与处理

| 风险 | 处理 |
|---|---|
| 对话回合预算耗尽（1.0.3 曾 24 回合耗尽） | 修改任务设回合上限；回显走结构化事件不占模型轮次；超限给明确归因 |
| 模型直接写入结构无确认门，写坏即落盘 | Git 历史逐次入档可回退；计划性变化强制单独说明附改回；台账与确定性对账兜底；对抗用例回归 |
| 结构文件失控膨胀（模型越写越细） | 字数预算冻结；超限入档前压缩、压缩随事务入档；只读页可见体量 |
| 自由格式失去可校验性 | 铁律固定开头保证常驻注入；正文台账与确定性对账补足章级事实；自查概率性如实标注；对抗用例回归护栏 |
| 结构与正文脱节（模型忘更新） | 同步绑定入档事务，无「只入正文」路径；全写入路径测试防绕过 |
| 模型顺着过期的「已写」标记在假前提上继续写作 | 正文台账由事实层维护（不进 `STRUCTURE.md`）+ 装配层确定性对账为主防线；提示词强制对账为第二道；预期正文缺失按任务失败归因（试验：被动注入 0/3，强制流程 3/3） |
| 静默记账掩盖计划变化 | 感知分类在装配层校验标注完整性；计划性变化必须单独一行说明 |
| 必发生清单派生为空或失真 | 改为模型自列＋回执展示＋宽松机检；自列为空如实说明并建议补骨架/模块，不猜 |
| 结构文件与模块内容重复冲突 | 分层判据写入起步与自查提示词；自查含一致性检查；重复不阻断、模型整理 |
| 外部编辑造成解析歧义 | 按磁盘现状如实注入，不设对照界面；铁律段标记丢失时降级为全文注入并提示 |
| 结构更新打断写作回合预算 | 结构更新随入档事务落盘，不占对话回合；压缩路径独立触发 |
| 全链路依赖在线模型，评测成本上升 | 确定性测试优先；在线用例失败修复后单例复测，不短时间重复 |

## 7. 文档与验证纪律

- 每阶段完成后写简短实施记录到 `notes/`，说明真实改动、验证命令、结果与未覆盖项。
- 决定变化时同步更新本目录文档与[产品方案](../../product-design/v1.1/README.md)，不保留相互矛盾的计划。
- 仅文档或版本号调整不跑后端全量；写入路径、联合提交或上下文链路实际改变后，按风险执行定向测试与一次必要广泛回归。
- 在线评测使用仓库 `.env` 的在线模型，报告在 `eval/runs/`；不使用本地模型、不保存凭据。
- 实施前按 v1.0.9 现状重新核对第 2 节基线表，差异登记到 Q0 记录。
- 根目录 README 仅在作者要求时修改；`mynotes/` 只读。
