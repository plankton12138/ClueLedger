# I5 使用记录与「用于写作」

日期：2026-10-25。状态：**已完成**。本阶段回答一个问题：这条灵感在哪次讨论里被带上、
在哪次对话里展开过、有没有真的写进正文；同时把「用于写作」接回普通写作受理。

## 1. 为什么把「用过」拆成三种事实

三条依据的权威不同，合成一个「使用过」标记就会失真：

| 显示 | 依据 | 不能拿来推断的 |
|---|---|---|
| 在讨论中引用 / 展开讨论 | 会话日志里已受理的 `turn_started` 事件 | 模型是否真的读了、是否采纳 |
| 写入正文 | 改动文件里实际出现的原文，加指纹、区间与引文核对 | 模型在回答里说「已经写进去了」 |
| 关联 | 作者手动登记的关联 | 不能当成已写入 |

写入还要能失效：正文后来被改动，路径还在但引文对不上，只能显示「该位置已变更」；
那次提交被明确撤销，即便正文又回到相同内容，也不能继续算有效写入。所以判定依据是
「当时的区间是否仍对得上」与「那次提交是否被撤销」，不是「文件还在不在」。

## 2. 服务端

**使用记录索引**

- 新增 `idea_activity.py`：回放会话日志里的受理事件，记下「哪个会话的第几条事件提到了
  哪条灵感的哪一版」，按用途分成引用与展开。索引只存标识、会话、轮次与时间，
  不复制灵感正文；丢了可以从事件日志重建。
- 重建按批推进（一次 400 条事件）。**未扫完时不发游标**：这一页本身还在长，给了游标
  翻页就会错位；界面显示「还在整理」，而不是「没有使用记录」。
- 修掉一个会让重建永久卡住的缺陷：批次用完时提前返回，游标没落盘，下次仍从同一处重读。
  现在先写回进度再返回。
- 会话标题与可用性在读取时解析：改名立刻反映；会话日志被删掉时保留当时那条记录并标为
  不可用，不悄悄隐藏，也不让作者点进一个打不开的会话。

**写入与撤回**

- 轮次提交成功后，逐个改动文件核对灵感原文是否真的出现；出现才登记 `applied`，
  并带上这次提交的标识。找不到原文就只保留引用事实，不制造「已写入」。
- 撤回以活动日志里的「撤销版本」操作为准：被撤销的提交显示为「已撤回」。
- 登记失败不重跑正文，也不影响本轮结果：留一条待补记录，下次读取使用记录时按当时的
  原文再核对一次。对得上补成「已写入」，对不上丢弃，始终不声称采用。
- `add_use` 的请求身份只取作者选择与核对结果，不再包含每次重新生成的标识与时间：
  同一个键重试回到同一条关联，不会被误判成「这个键用在另一件事上」。

**接口**

- `GET /ideas/{id}/activity`：返回 `items`、`total`、`complete`、`next_cursor`。
  每项有固定事件标识、关联修订、会话或目标路径、时间与当前可用状态。

## 3. 前端

- 新增使用记录状态层：读到一页就记下完整度与游标；整理中重复读第一页并按标识合并，
  扫完那一次换成完整快照，再按游标往下翻；切走或重读之后，迟到的响应不覆盖当前条目。
- 面板的「使用记录」区分引用、展开、写入与关联。会话不可用时不提供跳转；写入显示
  「当前仍可核对 / 该位置已变更 / 该次修改已撤回」。
- 「用于写作」：有脏稿先保存，再真正打开目标章节，然后带固定修订与目标路径走普通写作
  用途提交。模型未连接或已有一轮在跑时按钮禁用并说明原因；受理失败时面板保留选择与草稿。
- 「打开正文」与「打开讨论」都会先确认目标真的能打开，再收起面板跳到写作页。
