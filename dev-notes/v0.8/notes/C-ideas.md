# C：灵感本（条目服务与作品接口）

日期：2026-10-24。目标：让作者在不调用模型的情况下记录、修改、删除与恢复灵感，
并且这些操作有稳定的修订历史与明确的冲突边界。本阶段交付后端闭环；顶栏入口、
参考 chips 与 agent 工具分别在下一段前端与 F 阶段接入。

## 实际改动

### 条目与修订（`workspace/ideas.py`）

- 一条灵感一个 JSON 文件，放在作品 `灵感本/` 下：头指针、修订数组、来源、使用定位与请求键
  在同一文件内一次原子替换。
- 编辑、删除、恢复都**追加修订**，不移动指针、不删后续历史；恢复某个删除修订时保持删除状态，
  恢复删除前的修订才回到可用内容。
- 编辑要求 `expected_digest` 与 `expected_revision`；任一不符返回 `IDEA_STALE_CONFLICT`，
  文件保持原样。同一条目的并发修改串行化，后到者拿到冲突而不是覆盖。
- 请求键先于冲突检查：同键同内容重放上次修订，同键不同内容返回 `REQUEST_KEY_CONFLICT`；
  新建也按请求键去重，网络重试不会多出一条灵感。
- 标题可空，正文必填；正文上限 20,000 字符、标题 200、标签 20 个。超限直接拒绝，不截断保存。
- 主文件无法解析时返回 `IDEA_STORE_INVALID` 并保留原字节；列表把损坏文件计为 `invalid`，
  不因此隐藏其他条目。
- 使用定位 `add_use`：`author_link` 只需作者明确关联；`applied` 必须对得上目标正文当前的
  指纹、区间与引文，防止把助手自述当成「已落实」。
- 每条灵感一把线程锁加锁文件；不占用作品模型任务锁。

### 接口（`workspace/ideas_api.py`）

| 接口 | 行为 |
|---|---|
| `GET /api/file-workspaces/{id}/ideas` | q／deleted／cursor／limit；只返回摘要与 head |
| `POST …/ideas` | 新建；可带来源（角色、会话、消息序号、短引文） |
| `GET …/ideas/{idea_id}` | 当前修订、指纹、来源与使用定位 |
| `PATCH …/ideas/{idea_id}` | 编辑；必须给 expected_digest 与 expected_revision |
| `POST …/ideas/{idea_id}/trash` | tombstone 修订，同样核对版本 |
| `POST …/ideas/{idea_id}/restore` | 指定历史修订，以旧内容创建新 head |
| `GET …/ideas/{idea_id}/revisions` | 修订元信息分页，不返回全部正文 |
| `GET …/ideas/{idea_id}/revisions/{revision_id}` | 单条历史修订的完整内容 |
| `POST …/ideas/{idea_id}/links` | 作者关联或核对后的落实位置 |

`server/file_app.py` 挂载这组路由；它不引入模型依赖，也不改任何正文文件。

## 数据与边界

- 灵感目录不在 `files.py` 的受管路径内：`read_file`、目录与搜索都拿不到它；作品 Git 只提交
  正文与设定集，灵感不会进入版本记录。
- 来源只保存定位与短引文；来源会话被删后，笔记正文仍然可读。
- 恢复灵感不改正文：用例在恢复前后比对章节字节。

## 取舍

- **一条灵感一个文件**：编辑与历史一起原子替换，不需要「正文存了、历史没存」的补偿；
  代价是单文件随修订增长，用 5,000 条修订上限与分页读取控制。
- **请求键先于冲突检查**：网络重试时指纹已经变了，先查键才能把重试认成同一请求。
- **冲突不合并**：两处同时修改保留各自输入，由作者决定；系统不猜哪一版更好。
- **恢复是追加**：历史只增不减，误恢复还能再选一次，不需要回滚文件。
- **agent 权限靠结构隔离**：普通文件工具没有路径可达灵感；专用读取工具在 F 阶段接入前，
  不宣称模型可以读灵感。
