# Phase 19 开发计划：常驻对话侧栏与显式创作周期

> 状态：主体交付，代码审查缺陷已修复（2026-10-16），真模型 A13 仍待验收；本文保留验收目标，交付证据见 [审查修复记录](../phase-19-review-fixes.md)。
> 依据：作者要求主页面保留 chatbox，正常对话支持流式输出，只有明确触发 Harness 创作任务才进入创作周期；以前端交互设计驱动后端开发。
> 前置：Phase 16 的持久任务/候选/审阅、Phase 17 的七页工作台、Phase 18 的模型接入。
> 本文中的 Harness 指产品上的创作执行周期。普通聊天即使复用底层模型适配器，也不因此获得创作任务或领域写入能力。

## 1. 产品目标与交付边界

让作者在同一工作台完成「讨论构想 → 发起有范围的任务 → 查看过程 → 审阅候选 → 接受正式内容」。聊天始终可用，正文、账本与修订页面继续承担正式内容的查看和编辑。

交付后的三个可观察边界：

1. **普通发送只进行对话**：逐步显示回复，支持多轮、停止、重试、历史恢复；不会创建创作 Job，也不会初始化仓库 Commit。
2. **明确启动才进入创作周期**：通过任务建议卡的「开始」或带明确目标的页面操作提交；记录目标、输入版本、范围和模型。
3. **候选经作者接受后生效**：任务结束不等于内容已保存；沿用现有版本与审阅规则，不由聊天文本代替审批。

### 1.1 本阶段包括

- 七页共用的右侧对话栏，桌面可调整宽度/收起，窄屏可独立打开；
- 项目内多会话、新建、历史切换，服务端保存消息与回复状态；
- 真正的模型增量输出、停止、故障提示、重试和断线重连；
- 章节、账本对象、选中文字的显式上下文引用；
- 规划、章节起草、检查、定向修订四类创作入口；
- 侧栏任务卡与现有任务、变更、审阅页面联动；
- 当前模型的复用、每轮/任务执行的模型记录，以及本地模型验证；
- 前端模拟场景、契约测试、端到端验证与真模型走查。

### 1.2 本阶段不扩展

- 不重建既有仓库、工作流、Patch 和提交服务；
- 不恢复 V1 slug 会话、旧写工具和工作区迁移；
- 不做后台无限自动创作、无人审批的连续整书生成；
- 不做聊天分支树、任意历史消息编辑、跨项目全局聊天、账号协作；
- 不引入新的订阅登录方式，继续使用已交付的 API / Coding Plan / 本地模型连接；
- 不自动把对话推断为作者长期偏好或故事事实。

## 2. 现状与差距

| 现有能力 | 本阶段处理 |
|---|---|
| `App.tsx` 统一壳、七个业务页面 | 在页面路由外挂常驻侧栏，切页不销毁会话 |
| 创作台自身已有多个侧面板 | 收拢角色任务表单与辅助信息，避免变成四列拥挤布局 |
| `AgentTasks.tsx` 提交角色任务、列出候选与操作 | 提取任务卡/详情/审阅能力，复用为聊天内卡片与任务中心 |
| `/coordinate` 用关键词选择用例 | 保留其内部用途，普通聊天不直接调用它执行任务 |
| V2 Job 持久化、取消代际、恢复和审阅 | 作为创作执行事实源；聊天只持有稳定引用 |
| `/ws/v2/{project_id}` 推送 Commit 业务事件 | 保持业务含义；新增聊天流不混用其 sequence |
| Job 进度经 REST 查询 | 第一版继续复用，按活动任务刷新；不为聊天重建一套任务总线 |
| ProviderBook 共享当前模型 | 聊天和任务都从这里解析；补齐任务模型快照与可观测性 |
| 当前每次 worker 调用解析模型 | 多步骤创作周期需补充固定模型规则，不能把现状误写成整个周期已固定 |

## 3. 页面与交互规则

### 3.1 页面结构

```text
顶部：项目切换 / 搜索 / 当前模型 / 设置 / 对话栏开关
导航：概览 · 创作台 · 账本 · 变更 · 审阅 · 审计 · 作者模型
┌────────────────────────────────┬────────────────────────┐
│ 当前业务页面                    │ 对话标题 / 历史 / 新建  │
│ 正文、设定、计划或审阅结果        │ 连续消息与任务卡        │
│                                │                        │
│                                │ 上下文引用              │
│                                │ 输入框                  │
│                                │ 发送 / 创作操作         │
└────────────────────────────────┴────────────────────────┘
底部：项目版本 / 正文保存状态；连接状态按对话、任务分别显示
```

- 桌面默认右栏约 380px，可在合理范围调整；主区不足以编辑正文时切为覆盖面板，不硬挤多列。
- 右栏只保留一个输入框；原「协作主编」角色选择表单退出主流程，任务能力迁入创作操作与详情。
- 创作台保留章节导航和必要编辑信息，次要说明改成可折叠区。七页各做一次宽度检查。
- 沿用现有视觉风格和组件，不在这个阶段另起一套主题。
- 无项目时展示新建/选择项目指引；第一版聊天归属于项目。
- 收起侧栏、切页、切会话不停止后台响应；显示未读/活动状态，重新打开能接上。
- 窄屏通过顶栏按钮打开完整对话面板；关闭后返回原页面和滚动位置。

### 3.2 输入框

- 普通「发送」固定为聊天。桌面 Enter 发送，Shift+Enter 换行；中文输入法组合输入期间不发送。
- 发送前显示已附加的上下文；可删除、展开查看。页面切换不会悄悄替换已附加引用。
- 流式输出期间显示「停止回复」，下一条草稿仍可编辑；同一会话第一版不并发发送两轮。
- 第一版以明确错误与手动重试为主，不做可能重复收费的静默模型重发。
- 新建会话不携带其他会话的上下文或草稿；切回时恢复各自输入草稿。
- 模型标签来自服务端当前选择；发送后，消息显示本轮实际模型。切换影响后续发送。
- 用户阅读较早消息时不强制滚到底部，显示「有新回复」入口；接近底部时跟随输出。流式朗读提示节流，键盘能到达发送、停止、历史和任务操作。
- Markdown 允许代码、列表与引用，禁用模型输出的原始 HTML；任务按钮由结构化数据渲染，不能来自回复中的任意链接或伪造控件。

### 3.3 消息、建议与正式结果

| 类型 | 展示 | 能产生的业务动作 |
|---|---|---|
| 普通消息 | 流式文本、引用来源、实际模型、失败/中断状态 | 继续讨论、复制、基于回复准备任务 |
| 任务建议 | 目标、类型、范围、依据、缺失项 | 调整、开始、放弃；建议本身不创建 Job |
| 执行任务 | 阶段、状态、实际模型、结果入口 | 查看、取消、失败后重试 |
| 待审阅候选 | 摘要与正文/差异入口 | 跳转审阅，沿用接受/拒绝/部分接受规则 |
| 已接受结果 | 正式版本与目标对象链接 | 打开正式内容；以 Commit 回读为准 |

“帮我写第一章”在普通发送中可以产生任务建议，不直接启动生成。已经明确指定目标的「生成本章节草稿」按钮可直接提交，不再重复问一次同样的问题；缺少必要参数时先补齐。

任务建议必须是受限结构的数据。支持工具调用的模型可通过仅能提出建议的工具返回；不支持或输出无效时继续普通文本回复，保留输入框的创作操作入口。不得靠匹配“已经开始”等自然语言启动任务，也不让模型产生可直达写入的任意命令。

### 3.4 上下文

- 页面可以推荐「当前章」「选中人物」引用，只有作者添加后才进入本轮请求；后续可以增加可见的默认引用，但不做隐式整页注入。
- 已保存内容使用项目 ID、对象 ID、Revision/Commit 引用，构建本轮上下文时记录实际版本。
- 编辑器未保存内容仅在作者明确「引用选中文本」时以一次性摘录附加，标明未保存；不把整个编辑缓冲静默传入。
- 对话可讨论摘录；要据此生成可接受 Patch，必须先保存或绑定可验证的基础版本。
- 任务启动前检查引用和基础版本；过期引用提示重新读取/重建任务，不静默换用新内容。
- 会话历史按预算裁剪，保留最新指令与明确引用，记录 omissions；摘要只是对话辅助，不成为故事事实。

## 4. 两条独立状态流

### 4.1 对话轮次

```text
准备发送 → 排队 → 回复中 → 完成
                    ├→ 已停止
                    ├→ 失败
                    └→ 已中断（服务退出或无法继续）
```

- 用户消息与 turn 在同一事务创建，返回稳定 ID 后才消费流；丢失 HTTP 响应可以通过幂等键找回。
- “连接断开”是连接状态，不直接把模型执行标记成失败。网络恢复后读取同一轮的事件与快照。
- 停止是服务端取消操作，不只是前端关闭连接；已收到内容保留，迟到分片不能复活已停止轮次。
- 重试创建新的 attempt/turn，链接原失败轮次，不覆盖旧回复；同一幂等请求重发不能多次调用模型。
- 默认重试使用原轮次的模型绑定；要使用新模型则明确选择「用当前模型重新回答」，创建新尝试并显示模型变化。
- 刷新时优先读服务端终态与已保存文本；已中断轮次不自动重新调用模型。

### 4.2 创作任务

```text
讨论 → 任务建议 → 明确开始 → 排队/执行 → 候选待审阅 → 作者接受 → 正式内容
                         ├→ 需要补充
                         ├→ 合法空结果
                         ├→ 失败/取消
                         └→ 检查报告（不改正文）
```

- 上述为产品显示状态；后台仍使用现有 Job/Change 状态，建立映射，不新增同义但独立可写的任务状态机。
- “已生成”“待审阅”“已接受”分别显示；只有取得 Commit 及回读结果才显示正式生效。
- 点击停止回复不取消已有创作任务；任务卡有独立「取消任务」。
- 任务运行时仍可聊天，但补充讨论不修改正在执行的目标。新要求另建建议或在允许的检查点补充，范围变化走既有重新分析/批准规则。
- 第一版同一项目至多一个由本入口启动的活动创作周期，其他明确提交进入可见队列；同章多候选接受仍受版本冲突守卫约束。调度规则在服务端落实，旧提交入口同样遵守。
- 等待作者审阅不占用模型执行槽；已有修订依赖/批准规则继续有效。

### 4.3 创作周期如何复用既有工作流

| 作者操作 | 进入路径 | 停止点 |
|---|---|---|
| 规划故事/章节 | 现有 planner Job | StoryProposal 待接受 |
| 生成章节草稿 | 有可用计划时进入 writer Job；缺少计划则先规划 | 规划/正文分别审阅，不默认连环接受 |
| 检查人物知情或线索 | 现有 auditor / 审计用例 | Finding/空结果，不自动修复 |
| 修改设定并修订正文 | 现有 Change Set → 影响分析 → 批准 → 修订 | 范围确认、Patch 审阅与提交 |

创作周期先作为现有 Job/Change 及结果引用的聚合视图。第一版不实现任意工作流图，也不再造一个调度内核。若需要多步骤，步骤通过现有用例衔接并保留作者检查点。

## 5. 前端先行的执行顺序

按 19.1 → 19.2 → 19.3 → 19.4 → 19.5 → 19.6 顺序推进。每一步均有可演示结果和退出条件；阶段 19.1/19.2 使用模拟数据，不要求先实现全部后端。

### 19.1：页面壳与可交互原型

**交付**

- 在全局壳加入侧栏、拖动宽度、收起入口、窄屏布局；
- 实现会话标题、消息列表、输入框、引用条、任务建议卡、执行卡、结果卡的展示；
- 用可控模拟器演示逐段回复、停止、错误、任务推进、待审阅和接受后回读；
- 调整概览和创作台现有侧面板，保留正文主要空间；
- 形成可逐项走查的场景清单与截图。模拟模式只能在开发/测试入口启用，生产界面不展示虚假成功。

**退出条件**

- 从构想到候选审阅可以在前端完整走通；
- 切七页、开关侧栏、输入法发送、滚动、窄屏都能使用；
- 作者能从文案区分聊天、任务和正式内容；
- 每个按钮的前置条件、状态和错误处理明确后，才冻结下一步接口。

### 19.2：前端状态与公开契约

**先写失败测试**：跨项目晚到事件不能污染当前界面、同一分片去重、停止后迟到分片无效、切页保留输入、模型切换不改已有轮次标签。

**交付**

- 独立 `chat` 状态：按 project/conversation/turn 索引；不把流式消息塞入正文缓冲；
- API 类型、错误类型、状态 reducer 与模拟实现；
- 会话加载/空历史/读取失败/发送结果未知/回复断线的清晰界面；
- 输入草稿和面板宽度可存浏览器；消息事实、任务状态以服务端为准；
- API 协议版本/能力检查：缺少新版端点时显示重启后端指引，避免再出现空列表和无声失败。

**退出条件**：前端可用同一套组件切换模拟服务与真实 API；契约覆盖重连、取消、幂等和错误路径，不只定义成功返回。

### 19.3：V2 对话存储与真实流式服务

**先写失败测试**：聊天不产生创作 Job/Commit；项目隔离；发送幂等；取消竞态；部分回复保留；重启中断标记；Provider 失效不跨厂商回退。

**交付**

- 会话/消息/轮次/事件的服务端存储、增量建表和应用服务；
- 通过现有 ProviderBook 解析模型，独立的 ChatRunner 端口接入现有流式 Provider；
- 单纯聊天默认没有领域写工具，不挂载 V1 Hastings 工具；可见引用由只读上下文服务准备；
- 模型文本边接收边推送，事件批量持久化后发布，不能拿完整回复做前端假打字；
- 同一会话单轮执行、全局有界并发、服务退出清理、资源释放；本地模型的排队与较长超时；
- 为每轮设置上下文、输出长度、首段等待和总时长上限，具体值按本地/云端配置并记录；不因 SSE 心跳不断而无限执行；
- 明确区分无正文结果、用户取消、授权失败、连接失败和超时；不显示内部推理文本；
- 持久化流中已确认的部分回复与实际模型信息，启动后把遗留运行轮次标为中断，不自动重发。

**退出条件**：国内兼容 API / 本地模型均能在侧栏完成真实多轮增量对话，停止后服务端调用终止；刷新可恢复已落盘内容。

### 19.4：上下文引用与任务准备

**先写失败测试**：引用不能跨项目；草稿不自动附加；建议无执行权限；任意文本不能触发 Job；过期版本不能直接开始。

**交付**

- 章节/人物/选文添加到对话，消息显示使用的实际版本与省略情况；
- 定义受限 TaskDraft：类型、指令、目标、基础版本、上下文、缺失项；
- 输入框创作操作、消息「准备为任务」、可选的模型结构化建议都进入同一 TaskDraft；
- draft 能查看和调整，开始按钮在范围齐全时可用；模型不支持结构化建议时仍可用显式操作；
- 无可用计划、没有章节目标、未保存摘录、模型未配置等情况给出具体解决入口。

**退出条件**：讨论中的任何输出都不会自行进入创作；作者可以把讨论上下文带入一个可检查、可启动的任务。

### 19.5：接入创作周期、任务卡与结果审阅

**先写失败测试**：重复开始只产生同一任务；启动响应丢失可找回；等待审阅不自动接受；部分接受保留未接受差异；任务取消后迟到输出无效；切模型不改变已启动任务。

**交付**

- TaskDraft 显式启动服务映射到现有 planner/writer/auditor/Change 用例；
- 同一请求绑定 TaskDraft 修订、幂等键、Job/Change ID，处理「任务已建但卡片未关联」的重启恢复窗口；
- 页面按钮与侧栏共用启动服务，不因入口不同产生不同授权或调度规则；
- 任务卡仅投影实际 Job/Change/Commit，不维护另一份执行真相；
- 提取现有任务展示与操作，清理重复表单，旧详情入口仍能定位同一任务；
- 点击候选打开主区预览/审阅；已有未保存稿时先按现有规则处理，不能为导航静默丢弃；
- 每个任务持久化 provider 连接 ID/model/协议快照，密钥通过配置解析，不进入消息/事件；重试保持已绑定模型，改模型作为明确的新尝试；
- 多步骤周期沿用启动时的模型选择；来源失效明确失败，不静默换厂商。凭证撤销仍应生效，不把密钥永久复制到任务；
- 新建会话不影响现有任务；任务有稳定入口，历史聊天仍能打开结果。

**退出条件**：真实完成「讨论 → 规划候选 → 接受 → 起草 → 人工编辑 → 检查 → 设定变化 → 修订审阅」，每一步正式变更都能定位 Commit；取消与重启不造成重复提交。

## 6. 为前端服务的后端契约草案

以下是 19.2 的冻结起点，若原型证明信息不足，应先改前端场景与契约，再实施存储。路径前缀统一为 `/api/v2/projects/{project_id}`。

### 6.1 数据职责

| 对象 | 最小信息 | 权威来源 |
|---|---|---|
| Conversation | ID、project_id、标题、创建/更新时间 | 新对话存储 |
| Message | ID、conversation_id、role、正文、引用、关联 turn | 新对话存储 |
| ChatTurn | ID、幂等键/输入指纹、状态、provider/model、结束原因、generation | 新对话存储 |
| ChatEvent | conversation_id、sequence、turn_id、type、payload | 新对话事件日志 |
| TaskDraft | ID、修订、类型、范围、依据、缺失项、来源消息、启动关联 | 新任务准备服务 |
| 创作周期视图 | 来源 draft、Job/Change/Proposal/Commit 引用及投影状态 | 现有任务与领域服务 |

对话数据作为项目辅助数据落在现有 V2 SQLite 的独立表中，不为每条聊天生成 Repository Revision。版本化故事内容仍由 CommitService 管理；会话和任务之间使用稳定 ID 关联。

新建但尚无首个 Commit 的项目也能正常聊天；上下文为空是合法状态，不为聊天初始化创作仓库。服务端完整数据库备份包含对话；现有故事内容导出包第一版维持原范围，界面/文档明确不包含聊天历史，避免让作者误以为项目导出等于完整应用备份。

### 6.2 API

| 方法与资源 | 行为 |
|---|---|
| `GET/POST /conversations` | 分页列举/新建项目会话 |
| `GET /conversations/{cid}/messages` | 分页历史，带活动轮次、任务引用和快照游标 |
| `POST /conversations/{cid}/turns` | 接收消息、引用、幂等键，原子创建轮次；返回稳定 ID，后台执行 |
| `GET /conversations/{cid}/events?after=N` | SSE 增量/补齐，带 sequence；重新订阅不重复调用模型 |
| `POST /conversations/{cid}/turns/{tid}/cancel` | 幂等停止服务端当前轮次 |
| `POST /conversations/{cid}/turns/{tid}/retry` | 创建关联的新尝试，使用新的明确请求键 |
| `POST /task-drafts` | 创建可检查任务建议，不创建创作 Job |
| `PATCH /task-drafts/{did}` | 带预期修订修改建议，防多标签覆盖 |
| `POST /task-drafts/{did}/start` | 带预期修订与幂等键显式启动，返回已绑定任务引用 |
| 现有 `/agent-jobs`、`/changes`、审阅接口 | 查询/取消/恢复/接受等保持现有领域规则 |

API 以应用服务为边界，接口层不直接操作数据库或模型。会话列表/消息可分页；任务引用通过现有详情查询，避免每次重载整本故事。

### 6.3 流式事件

- 采用独立 SSE 读取通道：请求提交和事件消费分开，便于刷新后补齐；现有业务 WebSocket 保持原用途。
- 最小事件：`turn.accepted`、`turn.started`、`message.delta`、`message.completed`、`turn.cancelled`、`turn.failed`、`turn.interrupted`、`task.draft.created`、`task.linked`。
- 统一信封包含 `project_id/conversation_id/turn_id/sequence/type/payload`。事件序号仅在会话内递增，与 Job 和业务 Commit 游标分别管理。
- 流结束事件包含完整正文或内容校验信息和结束原因；前端不能以 TCP 关闭推断模型成功。
- 先持久化后推送；分片合并写入控制频率，终态先冲刷尾部。正文快照与游标一致，快照之后只追加更高序号。
- 客户端去重并检测序号缺口；重连只消费同一轮，重放不创建新轮。日志裁剪后返回明确「需要重新读取快照」。
- 心跳只证明连接存活，不伪装模型进度。长时间无正文显示等待与本地模型提示，不生成虚假百分比。
- 客户端断开后服务端在本轮时间/输出预算内继续；用户停止走取消接口。进程退出不保证继续生成，只保证保存内容可恢复且状态准确。

### 6.4 错误与约束

- 错误统一提供稳定 code、where、why、fix；区分输入违规、合法空结果、环境故障、版本冲突。
- 典型错误：模型未配置、凭证失效、本地服务未启动、输出超时、会话忙、引用越界、基础版本过期、重复键输入不同、任务缺少必要目标。
- 所有 conversation/message/turn/task-draft/job 引用都验证项目归属；项目 ID 是隔离范围，不新增虚假的账号授权概念。
- 普通聊天运行器拿不到提交端口；任务开始端口也不能绕过已存在的批准与写入守卫。
- 普通聊天不自动提取持久作者偏好；需要保存时进入已有显式声明入口。
- 模型凭证仅由服务端读取，流、日志、浏览器持久化和任务快照均不包含 Key。

### 9.2 主要风险与处理

## 10. 开发中的 Agent 设计检查点

这不是完成后的经验结论，而是各子阶段必须保留的设计问题；实际结果写入阶段构建笔记。

1. **错误消息作为模型 API**：引用过期、缺少章节、无可用计划是否说明哪里错、为什么、怎样继续？自然语言解释是否有稳定错误码支撑？
2. **硬约束在工具层**：纯聊天是否拿不到写端口？建议是否只能生成 TaskDraft？启动、批准、版本检查是否由应用服务强制？
3. **泄压阀**：模型无法建议任务、检查无发现、本地服务不可达是否是三个可区分的状态？是否容许合理的空结果？
4. **可观测性属于事件契约**：每条消息能否追到实际模型与轮次？每个任务卡能否追到 Job/Change/Commit？断线、取消、重试是否保持清楚的身份和终态？
