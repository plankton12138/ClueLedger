## 交付内容与关键决策

| 审查问题 | 修复后的行为 |
|---|---|
| 缺失项对象导致渲染崩溃 | 展示结构化原因与解决办法，兼容历史模拟器文本 |
| 起草/检查没有可补齐的范围 | 建议显式列出章节、已接受节拍或检查对象；调整表单可选择范围；未选节拍时开始禁用；允许为新章准备正文 |
| 执行卡丢失、终态不显示 | 建议与执行消息分别持久化；Job 状态投影为 `task.updated`，刷新与实时流读取同一份卡片 |
| 停止只冻结界面 | 先收束轮次，再取消后台任务、释放 Provider 连接和执行槽，等待首段时同样生效 |
| 引用只有标题 | 服务端校验归属与版本，读取真实正文/对象内容并登记实际版本；过期引用明确冲突，不静默替换 |
| 候选不能在主区预览 | 按 Job 身份读取完整候选，复用现有候选展示；预览不清除编辑缓冲，有未保存稿或正在保存时禁止接受 |
| 新项目规划被正文前置阻断 | 显式开始规划时才初始化创作工作流基础版本；普通聊天不创建 Commit |
| 从消息准备任务丢失要求 | 源消息正文进入 instruction，明确附加的引用带入任务上下文 |
| 重试静默切换模型 | 轮次保存无密钥的来源/模型/协议快照，默认重试沿用该绑定，来源失效明确失败 |

配套收口：

- 同一建议修订的启动请求保留稳定幂等键，响应丢失后重试不会生成另一个键；
- 定向修订打开既有 Change Set，并提供侧栏到对应变更的入口，保留分析、批准和差异审阅检查点；
- 同项目创作 Job、旧运行入口和 Agent 修订共用执行锁；等待作者审阅不占执行槽；
- 旧任务入口同样在提交时捕获模型绑定，聊天发起的变更把绑定传入后续修订步骤；
- 未修改 `tau_agent` / `tau_ai`；新增数据字段位于既有 JSON 记录中，老记录仍可读取。

## Agent 设计经验

### ① 错误消息是喂给模型的 API

缺失项需要以同一数据形状穿过后端、事件和界面。只有服务端拥有三要素还不够，
界面必须能展示它们；“已有计划”和“已选择本章节拍”也应分别反馈，避免按钮
显示可开始、实际调用却被另一层守卫拒绝。

### ② 硬约束放工具层，prompt 只负责解释世界

引用解析、模型绑定、后台取消、同项目串行和未保存稿保护各自落实在负责该边界的
服务或状态层。模型说“读过章节”不能替代实际读取，文本冻结也不能替代关闭调用。
定向修订只创建变更意图，不能越过既有批准和提交规则。

### ③ 泄压阀：区分违规、空结果、环境故障

引用过期要求重新添加引用；任务范围不齐要求调整建议；Provider 来源失效要求恢复
来源。它们不能靠自动换模型或假装任务已完成来消解。检查无发现仍沿用合法空结果，
失败与取消则投影为可见终态。

### ④ 可观测性是事件契约的一部分

任务卡必须同时有稳定身份、可恢复快照和状态变化事件。建议消息与执行消息共用 ID
会被正确的去重逻辑吞掉。浏览器测试必须穿过真实服务契约，否则模拟器中一致的两端
会掩盖生产接口的不一致。
