# 设计说明：architecture_version 用例路由开关（Phase 11 T11.6）

- 状态：已接受（2026-10-14）
- 关联：[DESIGN.md §11](../DESIGN.md#11-旧系统迁移边界)、[ADR-001](ADR-001-sqlite-repository-as-single-source-of-truth.md)

## 1. 问题

迁移期（Phase 12–17）旧 V1 写路径与 V2 用例并存。必须保证：同一项目始终走同一条写路径，绝不出现按请求、按会话或按重启随机切换；也不能让 Feature Flag 承担权限语义（plans/README.md §4 红线）。

## 2. 决定

### 2.1 开关粒度：项目级静态属性

`architecture_version = v1 | v2` 是**项目级元数据**，不是全局配置、不是用户偏好、不是请求参数：

- 存放位置：项目元数据由项目注册表（server/registry.py 的现有职责）扩展承载；V2 项目在创建/导入时确定并落盘，一经写入，普通运行期不可更改；
- 迁移（v1 → v2）只允许通过 Phase 17 的显式导入操作完成，完成即不可逆（防止双写窗口）。

### 2.2 路由规则

```text
请求进入 interfaces 层
  → 解析目标项目 → 读 architecture_version
  → v1：走现有 V1 用例（工具、reconcile、文件写入），行为零变化；
  → v2：只允许调用 V2 用例（命令 → 守卫 → Commit Service → Outbox）；
  → 缺失元数据的既有工作区：默认 v1（对齐"缺文件按兜底值处理"的 V1 惯例）。
```

判定点收敛在项目解析这一处（现有 `_workspace(slug)` 的同级位置），不得散落到各用例内部各自判 flag。

### 2.3 不变量

1. **无混合写路径**：一个项目的所有写操作要么全 V1 要么全 V2；禁止同一事务/会话内混用；
2. **开关不承担权限**：它只回答"走哪套用例"，谁能批准写什么由 V1 阶段状态机 / V2 Approval Receipt 各自负责；
3. **无部分切换**：不存在 `v1_with_v2_writing` 之类的中间态；一个项目要么完全 V1，要么完成 Phase 17 导入后完全 V2；
4. **可判定可测试**：`resolve_architecture_version(slug) -> Literal["v1", "v2"]` 是纯函数式的解析点，测试直接构造元数据断言路由结果，不需要起服务。

## 3. 明确不采用

- 环境变量/全局 Feature Flag：跨项目污染，重启期间可能翻转，且容易被误当权限用；
- 请求级参数（如 `?arch=v2`）：同一项目可被随机切换，制造双写窗口；
- 按实体级混合（Bible 走 V2、正文走 V1）：破坏版本与依赖图完整性，Phase 15 影响分析无法成立。

## 4. 重新评审条件

- Phase 17 导入被证明需要分批迁移超大型项目（如 100 章）时，可评审"只读期灰度"方案——但写路径单一的原则不变；
- 出现需要同一项目长期双轨运行的需求时，本设计作废并重新立项。
