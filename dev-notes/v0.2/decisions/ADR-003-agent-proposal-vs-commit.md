# ADR-003：Agent 只产出 Proposal，与 Commit 严格分离

- 状态：已接受（2026-10-14）
- 关联：[DESIGN.md §8.1](../DESIGN.md#81-工作者)、[guard-authorization.md](../modules/guard-authorization.md)

## 上下文

V1 中 Agent 通过工具直接写工作区文件（`bible_upsert`、章节写入工具），写入即生效，靠事后守卫和 reconcile 补救。模型输出一旦被工具接受，就成为"事实"，覆盖保护只能拦截部分情况，且无法回答"这次写入依据的是哪个版本"。

## 决定

Agent 不直接写数据库或文件。工作者（策划、撰写、修订、审计、观察）返回带 `base_revision_id`/`base_commit_id` 和目标范围的结构化 Proposal/Patch。应用层统一验证：版本检查 → 范围检查 → 领域不变量 → 作者审批 → 原子提交。Agent 的"完成"只表示 Proposal 已生成，绝不作为提交证据。`tau_agent` 可继续作为执行外壳，但不拥有领域状态或授权状态。

## 后果

- 越权、过期、超范围输出在提交前被拦截，错误信息可以三要素回喂模型修正；
- Agent 测试可以断言 Proposal 结构而非自然语言；
- 增加一层转换：每个工具输出需要定义 Schema，模型格式错误需要明确的失败分类（违规 / 合法空 / 环境故障）。

## 替代方案

- 保留"工具写入即生效"+ 事后 reconcile：交互延迟低，但覆盖与分叉问题无法根除，授权无法绑定具体变更；
- Agent 直接调用领域命令但绕过审批：等于没有授权模型，作者决定权（P1）失效。

## 触发重新评审的条件

- 某类交互被证明必须低延迟直写（如纯格式化操作），可为该窄类操作单独立项开直通通道，但默认仍是 Proposal 路径；
- Proposal Schema 复杂到模型稳定输出失败率过高时，优先改进 Schema 与错误回喂，而非放宽本决定。
