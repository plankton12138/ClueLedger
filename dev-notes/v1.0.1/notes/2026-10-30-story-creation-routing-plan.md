## 目标与边界

作者在构思区明确要求建立或修改创作结构时，线索、事件节点、调查推进和关系应进入当前方案。作者讨论方案时可以只在对话中得到建议；模块可用于承载补充资料，创作结构中的决定以结构数据为有效来源。作者无需了解内部工具名称。

此次会话已提供构思上下文，模型读取到空方案，并获得结构写入工具；随后它登记了两份模块内容并保存，未提交结构。现有空白方案输入被省略，通用提示仍要求将线索保存为模块，任务正常结束时没有检查实际结构提交。日志没有保存完整模型请求，提示冲突是结合当前代码与行为得出的原因分析，不能证明模型内部的决策过程。

两份已保存模块含实际创作内容，可能包含模型主动提出、仍待作者确认的调整。本计划不自动导入、删除或改写用户作品，也不把模块中全部内容视为作者已确认的真相。后续由作者明确要求时，再按来源和授权范围整理；本轮不考虑旧数据迁移。

## 设计原则

1. **区分页面与意图。** 当前构思页普通对话都携带 `purpose=design`，它表示工作语境，不能单独证明作者要求保存。讨论、比较、建议及明确暂不保存保持只读；明确提出建立、写入、修改时才形成结构写入目标。“用这个”“写入构思”须结合可定位的上一条候选，不能从历史中任意选方案。
2. **以实际提交为依据。** 写入目标、已完成单元和收据分别记录。已提交但只完成部分要求时保留成果并报告未完成项；暂停、冲突或模型未提交不能宣称完成。合法的无改动结果需有可核验依据，不能仅凭模型说“已存在”通过。
3. **保留授权与作品边界。** 保持方案、修订、节点范围、真相和约定授权检查；对引用、转述、问题和讨论不授予写权限。需要真实选择而无法定位时提出具体问题，不由模型扩大授权。
4. **不强制模块与结构同时保存。** 正常构思直接提交结构。明确要求附加资料时才考虑模块；若同一任务确需两类写入，分别报告提交结果，不能把模块成功当作结构成功，也不能承诺尚未实现的跨存储原子性。

## 实施步骤

### 1. 固定可复现的任务契约

涉及 `frontend/src/state/conversations.ts`、`workspace/materials.py`、`workspace/service.py`、`workspace/story_authorization.py` 和操作记录。

- 保留当前方案与修订冻结；在受理时增加可追溯的目标记录，区分讨论、明确结构修改、明确模块修改和待澄清。目标必须关联作者原话及必要时的候选来源，不把模型自行登记的范围当成作者授权。
- 对“先讨论、再说写入构思”的连续轮次，识别上一轮候选及本轮确认范围；存在多个无法区分的候选时提出问题。以真实会话文本作为回归样例，不要求在产品中使用固定关键词或模板。
- 让任务目标与授权保持分离：目标用于判断是否完成，授权继续限定可以修改什么。已有 `design` 语境、节点选择、只读标记和作者原话共同参与判断；未确定时不能自动开放额外写权限。
- 明确合法无改动的记录：目标对象、当前方案与修订、实际读取内容及为何无需修改。不能仅通过对象数量或事件存在推断语义完成。

验收：讨论不写入；明确写入候选时能定位来源；无可定位候选和相互冲突的要求进入待回答；引用中的命令不变成授权；选择的备选方案不污染主方案。

### 2. 修正模型输入与工具选择

- 根据任务语境区分通用资料与构思结构，移除“所有线索和真相都保存为模块”的无条件指引。明确要求构思时，以方案内线索、节点及关系表达；明确模块任务仍保持原有行为。
- 空白方案也输出简短、实际发送的构思语境：当前方案为空，允许从已授权的内容建立结构，未决定的真相保留未定。记录实际输入及其方案修订，而不是只在界面显示提示。
- 提供与现有数据契约一致的小型示例，说明一项线索如何在节点呈现并连接后续调查。下列为结构操作示意，实施时通过现有校验和提交接口验证，ID 由实际任务分配：

- 检查 `prepare_module_changes`、`apply_module_changes` 与 `update_story` 并存时的指引和收尾规则。两种存储的提交资格应一致受暂停和任务状态保护；若支持同轮分别提交，明确顺序、失败恢复和各自撤销，不将现有模块收尾机制直接当成跨存储事务。

验收：实际请求可看到空方案指引；构思任务与模块任务各自使用正确目标；已有结构的读取和范围保护不退化。

### 3. 根据提交收据判定完成

涉及 `workspace/story_tools.py`、`workspace/service.py`、`workspace/operations.py` 及事件契约。

- 为任务记录目标方案、基础修订、预期成果和各完整单元的实际收据。`story_changes_committed` 事件目前只有操作数量，需通过可靠的变更记录或扩展收据读取具体对象及变更类型，不能只用“有一个提交事件”判断所有目标已完成。
- 任务结束时核对当前代次、方案身份、收据和预期目标；模块保存不满足结构目标。部分完成用现有 `partial` / `needs_attention` 机制标明已保存与未完成；确实需要作者决定时使用 `needs_input`；失败和暂停沿用现有状态及代次保护。
- 语义完整性不能只靠计数保证。程序确认实际对象、关系和提交范围，语义检查结合本次任务要求报告具体缺口；无法确定时保留结果并明确说明，不自动补造真相或反复调用模型。
- 将结构工具与模块工具的收尾、暂停及提问资格检查统一审查：目前模块的 `finalizing` 检查和结构工具的代次检查是不同路径，需要明确两者的交互并覆盖竞态。

示意（为设计草图，非现有接口）：

```python
if intent.requires_structure_write:
    evidence = receipts.for_generation(operation_id, generation, variant_id)
    outcome = assess_requested_units(intent, evidence, current_revision)
    if outcome.needs_author_decision:
        status = "needs_input"
    elif not outcome.complete:
        status = "partial"  # 已提交单元保留，列出缺口
```

验收：只保存模块或只输出文字不能满足结构目标；提交一部分不能报告全部完成；核验后的合法无改动、暂停后的迟到结果、版本冲突和同键重试均有确定结果。现有授权与恢复规则继续生效。

### 4. 对齐页面与对话结果

涉及 `frontend/src/state/conversations.ts`、`frontend/src/state/operations.ts`、`frontend/src/state/story.ts` 及聊天任务卡。

- 使用后端操作状态和提交收据显示结果，区分已保存的结构、已保存的模块和未完成内容；失败提示按项目规定提供位置、现象和建议。
- 结构提交后刷新当前方案和节点详情；部分完成时仍显示已保存单元，刷新或重连不触发模型重跑。检查现有 `story_changes_committed` / `run_finished` 刷新逻辑，避免并发请求导致旧快照覆盖新结果。
- 保持普通模块编辑、讨论、构思引用写作和候选正文流程可用；不新增作者必须操作的复杂表单。

验收：真实服务返回的节点和线索在页面可见，重载后仍存在；模块成功但结构未完成时界面与任务卡不会显示整体完成。

### 5. 测试与验收

先用隔离作品和受控模型事件做确定性测试，再使用 `.env` 在线模型执行受影响场景；不使用本地模型评测。评测保留原始尝试、实际请求摘要、工具调用、收据、最终结构、任务状态和页面证据，不输出凭据。

必需覆盖：

1. 空白方案：先讨论线索与调查，再说“写入构思并构建线索”；验证实际保存的线索、呈现节点及必要关系，模块不能代替结构。
2. 直接要求建立结构；仅讨论、比较或明确不保存；“用这个”对应单一候选、多个候选和无候选。
3. 已有结构局部修改与合法无改动；模块单独创建；要求两类成果但仅完成一类；多个结构单元仅提交部分。
4. 其他备选、未经授权的真相修改、引文授权、暂停及迟到写入、修订冲突、同键重试、重载与撤销。
5. 浏览器真实服务旅程：观察节点、线索、连接、结果状态和刷新恢复；用前后端同一收据核对。
6. 在线模型使用隔离配置，至少运行本次两轮语义场景与既有 O01 受影响案例，记录模型选择和实际提交；按现有验收约定零自动重试，修复后单独编号重跑。在线表现不替代确定性约束和作者体验验收。

按受影响范围运行 `tests/workspace/test_story_context.py`、`test_story_tools.py`、`test_story_authorization.py`（以实际文件为准）、`test_story_api.py`、对话与操作测试及前端状态测试；再执行项目既定的后端、前端和浏览器交付检查。检查项以实际执行记录为准，未执行不能标记通过。
