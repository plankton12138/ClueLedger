# 全书构思总览与线索联动实施计划

日期：2026-10-30。状态：**待实施，供本轮讨论；本文中的新增字段、接口参数与代码示例均为拟议契约。**

承接作者反馈：实际生成结果以章节为单位构成单链，缺少故事内多线推进；构思需要成为文章整体结构总览，具体安排进入线索详情，并支持双向联动。

范围继续遵守[构思简化记录](2026-10-30-story-simplification.md)：每部作品只有一份构思，不恢复备选、试读或独立候选正文。现有缩放、滚动、暂停、插话、正文定位和撤销继续使用。

## 1. 本轮要解决的问题

完成后，作者打开构思能看到故事阶段、各条叙事线的关键变化，以及它们相互影响和汇合的位置。点击节点进入相关线索，点击线索中的安排能回到对应节点；已写内容仍能定位原文。

总览节点表示关键行动或变化，不以章节作为默认粒度。章节与节点继续通过正文区间建立多对多关联。不是每个行动都需要线索，也不是每条线都必须在每个阶段出现。

首版不增加复杂自由连线、独立影响管理页、双时间轴、任意层级的结构编辑器。较长作品通过阶段折叠减少同时展开的内容，节点内容本身也必须保持宏观粒度。

## 3. 模块 A：结构数据与线索身份

### 3.1 增补已有结构

增加 `StoryStage` 表达故事阶段，以 `stage_id` 替代图内无语义的 `group_id`。旧的“只看某分组”交互改为在全书中折叠阶段，保留前后关系。运行任务的拆组和“继续下一组”属于执行流程，与故事阶段分开。

故事线补充目标、主要阻力和计划收束。尚未决定的目标或结局可以为空，不要求作者填表，模型也不能为通过校验自行决定。

节点继续使用 `action` 保存行动，用 `change` 说明该行动使局面或理解发生的变化；展示标题和简短变化，完整行动在详情查看。共同节点仍只有一个 ID，通过多个 `thread_ids` 表达汇合。

拟议模型示例，省略项目已有的公共严格校验基类：

```python
class StoryStage(StrictRecord):
    id: StoryId
    title: ShortText
    order: int = Field(ge=0)
    summary: str = Field(default="", max_length=1000)


class StoryThread(StrictRecord):
    id: StoryId
    title: ShortText
    order: int = Field(ge=0)
    goal: str | None = None
    obstacle: str | None = None
    intended_resolution: str | None = None


class ClueUse(StrictRecord):
    clue_id: StoryId
    # 一次使用可以同时承担再次提及与重新解释等作用。
    roles: list[Literal["plant", "develop", "misdirect", "reinterpret", "resolve"]]
    presentation: LongText
    expected_interpretation: str = Field(default="", max_length=2000)
    # 保留已有 mode、speaker_id。


class StoryNode(StrictRecord):
    id: StoryId
    title: ShortText
    action: LongText
    change: str | None = None
    stage_id: StoryId
    thread_ids: list[StoryId]
    clue_uses: list[ClueUse] = Field(default_factory=list)
    # 保留 time_note、knowledge_changes；章节仍通过 ProseBinding 关联。
```

`roles` 表示作者的使用意图，不是正文账本里的实际埋设／回收状态。对于不承担误导作用的线索，不要求安排误导。

继续使用 `next / reframe / answer`，暂不增加一套边分类。`next` 表达揭示推进，跨线影响通过明确的两端节点与 `reason` 保存；重新解释和回应保留现有方向约定。仅有先后关系不代表因果已经成立。

### 3.2 同一线索的职责分配

| 对象 | 唯一负责的内容 |
|---|---|
| 线索账本中的 `ClueIdentity` | 稳定 `clue_id`、标题、身份修订 |
| 构思中的 `StoryCluePlan` | 用 `clue_id` 引用身份；保存作者真相、创作意图、计划回收位置，不重复保存标题 |
| 节点的 `clue_uses` | 此处如何呈现该线索、承担什么作用、希望引发什么理解 |
| 账本中的正文贡献 | 经核对的实际引文、提及／埋设／回收、来源有效性 |
| 统一线索详情 | 按同一 ID 组合上述内容，提供给两个页面；本身不另存一份可编辑副本 |

新线索由服务端分配 ID。一个提交内可以使用临时引用，协调器在校验前解析为稳定 ID，回执返回映射；同请求重试返回同一回执。不能依靠同名标题自动认定是同一条线索。

删除仍被节点或正文引用的身份应拒绝；撤销若会删除后来已被引用的新身份，也应返回具体冲突，不能留下悬空引用。

## 4. 模块 B：提交、撤销与影响

在现有提交机制中扩展线索账本写入，新增协调职责建议放在 `workspace/story_clue_commit.py`，避免继续增加 `StoryStore` 单文件的体积。

处理顺序：读取相关修订 → 在工作副本应用结构和线索操作 → 验证引用与权限 → 记录待提交内容和提交决定 → 发布全部相关内容 → 返回同一回执。

需要同时处理：

- 构思与线索账本采用固定锁顺序；独立线索写入也要遵守相同的恢复与提交边界。
- 读接口先恢复已决定的提交，联合读取时校验修订，避免看到两份文件发布之间的混合状态。
- 新增账本版本依赖；任务受理冻结结构版本和线索版本，提交前重新检查。
- 提交中途失败能补完；暂停后的过期任务不能发布。
- 撤销记录包含线索改动，但只撤销本次涉及且之后未被改动的对象。

拟议输入示例：

```python
class StoryClueCommit(StrictRecord):
    expected_story_revision: str
    expected_ledger_revision: str
    request_key: str
    story_operations: list[StoryOperation]
    clue_identity_operations: list[ClueIdentityOperation]
    prose_patches: list[ProsePatch] = Field(default_factory=list)
    # ClueIdentityOperation 为本模块新增的类型，不接受任意文件写入。
```

影响提示从实际修改对象、线索使用和正文关联导出：修改计划后相关节点需要重新核对；若需要判断正文与新计划是否矛盾，进行语义核对并给出具体差异。不能仅凭版本变化就宣称正文内容错误。

结构或计划变化不自动改写正文。作者要求正文一起改时，在明确范围内执行，未处理的位置保持待核对。

## 5. 模块 C：构思生成与核对

### 5.1 一次任务内先形成整体，再补细节

沿用已有任务、流式输出、暂停和插话，不新增另一套任务界面。正常创作不强制每一步等待作者确认；缺少会改变故事核心的决定时再提问。

1. 读取已确认要求、现有构思、必要正文与资料，区分实际内容和准备新增的内容。
2. 确定阶段、各线目标、主要阻力和跨线影响，先形成完整的关键推进与收束。
3. 给关键节点补充所需的线索使用、知情变化和正文关联。
4. 检查结构和叙事问题，进行一次有边界的修正；仍未确定的创作决定明确保留。

示例任务要求，可纳入 `prompts/authoring.py`，同时更新默认创建文本和工具示例：

```text
建立全书结构时，以关键行动和局面变化为节点，不按每章各建一个节点。
作者要求多线叙事时，为各线说明独立目标、主要阻力和计划收束。
记录实际的跨线影响：哪条线取得什么结果，怎样改变另一条线的行动或解释。
先安排整体关键推进与收束，再补充各处线索使用；章节通过正文关联体现。
已有正文的内容按实际归纳；新增冲突只登记为创作计划。
作者尚未决定的真相、人物目的或结局保持未定。
```

节点数量和故事线数量作为当前作品的创作建议，不作为所有作品的固定配额。在线样例若明确要求三条线，则按该要求验收，不能用三个名称包住同一条单链。

### 5.2 让模型持续读到完整结构关系

`read_story` 补充阶段、各线 ID 与目标、节点归属、边的 `reason`、计划线索身份与使用位置。达到容量限制时列明省略范围并允许定向读取，不能静默只取前若干节点后当作全书。

`assemble_story_input` 的全局输入包括阶段、故事线目标、关键变化、跨线关系与未定事项；局部任务包含当前节点、相关线索、必要前提与实际正文。切换对话和压缩后仍从当前保存结构重建。

作者计划与真实正文观察继续分区。未来计划可以指导安排，不能被放入“读者已见”或当作角色已经取得的证据。

### 5.3 分开结构校验与叙事判断

确定性校验负责引用存在、顺序无环、阶段引用正确、共同节点唯一、正文区间有效。叙事判断使用在线模型检查：

- 各线是否有不同目标与实际推进。
- 跨线影响是否说明具体变化，是否依赖缺失前提。
- 计划需要收束的故事线是否缺少安排；明确留白不强制补结局。
- 关键转折是否有前置内容，是否在结尾才引入决定性新条件。
- 是否将证词当事实，或将作者知道的真相当作人物证明。

结果是对应节点与原句的具体发现，不增加笼统的“精彩度”分数，也不宣称结构合格就代表文学质量合格。

## 6. 模块 D：统一读接口与前后端契约

尽量扩展现有接口，避免增加只供单个按钮使用的重复接口。内部仍保留现有当前构思身份路径，不在本轮顺便重命名所有 `variant` 协议。

| 现有接口 | 拟议补充 | 前端使用方 |
|---|---|---|
| `GET /api/file-workspaces/{id}/story/variants/{variant_id}` | `stages`、完整 `threads`、节点阶段与变化、线索使用引用；折叠在前端呈现，保留边界关系 | `StorySurface`、`StoryCanvas` |
| `GET .../story/nodes/{node_id}?variant_id=...` | 统一身份的线索摘要、正文入口、关联有效性 | 节点详情 |
| `GET .../clues?scope=story&node_id=...` | 作者构思范围，可包含尚无正文的线索；`node_id` 可选，无选中节点时列全书线索 | 新 `StoryClues` |
| `GET .../clues/{clue_id}?scope=story` | 作者计划、按节点记录的使用过程、正文观察与反向定位信息 | 共用 `ClueDetail` |
| 现有章界线索读取 | 不传新参数时继续按正文截止位置读取，不因构思浏览扩大读者已见范围 | `ChapterClues` |
| `POST .../story/changes` 及 Agent `update_story` | 阶段操作、身份关联操作、账本依赖和同一回执 | 页面、构思 Agent |

`scope` 是由当前页面选择的读取范围，不是给作者增加一个设置项。若将来增加读者视图或访问控制，不能把该参数当作权限凭据。

统一详情的作者侧契约示例：

```typescript
interface StoryClueDetail {
  clue_id: string;
  title: string;
  plan_revision: string;
  ledger_revision: string;
  view_revision: string;
  plan: {
    author_truth: string | null;
    intention: string;
  } | null;
  uses: {
    node_id: string;
    stage_id: string;
    thread_ids: string[];
    roles: string[];
    presentation: string;
    expected_interpretation: string;
  }[];
  // 复用现有引文及有效性结构；不由 uses 推导已埋设或已回收。
  observations: ClueDetail["observations"];
  evidence: ClueDetail["evidence"];
}
```

前后端共同提交固定的请求／响应样例，校验新增字段、空计划、空正文与未定情况。`plan_revision` 和缓存修订必须随相关内容变化，不能只看账本版本而漏掉构思修改。

`clue_context.py` 同步支持统一身份与计划版本：作者侧引用携带计划，读者已见部分只取有效正文与本轮写作截止位置。选中未来节点不改变正在执行任务的冻结对象。

## 7. 模块 E：总览布局与双向联动

### 7.1 保留现有画布，改变排布约束

继续使用当前画布能力，不引入新的图组件库。横向列按故事线固定排序，纵向按阶段和阶段内揭示顺序推进；实际事件时间仍在详情中查看。

布局计算独立为纯函数，例如 `frontend/src/components/story/storyLayout.ts`：输入阶段、节点尺寸、故事线与关系，输出位置。阶段高度按其中实际节点尺寸计算，允许空列；共同节点进入阶段公共行，显示参与线，且只绘制一次。

总览中只展示关键节点的标题和变化，不铺开长篇章节摘要。展开一个阶段时，其他阶段保持简短摘要和前后关系；折叠是浏览状态，不创建假的创作节点，也不删除真实边。

默认突出推进关系；选择节点后显示直接关联，选择线索后显示该线索的使用过程。跨线连接使用记录中的说明，不根据卡片位置猜测因果。缩放、全貌、1:1、双向滚动与返回位置沿用现有实现。

### 7.2 共用右侧栏和选择状态

`WritingLayout` 按当前内容选择 `StoryClues` 或 `ChapterClues`。构思下没有选中节点时显示全书线索，选中后显示相关线索；点击节点不强行关闭对话，作者点“查看相关线索”再切换右侧标签。

使用独立的浏览状态维护高亮线索、展开阶段和返回位置。反向定位先展开目标阶段，再选中、移到可读位置，保持当前缩放。该操作不调用模型。

拟议组件集成示例，`useStoryNavigation` 是本轮新增的浏览动作集合：

```tsx
const navigation = useStoryNavigation();

<ClueDetail
  workspaceId={workspaceId}
  clueId={selectedClueId}
  scope="story"
  onLocateNode={(nodeId) => navigation.revealNode(nodeId)}
  onLocate={locateProse}
/>
```

`revealNode` 应执行：确认对象属于当前作品 → 从当前图确认节点存在 → 展开所属阶段 → 选中节点 → 等待布局完成后移动视口。快速切换作品时丢弃过期请求，不把另一作品的迟到结果应用到当前图。

“带入对话”同时使用已有节点引用与统一线索引用，在受理时固定版本。浏览别处只改变浏览状态，不改变运行任务。正文返回后恢复构思选中对象、展开状态和视口。

## 8. 实施顺序与可检查结果

| 批次 | 完成内容 | 可检查结果 |
|---|---|---|
| 1：统一数据与提交 | 阶段／故事线／节点契约，稳定线索身份，联合提交与撤销，公共读模型 | 通过接口创建一组多线结构；新线索在构思和账本中使用同一 ID；重载、并发、失败恢复和撤销成立 |
| 2：接通总览与线索 | 受约束的布局、阶段折叠、相关线索、计划与引文、反向定位和返回状态 | 不依赖模型的浏览器样例能完成节点 → 线索 → 另一节点 → 正文 → 返回；无重复汇合节点 |
| 3：接通真实生成 | 默认创建要求、工具读写、全局／局部上下文、叙事检查与有界修正 | 使用真实模型直接生成并保存多线总览；普通对话修改后，图、线索和后续写作输入一致 |
| 4：完整验证与记录 | 在线样例、实际请求检查、窄屏、暂停恢复、受影响回归及文档 | 保存每次尝试和失败，分别报告结构通过、语义判断与作者体验；不以模拟数据代替生成验收 |

批次是开发切分，整体目标完成前不将单独的布局或跳转视为完整功能完成。

不做旧数据迁移。新格式及在线样例使用隔离作品和状态目录；不在实施过程中自动删除作者的正文、模块或当前数据。

## 9. 验收标准

### 确定性与浏览器

- 显式阶段、故事线和关键节点能够保存、重载和撤销，引用与顺序合法。
- 同一条线索改名或再次出现不生成另一身份；同名不同线索仍能分开。
- 只有构思、没有正文时，相关线索可见；正文贡献为空，状态不显示为已埋设。
- 计划改变后，相关视图和模型输入更新；正文引文改稿后仍遵守现有来源有效性规则。
- 一个共同节点只出现一次；折叠后能看见前后关系，反向跳转能展开正确阶段。
- 当前缩放、滚动、字号和窄屏阅读不回退；返回恢复原位置。
- 两份状态或正文联合提交在故障注入、进程重开、重复请求、并发编辑、暂停竞态下保持一致。
- 相关接口样例、前端类型与模型工具一致；没有页面存在而后端能力缺失的操作。

### 在线模型

只使用 `.env` 配置的在线模型，不使用本地模型。依次验证：

1. 空白作品中明确要求三条叙事线：各线有不同目标、至少一处有具体内容的跨线影响，并安排收束或明确留白。
2. 已有正文的作品：归纳实际内容，提出新增安排时标明计划，保留作者要求不改的真相和段落。
3. 局部修改：“把这条线索的回应提前，并保留原结局”，检查相关使用位置、依赖说明与保存结果。
4. 继续写作：后续场景实际收到当前阶段、相关故事线、计划和必要前文，不能只看对话回复自称已使用。
5. 刷新或换对话继续：仍能读取同一结构和线索身份，未来安排不被误算为已写事实。

判断“多线是否有意义”需要检查具体内容；结构校验和连线数量不能替代该判断。文学感染力继续由作者实际阅读评价。
