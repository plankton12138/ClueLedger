# U1 容量与整请求估算

日期：2026-10-27。阶段：U1（模型容量与完整请求估算）。状态：**已完成**。

这一阶段的交付是「装得下吗」这个判断所需的三样东西：一个模型能装多少（容量）、
这次要装多少（估算）、以及两者比较之后是什么状态（预算）。三样都不调用模型。

## 1. 交付

| 位置 | 内容 |
|---|---|
| `server/model_limits.py` | 按精确模型解析容量；回复预留与运行时实际上限一致；配置校验 |
| `server/provider_config.py` | 连接可保存 `model_limits`；旧配置照常读取；快照冻结容量 |
| `server/model_connections.py`、`model_api.py` | 保存、查看容量；省略与清空分离 |
| `workspace/context_usage.py` | 中文感知估算、请求指纹、预算状态 |
| `workspace/agent.py` | 提取 `prepare_request_inputs`，harness 与估算共用同一份 system 与工具定义 |

## 2. 容量的三条取舍

**不猜窗口。** 模型发现列表只给名字，同一个名字在不同平台上的窗口并不相同。
没有配置就是未知：界面不显示百分比，自动整理停用，手动整理照常可用。填一个
128K 的默认值看起来更有用，实际会让占比显得可信、判断却毫无依据。

**回复预留对齐实际请求。** 写作用途的回复上限是运行时固定的 4096
（`WORKER_OUTPUT_TOKENS`），容量配置没填预留时就用它。以前这个数字在适配器里
写死了两处，本阶段收成一个常量，避免「界面按 8K 预留、实际只允许 4K」。

**按精确模型匹配。** 配置以模型名为键，`deepseek-chat` 的容量不会顺带给
`deepseek-chat-v2`。前缀相同就推断容量属于计划里明确否掉的做法，因为猜错的
表现是预算看起来很宽松，直到请求被供应商拒绝。

容量来源目前只有两条：作者显式配置（`override`）与未知（`unknown`）。
`metadata` 这条路径在类型里保留，但**没有可信数据源**——发现接口不返回窗口，
不在本版伪造一个。

### 安全余量

未配置时按窗口的 5% 取，上限 4096。窗口小时余量跟着变小，不会出现
「窗口 8K、余量吃掉一半」的情况。

### 保存语义

提交里**没有** `model_limits` 字段表示沿用已保存的容量；显式传 `{}` 才是清空。
两种意图必须分开，否则任何不带这个字段的保存路径都会静默抹掉作者的配置。
移动模型出可选列表不删除它的容量，换回来还能继续用。

## 3. 估算方法与指纹

**中文感知折算。** 宽字符（汉字、假名、全角标点、韩文）一字一 token，其余四个
字符一 token，向上取整。方法标识 `cjk-aware-v1`。

选这个方向的原因是可解释与偏保守：中文按四分之一折算会让两万字的装配看起来只占
五千，预算判断永远显示「还早」。高估的代价是更早提示整理，低估的代价是请求被拒。

**结构开销单列。** 每条消息 4 token、每个工具定义 16 token 的固定开销。这两项
跟内容长短无关，但一次装配里有几十条消息与十几个工具，忽略它们会让估算系统性偏低。

**指纹覆盖全部输入。** 模型身份、系统提示、工具序列化、消息序列化、资料版本、
估算方法一起参与哈希。换模型或改资料后指纹变化，旧估算与旧校准不再复用。

估算读取的 `source_revisions` 由调用方给出，估算模块自己不读文件——否则一次
「看一眼占用」就会产生读取记录。

## 4. 预算状态

四种：`unknown`（输入上限未知）、`ok`、`near`（达到上限的 90%）、`over`。

`unknown` 不是「没问题」，而是「无法判断」：不能据此触发自动整理，也不能声称
还有空间。阈值取 90% 而不是 100%，因为整理本身需要空间，等到装满再整理
等于必然失败一次。

## 5. 共用装配入口

`workspace/agent.py` 新增 `prepare_request_inputs`，返回系统提示与工具定义，
`build_harness` 改为调用它。以前这两样只存在于 harness 内部，任何估算接口都只能
另装配一次，而两份装配的差异恰好是最难发现的错误。

这条入口**不执行模型、不写会话事件、不改作品文件**，有用例固定。它仍然读当前
资料版本，所以同一组参数在不同资料版本下结果不同——这正是指纹要跟着资料变的原因。

## 7. 限制与依赖

- **未做真实校准**：没有拿供应商实测用量反推估算偏差。R1 的在线对照才具备条件；
  在那之前估算只能保证方法一致与方向保守。
- **元数据来源为空**：`metadata` 分支未启用，目前只能靠作者填容量。
- **尚未接入请求边界**：本阶段只提供估算与判断，还没有在发出请求前做预算拦截，
  也没有在会话事件里记录估算值。这两件事属于 U2。
- **供应商侧的真实上限未逐家核对**：4096 是本应用自己设定的写作用途输出上限，
  不是供应商的最大输出；容量配置里的 `max_output_tokens` 需要作者按平台填写。
