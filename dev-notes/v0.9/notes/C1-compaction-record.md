# C1 第一片：压缩记录、投影与切点

日期：2026-10-27。阶段：C1（跨轮压缩）。状态：**进行中**。

本片交付的是压缩的「数据与判断」：记录长什么样、什么时候算有效、怎么投影到下一轮、
从哪里切、候选摘要怎么判。**还没有**生成摘要的流程、手动整理接口与界面按钮，
所以现在没有任何路径会真的产生一份压缩记录。

第二片补上了摘要生成（见第 10 节），服务层的 `compact()` 已经能产出可用记录并验证；
仍然没有接口与界面，作者还无法触发它。

## 1. 记录是追加的，对话不改写

压缩不删除、不改写任何原事件，只追加一条 `context_compacted`。记录里写明覆盖范围
（`covered_through_seq`）、保留点（`first_kept_turn_id`）、来源指纹与摘要条目。

这么做的理由是作者原话的两种用途不能被摘要替代：范围校验要从原话读出授权，
语义一致性要靠原话核对。摘要只是给下一轮看的简报，删掉原话之后就没有东西可核对了。

摘要条目带 `source_event_ids` 与 `quote`：一条概括必须能回到某一轮，
作者原话优先于改写后的说法。

## 2. 读取时四道校验

`active_compaction()` 从最新记录往回找，任何一条不成立就按未压缩处理：

| 校验 | 不成立的含义 |
|---|---|
| 摘要与条目非空 | 空摘要等于凭空删历史 |
| `0 <= covered_through_seq <= source_head_seq` | 范围本身矛盾 |
| 保留点存在于日志，且序号在覆盖范围之后 | 记录过期或日志被裁剪，硬用会把整段历史丢掉 |
| 覆盖范围的事件指纹与记录一致 | 原事件被改写，旧摘要不再代表它们 |

降级到未压缩的代价是上下文更长，但它不会让模型看到与原文不符的记忆。这个方向是
刻意的：压缩是优化，正确性是前提。

## 3. 投影

`replay_public_messages(events, compaction=...)` 在保留点之前的内容上停止回放，
把摘要作为一条带固定标识的 `UserMessage` 放在最前：

> （应用整理的较早对话摘要，供继续任务使用，不是作者的新要求）

标识要一眼看出是应用整理的。摘要不提升为系统指令：系统约定只说明摘要的用途，
不把摘要内容变成不可违抗的规则。

服务端在组装历史时接入这一条（`service._run`），没有记录时行为与 0.8 完全一致。

## 4. 切点

`plan_compaction()` 按轮次切，一轮的提示与回复不拆开。从最近一轮往前累计，
累计到保留量就停：

- 最新一轮无论如何都保留。把最近一轮压掉，模型接不上作者刚说的话。
- 问了没答的轮次强制保留。作者的回答只有在看到原问题时才有意义。
- 一轮都留不下时不压缩，返回 `None`——「全留着」不是压缩失败，是不需要。

保留量由调用方按整请求预算算，不在这里固定成某个常数。

## 5. 候选校验

`parse_summary()` 要求模型输出结构化 JSON，逐条检查来源：

- 引用了不存在的轮次 → 整份作废。这意味着模型在补写，补写出来的内容会被下一轮当成事实。
- 条目没有来源 → 整份作废。
- 允许模型带代码围栏或前后说明，但不接受「好的，我整理了一下：……」这类自由文本。

`validate_candidate()` 再查四件事：摘要非空、确实缩减、范围有效、整理后不超过输入上限。
不通过时抛带错误码的异常，调用方保留旧投影。

`build_candidate()` 会把摘要本身的规模计入 `estimated_after`——只算删掉的部分，
会得出「整理后变小了」的错误结论。

## 7. 下一步

按 C1 的计划，剩下三块：

1. **摘要生成**：用受理时冻结的模型发起一次无工具的独立请求，`stage="compaction"`，
   走同一个记录器计入用量；失败走降级，不反复重试。
2. **手动整理与队列**：`POST .../compact`、状态查询、停止；忙时登记到下一个安全边界。
3. **界面与恢复**：浮层里的「整理上下文」、整理中的状态、重启后按已提交记录恢复投影。

在这三块完成前，`README` 里 C1 的状态保持「进行中」，不能因为记录结构已就绪就说压缩可用。

## 8. 第二片：摘要生成（已完成）

`TurnService.compact(conversation_id)` 现在能真的产生一份记录，流程是：

1. 取会话事件，按可用输入的四分之一算近期保留量（上下限 2000 / 24000 兜住极端容量），
   选切点。没有可整理的较早内容就直接返回 `None`——这不是失败，是不需要。
2. 用提示词把被覆盖轮次的作者提示与助手回复逐轮列出（带 `[轮次ID]`），只发这些内容。
3. 一次**无工具**的独立请求，`stage="compaction"`，走同一个记录器计入用量。
   它不挂在任何写作请求下面，也不会递归触发整理。
4. 解析摘要、校验候选、追加 `context_compacted`。

几个刻意的选择：

- **失败不提交**：摘要格式不对或引用了不存在的轮次时抛 `COMPACTION_FAILED`，事件日志里
  不出现 `context_compacted`，下一轮仍用完整历史。压缩失败只损失一次模型调用的钱，
  不该损失上下文。
- **提示词版本进记录**：`prompt_version` 随记录保存，改提示词后旧摘要不会被当成同一种
  东西继续累加。
- **整理与写作串行**：共用同一把执行锁。整理改变的是下一轮的投影，不能和正在进行的
  写作交错。
- **不用摘要模型**：用本轮受理的同一个模型。另选一个小模型看起来省钱，但它对作品语境
  的理解是另一套，摘要质量无法用同一套标准衡量。

验证（`tests/workspace/test_compaction_service.py`，5 例）：成功提交并计入用量、
请求无工具且只含被覆盖轮次、单轮时不动模型、坏摘要保留旧投影、整理后投影变短且以摘要开头。

仍然缺接口与界面：作者现在无法从应用里触发整理。


## 9. 第三片：手动整理接口与入口（已完成）

### 接口

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/{workspace_id}/conversations/{conversation_id}/compact` | 受理一次整理，202 返回操作标识 |
| GET | `.../compactions/{operation_id}` | 查状态；`completed` 带记录，`failed` 带错误 |
| POST | `.../compactions/{operation_id}/stop` | 取消排队或运行中的整理 |

整理在后台跑：它要调用一次摘要模型，同步等待会让界面卡住。它不占创作轮次、不产生
作品提交、不注入作者消息——走的是自己的操作标识，不是一条假的助手回复。

同一个 `request_key` 只受理一次：重复点击或重试返回同一个操作，不会发出第二次摘要请求。

状态有四种终态：`completed`（提交了新记录）、`noop`（没有可整理的较早内容）、
`failed`（摘要不成立，旧投影保留）、`stopped`（作者取消）。`noop` 用一句正常说明表达，
不报错——「没有需要整理的」不是故障。

### 多次整理

第二条记录用 `previous_id` 指向第一条，覆盖范围只增不减，投影始终只有一份摘要。
记录链让「这条摘要从哪来」可回溯；本版没有回滚功能，链只用于诊断与将来的来源核对。

### 界面

上下文浮层底部有「整理上下文」：点击后按钮变成「正在整理…」，前端按 800ms 轮询操作状态，
到终态显示结果（`已整理：4.2 万 → 1.2 万`、没有可整理内容、或失败原因），并重新读取用量。

### C1 剩余

- **自动压缩**（按预算触发）属于 C2，本片只做手动。
- **操作状态不持久**：服务重启后旧操作查不到（返回 404 并提示重新整理）。已提交的压缩记录
  不受影响——投影始终从事件重建，这是有意的取舍：操作是短命的，记录才是事实。
- **浏览器走查未做**：按钮与结果的视觉、窄栏表现待 R1 的 UI 验收。
