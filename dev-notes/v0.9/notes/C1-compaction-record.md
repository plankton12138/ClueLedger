# C1 第一片：压缩记录、投影与切点

日期：2026-10-27。阶段：C1（跨轮压缩）。状态：**进行中**。

本片交付的是压缩的「数据与判断」：记录长什么样、什么时候算有效、怎么投影到下一轮、
从哪里切、候选摘要怎么判。**还没有**生成摘要的流程、手动整理接口与界面按钮，
所以现在没有任何路径会真的产生一份压缩记录。

## 1. 记录是追加的，对话不改写

压缩不删除、不改写任何原事件，只追加一条 `context_compacted`。记录里写明覆盖范围
（`covered_through_seq`）、保留点（`first_kept_turn_id`）、来源指纹与摘要条目。

这么做的理由是作者原话的两种用途不能被摘要替代：范围校验要从原话读出授权，
语义一致性要靠原话核对。摘要只是给下一轮看的简报，删掉原话之后就没有东西可核对了。

摘要条目带 `source_event_ids` 与 `quote`：一条概括必须能回到某一轮，
作者原话优先于改写后的说法。

## 2. 读取时四道校验

`active_compaction()` 从最新记录往回找，任何一条不成立就按未压缩处理：

| 校验 | 不成立的含义 |
|---|---|
| 摘要与条目非空 | 空摘要等于凭空删历史 |
| `0 <= covered_through_seq <= source_head_seq` | 范围本身矛盾 |
| 保留点存在于日志，且序号在覆盖范围之后 | 记录过期或日志被裁剪，硬用会把整段历史丢掉 |
| 覆盖范围的事件指纹与记录一致 | 原事件被改写，旧摘要不再代表它们 |

降级到未压缩的代价是上下文更长，但它不会让模型看到与原文不符的记忆。这个方向是
刻意的：压缩是优化，正确性是前提。

## 3. 投影

`replay_public_messages(events, compaction=...)` 在保留点之前的内容上停止回放，
把摘要作为一条带固定标识的 `UserMessage` 放在最前：

> （应用整理的较早对话摘要，供继续任务使用，不是作者的新要求）

标识要一眼看出是应用整理的。摘要不提升为系统指令：系统约定只说明摘要的用途，
不把摘要内容变成不可违抗的规则。

服务端在组装历史时接入这一条（`service._run`），没有记录时行为与 0.8 完全一致。

## 4. 切点

`plan_compaction()` 按轮次切，一轮的提示与回复不拆开。从最近一轮往前累计，
累计到保留量就停：

- 最新一轮无论如何都保留。把最近一轮压掉，模型接不上作者刚说的话。
- 问了没答的轮次强制保留。作者的回答只有在看到原问题时才有意义。
- 一轮都留不下时不压缩，返回 `None`——「全留着」不是压缩失败，是不需要。

保留量由调用方按整请求预算算，不在这里固定成某个常数。

## 5. 候选校验

`parse_summary()` 要求模型输出结构化 JSON，逐条检查来源：

- 引用了不存在的轮次 → 整份作废。这意味着模型在补写，补写出来的内容会被下一轮当成事实。
- 条目没有来源 → 整份作废。
- 允许模型带代码围栏或前后说明，但不接受「好的，我整理了一下：……」这类自由文本。

`validate_candidate()` 再查四件事：摘要非空、确实缩减、范围有效、整理后不超过输入上限。
不通过时抛带错误码的异常，调用方保留旧投影。

`build_candidate()` 会把摘要本身的规模计入 `estimated_after`——只算删掉的部分，
会得出「整理后变小了」的错误结论。
