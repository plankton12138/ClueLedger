# R2：独立写作任务的承接序号误填

日期：2026-10-27。状态：代码修复和回归通过，订阅端在线复测未执行。

## 现象与原因

实际会话的首条请求为「开始写第一章」，作者事件序号为 1。模型登记范围时填写了
`authorization_seq: 0`、`carried_from_seq: 0`，并给新建操作填写了 `target: ""`。
程序返回 `[TASK_SCOPE_EVIDENCE_INVALID] task_scope.set：承接的作者请求不在本轮可见的作者消息里`。
模型随后将承接序号改成 1，又触发「承接对象与授权语句是同一条消息」的校验。

这是独立任务，没有需要承接的旧请求。此前对授权序号和空目标路径的兼容处理没有解决
可选字段被填成占位值的问题。Responses 适配器未指定 `strict`，Codex 适配器指定为 `null`；
[官方说明](https://developers.openai.com/api/docs/guides/function-calling)指出，默认行为可能
将工具声明转换为严格模式，把可选字段转为必填。这与实际参数中成批出现的占位值一致。

## 修复与取舍

- 两个 Responses 工具序列化入口显式发送 `strict: false`，保留现有工具的可选字段语义。
- `carried_from_seq` 的参数说明明确：仅承接旧请求时填写，独立任务省略，不用 0 占位，
  不填写当前授权消息的序号。
- 参数和作者证据仍由工具层校验；不自动接受无效承接，不取消作者原话、修改范围和旧文件授权检查。
- 前端与后端业务接口无需变更。
