# Hastings 0.6 上下文与文件操作开发计划

> 编写日期：2026-10-22。状态：待实施；本文是开发目标，当前运行版本仍为 `0.5.0`。
> 本计划承接 [0.5 上下文计划](../v0.5/context-management-plan.md)中未实施的材料、索引和来源核对，并增加任务修改范围与有依据的写后检查。重叠目标统一以本文为后续实施依据，不同时维护两套契约。
> 当前实现见 [0.5 模块导航](../v0.5/modules/README.md)。本文示例是拟新增接口与关键逻辑，不是现有代码或可直接运行的补丁。

## 1. 目标与设计取舍

作者可以仅通过对话提出任务，也可以选择作品文件作为参考。系统需要找到相关材料、识别材料版本、区分参考与修改授权，并在需要时提供带原文依据的检查结果。

按以下顺序交付：**材料来源与版本核对 → 明确任务修改范围 → 有依据的写后检查**。第一部分先完成不依赖索引的文件参考闭环，再补章节索引；后两部分复用同一份来源记录，不另建内容数据库。

### 1.1 本版必须坚持

- 添加参考是可选入口。`context` 缺省、参考列表为空时仍可正常讨论、搜索、写作与修改；不能要求作者先选文件。
- 用户可以直接说“参考第一章修改第三章”。模型通过目录、搜索与原文，将自然语言对象解析为实际路径；解析结果必须可回看。
- 当前阅读位置、参考材料、允许修改的范围分别记录。选择参考不会授权修改，打开文件也不意味着模型已经读过。
- 保留单个写作 Agent 与现有执行循环，不修改 `tau_agent` / `tau_ai`；通过本轮状态、工具返回和写入检查实现约束，不引入固定多角色创作流程。
- 作者明确要求修改后直接写文件，不恢复候选采用或默认计划审批。写作质量检查不自动修稿。
- 材料和工具输出有明确上限，但本版不声称实现整条请求的总 token 预算或会话压缩。
- 真相继续允许用于规划与核对；不引入正文生成必须隔离真相的通用规则，不承诺确定性消除剧透。

### 1.2 本版不做

任意本机文件附件、外部资料导入、向量检索、会话压缩、长期记忆、角色知情状态机、章节锁定状态机、跨文件事务、分支管理、每章独立提交，以及每次保存后自动启动模型审计。人物状态与伏笔不另建一套权威结构化账本。

自动重试模型、停止后自动续跑、检查后自动扩大修改范围均不进入。程序保存校验与用户请求内的模型检查分别处理。

## 3. 作者操作与模型定位

### 3.1 可选参考入口

输入区提供“添加文件”，从当前作品的章节、人物小传、线索和真相中多选；目录条目提供“加入对话”，两处调用同一动作。文件按实际路径去重，保留选择顺序，可以逐个移除。

```text
当前阅读：第三章《书房里的脚印》
本轮参考：[第一章 ×] [林远小传 ×] [+ 添加文件]

参考第一章，修改第三章的问询，让回答呼应首次进入书房的细节。
```

当前阅读只帮助解析“这一章”。没有选择时不展示空参考标签区；发送不需要参考。第一版不要求实现 `@` 补全、拖放附件或操作系统文件选择器。

参考选择按作品和会话草稿隔离。仅选文件但无文字时保留当前界面选择，不创建正式会话；持久化沿用“非空文字草稿携带参考”的规则。删除文字草稿一并删除其参考。发送中修改的新文字或引用不能被受理回调清除。

### 3.2 自然语言与文件选择进入同一份材料记录

| 作者表达 | 定位与执行行为 |
|---|---|
| 不选文件，问“第三章有没有矛盾” | 找到第三章、读取并检查；不修改作品 |
| 不选文件，说“参考第一章修改第三章” | 解析两个章节路径；第一章为作者明确参考，第三章为修改目标 |
| 选人物小传，说“修改这一章” | 当前阅读定位章节，小传作为参考；不因选中而允许改小传 |
| “让回答呼应第一次进入书房的细节” | 搜索候选、读取原文；找到具体位置后登记补充来源 |
| “只改第三章，不动人物设定” | 记录第三章更新权限与人物设定禁止项；不得用同步一致性扩大范围 |
| “修改动机，并同步相关章节” | 先查找影响，允许在该请求目标内发现相关文件；关联原因与实际修改可回看 |
| “如果林远是凶手会怎样” | 按假设讨论，不写凶手标签，不自动修改设定 |
| 同名人物、重复章序或“这里”无法定位 | 先利用目录和原文消除歧义；仍影响创作决定时询问，不任选文件 |

模型先使用服务端目录的章序、显示名和路径，不凭列表位置猜“第几章”。自然语言定位可以产生合法空结果；没有有效索引仍可搜索原文，不阻断创作。

新增 `register_references` 工具：登记自然语言明确要求的参考，以及任务中发现的补充材料。作者文本来源必须包含会话事件定位与原文短引文；应用核验其确实来自本轮或被本轮明确承接的作者消息，不接受作品或助手回复作为授权来源。工具不能让客户端或模型自行写入“已读”状态。

来源类别分别为 `author_selected`、`author_text`、`discovered`、`system_setting`、`chapter_index`。用户的否定句、假设与普通提及是否构成参考仍由模型解释；引文存在不证明解释正确，需用语义样例验收。

### 3.3 模型实际收到的材料

按“固定行为要求 → 本轮原始要求与定位 → 作者指定参考 → 本轮修改范围/禁止项 → 有界目录 → 当前固定设定 → 有效索引 → 实际原文 → 执行事实”组织。作者原始消息只在消息序列中追加一次，系统块只引用其定位，不复制整条要求。

目录、摘要、搜索命中是定位材料。作品文字和工具摘录不是操作指令。旧聊天中的猜测不升为正式设定，旧任务范围不自动继承；“继续”只有能定位到此前明确的作者请求时才承接，否则澄清。

界面显示“已指定 / 已定位 / 已提供部分原文 / 已提供全文”，状态解释为应用实际提供的范围，不能证明模型理解或关注了内容。来源很多时详情分页，默认只展示简短状态。

## 4. 材料、版本和读取契约

### 4.1 受理快照与执行状态分开

受理时只冻结客户端输入的当前路径、显式参考、用途和服务端实际指纹。它是版本记录，不是跨文件原子快照，也不承诺保存全书内容副本。执行开始时版本已变则该轮失败，提示刷新后重新发送，不偷偷替换引用版本。

自然语言定位、发现的参考、实际读取区间和任务范围属于执行阶段记录，以事件追加，不能回写原始请求身份。参考文件后来变化，不得影响原请求键重试取回已受理轮次。

来源缺失、编码错误、无法读取和版本变化分别处理。当前阅读文件只是定位，未实际预读时不作为写作依赖；一旦参与指代解析，若原路径已失效且无法确定对象，不写入。

### 4.2 读取记录与依赖记录分开

- 依赖记录说明哪些版本被用于本轮材料，包括固定设定、索引的源文件和实际原文。
- 读取记录只记实际提供给模型的原文范围。目录、摘要、搜索摘录、界面打开、`edit_file` 内部读文件都不增加原文覆盖。
- 全文按 LF 规范化文本处理，指纹仍按磁盘原始字节。区间使用服务端 Python 字符索引，采用左闭右开；前端只展示，不自行计算，避免浏览器字符串索引差异。
- 工具分页使用字符游标，保留行号便于定位；现有 `offset` / `limit` 仍可作为行分页入口，但受字符上限约束。超长单行用字符游标继续，不永久卡在同一行。
- 同一 `(path, digest)` 的重叠区间合并。版本变化后不拼接新旧区间，旧内容无法从模型上下文撤回，只能明确失效并提供新内容。

`materials.py` 的关键逻辑示例：

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class SourceRef:
    path: str
    digest: str  # 磁盘字节指纹，不对规范化文本重新散列

def merge_spans(spans: list[tuple[int, int]]) -> tuple[tuple[int, int], ...]:
    merged: list[tuple[int, int]] = []
    for start, end in sorted(spans):
        if start < 0 or end < start:
            raise ValueError("原文区间无效")
        if start == end:
            continue
        if merged and start <= merged[-1][1]:
            merged[-1] = (merged[-1][0], max(merged[-1][1], end))
        else:
            merged.append((start, end))
    return tuple(merged)
```

实际实现还需校验区间不超出该版本全文长度。空文件可作为已完整读取的空内容记录，不靠非空区间判断。只读接口供前端展示的调用不能复用模型读取记账入口。

### 4.3 指定参考的完成条件

作者选择的文件和自然语言明确要求“参考”的文件进入同一必需参考集合。默认要求写作品前提供其全文；明确说“第一章结尾”时，可以登记已解析、带版本的具体范围，不强制读取无关部分。仅发现的候选不要求一律全文读取。

纯讨论允许依据部分原文回答，但必须说明范围；不能因未读全就禁止普通回复。索引发布和“已检查完整目标”的声明必须满足各自全文覆盖条件。

指定参考未定位、未完成读取或依赖版本变化时，写工具返回具体缺口。任务无法在回合或容量限制内完成时如实报告，不自动续跑、不静默丢弃参考。自然语言中的必需参考未被模型登记，是语义识别缺陷，不能声称程序已确定性覆盖所有作者要求。

目标文件也需要独立的读取前提：整体覆盖现有文件前要求当前版本全文已提供；局部替换要求被替换区间已提供；移动或删除要求已读取该版本、取得指纹并核对目标身份。新建不存在的文件无需旧文。应用根据工具操作生成读取要求，不能让模型传入参数跳过；内部读取不能补记这些前提。

### 4.4 输出预算初始值

| 输出 | 初始上限与超限处理 |
|---|---|
| 显式选择参考 | 最多 20 个；每份预读最多 2000 字符，总预读最多 8000，按选择顺序分配 |
| `read_file` | 原文最多 16000 字符，整个结果最多 20000；返回实际区间与下一游标 |
| `search_text` | 最多 50 条、每条摘录最多 240 字符，整体最多 8000；标明截断 |
| 系统目录 / `list_files` | 系统目录预览最多 8000；工具结果最多 12000，分页返回其余条目 |
| 有效章节索引注入 | 总计最多 8000；其他条目按需搜索 |
| `git_diff` / `git_log` | 差异维持 20000；日志最多 50 条、结果最多 12000；不改变 Git 权限 |

这些是实施初始值，集中定义并测试，不做一页用户配置。结构化字段也受上限约束；不能截断 JSON 后当成功返回。正文工具的大小错误不得通过静默截断待写文本处理。

### 4.5 写前核对与本轮自己的修改

所有作品变更在准备 Git 之前统一检查材料、任务权限和读取前提；Git 准备完成后、实际落盘前再次复核依赖，再调用原有文件方法检查目标指纹。检查失败不得先创建文件或准备基线来冒充无副作用失败。

检查和写入之间仍存在外部程序修改的时间窗口，本版不提供跨进程文件事务。单作品受理锁与执行锁继续保留。

本轮成功写入后必须更新记录：

- `write_file` 的全文由模型提供，可登记新版本全文；旧版本材料标为已替换，相关索引失效。
- `edit_file` 不能仅因内部组装了完整文件就登记“模型看过全文”。此前完整覆盖且能确定性映射时可更新覆盖，否则要求后续操作按需重读新版本。
- 移动保持内容指纹时可迁移已知区间，同时记录原路径消失；删除记录本轮删除事实，不能把合法删除误判为外部来源丢失而永久阻断后续操作。
- 外部变化必须重读；不允许模型仅提交一个新指纹就刷新依赖，也不允许提供“忽略过期”参数。

## 5. 章节索引与冲突核对

新增 `workspace/chapter_index.py`，索引保存在现有作品绑定状态目录的 `chapter-index.json`。作品仍只有章节、小传、线索和真相；索引是可重建派生数据，不参与作品 Git，不作为正式设定。

每章保存 `source_path`、`source_digest`、`recipe_version`、生成时间、摘要，以及带原文证据的事件/人物/时间地点/线索。状态为 `missing`、`valid`、`stale`、`source_missing`、`unavailable`；只有有效记录的内容可注入模型。无命中返回空结果，过期检查不启动模型。

作者通过“生成/更新所选章节索引”明确启动任务，每轮最多 10 章。工具仅开放目录、搜索、读取和 `save_chapter_index`；不能写作品。索引只由该章当前原文生成，不从上一版摘要递归压缩；发布需全文覆盖、引文匹配并复核源指纹，停止保留已发布项。

`chapter_index.py` 的发布接口示例：

```python
def publish_index(draft, *, workspace, ledger, store, allowed_paths):
    if draft.source_path not in allowed_paths:
        raise index_scope_error(draft.source_path)
    source = workspace.read(draft.source_path)
    if source.digest != draft.source_digest:
        raise source_stale_error(source.path)
    ledger.require_complete(SourceRef(source.path, source.digest))
    validate_evidence(draft.evidence, source.text)
    # store 在替换缓存前再次核对来源；中断不发布半份条目。
    store.publish(draft, expected_source=SourceRef(source.path, source.digest))
```

示例中的错误构造、结构验证和存储接口在实施时统一定义。默认每章摘要最多 500 字符、12 个事件、每段引文最多 160 字符，分类通过证据编号关联，结构约束与工具 schema 共用。

证据只能证明原文存在，不能证明“人物声称”为真实事件。区分明确叙述、人物说法和推测；遇到正文、小传、真相互相矛盾时给出出处，不能自行把现有设定改成模型推测。作者明确要求改变设定时按任务执行，不能用“原文优先”阻止作者修改。

## 6. 本轮修改范围

### 6.1 单 Agent 内部登记，不设默认审批

普通任务起初没有作品写权限，可以列目录、搜索、读取和回答。新增 `set_task_scope`：模型在定位目标后登记本轮任务理解、授权来源、必需参考、允许操作和明确禁止项；应用校验结构与路径，保存范围事件，写工具才可通过。

这是同一个 Agent 的工具约束，不要求另起一轮模型分类调用，也不强制拆成两个 harness。纯讨论可直接结束，无需先提交一份计划。未登记范围而调用写工具返回可修正错误，不直接终止整轮。

授权依据只来自作者消息。对“继续”，同时记录本轮承接语句和被承接的作者请求；助手计划、作品内容与旧范围都不能单独构成授权。范围与检查参数不因模型填了结构化字段就成为作者确认。

### 6.2 操作分别授权

| 操作 | 核对对象 |
|---|---|
| 创建 | 确切新路径；目标必须不存在 |
| 更新 / 局部修改 | 现有目标路径及其当前指纹 |
| 删除 | 确切路径、删除权限及指纹；“修改”不默认包含删除 |
| 移动 | 确切源目标路径对、源指纹与目标不存在；两端都检查 |

范围使用规范化的确切路径，不接受任意目录前缀或模型传入的通配符。作者明确允许跨章修改时，可以在读取影响后登记多个具体文件。材料选择不生成任何操作授权。

`task_scope.py` 的核心示例：

```python
from dataclasses import dataclass
from typing import Literal

@dataclass(frozen=True)
class Mutation:
    action: Literal["create", "update", "delete", "move"]
    path: str
    target: str | None = None

@dataclass(frozen=True)
class WriteScope:
    mode: Literal["read_only", "edit"]
    grants: frozenset[Mutation]
    denied_paths: frozenset[str]

    def permits(self, operation: Mutation) -> bool:
        touched = {operation.path}
        if operation.target is not None:
            touched.add(operation.target)
        return (
            self.mode == "edit"
            and touched.isdisjoint(self.denied_paths)
            and operation in self.grants
        )
```

实际模型还需记录授权消息/引文、目标说明、固定或可发现范围、版本及相关性证据；路径与操作组合必须通过共用校验，禁止为非移动操作传目标。

### 6.3 明确限制与动态发现

- 固定范围：例如“只改第三章”。本轮范围不能由模型扩大；需要范围外修改时说明剩余问题，由作者在后续明确要求。
- 可发现范围：例如“同步相关章节”。登记原始同步目标与允许的操作类别；后续发现文件可通过同一工具追加，但必须提供实际读取的关联证据，保留原禁止项，不得增加原任务未授权的操作类别。
- 追加只能增加与原目标有关的具体路径，不能把范围改为整个目录。追加事件在写入前生效，不追认已发生的越界写入。
- 本轮范围修改采用版本号，旧版本不能覆盖新版本；成功写入后不能回写原授权说明。模型可以缩小范围，不能删除已有执行事实。
- 作者中途发来的新要求作为下一轮任务受理，沿用单作品占用规则；不静默修改已经运行的请求。

首版不新增必填权限表单。将来若提供可选的显式路径/操作限制，必须由客户端作为独立字段提交，不能从参考列表推导；本次不预留无使用方的接口字段。

**确定性边界：**应用能证明操作没有超出已记录范围，不能证明范围解释符合自然语言意图。自然语言中的“只改”“同步”仍由模型解析；校验引文存在、关联证据存在，不等于验证语义正确。此项通过受控与真实模型样例单独验收，不宣传为完整授权证明。

## 7. 工具与执行接线

新增 `workspace/materials.py` 管理来源和读取，`workspace/task_scope.py` 管理本轮权限，`workspace/review.py` 管理检查。通用文件底层不知道会话和任务范围，正文导入与显式 Git 撤销沿用各自入口，不误走聊天权限。

`RunContext` 的拟定接口示例：

```python
@dataclass
class RunContext:
    workspace: Workspace
    session: WriteSession
    materials: MaterialLedger
    scope: ScopeController

    def before_mutation(
        self, operation: Mutation, *, required_read: ReadRequirement | None
    ) -> None:
        self.scope.require(operation)
        self.materials.require_target_read(required_read)
        self.materials.require_references_complete()
        self.materials.verify_current(self.workspace)
        if not self.session.prepared:
            self.session.prepare()
        self.materials.verify_current(self.workspace)
```

所有作品写工具调用同一入口；不能有 `edit_file`、移动或删除遗漏检查。`ReadRequirement` 由应用根据工具生成，区分全文、已匹配区间和目标身份；只有新建操作可为 `None`。`write_file` 根据目标存在性区分创建/更新，若存在性与提交意图冲突则失败，不自动换一种权限。实际文件方法仍执行目标指纹与元信息检查，成功后才能更新材料状态和发送成功事件。

文件工具成功表示实际已落盘。错误通过工具结果反馈模型，重读和合理调整属于本次请求内继续执行；没有外层自动重试整个任务。等待作者决定时输出具体疑问并结束本轮，不占用作品锁无限等待。

索引和只读检查用途开放独立工具集合，完全不暴露作品写工具。普通任务可以使用登记工具和受网关约束的写工具；`git_diff`、`git_log` 维持只读，提交和撤销不向模型开放。

## 8. 有原文依据的写后检查

### 8.1 启动方式与边界

程序已有的路径、指纹、格式检查继续随写入执行，不调用模型。需要理解剧情的检查仅有以下入口：

- 用户说“检查第三章”，或主动点击结果里的“检查本次改动”：受理 `purpose=review` 的只读任务。
- 用户明确说“修改第三章，改完检查与人物设定是否冲突”：在本轮任务登记中记录检查要求与作者引文，完成修改后进入只读检查阶段。

普通“修改第三章”不隐含开启独立模型审计；打开文件、刷新、保存、检测过期也不启动。登记检查要求不是文件工具可自行触发的授权。若模型没有正确识别自然语言检查要求，视为任务理解缺陷，纳入语义验收。

写后检查使用同一轮受理时固定的模型连接，消费本轮剩余回合预算，保留停止能力，不自动另建任务。只读检查阶段可建立工具更窄的 harness；不修改上游循环，不固定新增审阅者角色。

### 8.2 检查输入与输出

检查输入为实际落盘后的目标原文、修改结果、用户检查要求及按需读取的相关材料；不能只检查模型曾生成但未保存的文本。检查前冻结目标指纹，发布报告前复核所有依据。

报告保存目标版本、实际覆盖范围、问题、证据、建议和未覆盖项。每条问题至少有一处实际读取的原文证据，跨文件冲突应列双方出处；推测标为疑点。区分人物说法、回忆、叙事时间与客观事件，不把已死亡角色出现在回忆中直接判错。

`review.py` 的报告结构示例：

```python
from typing import Literal
from pydantic import BaseModel, ConfigDict, Field

class Evidence(BaseModel):
    model_config = ConfigDict(extra="forbid")
    path: str
    digest: str
    start_char: int = Field(ge=0)
    end_char: int = Field(ge=0)
    quote: str = Field(min_length=1, max_length=160)

class Finding(BaseModel):
    model_config = ConfigDict(extra="forbid")
    kind: Literal["continuity", "disclosure", "task_mismatch", "other"]
    certainty: Literal["supported", "suspected"]
    description: str = Field(min_length=1, max_length=500)
    evidence: list[Evidence] = Field(min_length=1, max_length=4)
    suggestion: str = Field(min_length=1, max_length=500)
```

保存工具还需核验字符区间、引文、版本与读取覆盖。结构 schema 正确不能替代这些验证，也不能证明语义判断正确。

报告状态区分 `findings`、`no_findings`、`incomplete`、`stale`；无问题且目标全文及必需参考确实覆盖时才能给 `no_findings`。未读全、来源不可用或预算耗尽给 `incomplete`，不能包装成检查通过。来源变化给 `stale`，不自动重跑。

报告存应用状态事件，不写设定、不产生作品 Git 提交。不提供自动修复工具；作者后续要求修复时作为新的修改任务，重新确定范围。

### 8.3 失败与历史记录

修改已落盘但检查失败时，保留修改并记录 Git，整轮按实际情况为部分完成；报告状态单独说明，不把检查失败混成“文件未保存”。检查发现疑点不自动撤销、阻断已完成保存或宣称作品错误。

跨文件修改失败继续保留已成功文件，清楚展示已完成、失败和未完成项。本版不提供全有或全无保证。报告回看时确定性复核目标版本，过期显示需重新检查，不启动模型。

## 9. 接口、状态与前端契约

### 9.1 共用受理模型

首次发送与续聊使用同一个输入定义与验证流程。接口前缀保持 `/api/file-workspaces`，不随产品版本重命名。

```python
from typing import Literal
from pydantic import BaseModel, ConfigDict, Field

class ContextInput(BaseModel):
    model_config = ConfigDict(extra="forbid")
    selected_path: str | None = None
    reference_paths: list[str] = Field(default_factory=list, max_length=20)
    observed_digests: dict[str, str] = Field(default_factory=dict)

class TurnInput(BaseModel):
    model_config = ConfigDict(extra="forbid")
    text: str = Field(min_length=1)
    request_key: str = Field(min_length=1)
    purpose: Literal["chat", "update_chapter_index", "review"] = "chat"
    context: ContextInput = Field(default_factory=ContextInput)
    index_paths: list[str] = Field(default_factory=list, max_length=10)
    review_paths: list[str] = Field(default_factory=list, max_length=20)
```

模型级验证补齐互斥规则：索引用途仅接受非空 `index_paths`，检查用途仅接受非空 `review_paths`，普通 chat 不接受这两项。自然语言只读检查可在 chat 内由模型登记并执行；显式结果按钮使用 review 用途，二者复用检查服务。索引与显式检查入口自行生成有意义的非空文字，不制造空会话。

`observed_digests` 只允许关联本次当前路径和显式参考，数量有界；它是客户端看到的版本，不是服务端内容依据。路径先经过现有工作区校验，不能拼接任意磁盘路径。

受理按“规范化输入 → 查请求键 → 比较已受理身份 → 校验新请求材料 → 登记与占用”执行。身份包含规范化文字、会话、用途、当前路径、保序去重后的参考、客户端观察指纹及各用途目标。首次/续聊共用；同键同输入返回原结果，同键不同输入返回冲突，重试不重新取材料版本。

原始请求身份、受理材料快照、执行材料与范围分别保存；模型后来发现的文件不改变请求身份。旧事件缺字段时显示“未记录”，不能依据今天的界面或文件补造旧材料。

旧已受理请求没有完整身份字段时，仅从原作者文字和原会话恢复旧身份，其新增字段取旧行为的空材料与 chat 默认值。同键携带新材料不能匹配成旧请求；不依赖当前磁盘反推旧版本，不批量改写旧日志。

`service.py` 的接线示例：

```python
# 位于原受理锁内；所有辅助函数均为拟新增的应用层接口。
request = normalize_turn_input(payload)
previous = store.find_accepted(request.request_key)
if previous is not None:
    require_same_request(previous.request_identity, request.identity())
    return previous.public_view()  # 不因文件已经变化而改写旧快照
snapshot = freeze_context(workspace, request.context)
accepted = store.accept_request(request, snapshot)

# 执行阶段使用持久化快照，不反读当前界面。
verify_accepted_context(workspace, accepted.context)
ledger = prepare_materials(workspace, accepted.context)
run = RunContext(workspace, session, ledger, ScopeController())
```

现有模型快照、受理占用、请求去重、停止及终态处理必须保留；示例省略这些现有步骤，不表示重新实现一套轮次系统。

### 9.3 前端模块与发送示例

新增 `ReferencePicker.tsx`、`TurnMaterials.tsx`、`TaskScopeDetails.tsx`、`ReviewReport.tsx` 和 `ChapterIndexPanel.tsx`。输入区保留简洁，材料、权限和报告详情按需展开，不显示必须填写的授权表单。

```tsx
// 组件生成快照；接口端序列化、重试均复用同一个 request。
const request: TurnInput = {
  text: draft.trim(),
  request_key: crypto.randomUUID(),

  },

  review_paths: [],

```

`TurnInput` 在 `frontend/src/api/workspace.ts` 定义，首次与续聊均传完整对象。`conversations.ts` 不反向依赖工作区状态；组件明确传快照，避免循环依赖。参考为空时仍发送合法请求。

草稿保存沿用现有版本与冲突合并机制，同一个 PATCH 同时提交文字与参考，不让文字清除而引用残留。受理后只清除仍与此次提交一致的草稿，重试保持请求键和原输入，不把当前选择偷偷带入旧请求。

### 9.4 错误与失败语义

| 错误码 | 处理 |
|---|---|
| `CONTEXT_REFERENCE_LIMIT_INVALID` | 材料数量超限；拒绝新请求、保留草稿 |
| `CONTEXT_SOURCE_NOT_FOUND` | 指定来源缺失，404；给出具体路径 |
| `CONTEXT_SOURCE_STALE_CONFLICT` | 受理观察版本、执行快照或写前依赖失效，409 |
| `REFERENCE_UNRESOLVED_CONFLICT` | 已登记的必需参考无法定位，不写作品 |
| `REFERENCE_NOT_FULLY_READ_CONFLICT` | 必需原文范围尚未提供，返回剩余范围 |
| `TASK_SCOPE_REQUIRED_CONFLICT` | 没有本轮范围就调用写工具 |
| `TASK_SCOPE_DENIED_CONFLICT` | 操作、路径或范围扩展不被允许 |
| `TASK_SCOPE_EVIDENCE_INVALID` | 引文不属于作者消息，或关联证据不匹配 |
| `TASK_SCOPE_STALE_CONFLICT` | 使用旧范围版本更新权限 |
| `CHAPTER_INDEX_SCOPE_INVALID` / `CHAPTER_INDEX_EVIDENCE_INVALID` | 索引用途、目标或证据不合法 |
| `CHAPTER_INDEX_WRITE_FAILED` | 缓存保存失败，原作品不受影响 |
| `REVIEW_SCOPE_INVALID` / `REVIEW_EVIDENCE_INVALID` | 检查目标、证据或覆盖声明不合法 |
| `REVIEW_SOURCE_STALE_CONFLICT` | 检查期间依据变化，不能发布当前有效报告 |

HTTP 基础类型/结构错误沿用 422；模型工具返回对应错误而不伪造 HTTP 调用。其他业务错误沿用后缀状态规则与 `{code, where, why, fix, details}`。文案示例：`[TASK_SCOPE_DENIED_CONFLICT] tools.write_file：本轮不允许修改设定集/真相.md。建议：保留该文件，并在回复中说明需要作者决定的关联修改`。

## 11. 验证与交付证据

### 11.1 确定性验证

| 范围 | 必须覆盖 |
|---|---|

### 11.2 任务理解与真实写作

受控 provider 验证工具规则、事件与磁盘结果；这不能证明真实模型理解自然语言。另用独立作品执行少量真实模型任务，保留作者要求、定位结果、实际读取、范围和最终文件/Git证据：

1. 不选文件，“参考第一章修改第三章”，确认能定位、读取和修改，第一章不被当作修改目标。
2. 只选小传，“修改这一章”，核对当前阅读定位与参考不授权。
3. “只改第三章，不动人物设定”，准备诱发跨文件调整的矛盾，验证不会扩展。
4. “修改动机并同步相关章节”，核对发现的文件、关联理由、操作类别与范围追加。
5. 假设凶手、只检查、同名人物、否定参考和“继续”缺少明确承接对象，核对讨论、澄清与写入边界。
6. 准备“首次进入书房”细节，验证后文能经搜索/索引回到原文并呼应；改变来源后旧索引不再使用。
7. 明确要求“改完检查”，准备回忆中的已死亡人物和一处真正时间冲突，核对疑点证据、误报与未覆盖项；普通修改不启动额外检查。

真实模型每项记录具体模型与样例，不宣称所有模型都正确或检查必然可靠。不因用例失败自动重跑扩大调用；查明原因后由开发者明确启动下一次验证。

### 11.3 前后端完整流程

使用真实后端和受控 provider，在浏览器完成：不选文件发送 → 选文件/目录加入 → 切换草稿 → 发送中换稿纸 → 回看材料 → 外部改源 → 写前拒绝与重新读取 → 查看范围 → 检查本次改动 → 停止/刷新/重启恢复。断线覆盖实时与回读一致，不用截图代替磁盘及接口断言。

实施后按阶段运行针对性测试；集成交付再执行 `uv run pytest -q`、`uv run ruff check src/hastings tests/workspace`、`uv run mypy src/hastings`，以及 `frontend/` 中的 `npm test -- --no-file-parallelism`、`npm run build`、`npm run test:e2e`。只编写计划时不运行这些代码验收，也不声称通过。
