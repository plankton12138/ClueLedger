# 0.6 下一阶段开发计划：状态层与装配分层

本计划属于 0.6 的后续阶段（V06-E），描述目标状态与推进顺序，**尚未实施**。当前能力仍以
[模块导航](modules/README.md)与[运行说明](release.md)为准；本文件中的字段、接口、事件与
界面在对应阶段交付并验证后，才写入模块说明。

## 1. 目标与边界

### 1.1 目标

让模型写第 N 章时，手里有一份「截至第 N 章」的可信状态，而不是靠回读前章推断；让作者
看得出这一轮模型知道什么、不知道什么。

0.6 已解决「准不准写」和「写完怎么验」，本阶段补「给什么上下文」的中间层。

### 1.2 必须坚持

- 声明与测量分开：作者意图写在角色卡元信息里，正文实际披露到哪由原文生成。
- 状态按「实体 × 时点 × 受众」组织，人物只是第一个域。
- 装配按上下文类型分开，写作类型里不出现真相与真身份。
- 装配结果可回放：本轮注入哪些条目、跳过什么、裁掉什么，都进会话事件。
- 冲突报告，不静默覆盖；能证明「原文里存在」，不声称「读者已理解」。

### 1.3 本版不做

作者手动修改状态（先保留位置，不实现）、向量检索、全员知情矩阵、章节锁定、每章独立
提交、跨设备同步状态目录、自动修稿、检查后自动扩大范围。

## 2. 设计原则

**声明与测量分开。** 声明进作品、走 Git、走指纹，人可读；测量进作品状态目录，可随原文
重建，不进 Git。两者混在一起就会出现第二份事实来源。

**状态是三个轴。** 人物、线索、物件、地点都有「截至第 N 章」和「谁知道」两个维度。任何
一条状态都能写成「实体、时点、受众」三元组，这样后面加域不用改结构。

**准入三条同时满足才进状态层**：随章节变化；装配时要按时点或受众过滤；不带它模型就会
写错。文风样本、写作要求、索引摘要、检查报告都不满足，不进来。

## 3. 数据归属

| 位置 | 内容 | 可否重建 | 参与作品 Git |
|---|---|---|---|
| 角色卡 front-matter | 声明：`roles`、`aliases`、`surface`、`disclosures` | 不能，是源头 | 是 |
| 作品状态目录，一域一文件 | 测量：披露、人物状态、名词、时间线 | 能，随原文 | 否 |
| 会话事件 | 注入记录：给了哪些、跳过哪些、为什么 | 不能，仅用于回放 | 否 |

状态目录维持现有位置（`<状态目录>/workspaces/<绑定 ID>/`），与 `chapter-index.json`、
`reviews.json` 同级：

```
<绑定 ID>/
├─ chapter-index.json      已有
├─ reviews.json            已有
├─ disclosure.json         新增：身份披露（E2）
├─ glossary.json           新增：名词与别名（E3）
├─ character-states.json   新增：位置、生死、立场（E4）
└─ timeline.json           新增：故事内时间（E4）
```

一域一个文件：失效独立、重建成本不同、坏一份不连坐。每个文件带 `record_version`
（结构版本）与 `recipe_version`（生成规则版本），规则变化整域过期，不猜测兼容。

现有 `state.py` 的 `conversation_root()` 已同时承载会话、索引与报告，语义超出会话。本阶段
改名 `workspace_state_root()`，**路径不变**，旧名保留一个版本作为别名，不做任何数据迁移。

## 4. 声明：角色卡元信息

### 4.1 字段

在现有 `roles` 之外增加三个可选字段，缺省即「未声明」，不影响现有解析。

| 字段 | 含义 | 约束 |
|---|---|---|
| `aliases` | 同一角色的其他称呼 | 数组；全书唯一，指向两人即冲突 |
| `surface` | 读者起初看到的社会身份 | 字符串，可为空 |
| `disclosures` | 身份披露事件列表 | 数组，按章节递增；每项 `fact` 加 `from_chapter` 或 `planned_chapter`，两者互斥 |

用事件列表而非单值揭底章，因为反转需要多次披露：第 9 章揭凶手，第 12 章再揭她是警方线人。

### 4.2 示例

```yaml
---
roles: [suspect]
aliases: [林医生, 林医师]
surface: 被害人的主治医师
disclosures:
  - fact: 主治医师
    from_chapter: 3
  - fact: 与死者有旧怨
    from_chapter: 6
  - fact: 凶手
    planned_chapter: 9
---
```

### 4.3 解析与诊断

解析仍集中在 `metadata.py`，接口、工具与前端不各写一套。规则：

- 未知键忽略，不阻断；未知 `roles` 值维持现有诊断。
- `fact` 为空、两个章节字段同时出现或都不出现、章节号不是正整数：**该条**作废并给诊断，
  不猜一个值顶上，其余条目照常生效。
- `from_chapter` 超出已有章节数：诊断（声明与正文不一致）；`planned_chapter` 超出：正常，
  按未来章处理。
- 别名重复、别名与他人姓名或 `id` 冲突：解析阶段只记录，装配前汇总成冲突清单。

## 5. 派生：披露记录

### 5.1 结构

```json
{
  "record_version": 1,
  "recipe_version": 1,
  "generated_at": "2026-10-23T09:00:00+08:00",
  "entities": {
    "C_002": {
      "path": "设定集/角色小传/林静.md",
      "declared": {
        "surface": "被害人的主治医师",
        "disclosures": [{"fact": "凶手", "planned_chapter": 9}]
      },
      "observed": [
        {
          "fact": "主治医师",
          "first_chapter": 3,
          "evidence": {
            "path": "正文/0003 雨夜.md",
            "digest": "9f2c…",
            "start": 412,
            "end": 468,
            "quote": "林静把病历摊在桌上……"
          }
        }
      ],
      "known_by": {"佐藤警部": 9},
      "sources": [{"path": "正文/0003 雨夜.md", "digest": "9f2c…"}]
    }
  }
}
```

`declared` 是从元信息抄下的快照，用来判断「声明变了」；`observed` 只能来自正文，每条必须
带路径、版本、字符区间与引文。区间语义与材料记录一致：服务端字符下标、左闭右开、按该版本
原文核对。

### 5.2 生成与发布

沿用章节索引的四道核对，抽取任务只读原文：

1. 目标角色在本轮允许范围内；
2. 读完该角色小传当前版本全文与涉及的章节原文；
3. 每条 `observed` 的区间与引文对得上；
4. 发布前复核所有 `sources` 指纹，任一变化整份不发布。

发布工具只接受结构化参数，不接受整份 JSON 覆盖：一条 `observed` 一条依据，缺依据的条目不
写入。实现方向与 `save_chapter_index` 的校验共用同一套证据核对函数，避免两套实现。

```python
@dataclass(frozen=True, slots=True)
class DisclosureDraft:
    entity: str            # 角色 id，来自小传元信息
    fact: str
    first_chapter: int
    evidence: IndexEvidence  # 路径、版本、区间、引文，复用索引的证据类型

def publish_disclosure(
    store: DisclosureStore,
    workspace: Workspace,
    drafts: Sequence[DisclosureDraft],
) -> DisclosureRecord:
    """整域发布：全部条目先核对，任一条不过就不写文件。"""
    for draft in drafts:
        check_evidence(workspace, draft.evidence)   # 版本、区间、引文
    return store.replace(workspace, drafts)
```

### 5.3 状态与冲突

记录本身是「上次生成的结果」，当前状态由磁盘算出，与章节索引一致：

| 状态 | 条件 | 装配时 |
|---|---|---|
| `valid` | 所有 `sources` 指纹与当前一致 | 正常注入 |
| `stale` | 任一章或任一小传被改过 | 不注入该条，注明最后有效章 |
| `conflict` | 声明与 `observed` 不一致（如两个真身份、计划章早于实际揭底） | 该实体整条不注入，进冲突清单 |
| `source_missing` | 来源文件被删 | 同 `stale` |

`conflict` 与 `stale` 分开，因为处理方式不同：过期等重算，冲突要人看。

## 6. 装配层

### 6.1 上下文类型

装配不再只有一份，按用途分开，每种有自己的白名单与断言：

| 类型 | 用途 | 带 | 不带 |
|---|---|---|---|
| `writer` | 写正文、改章节 | 目录、写作约定、状态（截至当前章）、近层原文、章节索引、设定集（含真相）、作者参考 | 真身份、计划揭底章、检查报告 |
| `extract` | 更新披露、索引 | 目标原文全文、输出格式 | 文风样本、写作指令、旧摘要、线索与真相 |
| `review` | 只读检查 | 目标正文、相关设定、状态、目录 | 写作指令、索引摘要 |
| `chat` | 讨论、问答 | 目录、作者指定参考 | 状态账本、真相（除作者明确要求） |

写作类型保留真相：本产品是单 agent 循环，规划伏笔与自查都要用它。隔离的对象是**作者侧
状态**——真身份、计划揭底章这类还没写进正文的信息不进写作上下文。这条在 E1 只做类型与
分区，E2 有了字段之后用断言落实。

### 6.2 顺序与分区

重要内容放两头，中间放资料：

```
[系统] 写作约定 + 文风样本
[用户] 本轮任务（写第几章、推进什么、回收哪条）
[资料] 检索到的原文片段（标为「参考资料」）
[资料] 前情索引摘要
[资料] 状态：截至第 N 章的身份披露、在场人物、未回收线索
[资料] 上一章结尾原文
[指令] 字数、视角、悬念要求
```

装配产物带分区标记（区名 + 来源 + 字符数），而不只是拼成一段字符串。分区标记是后面
「注入事件」和「界面显示」的唯一数据源。

### 6.3 预算与裁剪

| 分区 | 预算 | 超限处理 |
|---|---|---|
| 常驻（约定 + 当前锚点） | 1200 字符 | **报错** `CONTEXT_ASSEMBLY_FAILED`，不截断 |
| 状态注入 | 1500 字符 | 按优先级裁剪，裁剪项进事件 |
| 章节索引 | 8000 字符（沿用） | 按章序取最近，其余不注入 |
| 近层原文（上一章结尾） | 2000 字符 | 从结尾向前取足 |
| 作者参考预读 | 8000 字符（沿用） | 按选择顺序 |

状态裁剪优先级：当前章在场人物 > 计划本章回收的线索 > 未回收线索标题 > 本章出现的名词 >
其他人物。被裁的每一项都要写明原因，界面能看见。

```python
def allocate(budget: int, items: Sequence[StateItem]) -> tuple[list[StateItem], list[Skip]]:
    """按优先级装入，装不下的返回跳过原因，不做静默截断。"""
    taken: list[StateItem] = []
    skipped: list[Skip] = []
    left = budget
    for item in items:                      # 调用方按优先级排好
        cost = len(item.render())
        if cost > left:
            skipped.append(Skip(item.key, "budget"))
            continue
        taken.append(item)
        left -= cost
    return taken, skipped
```

### 6.4 注入事件

每轮装配完成后追加一条 `state_injected`，只记身份与结果，不存全文：

```json
{
  "type": "state_injected",
  "turn_id": "t_01J…",
  "profile": "writer",
  "chapter": 8,
  "injected": [{"entity": "C_002", "fields": ["surface", "known_by"], "chapter": 6}],
  "skipped": [{"entity": "C_007", "reason": "stale", "last_valid_chapter": 5}],
  "truncated": [{"entity": "C_011", "reason": "budget"}],
  "budget": {"limit": 1500, "used": 1180}
}
```

这条事件同时是三件事的依据：模型这轮看到了什么、界面显示的摘要、作者追问「它为什么这么写」
时的回答。

## 7. 工具与执行接线

### 7.1 模型侧工具

新增两个只读工具和一个发布工具，不扩成万能状态编辑器：

| 工具 | 用途 | 边界 |
|---|---|---|
| `list_state` | 列出某域条目：名称、当前值、最后更新章、状态 | 只给摘要，不给正文 |
| `read_state` | 读取单条完整记录与证据，按游标分页 | 单次最多 4000 字符 |
| `save_disclosure` | 发布披露条目 | 只在 `extract` 类型可用，每条必须带证据 |

**账本文件本身不开放读取**：`read_file` 的受管路径只有正文与小传、线索、真相，不包含状态
目录。否则模型一次拉全量，分层就作废。

### 7.2 任务用途

受理接口的 `purpose` 增加 `update_disclosure`，工具模式加 `state`：

- `state` 模式：只读工具（目录、搜索、读取）+ `save_disclosure`，不暴露作品写工具；
- 抽取任务的回合上限单独计，不与写作共享；
- 其它用途调用 `save_disclosure` 直接拒绝（`STATE_TASK_CONFLICT`），提示先以抽取用途发起。

### 7.3 回合与预算

抽取任务默认 6 个回合、最多 10 个角色。放弃或超时按部分完成处理：已发布的条目保留，未发布
的不写空记录，界面显示「本次更新了 4/7 个角色」。

## 8. 检查扩展

在现有只读检查中增加两类可判定问题，沿用报告结构：

| 类别 | 判定条件 | 输出 |
|---|---|---|
| 提前泄露 | 正文出现计划揭底章之后才该出现的身份信息 | 问题 + 计划章 + 实际章 + 双方证据 |
| 身份冲突 | 两个真身份、计划章早于实际揭底、别名指向两人 | 问题 + 声明出处 + 正文出处 |

证据要求与现有一致：每处问题至少一条路径、版本、区间、引文；跨文件冲突列双方。不能只因为
「记录里写着」就报问题，记录本身也可能是旧的。

明确边界：检查能证明「某章出现了某句话」，不能证明读者已理解，也不能判断披露写得是否自然。
这两件事分别用「疑点」与作者阅读表达，不计入可判定问题。

## 10. 分阶段实施

### V06-E1 装配容器

**目标**：把「一份合并注入」拆成按类型、按分区、可回放的装配。

- 改动方向：`context.py` 增加 profile 与分区；`service.py` 装配处改为调用装配器并写
  `state_injected`；`state.py` 的 `conversation_root` 改名；前端扩 `TurnMaterials`。
- 用例：`extract` 产物不含线索、真相与索引摘要；必装分区超限报错而非截断；每轮都有
  `state_injected`，跳过项带原因；事件记的分区与系统提示里实际出现的分区一致。
- 完成条件：断言测试、预算用例、事件同源用例全绿；无状态域时装配行为与 0.6 一致。
- **状态**：已实施（2026-10-23），证据见 [V06-E1](notes/V06-E1-assembly.md)。

### V06-E2 身份披露

**目标**：第一个域打穿：声明 → 抽取 → 记录 → 注入 → 检查 → 界面。

- 改动方向：`metadata.py` 增加字段与诊断；新增 `disclosure.py`；`agent.py` 增加三个工具与

## 12. 风险与退出条件

- **字段无人维护**：状态过期即不注入、界面标过期，宁可少给不用旧值。若某域连续三个版本
  没人更新，删除该域而不是留着假数据。
- **预算膨胀**：状态注入固定 1500 字符硬上限，裁剪必须报告；不接受「先放宽再说」。
- **抽取成本**：只在作者显式发起时跑，不做自动触发；单次最多 10 个角色。
- **误报**：检查新增类别先在样例作品上统计，误报超过作者可接受范围时降级为「疑点」，不计入
  问题数。
- **回滚**：每个域独立文件，删文件即回到上一阶段能力；新事件类型旧前端忽略即可，不改旧字段。
