# V06-E5 线索与伏笔台账

2026-10-23。目标：写第 N 章时，「第 3 章埋下、第 7 章该回收」的线索不会因为没人提醒而永远
留在第 3 章。

## 做了什么

**`clues.py`**：一条线索 = 内容 + 埋设章 + 计划回收章（可空）+ 状态（`open` / `resolved` /
`dropped`）+ 埋设处原文依据；标为已回收时还要回收章与回收处依据。

- **埋设处与回收处都要对得上原文。** 任一源文件改过，整条登记失效、不采用，并在状态里说明
  失效了几条。
- **只有未回收的进上下文。** 已回收与已废弃只给作者看，不占预算。
- **排序是确定的**：超期（计划章 ≤ 当前章）→ 下一章该回收 → 有计划但未到期 → 没定回收章。
- **超期判定不靠模型**：`due_chapter <= 当前章` 且仍 `open` 就是超期，状态里单列一份清单。

**注入**：写作与检查两种用途各加 `clues` 分区（500 字符），只列未回收的，超期在前，末尾两句
「这些是读者看到过的线索，不等于真相；这一章要么推进，要么明确不推进」。超预算按行裁并写明
还有几条未列入，不整块丢弃。

**工具与接口**：`save_clues`（整批发布，任一条不过整批不写）；`read_state` 的 `domain` 加
`clues`；`GET /state?domain=clues`；状态抽屉加「线索」标签，未回收与已回收/已废弃分列。

## 与计划的一处偏差

计划写的是「『什么算伏笔』由作者在界面确认后才入账」。本版明确不做作者手动修改状态，加一个
只有作者能点的确认按钮等于新增一条作者写状态的路径，所以改为：**核对任务登记即入账，面板显示
每条原文依据，误判由作者要求模型改或标 `dropped`**。

代价说清楚：模型把普通细节当伏笔时，会占掉预算。缓解有三条——注入有 8 条与 500 字符上限、
超期项排最前而其他按章序、面板给出原文引文让作者一眼看出误判。真正的修法（候选/确认两步）
留给作者手动编辑能力落地的那一版。

另一处是「超期未回收强制注入」：这里没有做成不可裁剪，而是**排在裁剪顺序的最前面**。做成硬性
必装分区会让一条误判的线索顶掉其余全部状态，代价大于收益。

## 未完成

- **浏览器端到端未走查**：四个标签、核对发起、台账刷新都只有单元测试与构建证明。
- **在线模型未跑**：「什么算伏笔」的判定质量、误判率、超期提醒是否真的让模型去推进，都没有
  数据。计划里 E5 的完成条件（含 5 条以上线索的样例上超期项全部可见）未在真实作品上验证。
- **没有候选与确认两步**：见「与计划的一处偏差」。
- **没有「这一章推进了但没写完整」这类半回收状态**：只有未回收与已回收，中间态靠作者判断。
