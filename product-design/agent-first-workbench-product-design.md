# Hastings 0.3：Agent 主工作区与故事账本产品方案

> 性质：产品设计提案，待评审；不表示已实现，也不分配新的阶段编号。
> 日期：2026-10-17。
> 目标版本：0.3（开发中）；接续 0.2（原 V2），版本约定见[产品设计入口](README.md#版本约定)。
> 依据：作者确认“主体类似 Work Agent，右侧边栏为小说专用账本；进入软件就知道先做什么、想法放哪里”。
> 本提案调整 Phase 19 的界面主次：尚无正文时以主区对话接住想法；已有正文后，创作台中间默认展示文章，右侧常驻故事账本。
> 创作台与对话框始终是主入口；直接编辑形成可回看的版本，整体故事调整在对话中完成，作者长期记忆在后台积累。
> 作者决定权、版本记录、影响分析和正文保护作为系统能力融入上述流程。

## 1. 产品定位与体验目标

**Hastings 以故事账本为创作基础，围绕人物、线索及其关联，帮助作者发展和书写故事。**

账本既记录故事中发生了什么，也承载这些内容将如何被读者逐步发现。
Agent 在创作过程中协助维护人物动机与事件因果的一致性，并结合伏笔、悬念、信息揭示和情绪变化提出写作建议，
最终由作者决定故事的表达。

对外始终是一个熟悉当前作品的写作伙伴；策划、写作、审计和修订是内部协作方式。
作者可以从一个人物、一条线索、一段关系或一个疑问开始，逐步建立关联并写成正文。
章节和场景承载故事内容，不构成必须先创建、审批才能开始写作的规划层级。
作者不必在第一次输入前选择后台角色，也不必先掌握变更集或提交等内部术语。

**主要互动始终发生在创作台与对话框中，通过直接编辑、自然语言和少量选择按钮完成。**
独立的协作主编表单、修改审计与修订审阅模块从产品中移除。修改故事不需要进入变更页面，作者习惯也不作为一个需要配置的功能模块。
直接编辑后，系统记录改动并在空闲时积累关于作者的长期记忆；更换凶手、手法或背景时，
作者在对话中说明要求，Agent 理解全局关联、确认必要选择后统一修改。

### 产品决定：取消节拍概念

2026-10-16 确认：项目取消“节拍”（Beat）这一独立概念。作者围绕人物、线索、章节和正文表达创作意图，
无需把故事拆成节拍，也无需创建、批准或维护节拍后才能写作。这样可以减少从想法到正文之间的组织负担。

此决定覆盖产品界面、领域对象与任务依赖：后续实现移除节拍目录、编辑与审批入口，以及以节拍为单位的生成、检查和关联契约，
不将节拍换名后继续保留，也不在后台自动创建隐藏节拍来满足旧流程。

原先由节拍承载的有效信息按用途归入已有内容：人物目标与变化关联人物及具体故事事件；
伏笔、未解疑问和揭示安排关联人物、线索及正文位置；视角、表达目的和写作范围直接进入本次任务要求。
章节、场景与选中段落用于组织和定位正文，不增加一个替代节拍的强制最小规划单元。
取消节拍不取消对叙事节奏、因果、悬念或信息披露的判断，这些判断结合账本与具体正文给出建议。

本次先记入产品设计，代码与存量数据尚未调整。[V2 总设计](../dev-notes/v2/DESIGN.md) 中的节拍层级及相关模块契约
属于待修订设计；涉及节拍的后续实现以本决定为准。实施时需同步清理前后端接口、任务输入、上下文与关联引用，
妥善处理已有记录中的有效信息，不以只隐藏界面入口作为完成标准。

### 创作判断如何融入产品

产品内部从两个角度理解同一组故事内容，两者共同服务于账本与正文：

| 观察角度 | 关注的问题 | Agent 的协助方式 |
|---|---|---|
| 故事内部是否成立 | 人物行动是否有动机，线索如何产生，时间与因果是否一致，角色从何处获得信息 | 指出相关记录、具体矛盾或缺少的依据，并提出可检查的调整方式 |
| 读者如何经历故事 | 此刻知道什么、怀疑谁，哪些疑问应保留，伏笔何时出现与回应，情绪怎样变化 | 结合正文与作者意图，提出有理由的表达方案，说明可能带来的阅读感受 |

这两个角度不成为产品中的独立模式、导航页或评分体系。用户始终围绕人物、线索、真相和章节操作，
看到的是具体提示，例如“妹妹还没有获得这条信息”或“这里说明姐姐的动机会提前解开疑问”。
事实冲突需要依据；信息缺失需要说明未知；表达建议保留作者取舍。
刻意留白、延迟解释和不可靠叙述不能直接判为错误，阅读体验建议也不能作为阻止写作或采用正文的硬门槛。

### 用户需要获得的清晰感

三个需要直接被界面回答的问题：

1. 我的想法放哪里？——工作区唯一的协作输入框，文字、摘录和参考材料都从这里进入；已有正文时，输入框服务于正在阅读和编辑的文章。
2. 现在可以做什么？——Agent 根据实际进展给出一个主要建议和至多两个备选动作。
3. 哪些已经确定？——右侧账本的“已确认”内容；讨论、候选和正式正文有各自明确状态。

产品成功首先取决于这三个答案是否清楚。视觉与交互以“作家的桌面”为基准：一张稿纸、几本书、
一支代表 Agent 的笔，以及少量明确操作。正文居中，工具安静可达，留白和排版形成简洁优雅的阅读环境。
完整原则见[作家的桌面](writers-desk-design.md)。

### 各区域的职责

2026-10-17 补充：采用[模块化布局与空间利用原则](writers-desk-design.md#模块化布局与空间利用)，参考 dark 原型的大字号、清楚分区与充分使用页面的方式。
各模块按当前任务分配宽高，保留适当间距与内部边距；下列侧栏宽度为起点，可随内容和屏幕调整，优先保障文字可读。
布局与控件结合已确认的老 iOS 风格，原型中的功能和页面不作为成品要求。

| 区域 | 固定职责 | 规则 |
|---|---|---|
| 顶栏 | 作品身份、模型、作品设置 | 配置完成后收纳全局入口；未配置时主动显示接入引导，不能只留下一个空模型菜单 |
| 左侧导航，展开时约 180–220px | 找回讨论、正式稿件和参考材料 | 默认紧凑目录，可收起；移除七个平级业务页面作为主导航 |
| 主区，使用剩余宽度 | 构思时展示对话；已有正文时默认阅读和编辑文章 | 创作台与对话框持续可用，文章占据主要空间；历史、方案和图谱作为临时视图按需打开 |
| 右侧账本，展开时约 300–340px | 已确认事实、结构与待确认候选入口 | 桌面保留轻量摘要，可收起；优先本章相关，完整目录与详情按需展开 |

主区按内容状态确定默认工作焦点：没有正文时展示完整对话；已有正式正文或导入稿件时，
进入创作台直接打开当前章节，没有阅读记录则打开第一章。仅有未采用试写时仍明确标为候选，不能冒充正式稿。

正文下方保留同一个对话区和输入框，引用条标明当前章节和版本；选中文字后可将该段作为明确引用。
回复先在下方的紧凑结果区呈现，长讨论按需展开并限制高度，文章保持主要阅读空间。
作者可以主动打开完整讨论、候选、方案、差异或图谱；提供清楚的“返回正文”入口。
来回切换保留文章的未保存编辑、光标、选区和滚动位置，也保留讨论的滚动位置。
关闭临时成果后恢复正文及其目标引用；切换当前对象时更新自动引用，作者手动添加的引用继续保留。

发送消息、收到回复、任务完成和收到设定候选，都不能自动把正在阅读的正文替换成完整聊天记录或新候选。
明确点击“查看候选”“查看改动”才进入对应视图。作者采用首章后，主区显示刚采用的正文，进入写作状态。
已明确授权的整体修改完成后，同一正文视图更新至新版本并保留章节定位；有正在编辑的内容时先处理版本冲突。

主区最多打开一个完整成果或完整讨论，协作输入与摘要位于其下方，避免重现四列布局。
用户需要完整空间时，可以收起左侧导航和账本。
正文上方只保留章节名、简短状态和必要动作；历史、审计和图谱不各自占据一张常驻卡片。
功能入口使用明确文字，纸张、书籍、印章等意象用于指导视觉轻重，不替代可理解的功能名称。

### 屏幕适配

- 宽屏：左导航、主工作区、账本三部分；主区保留可读的文字宽度。
- 中等屏幕：左导航折叠，主区与账本并列；空间不足时账本改抽屉。
- 手机：先呈现主区；已有正文同样默认显示文章，协作输入可收起再展开；顶栏“账本”打开抽屉。

## 3. 首次进入：先准备模型，再接住想法

首次进入先读取模型配置和实际可用状态。未配置时优先展示 §3.2 的接入引导；
已配置且可用时直接进入构思或正文。已有配置但连接失败时保留原配置，提供重试与切换入口。
接入模型不要求先创建作品，也不收集作品名、大纲等业务字段。

### 3.1 没有作品

模型已就绪、尚无作品时，主区文案：

> 你想写一个怎样的故事？
> 一个画面、一个人物，或一句还没想清楚的念头，都可以从这里开始。

下方直接显示输入框，示例占位：“一场暴雪把几名住客困在雪山旅馆，第二天有人死了……”
辅助入口只有“导入已有稿件”，它进入同一个工作区。

不要求预填作品名、字数、类型、文风或完整大纲。第一次发送创建一个“未命名作品”，
保存这条讨论，之后再建议合适的作品名。发送前的小字说明“发送后开始一部新作品”。

还没准备展开的念头可以从消息操作“存为灵感”保留到左侧材料，记录原文和来源；
之后从该条目“继续讨论”。它只是一条可找回的想法，不会因此进入正式设定。
普通消息本身也持续保存，不要求先点收藏才能留住自己的输入。

右侧账本空态：

> 这里会保存你确认过的故事设定。
> 先说说想法，稍后再整理也可以。

不显示空表格、虚构的完成百分比或要求作者填满的设定清单。

### 3.2 没有配置模型

**检测到未配置模型后，立即引导，不等作者点击发送才告知无法对话。**

没有正文时，主区首先展示：

> 先为你的写作伙伴连接一个模型
> 可以连接你自己的模型服务账号，也可以下载本地模型试用。
> [连接已有模型]　[下载本地模型试用]
> 也可以先记录想法或导入稿件，稍后再配置。

两条路径并列可见，不要求用户先理解“提供商”“端点”等技术概念：

| 路径 | 引导步骤 | 完成后 |
|---|---|---|
| 连接已有模型 | 选择服务 → 填写用户自己的 API Key → 获取并选择模型 → 测试连接 | 保存用户的连接与当前模型，显示测试结果并进入创作 |
| 下载本地模型试用 | 检测本地运行环境与已有模型 → 使用已有模型，或选择适合设备的试用模型 → 安装引导/下载 → 加载并测试 | 设为当前模型，返回原工作区 |

已有本地模型时优先提供“直接使用”，不要求重复下载。对熟悉本地服务的作者，保留连接已有本地服务的入口。
服务预设隐藏不必要的地址字段；仅自定义连接展开高级配置。

#### 用户自带 API Key

当前产品按“用户使用自己的模型服务账号与 API Key”设计。连接页直接提供服务选择、
“填写你的 API Key”、获取密钥帮助、测试连接和模型选择；用户可以更换或删除自己的连接。
已保存密钥只展示掩码与配置状态，修改时重新输入，不在普通查询、日志、对话或导出中暴露完整密钥。
本地桌面形态由应用管理用户自己的凭据，不能要求普通用户编辑环境变量或项目配置文件。

现有界面的“使用服务端环境变量 DEEPSEEK_API_KEY”表示从运行后端进程的环境读取密钥，
属于开发或自行部署的配置能力；新产品的普通接入流程移除此选项，避免用户误解为使用平台提供的额度。
界面未配置个人密钥时明确引导填写，不静默借用部署环境中的其他凭据。
配置保存、连接测试、模型选择和实际任务调用必须使用同一个用户连接，前后端保持一致。

当前范围是个人 API 接入和本地模型使用。Hastings 的收费、订阅、充值、平台代付及统一模型额度
留待后续独立讨论，不在本轮引入收费计划，也不把用户自己的 API 使用称为平台免费试用。
模型服务费用由用户与所选服务方的关系决定；本地模型入口明确写“下载到本机运行”。

#### 本地试用的具体体验

1. 先检测运行环境、可获得的设备信息和已安装模型。环境缺失时显示安装引导及重新检测，不能声称模型已经可用。
2. 默认突出一个适合当前设备的试用选项，并提供“其他模型”。展示模型名称、下载大小、资源需求和预期用途；
   无法可靠检测设备时说明依据不足，由作者选择，不能保证流畅运行或高级创作任务一定成功。
3. 作者点击下载后显示真实阶段：等待下载、下载中、加载中、连接测试、可使用；下载进度、大小和错误来自实际服务。
   进度不可得时展示阶段，不编造百分比；提供取消和失败重试，返回引导时回读真实状态。
4. 下载成功只表示文件已获取。模型加载及实际调用测试通过后才能标为“可使用”，再提供“开始创作”。
5. 环境安装失败、资源不足或模型调用失败时，说明具体原因并提供重新选择或连接已有模型；
   不把安装、下载或调用故障包装成故事任务失败。

不在产品方案中固定某个模型及硬件门槛；交付时依据实际可用目录和设备适配给出选项。
复用现有本地模型检测、下载与配置能力，新增的是首次引导与状态衔接；现有设置入口继续可用。

#### 保留想法与已有作品

模型引导为优先入口，仍允许“先记录想法”或“导入稿件”。未就绪时明确标示暂不能使用 Agent，
输入内容保存为草稿，不制造已回复的消息。配置过程中、失败或刷新后均保留草稿；完成后回到原位置，由作者发送。

已有正文时，模型未配置也保持文章在中间可阅读、编辑和保存，在正文下方协作区展示接入卡片，
不以整页配置遮住文章；右侧已有账本仍可查看和人工维护。作者点击 Agent 功能时展开同一接入流程。
连接失败保留输入和原配置，并区分未配置、下载中、加载中、可用与连接失败，不能只显示一个笼统的“未连接”。

### 3.3 已有作品，重新进入

进入创作台时，有正文就恢复上次阅读的章节及位置，无阅读记录则打开第一章；没有正文才恢复上次讨论。
作者主动进入左侧“讨论”时可以查看完整对话，并随时返回正文。继续提示放在正文下方的协作区或构思对话中，例如：

> 上次讨论到姐妹关系；开场试写还没有采用。
> [继续修改开场] [接着讨论] [查看待确认设定]

提示依据真实的讨论、候选和任务状态生成。打开作品只回读状态，不因进入页面创建新的创作任务。
如已有任务正在执行，显示当前阶段及取消入口；如失败，显示恢复动作，而不是假装已经完成。

## 4. 单一输入框与引导方式

输入框始终接收作者自然语言，不出现“planner/writer/auditor”等角色选择。
输入框附近只放引用、附件和必要的发送/停止操作，创作动作出现在具体讨论附近。

| 用户行为 | 产品如何响应 | 作者看到的下一步 |
|---|---|---|
| 讲想法、提出假设 | 讨论、对比方案；不自动修改故事 | 一段回应，必要时一个关键问题 |
| 粘贴材料或导入稿件 | 先作为材料保存，说明已读范围 | 继续讨论，或准备设定提取候选 |
| 选择一种故事方向 | 显示该方向的清晰摘要 | “记入账本”或“继续调整” |
| 请求试写或起草 | 汇集相关人物、线索、已确认事实及作者的表达要求，整理本次范围 | 一次明确的生成动作 |
| 想埋伏笔、保留悬念或改变读者判断 | 基于相关人物、线索及已有正文提出表达候选，说明可能的效果 | 选择一种写法、继续讨论或保持原稿 |
| 直接编辑正文 | 持续保留草稿，完成时记录前后差异和一个新版本 | “完成本次修改”；随后可查看历史或继续写 |
| 请求修改建议或备选写法 | 绑定当前正文与选中范围，给出可比较的候选 | “使用这版”或继续提出要求 |
| 明确要求修改现有正文 | 确认必要的意图与范围，在授权内修改并记录版本 | 结果摘要、“查看改动”“撤销这次修改” |
| 要求更换凶手、手法或故事背景 | 在对话中理解全局关联，澄清必要选择后统一修改账本与相关正文 | 一次整体执行选择；完成后继续阅读和修改 |
| 纠正写作习惯或询问作者记忆 | 按作者要求更新或解释相关长期记忆及其来源 | 对话中“记住”“仅用于本书”或“忘记这条” |
| 检查已写正文中的悬疑问题 | 有正文后选择范围，核对人物认知、线索、时间与揭示内容 | 显示实际检查范围、具体问题和原文定位；可在对话中处理 |

### 引导原则

- 每次只问一至两个真正影响下一步的问题，避免连续填写式的访谈。
- 已给出的信息不再重复索取；未确定的内容允许保持开放。
- 推荐动作至多三个；给出“为什么现在适合做这件事”，例如“姐妹关系已确定，可以试写她们抵达旅馆时的第一次交锋”。
- 用户随时可以忽略推荐并继续说话，不用完成整个设定清单才能尝试一幕。
- 对已经完成的工作不反复推荐同一个动作；切换讨论也不清空作品进展。
- 对读不完的材料明确显示范围与省略，不能把标题、摘要或局部摘录说成全文已读。

### 前端说明与反馈

功能入口使用明确名称；打开时用简短说明解释“检查或修改什么”“操作哪些内容”“完成后得到什么”，详细规则按需展开。
使用前提供必要的范围与条件，使用中显示实际状态，使用后在原位置更新为可查看的结果，避免不断新增状态卡。
避免用“洞察故事脉络”“让故事更精彩”等修辞替代功能介绍、空态或结果说明。
按钮写具体动作，例如“检查当前章”“定位原文”“重新检查”，不只写“探索”“优化”“处理”。
错误提示说明失败对象、原因及下一步；没有结果、尚未完成和执行失败分别呈现。
这些规则适用于整个前端；悬疑审计的具体文案与状态见[悬疑审计交互设计](mystery-audit-interaction-design.md)。

### 执行边界

系统区分讨论、试写建议和明确执行要求。“假如姐姐是凶手会怎样”进入讨论；
“给我一个替代写法”产生候选；明确的“按这个改”授权在已说明的范围内执行并记录版本。
意图、对象与范围已经清楚时可以直接开始，不再要求填写角色表单或重复点击确认。

若作者要更换凶手、手法或背景，Agent 先阅读相关账本与正文，整体确认理解：将改变什么、保留什么、
哪些已写内容需要联动，以及哪些关键选择尚不明确。必要的澄清和选择全部在对话中完成。
未确定范围时提供“按这个整体修改”“调整要求”“先看看方案”等按钮；作者已明确认可同一范围时不再重复确认。
内部的分析、起草、校验和版本记录由系统连续执行，不要求逐页发起或逐章批准。

首章试写和明确要求比较的方案仍先以候选呈现；已授权的整体修改则在检查通过后统一形成新版本，
不追加逐段采用的必经环节。超出授权的事实变化、关键歧义或与新编辑的冲突才返回对话询问。

### 思考与执行过程：默认折叠，随时展开

每轮回复或创作任务提供一个可展开的过程区域，放在对应回复或任务卡上方。
默认只占一至两行，显示当前状态、简短过程预览和展开入口；用户能看见过程正在输出，也能按需查看详情。
已有正文时，该区域位于正文下方的协作区，限制展开高度并独立滚动，保持文章的阅读和编辑空间。

```text
▸ 思考过程 · 正在输出                   [展开] [停止]
  （预览模型公开返回的最新一段过程内容）

展开后：
▾ 思考过程                              [收起]
  模型公开返回的思考内容或推理摘要，随接收逐步显示……
▾ 执行记录
  实际读取的章节与账本条目、检查结果、已完成或失败的操作……

正式回复 / 修改建议
  ……
```

展示内容按来源区分：

| 内容 | 展示规则 |
|---|---|
| 模型公开返回的思考内容或推理摘要 | 有对应输出时逐步展示；若服务只提供摘要，明确标为“思考摘要” |
| 应用的执行记录 | 根据实际事件显示读取、检查、生成等阶段，以及相关对象和结果；可从引用定位依据 |
| 正式回复与创作结果 | 独立展示，可直接阅读；不与过程内容混为同一段正文 |

模型没有提供可展示的思考内容时，显示“该模型未提供思考内容”，仍展示真实执行状态。
只有收到对应过程输出或执行事件时才描述具体活动；等待响应时显示“等待模型响应”，不能编造正在分析哪些人物或线索。
过程预览是临时推演，不能自动成为账本事实、正式正文或已执行操作的证明。

交互细则：

- 生成中可以随时展开或收起，展开后继续流式显示；用户向上阅读时停止自动滚动，提供“回到最新”。
- 完成后保留可回看的过程；折叠标题更新为“已完成”，作者主动展开的区域保持展开，不强行收起。
- 停止或失败时保留已经收到的内容并标明“已停止”或“失败”，同时提供具体恢复动作。
- 重试作为独立尝试记录，前一次的过程与结果不会混入新一轮；刷新后可恢复已保存的过程和真实任务状态。
- 详情只呈现可公开展示的模型输出与应用事件，不把凭据、内部配置等敏感内容带入界面。

实现时需要前后端分别传递和保存过程内容、执行事件及最终回复，不能只在最终文本里寻找特定标签来猜测。
是否支持思考内容以实际服务能力及返回结果为准；不能设计一个可展开入口却没有相应的数据与恢复接口。

### 执行日志：保留 Agent 事件流

2026-10-17 已确认：**产品仍需保留执行日志，用于记录和回看 Agent 事件流。**
日志帮助作者理解 Agent 实际做了什么、任务停在哪里，也为学习和检查 Agent 编排过程提供依据。
默认收起过程详情只改变展示方式，事件仍持续记录并保存；对话摘要和最终回复不能替代执行日志。

- **入口与展示**：创作台保留明确的“执行日志”轻量入口，按需打开独立滚动的日志视图；
  对话中的执行记录展示同一事件流的任务片段，并可定位到对应日志。后台任务也纳入记录，不要求先有一条对话回复。
- **记录范围**：包括任务开始与结束、Agent 调度与交接、模型调用、工具调用及结果、作品内容变更，
  以及等待作者输入、失败、停止和重试等实际发生的事件。思考内容是否可用不影响事件记录。
- **事件信息**：每条事件保留唯一标识、发生时间、执行顺序、所属作品、任务与本次尝试、执行 Agent、事件类型和结果摘要；
  涉及子任务、工具或内容变更时关联相应调用、对象与版本，展开可看必要详情和失败原因。
- **实时与回看**：执行中持续追加，支持按任务和事件类型筛选；向上阅读时暂停自动滚动，可回到最新。
  刷新、重进作品后可恢复历史；停止和失败保留已有事件，重试单独记录尝试并关联原任务。
- **前后端一致**：后端持久保存真实事件，提供历史查询与实时订阅；重连能补齐断开期间的事件，
  前端按事件标识去重并保持执行顺序，不从回复文字推测事件。没有事件时明确空态，连接中断不能显示为任务完成。

执行日志记录应用可观察到的行为；模型公开返回的思考内容或摘要仍在对应过程区域展示。
日志中的调用详情需过滤密钥等敏感信息；作品变更事件关联版本历史，日志本身不替代正文版本与恢复能力。

## 5. 右侧故事账本

账本是创作的组织基础，围绕人物、线索及其关联保存可检查、可引用、可修改的作品依据。
同一条目同时关联其故事事实和叙事作用；讨论中的可能性、作者的安排与正文中已发生的表达必须区分。

### 5.1 内容组织

1. **本次相关**：当前打开的章节或任务用到的条目；显示相关原因，点开能看完整内容。
2. **待确认入口**：例如“待确认 2 条”，展开为独立候选区，不混入已确认条目列表。
3. **已确认目录**：故事核心、人物与关系、真相与线索、时间与地点、章节与场景。
4. **最近确认记录**：谁确认了什么、何时更新；版本细节按需展开。

上述分组是内容组织方式，不要求同时展开。右侧默认只展示本章相关的简短摘要、完整目录入口和非空待确认提示。
点人物打开详细设定；点章节打开主区稿件；点修改记录打开差异，历史记录按需展开。
大篇幅编辑可以在主区打开账本条目详情，右侧仍保留目录定位。

账本同时提供人物关系、线索关联、手法结构和时间线的可视化入口，详见 §5.4–5.8。
这些视图承担作者理解与推演故事的核心工作，不作为交付完成后的装饰性增强。

### 5.2 什么能进入账本

| 内容 | 保存在哪里 | 是否成为生成依据 |
|---|---|---|
| 作者随口提出的可能性 | 讨论记录 | 作为假设讨论，不能当成既定事实 |
| Agent 整理的设定候选 | 待确认候选及其来源 | 可以比较，不自动当成正式事实 |
| 作者确认的设定或直接编辑保存 | 正式账本及版本 | 可以；任务记录实际使用的版本 |
| 作者确认的伏笔、悬念或揭示安排 | 相关人物/线索条目的叙事安排及版本 | 作为写作指导；计划中的安排不代表正文已经实现 |
| 参考材料中的信息 | 材料库及引用 | 不自动成为小说中的事实 |
| 采用后的章节 | 正式稿件及版本 | 正文事实仍需经过核对才能更新账本 |

“作者确认了某条设定”与“角色知道这件事”是两个维度。
悬疑账本继续区分真实发生的事、角色认知、读者已知；不能把角色猜测登记成客观真相。

### 5.3 设定确认与修改

候选卡展示具体条目、原文来源以及“哪些仍未确定”。提供“采用选中条目”“调整”“暂不采用”。
允许同一小组候选一次确认，也允许只采纳其中几条；不会要求每句话都点击确认。

作者从账本直接编辑并点击保存即构成明确操作，保存后回读实际版本。
既定设定的变化附带影响说明，例如“涉及第1章和第3章”；这个数字必须来自实际分析。
仅保存账本条目时，提示相关正文可能需要同步，并在对话中提供“同步修改相关正文”。
作者已通过对话授权整体调整时，账本和相关正文由同一次任务统一更新，不再要求分别批准。
正文与账本暂时不一致时保留可见提示，不能把单个条目保存成功说成整个故事已同步完成。

### 5.4 视觉账本：右侧概览、主区展开

作者补充要求：线索、作案手法、角色等需要更直观的可视化展示。

右侧账本提供“目录 / 人物关系 / 线索关联 / 手法结构 / 时间线”的视图选择。
默认呈现与当前工作相关的摘要、小图及选中条目，不把整个作品的几十个节点塞进窄栏。
点击“展开查看”在主区打开同一视图，底部保留唯一输入框；返回正文或讨论时保留图谱的定位，再次打开可继续查看。
账本目录和图形共用同一组对象与版本，不重新维护一份“图上的真相”。

各视图只展示能帮助作者作决定的信息：谁与谁有关、这条线索说明什么、手法怎样在故事中成立、
某个时间点发生了什么。节点数量、网络密度或视觉中心位置都不表示故事质量或嫌疑程度。

### 5.5 人物关系图

**主要回答：这些人怎样关联，各自想要什么、隐瞒什么、知道什么？**

- 节点是角色，卡片摘要包含身份、当前目标；秘密和动机点开查看，避免所有信息挤在图面上。
- 连线带关系名称和必要方向，例如“姐妹”“雇佣”“怀疑”“隐瞒”，不让作者猜线条含义。
- 真实关系和人物理解分开显示；可选择“作者全知”或某个角色视角。
- 选择章节/场景后，显示该位置已记录的关系与认知；信息缺失显示“未记录”，不能默认成“不知道”。
- 选中姐姐时，突出与她相关的人物、线索和场景；其他节点淡化，便于从局部理解故事。
- 人物详情可查看与其有关的未解疑问、读者目前对其身份与动机的认识，以及作者希望逐步展示的变化；未确定的内容可留空。

示例：姐姐与女侦探之间可以同时存在“姐妹”的真实关系，以及“妹妹怀疑姐姐隐瞒行程”的角色认知。
后者不能自动变成“姐姐作案”的作者事实。

### 5.6 线索关联图

**主要回答：这条线索在哪里出现、指向什么、曾被怎样误解、最终怎样解释？**

以线索为中心连接人物、事件、真相、误导解释和出现/回收的章节，边明确标注
“支持”“反驳”“曾被解释为”“首次出现”“最终解释”等关系。

示例叙事链：

```text
第2章发现的停走怀表
  ├─ 角色的初步解释 → 姐姐当晚离开过房间
  ├─ 已确认的客观事实 → 怀表在更早以前已经损坏
  └─ 第5章重新解释 → 原先用于判断时间的依据不成立
```

这些连接只有在账本存在对应记录时才展示为正式关系。Agent 提出的连接显示为待确认候选，
没有来源时显示缺口；不能仅凭回复措辞画出看似已被证实的推理链。

点击线索展开“客观内容、来源原文、作者解释、角色解释、读者何时看到、留下什么疑问、后续如何回应”。
计划出现、已在正文出现、计划解释、已在正文解释分别记录；已实现的状态必须关联具体正文及版本。
可选择“截至第几章”查看已披露的线索，防止作者把后文才出现的证据误用到前面的推理中。
“还没有关联解释”可以是作者刻意保留的悬念，不直接判定为错误。

### 5.7 作案手法结构图

**主要回答：作者设定的真实过程、表面现象和破解依据如何对应，哪些成立条件尚未交代？**

以叙事机制组织，而不是只显示一段长文字：

```text
核心假象：看起来不可能发生的事情
  ↓ 依赖哪些人物、地点、时间与既定规则
真实过程：准备条件 → 关键事件 → 事后表象
  ↓ 产生哪些可以被观察到的证据
破解依据：哪条线索推翻哪种表面解释
```

- 每个步骤可以展开关联人物、位置、时间、前置条件、可观察结果与对应章节。
- 将“实际发生”与“证词/表面解释”分成明确的轨道，能对照查看差异。
- 同时只聚焦一个机制；整部作品存在多种方案时，允许比较备选，采用前不替换正式真相。
- 缺少时间依据、某个前置条件未设置时，标为“待补充”；已有规则检查发现矛盾时，展示依据和定位。
- 只有检查报告明确证实的问题才能标为冲突；图画得完整不代表手法逻辑已经成立。

当前实现中作案手法主要是文字描述，已有真相、时间线和线索引用可支撑部分投影。
若需要从文字补出步骤与关系，必须先形成有来源的候选并由作者确认；不能把模型补充当成既有记录。
更完整的步骤、条件及证据关联属于需要明确设计的新领域能力，不声称现有数据已全部支持。

### 5.8 时间线、视角与图谱交互

时间线按角色或地点分轨展示故事中的事件。实际事件与证词中的事件明确区分，
时间不确定时显示范围或“时间未定”，不能用猜测补齐精确时间。
选择一个时段可突出相关人物、线索及手法步骤；故事发生时间与章节叙述顺序分别表达。

所有图谱遵循共同的操作规则：

1. 点节点看条目；点连线看关系含义及来源；从来源可定位正文、讨论或确认记录。
2. “加入讨论”把选中对象作为可见引用附到主输入框，例如“检查这条线索是否足以支持妹妹的判断”。
3. 已确认与待确认用文字标识配合线型区分；人物的误信、猜测是认知类型，不能混同于未确认数据。
4. 切换作者全知/角色视角/截至某章时，显式显示当前视角与范围；未知资料显示未知，避免提前泄露后续信息。
5. 拖动节点只调整布局；新增关系、修改手法步骤必须通过有类型的编辑与确认，不能靠拖线直接写入正式账本。
6. 条目修改后按实际版本刷新，影响到的节点与连线可高亮；高亮只说明影响，不代表已完成修订。
7. 无障碍目录与文字详情同步可用，不能要求作者必须操作画布才能读写设定。

图谱引导也跟着创作进展出现：人物较多时建议查看关系图，线索出现后建议查看关联，
开始设计案件时建议打开手法结构；空作品不先给一个等待填满的大画布。

### 5.9 账本条目的叙事作用

伏笔、悬念、误导与揭示依附于具体人物、线索、关系或事件，并关联承载它们的正文位置。
作者可以从任意条目继续写作，例如“写出她第一次隐瞒行程的对话”“让这条线索先引起一个错误怀疑”。
这些要求直接进入本次写作任务，不要求建立额外的中间规划对象。

以“停走的怀表”为例，同一条目可以包含：

| 条目内容 | 示例 |
|---|---|
| 已确认事实 | 怀表更早已经损坏，与人物推断的时间不同 |
| 人物认知 | 妹妹暂时把它当作判断姐姐行程的依据 |
| 作者希望留下的疑问 | 姐姐是否隐瞒了当晚的去向？ |
| 计划中的呈现 | 首次出现时让人物自然注意到时间，暂缓解释损坏原因 |
| 正文中的实现 | 关联已出现的段落；尚未写到的内容保持“计划中” |
| 后续回应 | 在获得新信息后重新解释怀表；具体位置允许未定 |

以上信息按需补充，不作为创建条目或写正文的必填清单。伏笔可以是动作、对话或人物关系中的细节，
不要求所有伏笔都成为案件证据，也不要求每条线索都有误导或反转作用。
悬念可以来自人物命运、关系变化或事件结果；表达方式由作者选择。

Agent 的提示同时引用相关账本与正文：有证据的冲突指出具体矛盾；尚未落实的安排提示“还未写到”；
阅读体验建议说明意图和取舍，例如“暂缓这句解释可保留对姐姐的疑问，但会降低当前段落的清晰度”。
作者可以接受、调整或忽略建议，不设“精彩程度达标”之类的强制门槛。

## 6. 创作台中的正文、修改与记忆

创作台承载正文，对话框承载意图与选择。下面两条修改路径共用正文历史，详细交互和状态规则见
[正文修改与作者长期记忆](editing-and-author-memory.md)。

### 6.1 对话中的成果卡

卡片显示名字、性质、简短摘要和状态，点击后在主区打开：

- “故事方向·候选”——主要设定与结构建议；
- “抵达旅馆·试写”——正文候选，尚未进入正式稿；
- “第1章·当前稿”——已采用的正式内容；
- “姐妹关系调整·修改摘要”——对话中的理解、关联范围和执行结果，可按需展开；
- “第1章·修改建议”——带基础版本的候选，作者主动请求建议时出现；
- “已完成整体修改”——一个完整版本及其改动摘要，可查看或撤销。

同一个内容只有一个稳定身份；聊天卡、左侧目录和账本入口打开同一对象。

### 6.2 正文视图

已有正文时，创作台以文章为默认中心，主区展示完整文本和必要的保存状态，作者可直接上手修改。
可选的阅读模式减少操作干扰；底部对话框明确绑定正在看的稿件。
编辑时自动保留草稿，“完成本次修改”将这一轮人工修改记录成版本；正文旁提供轻量“历史”入口。
首章试写的主要动作是“采用为第1章”，比较候选时可选“使用这版”“继续修改”“保留备选”。
完整讨论通过“展开讨论”按需进入；临时视图始终提供“返回正文”。

选中一段正文后，可直接提出“这段节奏太快”“检查此处与线索是否一致”等要求。
Agent 的反馈显示在对话区；请求建议时展示候选，明确授权执行时在范围内完成修改并记录版本。
查看改动是按需入口，不是每次执行的必经页面。生成期间仍可阅读和编辑；如基础版本已变化，
写入前必须处理版本冲突，不能覆盖作者的新修改。

试写生成完成只表示有候选。作者采用后才进入正式稿，并显示可回读的保存结果。
对候选的人工调整保留在该候选的编辑缓冲中，采用时必须提交作者实际预览的版本；
这是需要新增的稿件缓冲能力，不能沿用“接受原始 Job 输出”来静默忽略作者修改。
若首版尚未提供候选编辑，必须明确只读，只支持对正式稿编辑或通过“继续修改”产生新候选。

切换视图或作品时保留自动保存的草稿，未点击“完成本次修改”的草稿仍可继续，不反复打断导航。
草稿保存失败或即将被其他内容覆盖时，才提供重试、保留返回或明确放弃的选择。
返回对话只隐藏编辑视图并保留缓冲，不为一次导航丢弃文字。

### 6.3 从账本内容直接进入写作

作者可以从对话、人物或线索条目、现有正文的选中段落直接发起写作。
任务以相关账本内容和作者要求为依据，输出到新稿或指定章节、段落；章节与场景用于定位内容，
不要求先完成完整大纲或批准中间规划对象，也不在后台自动创建此类对象来满足旧流程。

任务卡按本次需要呈现：

- **相关内容**：人物及关系、已有线索、需要遵守的事实及其版本；没有相关线索时允许为空。
- **写作要求**：作者希望写什么、采用谁的视角、写到哪里及大致长度；只追问会影响本次输出的缺失信息。
- **表达意图**：希望保留的疑问、呈现的伏笔、暂缓的解释或情绪变化；可以未定，不强制填写。
- **写入范围**：生成试写候选，或按明确要求在当前版本上执行指定修改；记录具体对象与版本，防止越界覆盖。

例如：以姐妹关系与旅馆设定为依据，写妹妹视角的抵达片段，保留姐姐隐瞒事情的感觉，
暂不确定凶手，也不提前解释姐姐的动机。作者即可开始试写，不需要补齐整个案件。
作者的“确认依据并试写”只授权卡片列出的内容和范围，模型新增的故事事实继续作为候选。

实现需要调整起草与修改的任务契约，使账本引用、作者要求及正文基础版本成为直接输入。
版本检查、作者授权和候选采用的适用边界需保持清楚；原有固定规划前置依赖属于需要移除的实现差距，
不能仅将入口换名后继续要求作者走旧流程，也不能把阅读体验建议变成保存正文的阻塞条件。

### 6.4 直接编辑形成版本，空闲时积累作者记忆

作者直接修改不满意的语言，点击“完成本次修改”即可。系统保存与上一版本的差异、时间、修改来源及简短摘要，
不要求填写提交说明；没有模型或模型繁忙也能立即完成记录。输入过程中的自动保存负责防丢失，完成修改形成可回看的版本。

模型空闲时整理已完成的人工修改，归纳有依据的表达偏好并记录到作者长期记忆，供后续写作参考。
一次修改先作为带来源和适用范围的观察，重复出现或作者明确要求后再形成更稳定的偏好；
作者改了某个事实不等于改变文风，接受整段生成内容也不等于作者亲自写出了这段文字。

作者无需打开专门的模型或偏好页面。可以在对话中问“你记住了我的哪些写作习惯”，
或说“这只适用于这本书”“忘记这个习惯”；系统给出相应记忆、来源和调整选项。
记忆整理不会重写已完成的正文，也不会为了更新记忆占用正在进行的前台写作。

### 6.5 对话发起整体故事调整

例如：“把凶手改成姐姐，保留妹妹的视角和旅馆背景，把前面的伏笔也一起调整。”
Agent 在同一对话中梳理动机、手法、证据、人物认知及已有章节，提出确实需要作者选择的问题，
确认整体理解后连续修改相关账本和正文。用户不需要创建变更单、跳转影响页面或逐章发起修订。

“整体修改”表示检查全局关联并覆盖所有受影响内容，无关章节保持原样。执行前保留当前版本，
工作过程中显示可展开的过程并允许停止；内部修改与检查完成后，统一形成可回看的作品版本。
完成后对话显示修改摘要和“查看改动”“撤销这次修改”“继续调整”，中间仍是正文。

失败、停止或版本冲突时保留已经完成的内部工作与原稳定版本，不将部分更新伪装为整体完成。
对尚未解决的关键问题，在同一对话中提供具体选择；继续执行时承接已有进展。
较早版本的恢复也需要保留后续人工修改，不得以一次撤销静默抹掉新内容。

### 6.6 有正文后使用悬疑审计

悬疑审计检查已经写出的正文，并对照相关账本，定位人物提前知情、线索解释冲突、时间矛盾及信息揭示问题。
只有作品中存在非空正文才可启动；作品名、大纲、账本条目和聊天中的试写建议不满足条件。
没有正文时显示“添加正文后可检查人物认知、线索和时间是否一致”，提供开始写作或导入正文的入口。

创作台正文工具栏提供“悬疑审计”按钮，点击后在对话区展开检查卡：说明功能、选择“当前章 / 已写全部章节”，
点击“开始检查”。通过对话提出相同要求使用同一流程；范围已明确时直接执行，不额外跳转到独立业务页面。

检查中显示实际范围与进度；结束后在对话区保留结果卡，明确列出冲突、待确认问题和表达建议的数量。
结果在原任务位置更新，默认提供简短结论与“查看问题”，展开后再显示分类和每条问题的依据，避免重复堆叠卡片。
每个问题包含具体描述、对应原文与章节、相关账本依据，并提供“定位原文”“讨论修改”等动作。
未发现问题也需明确反馈“在本次检查范围内未发现问题”；部分完成、失败、停止和版本已变化分别显示。

悬疑审计只生成检查结果，修改仍通过原有的直接编辑或对话执行路径完成。修改之后先标记“待复查”，
重新检查确认后才显示已解决。详细布局、前置条件、文案和验收要求见[悬疑审计交互设计](mystery-audit-interaction-design.md)。

## 7. 从首次创作到持续修改的完整例子

| 时刻 | 作者动作 | 主区反馈 | 右侧账本变化 |
|---|---|---|---|
| 模型准备（未配置时） | 选择连接已有模型，或下载本地模型试用 | 展示真实配置/下载/测试阶段；就绪后进入构思，允许先记想法 | 不创建虚构设定，不要求预填作品资料 |
| 进入 | 看到输入框，尚未命名作品 | “说说你想写的故事” | 空态，解释确认后会保存什么 |
| 第一次输入 | “想写雪山旅馆谋杀案，凶手还没想好” | 保存想法；询问更想跟随侦探还是住客 | 不自动记录“凶手未知”为具体人物真相 |
| 补充 | “年轻女侦探，与关系紧张的姐姐同行” | 整理一小段故事方向与两个人物候选 | 出现待确认入口，不冒充已确认 |
| 确认 | 采用故事核心和姐妹人物条目 | 回报已记入，并保留来源 | 正式目录出现条目；凶手保持未定 |
| 选择下一步 | “先写她们抵达旅馆，让读者感觉姐姐在隐瞒什么” | 引用姐妹关系与旅馆设定，列出视角、范围及暂不解释动机的写作要求 | 本次相关突出人物关系；表达候选可继续调整 |
| 明确开始 | 点击“确认依据并试写” | 显示准备/生成阶段，可以取消；仍可聊天 | 依据引用可查，未新增最终真相 |
| 读结果 | 打开“抵达旅馆·试写” | 主区读全文；可要求“姐姐的台词再冷一点” | 仍展示同一组事实，不把新台词变设定 |
| 采用 | 点击“采用为第1章” | 回读正式稿并展示保存状态；正文成为创作台默认中心，讨论入口留在下方 | 章节目录出现第1章；提示可继续设计命案 |
| 继续发展 | “把停走的怀表放进下一段，先让妹妹误会它的含义” | 引用已确认的怀表事实与妹妹的认知，准备呈现方式候选；缺失事实保持待确认 | 在同一线索条目关联拟留下的疑问、计划中的解释与实际正文位置 |
| 人工润色 | 直接删去套话、调整对话，点击“完成本次修改” | 立即记录版本；空闲时整理有来源的作者记忆 | 故事事实未变时不改账本；发现事实变化则提出具体提示 |
| 整体调整 | 在对话中要求更换凶手并调整相关伏笔 | 整体确认理解后执行，完成时显示摘要与撤销入口 | 与受影响正文一起更新到同一作品版本 |
| 检查已写内容 | 点击“悬疑审计”，选择当前章并开始 | 显示真实进度；完成后列出问题、原文位置或明确的无问题结果 | 相关依据可定位，审计本身不修改账本 |

这条路线跨越首次构思和已有多章正文后的持续创作，验证作者能表达、作决定、读到成果，
并始终知道想法、候选和已确认内容分别在哪里。

## 8. 当前七页能力的去向

| 现有入口 | 新的主要位置 |
|---|---|
| 项目概览 | 初次引导、作品选择与恢复继续提示 |
| 创作台 | 主区稿件视图；左侧稿件目录 |
| 故事账本 | 右侧常驻账本与小图；人物、线索、手法、时间线的大图和复杂编辑在主区打开 |
| 变更影响 | 内化为对话中的整体理解与范围摘要；详细依据按需展开，无独立发起页面 |
| 修改审计 / 修订审阅 | 删除独立模块与入口；版本历史和“查看改动”保留为正文的按需操作，不形成额外审核流程 |
| 悬疑审计 | 有正文后在创作台启动，范围选择、进度与结果在对话区显示；问题可定位原文并继续处理 |
| 作者模型 | 内化为有来源的作者长期记忆，空闲时从人工修改中积累；通过对话查看、纠正或忘记 |
| 协作主编角色表单 | 从界面移除；创作请求、选择和执行状态全部进入同一个对话区 |
| 执行日志 | 保留明确的按需入口，记录并回看 Agent 事件流；对话中的执行记录关联同一日志 |

保留必要的数据和执行能力，取消以后台模块划分的用户流程。历史、图谱和差异均为创作台内的按需视图，
不能以“高级入口”的名义继续要求作者进入旧页面完成主要操作。现有底层能力是否可复用需按新流程逐项验证。

## 9. 改造范围与实现顺序

### 第一批：主工作区与首次体验

交付左侧简导航、无正文时的主区对话、有正文时默认显示的文章编辑区、下方协作输入、右侧真实账本、空作品欢迎语；
未配置模型时优先引导连接已有模型或下载本地模型试用，衔接检测、下载、加载、测试和返回创作。
同时交付对话中默认折叠的过程区域，按实际模型能力展示公开返回的思考内容或摘要，支持流式展开与历史回看。
保留执行日志入口，同步交付 Agent 事件持久记录、实时展示、历史查询与断线补齐，覆盖对话任务和后台任务。
移除独立协作主编表单及变更、修改审计/修订审阅、作者模型主导航，让创作台与对话区成为固定操作中心。
所有功能入口补齐具体介绍、使用条件和结果反馈，空态与错误说明下一步动作。
同步落实稿纸中心、轻量侧栏、简洁排版与按需展开的视觉原则；功能说明在使用时呈现，正常桌面保持安静。
结合 dark 原型的模块化空间组织，保证工作区充分使用视口、主要文字较大易读、模块之间舒展且不拥挤。
退出条件：使用生产构建和默认启动入口，未配置时立即看懂两种接入路径，模型可用后知道在哪里输入；
已有正文进入创作台直接可读可改；不用打开旧角色表单就能讨论。

### 第二批：从讨论到设定确认

交付从讨论/材料整理受限设定候选、来源定位、选中采用、账本回读和当前相关引用；
同时交付基于真实条目的基础人物关系图与线索关联图，以及条目关联的疑问、伏笔和揭示安排。
退出条件：“假如姐姐是凶手”保持假设；明确采用后才成为故事依据；修改后能追到原始来源与版本；
同一人物或线索从目录与图谱打开一致，图中连线可解释；计划中的呈现与正文中的实际出现能区分。

### 第三批：从人物与线索到正文

交付从人物、线索及相关账本内容直接发起写作、可见范围确认、可展开的任务执行记录、主区完整候选、采用与正式稿编辑；
交付人工编辑草稿保留、完成修改后的版本记录、历史回看及后台作者记忆整理；
交付有正文才可启动的悬疑审计、范围选择、真实进度、问题定位和明确的结束反馈；
移除固定规划对象作为起草前置条件，结合作者的伏笔、悬念、信息揭示及情绪要求提供表达候选；
加入手法步骤、条件、证据的候选整理及展开视图，关联章节中的出现与解释。
退出条件：从一个模糊构想走通第7节的写作与人工润色，无需额外规划对象即可从账本生成正文候选；
人工修改的实际差异可回看，记忆能说明来源并接受对话纠正；悬疑审计可在有正文时检查并定位问题，无正文时不能启动；
明确实现候选人工编辑的版本契约，或只读展示其限制。

### 第四批：修改与长期继续

交付对话发起的整体调整、必要澄清、连续执行、账本与正文统一版本、检查结果和撤销；
完成跨会话继续、失败恢复及作者记忆的持续使用；
完善时间线与证词对照、角色认知及读者披露视角、图谱中的影响高亮。
退出条件：换凶手、手法或背景都能通过对话与选择按钮完成，无须独立变更页面或逐章审批；
停止/失败/刷新/切换作品都不丢事实和编辑稿，部分完成不会污染当前稳定作品。

### 现有能力与新增工作

- 可复用的基础：项目身份、对话存储与流、持久任务、模型绑定、正文版本及影响分析；现有候选接受与检查能力需按统一执行流程调整。
- 主要前端工作：界面层级、主区成果视图、账本投影、引导状态、统一操作入口。
- 必须补的应用能力：讨论到受限设定候选、候选的来源记录、首次想法与项目建立衔接、以人物和线索等账本引用直接构成写作依据。
- 写作契约调整：前后端同步改为账本引用、作者要求、表达意图与正文范围，移除节拍对象及相关接口、任务和上下文依赖；已有记录中的有效叙事信息归入对应账本条目或正文关联，不得只改界面名词或在后台生成隐藏规划对象。
- 叙事关联能力：条目关联未解疑问、伏笔、揭示安排和正文位置；区分计划与实际实现，支持故事依据检查和可选择的表达建议。
- 人工编辑与记忆：草稿保存和完成修改的版本记录分开，保留真实差异与来源；后台空闲任务整理作者记忆，支持适用范围、证据、纠正及忘记。
- 整体修改执行：统一承接对话意图与授权，内部完成关联分析、修改和检查，账本与正文形成同一版本；支持恢复、冲突保护及不损失后续编辑的撤销。
- 悬疑审计对齐：前后端共同校验非空正文和实际范围，记录正文与账本版本、覆盖情况、带依据的问题及任务状态；只提供完整实现的数据与操作，不展示无后端支持的按钮。
- 模型接入对齐：以用户自己的连接贯通配置、测试和任务调用，普通界面移除环境变量选项，明确凭据保存与删除行为；收费计划后续另议。
- 过程展示对齐：模型可展示的思考输出、执行事件、最终回复分别传递与保存，支持流式更新、停止、重试与刷新恢复；没有思考输出的服务保留真实状态提示。
- 执行日志对齐：统一记录 Agent 事件流，贯通任务、尝试、Agent 和相关对象；历史查询与实时订阅共用事件标识及顺序，刷新与重连后可完整回看，前端入口不能只展示临时消息。
- 可视化新增能力：同版本的图谱查询投影、带来源的类型化关系、手法步骤/条件/证据的结构化准备与确认、
  章节披露和故事时间的独立选择；不能只让模型画图而没有对应的可检查事实。
- 不能伪装成布局已解决：现有普通 ChatRunner 没有工具或领域提案能力，不能靠抽取回复文字自动写账本；
  必须新增只生成候选的受限准备端口，并继续通过作者确认和现有提交管线生效。

## 10. 产品验收清单

1. 冷启动、旧浏览器偏好、已有作品恢复三个入口，都有明确的第一动作。
2. 作者首次表达想法前的业务必填字段为零；未配置模型优先展示接入引导，仍可先记录想法，配置后草稿可继续发送。
3. 使用同一个输入框完成讨论与提出创作要求；角色和后台任务类型不成为前置选择。
4. 输入“假如……”不会改变正式账本；候选/已确认/正式正文一眼可区分。
5. 从一条已确认设定可以回到其来源；换会话或模型不会丢失作品事实。
6. 从相关人物、线索及作者要求即可起草，不要求完整大纲或预先批准中间规划对象；实际写入守卫仍有效。
7. 生成前有可检查的目标、依据、范围；范围已明确的动作不再重复填写和确认。
8. 试写与建议生成候选；明确授权的整体修改完成后统一记录版本，无需逐段采用；切换视图和刷新保留草稿。
9. 单独保存账本不会擅自重写正文；对话授权的整体调整同步更新相关账本与正文，并能查看结果、撤销或继续调整。
10. 不同窗口与屏幕宽度下仍有可发现的主输入，账本不挤掉核心工作区。
11. 自动化必须走默认 CLI 启动、生产构建和真实应用契约；模拟演示与真模型证据分开记录。
12. 人物、线索、手法和时间线四类视图都有明确的问题与交互；窄栏概览能在主区展开。
13. 节点、连线及高亮能追到真实记录和版本；缺失、假设、已确认、角色误信分别表达。
14. 从图谱“加入讨论”后引用明确可见；切换视角不修改事实，也不向限定视角泄露后续记录。
15. 拖动布局不产生事实变更；修改图谱中的内容仍经过相同的确认、版本和影响规则。
16. 已有正式正文或导入稿件时，进入创作台中间默认显示文章；恢复当前章节和阅读位置，无记录则打开第一章。
17. 在正文下方发送消息、收到回复或等待任务完成，文章均保持可见；完整讨论、候选和图谱仅由作者主动打开，返回后恢复编辑与阅读状态。
18. 选中段落能附带明确的章节和版本引用；建议与执行要求有明确区别，实际修改记录版本，存在并行编辑时保护作者的新内容。
19. 未配置模型时无需先点击发送，即可看到“连接已有模型”和“下载本地模型试用”；配置成功后返回原工作区，不丢输入。
20. 本地模型下载、加载和实际调用测试分别可见；取消、失败、重进页面均反映真实状态，仅下载完成不能标为可用。
21. 模型未配置或不可用时，已有正文仍在中间可阅读、编辑和保存；接入引导位于协作区，不能阻断人工创作。
22. 用户可在界面填入自己的 API Key、测试并选择模型，无需操作环境变量；查询不回显完整密钥，实际任务使用该用户连接，未配置时不借用平台凭据。
23. 思考与执行过程默认以紧凑区域展示，生成中和完成后均可展开；有正文时不挤走文章，正式回复与过程内容分开。
24. 模型支持的可展示过程能够流式呈现和回看；不支持时明确说明，不伪造思考或执行活动；停止、失败、重试及刷新后的记录与实际状态一致。
25. 人物、线索条目可直接关联伏笔、未解疑问与揭示安排；未确定内容允许留空，计划中的表达不冒充正文已实现的内容。
26. Agent 对有依据的事实冲突、信息缺失与阅读体验建议采用不同的说明；留白、不可靠叙述和未采用的表达建议不自动导致正文被拒绝。
27. 用户围绕人物、线索和章节完成创作，无需切换两套质量模式或满足统一评分；写作请求中不隐含创建与批准额外规划对象。
28. 作者直接修改正文后可一键完成并记录版本，无需填写提交说明；模型不可用时仍可完成，未完成草稿不丢失。
29. 空闲时从真实人工差异形成有来源、适用范围的长期记忆；不把生成内容、事实修改或单次局部选择直接当作通用文风偏好。
30. 通过对话可以查询、纠正或忘记作者记忆；无独立作者模型模块，也不要求逐条审批学习结果。
31. 更换凶手、手法或背景可全程通过对话与选择按钮完成；无独立变更发起页面、协作主编表单或逐章审批步骤。
32. 整体修改的账本和正文一致完成后才成为当前版本；失败、停止、重试及撤销不覆盖未授权内容或丢失后续人工编辑。
33. 产品与领域模型不再包含独立节拍对象；从人物、线索或正文发起创作、检查与修改均无需节拍标识，前后端与后台任务不隐含创建、审批或依赖节拍；原有有效叙事信息仍可定位和使用。
34. 修改审计与修订审阅不再具有独立模块或导航入口；查看版本差异不要求发起审计或完成审批。
35. 无正文时不能从按钮、对话或接口启动悬疑审计；有正文时可明确选择范围，未覆盖内容不冒充已检查。
36. 悬疑审计有清楚的功能介绍、使用步骤、执行反馈和具体结果；问题可定位到原文及依据，无问题、部分完成、失败和停止各有明确反馈。
37. 审计结果对应实际版本，正文或相关账本变化后提示需复查；修改完成不能直接冒充问题已解决。
38. 默认桌面突出文章和对话入口，账本仅展示相关摘要；完整目录、长说明、历史和详细结果按需展开，不堆叠常驻功能卡。
39. 功能文案保持明确，结果通过原位更新清楚反馈；纸面感不依赖装饰性拟物、低对比度或隐藏重要操作。
40. 执行日志有明确入口，真实记录对话及后台任务的 Agent 事件流；可按任务回看调度、调用、结果与异常，刷新和断线重连不丢失或重复展示已记录事件，失败与重试的尝试可区分，日志不暴露密钥。
41. 参考 dark 原型的模块化排布与较大字号，工作区充分使用页面宽高，分区清楚且间距适当；不通过缩小文字或堆叠无关内容解决空间分配，正文保持舒适行宽，辅助模块可随屏幕折叠。

## 11. 本提案的取舍

- 默认焦点随作品状态变化：构思期以对话接住想法，有正文后以文章阅读和编辑为中心；协作输入持续可用，完整讨论与图谱按需打开并能返回正文。
- 以人物、线索及账本关联组织创作；故事依据与阅读体验共同作用于具体条目和正文，表达建议保留作者选择，不增加独立质量模块或强制创作模板。
- 作者确认作为正式事实入口保留；通过小组候选与具体动作减少机械确认，不把自由讨论变成隐式授权。
- 人工修改直接形成版本，作者记忆后台积累；整体故事调整在对话中确认意图后统一执行。作者控制落实为清楚的范围、可回看和可撤销，流程中避免重复审批。
- 悬疑审计在有正文后提供独立、明确的检查动作，但整个操作与反馈仍融入创作台和对话区；前端文案解释实际功能与结果。
- 引导采用状态提示和上下文建议，避免用必须走完的全局阶段机限制探索。
- 首版将真实创作路线与“作家的桌面”视觉原则一起交付；任意自动整书写作、多人协作不在本轮。

评审时建议先确认第1节产品定位、第2节布局、第4节执行边界及第6节的两条修改路径，再冻结接口与具体开发计划。
