承接[分支时间线想法](README.md)。本稿回答线索如何保存、如何持续指导模型、如何更新和展示，以及作者不满意时如何通过对话修改。字段是职责示例，不是冻结的数据库或接口规格。

已确认的要求：先构思再写正文；故事内分支与创作备选分开；取消故事资料板块；所有模型调用真实流式展示，支持立即中断、继续和插话；暂不考虑桌面端。以下对象划分、自动保存边界和核对策略是本轮建议。

## 1. 产品形态与取舍

工作区围绕**构思、正文和同一个对话区**展开。构思显示可分支、汇合与收束的结构，正文显示其实际写作结果。作者选中节点、线段或正文后直接提出要求，Agent 负责读相关内容、修改结构、写作和更新关联。

线索需要同时回答三个问题：这件事实际是什么，故事在什么位置呈现什么，呈现之后怎样改变理解。保留这三个层次，才能表达真实细节造成误导、人物说谎、错误相信和后续反转。

长期连续性由作品中的有效数据、按任务装配的模型输入和写后核对共同承担。会话记录保留讨论经过，不能成为唯一的创作记忆。作者打开新对话、压缩上下文或更换模型后，仍应使用同一份有效结构。

交互采用以下默认规则：

- “讨论一下”“给我两种方案”产生可继续讨论的候选；“按这个改”“帮我重写这段”允许在明确范围内执行并保存，结果可撤销。
- 一句话即可开始。只有任务确实依赖尚未决定的内容，或两项要求无法同时成立时，才在原对话中提一个具体问题。
- 卡片默认显示一句安排和必要的连接。真实作用、正文依据、修改记录点开再看；不让作者维护数据字段、版本或提示词清单。
- 生成、核对和必要的局部修正属于一次可见任务。打开页面、保存普通编辑、移动节点和普通预览不启动模型。

## 3. 数据结构：线索保持身份，节点记录每次呈现

### 3.1 核心对象

| 对象 | 保存的内容 | 作用 |
|---|---|---|
| 方案 | 作品与方案身份、当前修订、来源方案修订、故事分支、有效节点与连线、本方案约定 | 保证同一个故事里的并行分支可以共同推进，互斥备选分别保存 |
| 线索 | 稳定身份、名称、作者确定的真实情况、设计意图、计划如何回应及其来源 | 同一线索多次出现时保持连续性；真相未定时允许留空 |
| 节点 | 具体事件或一次呈现、所属分支、实际事件时间、揭示顺序、涉及线索、此处呈现和预期理解、角色知情变化 | 描述“何时发生、何时让谁知道、为什么继续” |
| 连线 | 两端节点、推进／改变解释／回应的关系、关系成立的说明 | 表达分支、汇合、反转和收束；相邻摆放不自动产生因果 |
| 正文关联 | 节点与线索、正文位置和版本、原句、实际完成情况、核对来源 | 将计划与已经写出的内容对应，支持定位、重写和重新核对 |

本书约定和局部要求作为方案内的有作用域记录保存：原始要求、适用对象、必须遵守或偏好、来源作者消息、有效修订。任务临时要求另随任务保存。“这一段少写对话”不会自动成为全书规则；模型提议的偏好也不自动升级为作者约定。

记录身份、时间、修订和授权来源由应用补充，模型负责内容与关系。标题相同不表示是同一个对象，改名也不改变身份。

节点也可以只记录人物行动、冲突或情绪变化，没有关联线索。写作还需完成这些场景目标，避免每个段落都只承担解释线索的任务。

### 3.2 一条线索的示例

```json
{
  "id": "clue-letter-back",
  "title": "林岚知道遗书背面的文字",
  "author_truth": "林岚见过旧照片，没有接触本次保管的原件。",
  "intention": "先让人怀疑她接触过原件，后来用照片解释她的信息来源。",
  "resolution": {
    "intent": "explain",
    "node_ids": ["node-old-photo"]
  }
}
```

这条记录属于某个方案的特定修订。`author_truth` 可以为 `null`，`resolution.intent` 可为解释、刻意保留或未决定。模型不能把未决定自动当成不存在，也不能为了开始写作而补齐所有未知。

“分遗物时林岚暴露知情”和“后来发现旧照片”分别是两个节点，均引用这条线索：

| 节点 | 此处呈现 | 预期理解 | 后续作用 |
|---|---|---|---|
| 林岚暴露知情 | 她知道背面有一段未公开文字 | 她可能接触过原件 | 提出需要解释的疑点 |
| 旧照片出现 | 照片记录了同一段文字 | 存在不接触原件也能知情的途径 | 修正先前解释；单凭照片不能排除她的全部嫌疑 |

不设置互斥的“真线索／假线索”开关。物品真实、内容伪造、人物误信、叙述省略等，由作者真相与每次呈现的差别表达。对于证词，节点记录说话者与说法；正文写过这句证词，只能确认该说法已呈现。

节点中的一次线索使用可表达为下面的记录；后续再次提及时引用相同 `clue_id`：

```json
{
  "node_id": "node-inheritance-dispute",
  "clue_id": "clue-letter-back",
  "presentation": "林岚在别人翻到背面前先伸手遮住某一行。",
  "mode": "observed_action",
  "expected_interpretation": "她可能知道遗书原件的内容。"
}
```

`presentation` 是拟呈现的内容，未关联正文前仍是计划。知情变化另记录主体、知道或相信的命题、发生节点和信息来源；不能从预期读者理解直接生成角色已知事实。

### 3.3 时间、知情与分支

- **实际时间**允许时间说明和相对先后关系，不强制每个节点填日期；**揭示顺序**单独记录，可先写结果再揭示原因。已确定的先后关系不能构成循环，未确定的关系不强行补全。
- 推进线组织阅读顺序；“重新解释”可以从后文指回前文，不把这种关系误判为时间循环。事件因果有单独的关系说明，图上连接不能替代论证。
- 角色知情记录谁在何时知道或相信什么，以及信息来源。角色误信可以与作者真相不同；读者看到证词不表示角色或读者相信了证词。预期读者理解始终只是创作目标。
- 一个节点可以属于多条故事分支，作为汇合处。一个场景能实现多个节点，一个节点也能由多个场景共同实现。
- 备选方案保存可独立解析的版本；共享的旧记录保持不可变。修改备选不会改变主方案。写作任务只绑定一个明确方案，比较任务才分别读取多个方案。
- “把这个方案中的照片安排用到主方案”会生成对主方案的明确改动，连同必要铺垫一起检查。不能只复制一张卡片而遗漏它依赖的事件。

### 3.4 计划、正文和判断分别记录

计划可以写“旧照片解释知情来源”，正文关联则需要指出文章在哪里实际呈现了照片与文字。正文版本和引文可由程序核对；是否充分解释知情来源需要语义判断。

正文关联至少包含 `node_id`、可选 `clue_id`、正文身份与修订、字符区间和原句；核对记录另外引用所用结构与正文版本。结构改动使原核对过期，正文改动使原定位和相关核对需要重查。应用可以重新定位完全一致的原句，但不能仅凭原句仍存在就推断上下文含义未变。

因此，应用不能用一个可任意写入的 `resolved=true` 同时表示计划已安排、文字已出现和逻辑已成立。建议分别保留计划意图、有效正文依据和核对结果，再生成简洁显示。

通常卡片只显示正文入口；出现遗漏、冲突或来源变化时显示“待调整”。需要展示“已回应”时，应有当前版本的正文关联及核对依据。计划已经安排好、模型自称写好了或只有过期引文，都不足以产生这个状态。模型核对与作者裁决保留各自来源。

## 4. 长期记忆：每次任务重新读取有效作品状态

### 4.1 保存哪些东西

| 数据 | 长期职责 | 更新原则 |
|---|---|---|
| 作者的有效结构与约定 | 记录本方案想写什么、哪些决定已经成立 | 根据明确创作要求更新，保留修订和原始要求 |
| 正文及其版本 | 记录读者实际能看到的文字 | 通过写作或修改任务提交；保留变更依据 |
| 正文关联、摘要、知情与进展索引 | 定位正文、帮助选择本次材料 | 绑定来源版本；过期即停止作为当前事实使用，可从原文重建 |
| 任务记录 | 保留本次要求、实际输入、草稿、提交结果与未完成事项 | 支持中断、继续、追查和撤销 |

对话压缩只整理讨论经过。有效约定、真相、计划回应和正文来源从作品数据重新装入，不能随着聊天摘要逐轮丢失。摘要是辅助材料，应能追溯到原文；避免无限用上一版摘要继续生成下一版摘要。

新对话默认恢复当前方案和所选位置。正在进行的任务另有明确记录，作者选择继续后读取已完成部分及剩余事项，不由模型猜测上一次执行到哪里。

### 4.2 如何变成模型输入

应用按任务类型组装输入，模型可以补读允许范围内的内容，但不能自行决定漏掉必需约束。

| 输入部分 | 选取规则 |
|---|---|
| 本次任务与范围 | 作者当前要求、当前方案、节点或正文范围、允许改变的对象 |
| 本次必须遵守的约定 | 全局必需约定和命中本次范围的局部要求；保留原意与来源 |
| 相关创作结构 | 目标节点、相关线索真相、必要前提、当前要推进或回应的安排、与这些安排直接相关的后续目标 |
| 当前信息边界 | 读者此前看到的内容、当前角色知道或误信的内容、本段可呈现与需要保留的内容 |
| 版本有效的正文 | 当前段落、必要的前后文、相关线索的原文依据；长距离依赖按结构与来源取回 |
| 辅助上下文 | 其他相关概述、可选参考与近期对话，在剩余容量内加入 |

必需项优先按关系和作用域确定，补充搜索用于找遗漏与原文，不能只靠相似度决定是否带入关键线索。检查必要前提时不能固定只取图上的一层邻居。角色动态状态按写作位置取值，回写前章时不能使用后章状态。

结局尚未确定时不强迫作者决定；如果当前写作确实依赖一个尚未确定的关键前提，提出具体问题。已确定且与本次有关的结局约束需要带入写作模型，同时明确哪些信息不能在该位置披露。

组装结果需记录实际发送的文字与版本、必需项覆盖、可选省略项及原因、模板版本和任务身份。只把对象 ID 或目录发给模型，不算已经提供相应内容。完成后的“查看本次依据”从这份实际请求记录生成。

容量不够时，先移出可选材料，再按可独立完成的场景拆分；每个场景仍携带完整的适用约束。最小工作单元也放不下时，说明缺少什么并暂停依赖部分，不能偷偷截断必需要求。输入还要留出输出与补读空间。

### 4.3 输入示例

下面是应用生成的可读内容示例，作者不需要维护这段提示词：

```text
任务：写分遗物的争执，保留林岚无辜、周衡伪造遗书的结局。
本次范围：当前方案第 12 版；只修改这一场景及其正文关联。

作者真相：林岚通过旧照片看过遗书背面的文字。
本段必须呈现：林岚暴露她知道一处尚未公开的内容。
本段可以引发：他人怀疑她接触过原件；证据仍不足以下结论。
本段需要保留：旧照片尚未出现；不能确认林岚的信息来源。
角色知情：林岚知道照片的存在，其他在场人物暂不知道。
后续依赖：照片节点将解释知情途径，但不能凭此证明全部案情。

场景目标：人物争夺遗物，各自有理由追问与回避。
正文依据：这里附上实际读取的相关原文与版本。

执行：流式生成候选正文；核对本段要求；提交允许范围内的改动。
遇到互相冲突且无法确定取舍的要求，提出具体问题。
```

固定执行规则与作品材料分区传入。引文、证词、参考小说和工具结果属于内容，不能借其中的措辞扩大写权限或改变任务。作者约束以可识别的作用域记录承载，不能靠把全部故事文字塞进高优先级提示词来取得控制。

### 4.4 写作、构思与试读的输入区别

构思和写作可读取本任务需要的作者真相。试读使用独立请求，只接收截至指定位置的实际正文；无正文时只能试读明确选定的呈现稿，并注明范围。

试读输入、历史、标题、摘要、缓存、工具返回和核对问题都要经过同样的范围筛选，不继承作者讨论或隐藏结局。不能先给模型真相，再让它“假装不知道”。它的猜测仍只是一份模型反馈，不能当成所有读者的反应。

## 5. Agent 生命周期：一个可见任务完成闭环

界面只呈现一个助手。应用负责材料组装、版本校验、写入和任务状态；模型承担构思、写作及需要语义理解的核对。核对可以使用独立调用，但过程仍在同一任务中呈现。

```mermaid
flowchart LR
    A[作者表达要求] --> B[读取当前方案与正文]
    B --> C[装配本次必需材料]
    C --> D[流式生成候选改动]
    D --> E[核对要求与版本]
    E --> F[按授权范围提交]
    F --> G[展示结果与正文关联]
    G --> H[继续修改或撤销]
    H --> B
```

| 阶段 | 应用与模型如何配合 | 作者看到什么 |
|---|---|---|
| 提出要求 | 绑定选中位置、当前方案和任务范围，区分讨论、试写与直接修改 | 一句明确执行说明；存在取舍问题才询问 |
| 形成结构 | 模型输出节点、关系或线索的候选改动；应用保留生成进度 | 新安排逐步出现，可在对话中纠正；尚未提交的内容不冒充正式结构 |
| 保存结构 | 应用检查对象归属、修订、关系与任务范围，提交完整改动单元 | 明确修改请求可以直接保存；讨论候选可以“用这个”或继续改 |
| 准备写作 | 从当前方案、约定和正文组装实际输入，记录版本 | 必要时简短说明“这段要完成什么”；依据按需查看 |
| 写出正文 | 模型在工作副本中流式写作，补读必要原文 | 正文逐步可读，随时暂停和插话 |
| 核对与局部修正 | 将实际候选正文与任务要求对照；报告具体位置，必要时局部修改 | 显示正在核对及真实输出的问题或结论，不展示伪造进度 |
| 提交与回写 | 将正文和已通过校验的关联成组保存；摘要等派生结果绑定此次正文版本 | 从节点定位正文，看到实际修改结果和撤销入口 |
| 后续变化 | 重新检查来源与依赖，旧结果标为待核对；按作者任务继续调整 | 可以说“保留结局，重做这条误导”或“撤销刚才的修改” |

模型维护结构时提交明确的新增、修改、连接、删除或正文关联操作，不覆盖整本数据。每组操作带着基准修订、修改范围和所属任务；应用补齐并核对这些信息。工具回报实际提交结果后，助手才可以说已经保存。

构思图、正文定位和“本次使用了什么”读取同一套提交与任务记录。前端不根据模型最后一句回复自行猜测状态，后端也不能只有写入能力而不提供结果、暂停、继续和撤销所需的信息。

正文、结构和派生关联的提交边界需要明确：一个完整改动单元全部成功后才成为当前版本。多章任务可以分成多个完整单元，已完成与未完成部分分别报告。摘要或语义提取失败可以保留正文为草稿，但不能把没有依据的进展标成完成。

### 5.1 模型维护的权限

- 当前任务内的正文定位、来源绑定和有效性标记由应用管理，模型不能伪造原文或指定“已校验”。
- 新正文涉及的角色状态、线索出现和回应由模型提出关联，应用核对来源；语义判断保留其来源与适用版本。
- 改写文章不自动授权改变作者真相。正文偏离结构时，先按现有要求修正文；如果新发展值得保留，在对话中提出结构修改建议。
- 明确要求改变真相或结局时，Agent 可以处理该决定及其已授权依赖。关联分析发现范围外的已写章节时，说明影响；未经授权的文字保持待调整，不能报告整体已同步。

### 5.2 流式、暂停、继续与插话

构思、写作、核对、试读以及需要模型的摘要或压缩都使用统一任务通道。每次模型调用有可辨认的目的，真实文本增量直接展示；核对展示发现、依据与结论，不要求输出模型内部思考。进度动画不能替代流式内容，未完整生成的结构化操作也不能提前提交。

**暂停**立即请求中断当前生成，并在服务端撤销旧生成继续提交的资格。已经显示的文字保留，尚未完成的候选可回看；暂停前已提交的完整单元保留并明确列出。请求发出后迟到的文本或写入不得继续改变当前结果。

**继续**是根据当前有效版本、保留草稿和未完成事项发起后续生成，不承诺接回原来的模型连接。先核对方案与正文是否发生变化，已提交操作不重复执行。刷新或断线恢复只重接事件与结果，不自动重跑模型。

**插话**先暂停旧生成，再将作者的新要求用于剩余工作。新要求影响已保存内容时也需形成明确修改，不能仅改变接下来几段。撤销本次操作通过变更记录完成；若后面已有依赖改动，先计算影响，避免一键覆盖后续独立创作。

## 6. 严格遵循：程序约束与语义核对分别承担责任

| 事项 | 可以提供的保证 |
|---|---|
| 方案、版本、作用域和读写权限 | 应用强制校验；旧版本、越界或跨方案操作不能提交 |
| 已声明必需的材料是否实际进入请求 | 根据实际请求快照检查覆盖；缺失时停止相应生成或拆分任务 |
| 试读是否接触隐藏资料 | 请求装配与工具访问共同过滤；不复用含隐藏资料的历史 |
| 正文关联是否引用当前存在的原句 | 核对版本、范围与原文；正文变化后旧关联失效 |
| 是否提前透露、误导是否自然、推理是否充分 | 需要模型及作者判断，存在漏判和误判，不能承诺百分之百正确 |

语义核对围绕本次明确目标：应呈现的内容是否出现、需保留的信息是否泄露、角色是否越过自己的知情范围、既有真相是否被改变、汇合是否有必要前提。每项发现关联具体原文与要求，不能只给总分或“全部通过”。原句存在不能证明结论成立。

建议默认允许一次任务内的有限局部修正，修后重新核对；仍无法满足时保留草稿并提出具体取舍，不无限循环。修改核对目标本身需来自作者要求，模型不能靠降低要求使自己通过。作者认可保留未解决的问题时记录该决定与范围，不伪装成模型已经核对成功。

发生正文版本冲突等确定性错误时使用事实型提示，例如：

> [STORY_REVISION_CONFLICT] 第三章：正文在生成期间发生变化，本次结果尚未提交。建议：按最新正文继续调整。

“已记录的依赖都处理完”也不代表发现了所有潜在影响。改变结局或关键真相时，应扩大到相关结构和已写正文的检查；无法覆盖的部分明确保留待处理，避免把局部检查称为全书一致性保证。

## 7. 不满意时的对话修改

作者选中线索说：

> 林岚直接说出原文太明显了，换一种隐蔽一点的方式，保留她无辜、周衡作案的结局。

Agent 读取当前线索、该场景和后面的照片安排，提出并执行范围内的修改：例如让林岚在别人翻到背面前伸手遮住某一行；后文照片仍解释她为何事先知道位置。模型同时处理人物动作、他人反应和后续解释，作者无需逐项改字段。

生成过程中作者插话：

> 她是在保护妹妹，不要写成只顾自己。

旧生成立即中断。Agent 将这个要求用于本次人物动机与场景调整，重新核对是否仍满足既定结局；不会把它推断成所有作品的通用写作偏好。

完成后对话显示简短结果和变更内容，例如“已调整知情表现与照片的解释，结局保留”。提供**继续修改、试另一版、撤销**。已写部分能直接定位到修改处；未完成或仍需取舍的部分单独说明。

如果作者只说“不满意”，Agent 可以结合当前内容指出一两个具体方向，如“误导更自然”或“动机更有说服力”，也接受自由描述。不要把作者送回多字段编辑表单；存在不同结局取舍时才询问，不要求作者自行推演所有依赖。

“只改构思，正文以后再动”会保存新的结构，同时把相关已写内容标为待调整；“把相关正文也一起改”则在明确范围内继续完成。撤销记录应覆盖这一组结构与正文改动，保护之后独立产生的内容。

## 8. 取消故事资料的完整范围

取消独立故事资料板块是已确认要求。新结构进入创作工作区的构思视图，不能以更名方式恢复旧五页资料管理。

| 范围 | 拟移除或调整 |
|---|---|
| 导航与页面 | 移除故事资料主导航、页面装配、专用路由与位置记忆，清理空壳和占位入口 |
| 跨页入口 | 当前“全部线索”等入口转为在创作工作区查看相关结构，清理对旧页的跳转 |
| 旧整理交互 | 移除旧页面上的范围选择、逐域整理、表格式推理配置和专用任务条；必要的整理由当前对话中明确发起 |
| 前端数据访问 | 移除专用页面状态与无调用方的客户端，避免只隐藏菜单而保留可进入的旧功能 |
| 后端与 Agent | 清理旧资料页的专用读取接口、任务入口和工具暴露；真实仍被写作使用的来源校验、角色知情等能力移到对应的内部职责，不让新旧任务体系并行维护同一事实 |
| 文字与验证 | 同步当前帮助、快捷入口与验证项；历史文档保留历史身份，不再作为当前入口说明 |

旧 `material-tasks` 也被本章线索使用，`CoverageStore` 等被写作与索引引用，实施时要沿调用关系拆开依赖。移除旧公共入口与保留必要内部能力应同步完成，避免前端断开后后端仍能启动旧流程，或删掉共享代码导致正文写作失效。

灵感与模块仍按各自用途存在，创作结构中同一决定只有一处有效来源；附加材料可以引用这一决定，不能形成另一份可独立改写、同时被当作真相注入的副本。角色知情、原文定位、摘要失效属于必要内部能力，均不需要恢复故事资料页面。

旧数据不做迁移或兼容入口；新版本按新结构使用。实际存储、接口拆分、调用方清理和代码示例留给详细开发计划。桌面端继续排除。

## 9. 本轮讨论后的状态

本稿保存数据职责、上下文装配、任务生命周期、对话修改和故事资料移除原则。首版范围、字段、接口、实施顺序及在线评测已另行记录在[开发文档](../../dev-notes/v1.0.1/README.md)，尚未实施。

后续评审至少应能解释这些情形：空白书开始构思；压缩或换对话后继续写；相同线索在后文改变解释；改动备选不污染主方案；回写前章不使用后章知情；正文重写后旧回应失效；暂停后无迟到写入；作者插话后按新要求完成依赖修改。这些是检验设计是否闭合的情形，不代表已完成测试。
