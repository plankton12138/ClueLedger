# 1.0.4 悬疑视图与构思诊断

日期：2026-10-31。状态：**定向实现完成，完整在线验收待执行**。开发入口见 [1.0.4 开发文档](../../dev-notes/v1.0.4/README.md)。

## 为什么做这一版

作者的真实构思已经有阶段、故事线和线索，但画布仍以节点和推进边为主：20 个节点被一条 `next` 主链串起来，实际时间只登记了少数关系，线索藏在右侧详情里。作者看到的是“一章接一章的流程”，不是“实际时间轴上，线索如何被埋下、误读、重新解释和回收”。

本版不重写故事模型。它先把已有数据整理成作者能直接读的悬疑视图，再用诊断和创建 brief 推动模型补上实际时间、线索生命周期与侦探/助手认知。

## 作者看到什么

构思页顶部增加“悬疑视图 / 结构视图”切换，默认悬疑。

悬疑视图以故事内实际时间为横轴。未登记实际时间的节点按阶段和叙述顺序追加，并标注“时间未登记”，不把叙述顺序伪装成实际时间。

时间轴分三层：

- **实际发生**：真正发生了什么，节点标题与关键行动。
- **侦探 / 助手**：该节点登记的 `knowledge_changes`，按主体分组，显示谁知道或相信什么。
- **读者**：该节点上写明的 `expected_interpretation`，即文本想让读者先相信什么。

每列底部是线索使用点。点击线索，下方显示它的表面呈现、作者真相、想引导的读者理解、相关知情和生命周期（埋设、推进、误导、重释、回收）。点击节点可回到结构视图查看完整节点详情。

## 诊断怎样帮助作者

悬疑视图顶部显示可判定的结构缺项：

- 最长推进链覆盖多少节点，是否仍是一条主链；
- 实际时间覆盖多少节点；
- 哪些线索只有埋设或推进，没有回收或重新解释；
- 哪些误导线索没有写读者读法；
- 计划解释的线索是否缺少作者真相；
- 是否有线索使用点但完全没有角色知情。

诊断只提示，不阻止作者保留单线、开放结局或有意的模糊。

## 创建构思怎样改变

创建入口默认给出悬疑 brief：谜题与场景、真相与实际时间线、嫌疑人与秘密、关键线索（表面读法 / 作者真相 / 埋设 / 回收）、误导与两个结论、侦探与助手各自知道什么。

系统提示同时要求：先登记实际时间和线索生命周期，再写节点；`next` 只表达揭示依赖，不用来串联发生先后；误导线索写清读者读法；各故事线有自己的关键变化和汇合。

## 范围

本版只做“悬疑视图 + 只读投影 + 诊断 + 创建 brief”。不重写 `Event / Reveal / Clue / Hypothesis` 模型，不增加自动读者模拟器，不改正文写作与现有提交/撤销协议，不迁移旧数据。

如果这版仍不足以让模型稳定产出多线、多线索结构，下一版再考虑分阶段工具和自动公平性校验。完整范围与验收见[开发计划](../../dev-notes/v1.0.4/development-plan.md)。
