# 1.0.2 上下文容量与输入预算

日期：2026-10-30。状态：**容量与预算已接入，在线验证与作者体验验收待完成**。开发入口见 [1.0.2 开发文档](../../dev-notes/v1.0.2/README.md)。

## 目标

作者需要知道本次请求大约使用多少输入、项目允许使用多少，以及什么时候压缩。模型列表没有返回容量，不应使应用失去输入上限。

同时，项目主动限制输入不能被解释成模型能力不足。例如模型可以处理约一百万 tokens，项目仍可以为了成本、响应时间和较早压缩而只使用其中一部分。

## 本版方案

- 模型窗口保留真实来源：服务商元数据优先，内置官方目录补缺；无法确认时仍如实标记模型窗口未知。
- 项目设置有限的输入上限，计划默认 `128,000 tokens`，供开发实施时采用；这是策略选择，非服务商推荐值或在线验证结论。
- 有效输入预算取项目输入上限与模型允许输入的较小值。模型容量完全未知时，使用项目输入预算，仍执行自动压缩和发送前检查。
- 128,000 的默认值主动牺牲超大窗口的一次装载量，以减少单次请求规模并提早压缩；新增服务端配置可调，首版不增加页面设置项。它不是最佳质量或最低成本的保证。
- 总量与占比的主口径统一为有效输入预算；模型窗口在现有容量明细中解释，不再让整个上下文状态停留在“总容量未知”。

## 页面

示例中的数字用于说明，均非已实施结果：

```text
当前上下文                         估算
≈19,023 / 128,000 tokens · 14.9%
约定与资料                         3,253
工具定义                          10,580
对话与结果                         5,190
回复预留 4,096 tokens

容量明细
输入预算                         128,000
模型窗口                       1,048,576
容量来源                         官方目录
自动压缩起点                     115,200
```

模型窗口无法确认时，明细显示“模型窗口：未获取；按项目预算控制”，主区域仍有预算与占比。首次尚无请求、输入尚未估算时显示“待估算 / 128,000 tokens”，不把缺少估算当作零使用，不显示百分比。

明细还应能解释项目上限、模型可用输入、安全余量和当前模型身份；无需给每一行追加描述。只有存在两个模型上限数值时才展示可用输入换算，不伪造未知字段。

运行中的数字绑定该次受理模型和预算，包括两次模型请求之间执行工具的时间。空闲后读取当前模型容量与项目预算；同一连接与模型可复用输入规模估算，并按新预算重算占比。切换连接或模型后显示当前预算与“待估算”，等待下次请求更新输入规模。打开容量面板和修改模型设置都会重新读取，不要求作者先发一条消息。

## 边界

项目预算不能证明未知服务商一定接受该长度。必要原话或最新完整工具单元放不下时，沿用明确报错，不靠截断必要内容继续；供应商明确拒绝后沿用单次恢复。

本版更新当前 DeepSeek 官方模型目录，并验证发现、保存、重启与实际请求链路。模型发现是读取元数据，不应因此自动发起生成请求。旧版完整轮次摘要与裁剪语义不在本版重做。
