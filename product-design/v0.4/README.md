## 1. 为什么重新简化

作者的操作对象是文章。0.4 让文章直接以可阅读、可编辑的文件存在，应用围绕文件提供阅读、对话与修改能力。作者用其他编辑器修改后，应用应当读到同一份内容。

作品内容以工作目录中的 Markdown 文件为准，历史使用真实 Git 管理。取消自建的段落对象、作品版本数据库、候选采用和工作副本流程。首版优先把一次创作请求到文件修改、差异查看和撤销做完整。

这样会失去段落稳定身份、关系级校验和自动合并等旧能力；本版接受这些取舍，不为保留旧能力再引入一套内容模型。

## 2. 已确认的内容结构

作品内容只有正文和设定集两块：

```text
我的小说/
├─ .git/
├─ .gitignore
├─ 正文/
│  ├─ 0001 雨夜.md
│  └─ 0002 来信.md
└─ 设定集/
   ├─ 角色小传.md
   ├─ 线索.md
   └─ 真相.md
```

| 内容 | 含义 |
|---|---|
| 正文 | 按章划分，一章一个 Markdown 文件 |
| 角色小传 | 角色设定、个性、往事 |
| 线索 | 从读者视角可观察的信息，呈现所有嫌疑人的作案可能性；可以支持错误推断 |
| 真相 | 实际发生的情况，包括真实作案手法 |

设定集有且仅有以上三类。首版采用三个固定文件，内部通过标题组织人物和条目。不再增加大纲、时间线、地点、约定、摘要等作品类别。真实事件经过写入真相，角色往事写入小传，当前创作要求通过对话表达。

`.git/`、`.gitignore` 是技术文件，不是第三类作品内容。聊天、模型配置、阅读位置与运行记录放在应用状态目录，不放进上述内容文件，也不成为另一份正文。

## 3. 创作与修改流程

```text
打开工作目录 → 阅读或讨论 → 明确提出修改要求
  → Agent 查找并读取相关文件 → 直接修改文件
  → 显示改动文件、差异与 Git 记录 → 继续修改或撤销
```

- 普通讨论可以只回答，不产生文件变化。
- 作者明确要求创作或修改后，Agent 直接写文件，不再要求接受候选、采用设定或发布正式稿。
- 写入后的内容立即生效。Git 记录失败时应说明“文件已修改，历史尚未记录”，不能显示全部成功，也不能自动重跑模型。
- 停止或任务失败时保留已经写入的文件，显示实际改动，不在后台自动恢复原文或继续执行。
- 查看差异发生在修改之后，不增加写入前的逐次审批。

## 4. 文件与 Git 的分工

Markdown 表达内容，文件路径表达章节位置，Git 表达历史。当前内容取自磁盘工作目录，不能只读最后一次 Git 提交。

首版一个工作目录对应一个独立 Git 仓库；不提供分支管理、远程同步、多人协作或 Git 托管平台接入。作者仍可以在应用之外使用自己的 Git 工具。

一次修改请求完成后形成一次 Git 提交；没有内容变化时不生成空提交。外部编辑器留下的内容先记录为独立版本，再开始下一次 Agent 修改，避免把作者改动混入模型改动。具体失败和并发边界见实施计划。

撤销通过新的反向提交保留历史，不使用清理工作目录或改写分支历史的方式回退。首版自动撤销只覆盖最新一次应用修改；存在后续改动时明确报告，不实现旧版的段落三方合并。

## 5. 界面与模型范围

保留正文、对话、设定集的写作台布局。正文和设定集在应用内先以只读 Markdown 展示，作者可以通过对话或外部编辑器修改。不在这次架构调整中加入完整的富文本编辑器。

设定集严格展示角色小传、线索、真相三个入口。改动与历史按需展开，任务完成后可查看，不增加候选审阅页面。

模型可读取真相以规划和检查，但不能把真相直接视为读者已知。生成正文时依据作者要求和现有正文安排披露；不再保留专门的角色认知、读者披露或证据锚点对象，也不宣称能够确定性保证无剧透。

不自动运行摘要、账本抽取、学习、审计或后台创作任务。需要长文材料时先搜索、按需读取原文；不能装入上下文时说明读取范围，不伪称读过全文。

## 6. 本版交付边界

必须交付：创建与打开目录、正文分章、三份设定文件、文件读取与搜索、Agent 直接修改、Git 差异与历史、最新修改撤销、外部编辑刷新、真实模型接线。

不进入首版：Obsidian 插件及专用语法兼容、双向链接图谱、知识图谱、自动摘要、RAG、长期记忆、独立审批工作流、全书自动创作、远程 Git 操作。普通 Markdown 文件可以由 Obsidian 打开，不等于交付其插件或全部功能。

0.3 数据保留，不自动升级或删除。需要搬运旧作品时显式导出到新的工作目录；迁移工具与新运行链路分开，不能因此继续依赖旧内容数据库。
